# Client Interface Specification

This specification defines the observable desktop interface exposed by the exported client. It uses generic terminology for screens and controls. It specifies user-facing state and transitions, not implementation technology, window messages, resource identifiers, artwork, or original text.

## Application shell

The application has a single top-level workspace with these persistent regions:

- A title area that identifies the current game or document context.
- A command menu for file/session operations, map navigation, object operations, reports, configuration, and help.
- A toolbar that exposes frequently used navigation and object commands as icon buttons.
- A primary map canvas.
- Transient status text, tooltips, progress feedback, and modal dialogs.

The workspace supports a draggable divider between its map and auxiliary regions. While the divider
is dragged, the client shows a live split preview and clamps the result to minimum usable sizes for
both regions. Releasing the pointer commits the new layout and redraws the affected views. This is
a layout preference only; it does not alter game data.

Commands may be available in more than one place. A toolbar button and its corresponding menu command must have the same availability, effect, and enablement state.

Confirmed by inspection of the exported client: the file-open command maintains a **9-slot Recent Files list**, which reuses the same load pathway as an ordinary Open command (loading is gated on whether a filename was pre-supplied by the recent-files list versus prompted via the standard file picker). Map printing (see below) computes its page layout from the printer device's reported resolution and prints a paginated grid of planet rows using the same small per-planet status icon set used elsewhere in the client.

The interface responds to resizing by recomputing the usable client area and redrawing the active view. Controls that depend on text width or current display scaling must be repositioned rather than clipped.

**Startup display detection, confirmed by inspection of the exported client.** At launch, the client reads the screen resolution and classifies it into one of four quality tiers, each tier enabling or disabling a distinct internal display-quality flag pair: below 800×600 is the lowest tier; 800×600 up to 1023×767 is the second tier; 1024×768 up to 1110×887 is the third tier; 1111×888 and above is the highest tier. Separately, the client computes a device color-capacity figure (color planes times bits-per-pixel) and, if that figure falls below a fixed threshold (equivalent to a very low color mode), shows a one-time startup warning unless the user has previously dismissed it (tracked by a dedicated persisted flag) or has already run the client several times. Startup also builds the full shared GDI resource set used throughout the client in one pass: solid-color brushes and pens derived from a fixed palette table, several pattern brushes loaded from bitmap resources, a set of cursors and icons, and a table of fonts constructed via CreateFontIndirect from a shared font-name table, with point sizes computed from the display's reported DPI and per-font row heights cached for reuse by later layout code.

**On-demand GDI resource helpers, extending the startup GDI-resource-pass finding above.** Beyond the fixed table of brushes/pens/fonts built once at launch, several further helpers create and manage GDI resources on demand:

- A small **reference-counted solid-brush cache** (capacity 32 entries, keyed by color value): requesting a brush for a given color returns an existing cached handle and bumps its use count if one already exists, or creates a new one via the standard brush-creation API and adds it to the cache otherwise; releasing a brush decrements its count and only actually deletes the underlying GDI object once the count reaches zero. This avoids repeatedly creating and destroying identical solid brushes for the same color across many draw calls.
- A small cluster of **device-independent-bitmap (DIB) helpers**: a header parser reads a DIB resource's declared color-table size across both the older and newer bitmap-header formats (handling the fixed 12-byte legacy header as a distinct case from the newer, larger header, and falling back to a bit-depth-implied count — 2/16/256 — when no explicit count is stored); a paired "pixel-data offset" helper uses the same header-format distinction to compute where the actual pixel data begins after the header and color table; a **palette builder from a DIB resource's own color table** locks the resource, copies its color entries into a temporary logical-palette buffer, byte-swaps each entry's red/blue components, and creates a GDI palette from the result; and a **DIB blit helper** either flat-fills a rectangle (when passed no bitmap handle) or locks a DIB resource and stretches it into the destination via the standard DIB-stretch API, using the pixel-offset helper above to locate the source pixels. A separate, simpler routine builds a **fixed default 256-entry palette** (not derived from any resource) for use before a resource-specific palette is available.
- A **chunked large-resource loader**: rather than using the ordinary resource-load API, this pair locates a named resource, allocates memory for it directly, opens the executable itself as a plain file to access the resource's raw bytes, and reads it in bounded chunks (capped per individual read call, looping until the full declared resource size has been transferred) directly into the allocated buffer — a technique for pulling in a single resource larger than the ordinary 16-bit resource/read-call size limits would otherwise allow.

**Persisted settings, confirmed by inspection of the exported client.** Beyond the toolbar layout and autosave interval already noted below, startup reads a large block of `.ini`-resident settings, including: up to four windows' saved placement (position, size, and a Maximized/Restored/Iconic state letter) via a shared decode routine; a registration/serial-style value stored as a hex string and parsed manually into a 32-bit number; default player-name and race-name strings; up to nine saved play-by-email player addresses and up to thirteen obscured per-player passwords, each read from a block of indexed keys into fixed-size tables; and a two-character default-game-type code (a mode letter plus a constrained secondary letter) decoded into flag bits, whose exact real-world labels could not be recovered from decompiled code alone.

## Command availability

Every command is evaluated against the current session, selected owner, selected object, and editing permission. A command is disabled when its required context is absent or read-only. Disabled controls remain visible unless the surrounding mode explicitly hides them.

Opening a modal editor suspends conflicting workspace commands until the editor is accepted or cancelled. Opening an informational view does not itself modify game state.

**Trait-gated control validation, confirmed by inspection of the exported client.** A shared dialog-control validator decodes a packed control/item identifier into one of 16 categories plus a sub-index, resolves the sub-index to a caption/resource string through a per-category lookup table, and then — for most sub-indices — separately checks the currently selected race's Primary Racial Trait and up to 11 distinct trait/technology-availability flags, rejecting an item whose category conflicts with the current race's configuration. A companion routine walks a category's items from the highest sub-index downward, calling the validator until it finds one still valid for the current race (or exhausts the category), and is used to pick a new default selection when the previously active one becomes invalid after a trait change. A related helper performs a graded comparison between a candidate race's environment/trait value vector and the corresponding stored vector, distinguishing "identical," "differs by exactly one step in one field," "differs by more than one step in exactly one (linked) field" (returning the signed step count), and "differs in more than one field" — the same graded-compatibility shape documented below for the ship/component slot editor, here applied to race data.

**Correction, verified against the exported client.** This validator is not primarily a *dialog* gate at all — tracing every call site (over 60, across roughly 20 of the client's ~37 code segments) shows it is the client's single general-purpose "is this game item legal for the current race" resolver, called far more often from plain game-logic code than from any dialog procedure: ship/starbase design cost and mass aggregation, the map's per-planet Starbase/Stargate/Mass-Driver icon-dot checks (see "Starbase capability indicators" above), AI starting-fleet template hull selection during new-game setup (segments 19 and 21, which contain no dialog/window-control code at all — see `new-game-setup.md`), and the production-queue item validator's fallback to a new default sub-item when the previously selected one becomes illegal (segment 24; the "find next valid default" companion routine documented above). The race-design wizard's own trait-toggle stage (the slider/checkbox segment) was searched specifically and contains **no calls** to this validator, refuting the earlier "most plausibly the trait pages" guess as stated. Two genuine, concrete UI call sites were found instead: (1) the same segment that builds the wizard's trait-conflict explanatory text (`race-traits.md`'s and `race-designer-ui-and-availability.md`'s "Trait stage") also uses this validator, immediately after a trait changes, to walk every installed component slot of the affected ship/starbase design and silently clear (uninstall) any slot whose component fails re-validation under the new configuration — a previously-undocumented "trait change strips now-illegal components from existing designs" mechanic, distinct from the explanatory-message behavior already documented; and (2) the Ship and Starbase Designer's Slot/equipment editor (see `client-ui-dialog-catalog.md`) calls it while building the list of components offered for a slot, including a specific, size-class-filtered case for the shared "orbital special equipment" category that also drives the map's Stargate/Mass-Driver dots. The validator itself remains a strict binary (legal/illegal) gate in all of these call sites; it does not implement the graded tech-level-distance feedback described for the slot editor, which remains unresolved (see `ship-design-and-components.md`'s Open Questions).

All editable dialogs use a working copy. Accept commits validated changes; cancel discards uncommitted edits. If a dialog changes a record before the user moves to another record, the interface commits the previous record's working copy before loading the new record.

**Working-copy record accessors, confirmed by inspection of the exported client.** At least two concrete instances of the underlying load/commit mechanism were traced: one pair of routines looks up a planet record by its stored ID (a direct-index fast path when the live planet count has no gaps, falling back to a binary search over a sorted array otherwise) and either copies it out into a caller's working-copy buffer or, on commit, swaps the working copy back into the live array while carefully preserving one field that is itself an out-of-line pointer (a per-planet production-queue block) rather than overwriting it wholesale — so the "record" and its variable-length queue data are committed through two different paths in the same operation. A second, differently-sized record table has its own analogous get/set pair. Both commit paths conditionally trigger a full dependent-value recalculation afterward, gated on a "not currently viewing another race's data" check, consistent with the rule that accepting an edit should not silently recompute state for a race the user isn't looking at. **A third instance, sampled this pass:** a commit routine for a record carrying a variable-length trailing string swaps the fixed-size portion of the record wholesale, then separately grows or shrinks a backing allocation and copies the trailing string into it — the same "fixed fields swapped directly, variable-length trailing data handled through its own allocate/copy path" shape as the planet/production-queue case, applied to a different (unidentified) record type.

## Map canvas

The map is the primary navigable surface. It displays spatial objects and accepts selection, navigation, and contextual interaction.

- Selecting an object makes it the active subject for object-specific commands and information panes.
- Selecting a fleet displays its pending route on the map. The route is drawn as an ordered series of legs from the fleet's current position through its remaining waypoints, so its intended travel path is inspectable without opening the order editor.
- The active fleet's current position, route origin, intermediate waypoints, destination, and leg direction are visually distinguishable. The selected route overlay takes precedence over ordinary map clutter and is redrawn whenever the selected fleet, its orders, or the map viewport changes.
- Selecting a different fleet replaces the previous route overlay. Deselecting the active fleet, closing the game context, or entering a mode that hides fleet data removes the overlay.
- Object-specific actions are unavailable until a compatible object is selected.
- A search dialog can locate a named or otherwise filterable object and then focus the map on the result.
- Map printing opens a configuration dialog before output is produced.

**Correction, verified against the exported client.** The map's contextual popup is **not** an action/command menu — it never offers a per-object action (no rename, no scrap, no order-editing verb). It is purely an **object-disambiguation picker**: right-clicking a map position lists every fleet present there, then every planet present there (with a divider between the two groups when both exist), with the currently-selected object shown checked; choosing an entry simply makes that object the active selection and syncs the fleet/planet side panels — nothing else happens. Plain left-clicking selects an object directly, and clicking the same already-selected position repeatedly cycles through a stack of co-located objects one at a time as an alternative to opening the picker. Clicking the small status strip beneath the map viewport (as opposed to the map itself) opens a separate, unrelated read-only popup showing the selected object's cargo/mineral breakdown; that popup has no interactive controls either.

**Plotting a course, confirmed by inspection of the exported client.** Holding Shift while right-click-dragging, or dragging with the middle mouse button, draws a live rubber-banded line from the drag origin to the current cursor position and shows a tooltip naming whatever object (or "Deep Space") is currently under the cursor; releasing commits the course/waypoint. Separately, holding Ctrl while left-clicking during multi-fleet route editing inserts a new waypoint into the route being edited at the clicked position, provided it falls far enough from any existing waypoint.

**Object-identification text builder, confirmed by inspection of the exported client.** A shared routine turns a found object handle (as returned by the nearest-object search described in `fleet-movement-scanning-cargo.md`'s "Object-proximity search utility") into the descriptive phrase used by this under-cursor tooltip: for an object owned by another race it substitutes that race's display name (via the race-name/summary string builder) into an "owned by ___" template; for an object in the map's "orbital special equipment" component category it selects among a small set of alternate templates depending on whether a qualifying component (matching the same Stargate-range check documented under "Starbase capability indicators" above) is actually present; other categories fall back to a plain category-name template. This is the most likely source of the course-plotting tooltip's object name and a plausible source for the status-strip text as well, though the exact call sites tying it to each specific surface were not individually traced. A separate, much simpler routine (design-name-by-index) was also sampled this pass: given a race and a hull/starbase design slot index, it checks the design's deleted-flag bit and, if clear, copies out the design's own stored name string — a plain accessor, most plausibly feeding a design picker/dropdown rather than the map tooltip itself.

**Default planet-name table, newly identified this pass.** A dedicated decompression routine takes a numeric index (wrapped into a fixed range of roughly a thousand entries) and unpacks one entry from a compact, variable-width-nibble-encoded name table into a plain capitalized string (capitalizing the first letter and the first letter after any internal space or hyphen). Its caller combines that decompressed name with a small numeric suffix — an index value plus one, formatted directly after the name — matching the game's known "`<default name> <number>`" convention for automatically-assigned planet names before a player renames them. This is the client's built-in default planet-name generator; the underlying name table itself is compressed program data with no surviving plain-text initializer in the exported source, so the actual roster of names could not be recovered, only the unpacking mechanism.

The map supports additional overlays and inspector windows for scanning and minefield-related information. These views are derived from the current game state and refresh when the relevant selection or viewpoint changes.

**Starbase capability indicators, confirmed by inspection of the exported client.** The map's planet-icon painter draws up to three small colored square overlays ("dots") on a planet's icon, one per independent boolean condition, each in its own fixed position relative to the icon and its own distinct color:

- **Starbase presence** — read directly from the planet's stored status: a specific status bit is "has a starbase." When present, the code separately inspects the starbase's own design record: if a specific leading field of that design equals a distinguished value, the dot is drawn in a second, different color instead of the ordinary one — i.e., the client distinguishes at least one specific starbase design/type from an ordinary starbase using a different color for this same dot, though the exact design/type this represents could not be identified (no label/string data survives in the analyzed material).
- **Stargate capability** — a dedicated check walks the starbase's installed components looking for any component in a shared "orbital special equipment" category whose subtype falls in the lower half of that category's range, consistent with the game's roughly six Stargate tiers. Drawn as a second dot, in a second color, at a different fixed offset from the starbase dot.
- **Mass Driver capability** — the same shared component category is checked again, this time for a subtype in the upper part of its range, mapped to a driver level; the *highest* level found across all installed components is used. This range and mapping line up exactly with the game's known Mass Driver → Super Driver → Ultra Driver progression (levels 5 through 13). Drawn as a third dot, in a third color, at a third fixed offset.

**Scope caveat.** This detailed indicator rendering was only confirmed to fire for the planet matching the client's currently-tracked *selected-object* position (the same selection state the object-summary panel uses) — a compatible implementation should verify against live play whether every colonized planet's icon shows these dots simultaneously, or only the currently-selected one, before assuming universal rendering.

**Scan-range circle overlay, confirmed by inspection of the exported client.** A dedicated overlay toggle (one bit of a shared view-options word — see the "shared view-option slots" note below) draws a scan-range circle for every planet and fleet belonging to the current race, using the standard circle-drawing primitive in an XOR/overlay drawing mode so the circles never obscure underlying map content. Each circle's true-scale radius comes from a per-object range lookup and is then passed through the same zoom-scaling arithmetic used for all map coordinates (see below), plus an additional correction whenever a separate "scanner display" percentage setting (2-100%, default 100) is below 100. That percentage is edited through a dedicated numeric/slider control (documented in `client-ui-dialog-catalog.md`'s Planet inspector entry) that always force-enables the scan-circle overlay when changed. Objects whose range lookup also reports a positive secondary detection value get a *second* circle drawn at exactly half the primary radius — consistent with the game's separate penetrating-scan range being distinct from its normal scan range. A batching helper accumulates circles per redraw region and skips drawing any circle fully nested inside another already-queued circle in the same region, an overlap-culling optimization that does not otherwise change what is visible.

**Exact zoom scale factors, confirmed by inspection of the exported client.** The map's world-to-screen and screen-to-world coordinate helpers are keyed by the same 9-level zoom index the Zoom submenu sets (see "Navigation controls" below), and use these exact integer-arithmetic scale factors rather than true floating-point percentages: 25% (¼×), 37.5% (a 3×/8 shift, i.e. slightly above the "38%" label), 50% (½×), 75% (¾×), 100% (unchanged), 125% (5×/4), 150% (3×/2), 200% (2×), and 400% (4×). These same helpers scale every map-drawn radius, including the scan-range and minefield-related circles described here.

**Mass-Driver range overlay for Packet Physics, confirmed by inspection of the exported client.** When the current race's Primary Racial Trait is Packet Physics, the map draws an additional range circle around each qualifying Mass-Driver-class starbase component (radius derived from the driver level per the Mass-Driver capability check documented above, scaled the same way as scan-range circles). This overlay is not drawn for any other Primary Racial Trait, consistent with Packet Physics' packet-mineral-launching mechanic; no other PRT-specific map overlay was found.

**Minefield visibility overlay, confirmed by inspection of the exported client.** A separate overlay toggle draws minefields using one of three distinct fill patterns (matching the game's three minefield types), gated by an independent 4-bit visibility mask covering the player's own fields, other owners' fields, and a further split for enemy fields depending on whether they have been detected (checked against a per-relationship detection table). This mask is edited through a dedicated popup checklist menu (opened via the same view-option slot mechanism noted below) offering an "All"/"None" pair plus one independently toggleable line per other player in the game.

**Route-overlap overlay, confirmed by inspection of the exported client.** A further overlay toggle affects the route/waypoint editor's map drawing: when the plotted route contains two legs sharing the same pair of endpoints (an overlap or reversal), the overlapping leg is drawn with a distinct dashed pen instead of the normal solid one, and an underlying straight base path connecting every waypoint in order can optionally be drawn beneath the actual route. Cloak-adjusted circle rendering (a reduced or hidden circle for a cloaked object) was not located in this pass and remains unconfirmed; a compatible implementation should not assume it exists without further verification.

## Navigation controls

The client provides several related navigation affordances:

- A toolbar for direct map and object-navigation commands.
- Tooltip text for toolbar actions after pointer hover.
- A browser-style selection window for moving through a collection of records.
- A find dialog for locating a specific target.
- A compact popup window for local contextual commands.

The toolbar is a vertically arranged, finite action strip. It supports hover feedback, press and
release feedback, disabled actions, and at least one action with a finite preset-value drop-down.
Changing that preset immediately updates the associated view setting and its displayed value.

**Correction, verified against the exported client's real menu resource.** The preset drop-down referenced above is **not** a map display-mode selector — it is a **3-way window-layout preset** ("Large Screen" / "Medium Screen" / "Small Screen"), immediately invalidating and redrawing the map canvas and recomputing the workspace layout when changed. This corrects the earlier "map display-mode" characterization. Map magnification is a separate, unrelated 9-step **Zoom** submenu (25%/38%/50%/75%/100%/125%/150%/200%/400%) reached from the View menu, already documented in `fleet-movement-scanning-cargo.md`'s zoom-level findings — the two must not be conflated. Confirmed by inspection of the exported client: selecting a Zoom level explicitly recenters the map view on the same world point it was centered on before the change (computed from the visible client area's half-width/half-height in the new scale) before triggering the full repaint — the map does not simply rescale in place around its top-left corner. The exact per-level scale factors are documented in "Map canvas" above.

A separate command (command code 0x88, confirmed below) also flips a bit that controls a
floating/dockable auxiliary panel's visibility (created on first toggle, destroyed on the next) —
**confirmed by direct observation of the running client (2026-09-11) to be the Technology Browser**
(Prev/Next paging through tech entries, a category filter combo, and a "Show Only Available
Technology" checkbox — already documented in `client-ui-dialog-catalog.md`'s "Additional confirmed
surfaces" section from the dialog-resource side; this is the toolbar/command-code path that opens the
same surface, separate from its `Technology &Browser\tF2` menu entry). Screenshot preserved at
`docs/ui-reference/live-game-command-0x88-technology-browser.png`.

Confirmed by inspection of the exported client: the toolbar's button set and ordering are
**user-configurable and persisted** across sessions via a saved preference string, rather than
being a fixed layout — not previously documented here. A separate, similarly-persisted preference
governs an autosave/backup interval, clamped to the range 100-30,000 (milliseconds or an
equivalent internal unit), defaulting to 5,000; confirmed by inspection of the exported client, this preference is read from one specific `.ini` numeric key at startup and uses its own previous value as the fallback default when the stored value is out of range, rather than always resetting to 5,000.

**Shared view-option slots, confirmed by inspection of the exported client.** The map's scan-range-circle toggle, minefield-visibility toggle, and route-overlap-dash toggle (all documented above), together with the object-information panel's content mode (see below), are all bits or fields of the same two packed "view options" words, read and written through one shared pair of get/set routines. At least 13 addressable slots exist: 6 are mutually exclusive and select the info panel's content mode; one each enables the scan-circle overlay and the minefield-visibility popup; one enables the route-overlap dash overlay; and several more independent bits exist whose real-world meaning could not be confirmed. The main keyboard-accelerator path (see "Reusable control behavior" below) binds the top-row digit keys 1-9, 0, and Shift+0 directly to these slots in order, so pressing 7, 8, or 9 toggles the scan-circle, minefield-popup, and route-overlap options respectively, in addition to 1-6 switching the info panel's mode.

List and browser views maintain a current item. Moving to a different item updates dependent controls and must not lose pending edits to the previous item.

## Object information and orders

The client provides dedicated views for planets, fleets, minefields, scans, messages, and reports. An object-information dialog displays the current object's known state and exposes only actions valid for that object.

**Correction, verified against the exported client's real dialog resource.** The order-information dialog referenced elsewhere in this document is confirmed by its real caption text to be an "Ordering Information" box — a static informational popup about **purchasing additional copies of the game** (its exact stored content: "To order additional copies of Stars!: In the US call 1-800-216-9706 or see our Web Page at: http://www.webmap.com/stars!", plus an OK button), not an in-game fleet/order-data display at all. This supersedes the earlier softer wording ("should not assume... more dynamic than..."): the dialog is confirmed **entirely unrelated to fleet orders**, and any spec or implementation note that associated it with in-game order data should be disregarded.

**Object-information panel content modes, confirmed by inspection of the exported client.** The object-information panel described above is backed by a shared "current mode" field with exactly 6 mutually-exclusive values, directly selectable via the 1-6 number keys (see "Reusable control behavior" above) as well as by whatever on-screen controls invoke the same setter. The panel and the main galaxy/system map view are each implemented as more than one physical child window (window-class registration confirms two distinct window classes share the panel's window procedure, and two distinct classes share the map's), consistent with the planet and fleet summaries being separate windows rather than one window redrawing two different layouts.

**WM_COMMAND routing, confirmed by inspection of the exported client.** Inspection of the main frame's command dispatcher confirms: Recent-Files menu commands index directly into the stored recent-file path table (one fixed-size slot per entry) and extract the file's extension before invoking the same load pathway as the ordinary Open command, mechanism-level confirmation of the 9-slot Recent Files behavior documented above. Many ordinary menu commands are gated behind a "tutorial active" flag and, while a tutorial is running, are redirected into the tutorial engine instead of performing their normal action (see `tutorial-system.md`). A "reset to stored data" working-copy revert and its accept/commit counterpart are dispatched through this same command switch for at least two different editing contexts (a general one and one scoped to the currently selected race), consistent with the "editable dialogs use a working copy" rule stated above. Two additional sound-related menu toggles (beyond any already documented elsewhere) call directly into the audio subsystem and flip persisted preference bits.

The message view exposes exactly **four** category-selection controls (confirming the count stated in the dialog catalog) and maintains, per message, an associated target object and type code; activating a message (via Enter or double-click) jumps to one of at least eleven distinct destination views/actions depending on that message's recorded type — object-information views, a rename prompt, a technology/component availability check, and others — rather than only ever opening a single generic "jump to source" view. Hovering the portion of a message's text that carries a jump target shows a distinct pointer affordance.

**Further WM_COMMAND branches, confirmed by inspection of the exported client.** Continued tracing of the same ~1440-line command dispatcher located several more self-contained mechanisms beyond those already listed above:

- **Two sound-preference menu toggles, pinned to exact command codes.** The first toggle is disabled outright while the tutorial-active flag is set; otherwise it commits the current working-copy context, calls into the audio subsystem to mute or unmute, updates its own menu checkmark, and flips a persisted preference bit. A second, adjacent pair of command codes (mapped to the same handler) does the same for an independent preference bit, gated the same way. This confirms and sharpens the previously-noted "two additional sound-related menu toggles" into a concrete mechanism: commit-working-copy, call audio subsystem, toggle menu check, flip one persisted bit — with no other side effects.
- **A "force immediate redraw" command**, distinct from an ordinary invalidate: it sets a temporary suspend/re-entrancy flag, calls two internal repaint helpers directly (rather than merely posting a repaint message), clears the flag, and then still performs an explicit invalidate-and-update pass on the map window. This command is a no-op if the map window does not yet exist.
- **A toggled "object-count summary" popup family.** A cluster of adjacent command codes selects among (at least) four mutually exclusive content modes for a small modeless popup: one mode counts, for the current player, matching entries in one in-memory record list; a second mode counts entries in a *different* list, filtered by the opposite ownership test (belongs to another player rather than the current one); a third mode instead asks the Battle-VCR subsystem (segment 30) for its own count rather than walking a list directly. Each mode formats a singular/plural count string (via a shared string-resource pair) into the popup's caption and creates it positioned near the main window. Selecting the currently-active mode's command again closes the popup; selecting a different mode destroys the existing popup and creates a new one in the new mode. The real-world label for each of the three counted categories could not be recovered from decompiled code alone (no surviving string data), but the mechanism — mutually exclusive toggle modes backed by list counts, with reselect-to-close and switch-to-replace behavior — is fully traced.
- **A separate auxiliary modeless window**, opened by its own dedicated command, sized notionally to 640×480 and centered on the screen using the display's reported metrics (falling back to a fixed top-left position on very small displays). Its window handle occupies a single shared "current auxiliary window" slot that is also created/destroyed by unrelated code elsewhere in the client, confirming it is a reusable single-instance slot rather than a handle dedicated to this one command. While that slot is occupied, a small subsequent range of command codes is relayed to it directly via PostMessage rather than being handled by the main dispatcher itself, and those commands are silently dropped if the slot is empty. Which specific feature this auxiliary window represents (candidates include the score view or another of the modeless report surfaces already documented under "Reports, messages, and playback") could not be pinned down with certainty from decompiled code alone.

**A further pass, confirmed by inspection of the exported client, read the entire body of the ~1440-line dispatcher function (rather than a further sample) and located these additional self-contained mechanisms:**

- **A packed-flag toggle for a display option, pinned to command code 0xb3 — identified by cross-reference to the real menu resource as the View menu's "&Toolbar" entry.** This command commits the current working copy, toggles one further bit of the same general-purpose persisted options word already documented above for the sound-preference toggles and the tutorial-active flag (this instance sits at a different bit position from those), updates its own menu checkmark, and immediately forces a map redraw via the "force immediate redraw" mechanism documented above — consistent with hiding/showing the toolbar row and recomputing the workspace layout underneath it. **Confirmed by direct observation of the running client (2026-09-11):** toggling this command visibly shifts every info-panel's top edge upward by one toolbar-row's height, with no other visible change — direct behavioral confirmation of a toolbar-visibility toggle, not a map-content display option. Screenshots preserved at `docs/ui-reference/live-game-main-window-toolbar-shown.png` and `docs/ui-reference/live-game-command-0xb3-toolbar-hidden.png`.
- **A three-way, mutually exclusive display-mode selector, commands 0x82/0x83/0x84 — identified by cross-reference to this document's own "Navigation controls" section above.** These are the same three command codes already confirmed, via the exported client's real menu resource, as the **"Large Screen" / "Medium Screen" / "Small Screen"** window-layout preset (not a map display mode — see the correction above). This pass adds the mechanism behind that selection: the chosen mode (0, 1, or 2, derived directly from the command code) is stored in a dedicated slot, the map window is invalidated, and — only for the third mode ("Small Screen") specifically — an extra boolean is passed into a segment-8 helper (plausibly gating some small-screen-specific layout simplification), before the same "force immediate redraw" path runs.

## Planning and diplomacy

The client exposes independent editors for research preferences, battle plans, and inter-owner relations.

- Research preferences select a focus discipline and allocation behavior.
- Battle plans are ordered, named records with targeting, movement/behavior, and opponent-policy attributes. The first record cannot be removed; later records can be created, selected, edited, and removed subject to the applicable plan limit.
- Relations are edited through a dedicated dialog and are separate from battle-plan targeting preferences.

These editors must preserve the selected owner context, distinguish a changed working copy from a stored record, and synchronize accepted changes through the ordinary persistence pathway.

**Battle Plans and Relations dialogs, confirmed by inspection of the exported client.** Both real dialog window procedures were located and traced directly (previously misattributed as living elsewhere, or not attributed at all — see the segment 31 note in `combat-resolution.md` §8 for the full correction):

- The **applicable plan limit is exactly 15** additional plans per race (a per-race count byte is refused once it reaches 15), on top of the un-removable first plan, matching this document's "subject to the applicable plan limit" wording with a concrete number.
- The **"first record cannot be removed" rule** is enforced simply by disabling the Delete control whenever the currently-selected plan index is 0 — there is no separate special-case check inside the delete handler itself.
- **Deleting a plan that is still assigned to at least one fleet** triggers a confirmation prompt (a generic Yes/No message box) before proceeding; declining leaves the plan and every fleet assignment untouched. Accepting (or deleting an unused plan, which skips the prompt) removes the plan record, shifts every later plan down one slot, and walks every fleet in the game once to renumber any fleet whose assigned plan index needs to shift down to match, so existing fleets' plan assignments stay consistent with the new, shorter list rather than silently pointing at the wrong (shifted) plan.
- The dialog's working copy is a **36-byte record** loaded/committed as 9 packed fields at a time, independently corroborating the "fixed 36-byte structure" already documented in `combat-resolution.md`'s "Correction, verified against the exported client" note for the primary/secondary target type and movement-tactic byte layout.
- The Relations dialog and a companion "name this battle plan" prompt dialog are both real, distinct window procedures confirmed in the same code region as the Battle Plans editor; the Relations dialog itself is presentation-only in the portion traced (paint/repaint and an enable/disable pass over its controls keyed off the currently selected relationship row), consistent with `diplomacy-relations.md`'s existing description of the underlying relationship data.

## New-session and game-setup flow

The client supports both simplified and detailed new-session flows. The detailed flow is divided across multiple dialogs and presents one coherent setup draft. A random-seed dialog is available where reproducibility or explicit randomization configuration is required.

The setup flow includes a six-stage race designer. Its stages cover identity and archetype, environmental tolerance, optional traits, economy, research, and finalization. The full behavior of that wizard is specified in the race-designer specification.

The setup flow must retain user-entered values while moving between stages and must not create a usable session until required stages have accepted valid input.

## Reports, messages, and playback

The client has separate information surfaces for messages, reports, scores, tutorials, and battle or event playback.

- Message and report windows present recorded information without changing it merely by opening it.
- A score view presents comparative standings.
- A tutorial view can be opened independently of game-state editing.
- A replay controller presents recorded event progression using transport-like controls; playback changes only the displayed point in the recording, not the underlying game state.
- Long-running actions use a progress dialog with a gauge and may display a failure or recovery dialog when the action cannot complete normally.

## Authentication and sensitive settings

The client contains entry and replacement dialogs for a local access secret. These dialogs must keep entered characters concealed, require explicit acceptance to save a replacement, and discard incomplete or cancelled input. The secret entry surface must not reveal the stored value through tooltips, reports, or ordinary editing controls.

## Reusable control behavior

Several custom controls supplement standard text fields, lists, and buttons:

- A styled editable field behaves as a text input while preserving the application's visual treatment.
- A styled selection field behaves as a compact single-choice control.
- A list control supports selection changes and event-driven redraw.
- Tooltip controls describe adjacent actions without mutating state.

For all of these controls, keyboard activation and pointer activation must reach the same logical command. Focus changes must be visible and must not silently commit unrelated input.

**Correction, verified against the exported client.** A previously-noted "generic dialog window-proc subclass for keyboard navigation among controls" is **not** a Tab-order/arrow-key control-to-control navigator. Confirmed by inspection of the exported client, it is a fixed-key global hotkey relay installed on an auxiliary (non-main-frame) window, used so a handful of keyboard shortcuts keep working while focus sits in a modeless side panel rather than the main frame:

- Escape closes a tracked popup window when specific tracked-window conditions hold.
- Escape and Enter, when focus is within a specific tracked parent window, are forwarded as an accept/cancel signal into the object-information panel's own key handler (see "Object information and orders" below), rather than being handled generically.
- The digit keys 1-9 and 0 (plus Shift+0) are intercepted and dispatched to the shared view-option slot mechanism documented in "Navigation controls" above, rather than to whichever control currently has focus.
- Delete and Backspace remove the currently selected waypoint, but only while a specific route-editing mode is active.
- The `[` and `]` keys step to the previous/next message.
- `,` and `.` step a bounded (0-11) per-item field of the currently selected production/order-list row up or down, again only while the same route-editing mode is active.
- Any other handled navigation key (Up, Down, Home, End, and similar) that reaches a control outside a fixed exclusion list of specific controls is relayed unchanged to the main application window, so the main frame's own accelerators still fire; keys outside this fixed set are not intercepted at all and reach their control normally.

## Help and error feedback

Most modal editors provide contextual help. Invoking help leaves the editor's working copy unchanged. Invalid operations or unrecoverable conditions produce a generic message or recovery dialog rather than silently changing state.

The UI must preserve a distinction between an informational warning, a validation failure, and a cancelled operation. Only an accepted operation may alter persistent game or configuration state.
