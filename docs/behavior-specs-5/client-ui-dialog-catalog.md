# Client UI Dialog Catalog

This catalog extends the client-interface specification with every distinct interactive surface identified in the exported client. Names below are functional descriptions, not copied identifiers. An entry states only behavior supported by the client surface; it does not infer rules that belong to turn processing.

## Global dialog contract

Every modal surface has these common attributes:

- It is initialized from an explicit subject, selection, or session draft.
- It supports accept, cancel, and contextual help when help is available for that surface.
- Accept returns a meaningful result to its caller. Cancel returns a distinct no-change result.
- Editable surfaces use a local working state and commit only their own scoped fields.
- Read-only and authority-limited contexts disable mutation controls while retaining useful inspection controls.
- Keyboard and pointer activation of an accept, cancel, list, or button control follow the same state transition.

## Workspace surfaces

### Main workspace frame

The top-level frame creates and owns the map workspace, command menu, toolbar, status content, and subordinate information windows. It routes keyboard accelerators to the active child surface when that child is entitled to receive them. It supports normal, minimized, and restored display states.

The frame handles controlled shutdown. When unsaved state or an active session requires a decision, it opens a confirmation flow rather than terminating immediately. It may save or prepare pending session data before completing the close action.

### Title and status area

The title/status area presents the current context and supports lightweight updates without rebuilding the map. It refreshes when the active owner, open game, or current view changes.

**Race-name/summary string builder, confirmed by inspection of the exported client.** A shared routine builds a display form of a race's name from its stored singular and plural name fields, parameterized by: singular versus plural form; whether to prefix an article ("a"/"an," chosen by the name's leading sound); whether to apply a possessive/adjective suffix; and, when no explicit plural name was set, an automatic English pluralization fallback (append "s," unless the singular name already ends in "s" or in a sibilant-plus-"e" pattern, in which case a different suffix is used). This is the routine that renders the current race's name into the title/status area, and it is reused throughout the client wherever a race's name needs to appear in a sentence — reports, dialog captions, and the report-text escape-formatting engine described under Custom widgets below.

### Toolbar, tooltip, and contextual popup

The toolbar maintains an ordered group of icon actions. Each icon has an enabled state, a press/hover state, and explanatory tooltip content. Hovering does not change the selected object or persistent state.

The contextual popup is built from the current pointer target and selection. It contains only operations legal for that target. Closing it without activation has no effect.

### Search and record browser

The search surface accepts a query, evaluates it against the relevant object collection, and returns a selected result or no result. The browser surface presents a navigable collection with one current item and can update the workspace focus to that item.

**Located and confirmed by a later pass, previously unattributed to any segment.** A distinct dialog procedure (in the same code segment as the Research dialog below, but otherwise unrelated to it) populates a roughly 17-entry listbox from a string-table run at initialization and, on selection change, renders a detail card for the highlighted entry through the same large, shared "object/context detail" content renderer that also backs the mode-switched hover/info popup's richer modes above — an object-type/subtype dispatch that draws whichever of several layouts (a color-coded environment/habitability-style value breakdown, a proportional resource/mineral bar summary, or a ship/component-style info block, among others) matches the selected entry's kind, rather than one fixed layout for every row. This matches the "browser-style selection window for moving through a collection of records" bullet in `client-interface.md`'s "Navigation controls" list at the mechanism level, and is a strictly richer per-item detail display than that entry currently describes.

**The 17-entry listbox content is now pinned down with high confidence, resolving the prior open question.** The listbox-selection handler and the dialog's Prev/Next step buttons all index the same fixed lookup table through a listbox/step index that is confirmed (by the step buttons' own wraparound logic) to range only over **1 through 16, never 0** — the table itself spans 17 word-sized slots, but slot 0 is dead/unused, which is why an earlier pass's raw byte-count read as "roughly 17 entries." Each of the 16 live slots holds one value that is fed directly, unchanged, as the "category" tag into the shared component category/subtype availability resolver (`FUN_1008_5194`, this project's segment 2, documented in full in `ship-design-and-components.md` §4) — and the values found are exactly that resolver's 16 valid category bit-flags (`0x0001` through `0x8000`, one bit each). Stepping to the next/previous entry then walks that category's subtypes (via the same resolver call, skipping any subtype the resolver reports as nonexistent or unavailable to the current race) rather than walking a separate flat list of records. **This makes BROWSERDLG a component/hull-slot category browser, not a browser over some other collection:** its outer listbox lists the 16 fixed component categories from `ship-design-and-components.md` §4 (the same categories the Ship/Starbase Designer's slot editor validates against), its Prev/Next buttons cycle through the eligible subtypes (individual components) within the selected category, and each selected component is rendered through the shared detail-card renderer described above. This confirms the "component category list" candidate over the "hull/design-type list" alternative previously floated here, and ties this dialog directly to the same resolver `ship-design-and-components.md` documents from the design-slot-editor side.

**The shared detail-card renderer (`FUN_10d8_1e40`, segment 28, 1847 lines) has now been traced systematically rather than sampled, closing this segment's last substantial gap.** All three call sites were confirmed by direct inspection: BROWSERDLG's paint handler calls it with the dialog's own selected-item descriptor; RESEARCHDLG calls it similarly; and segment 25's mode-switched popup (see "Toolbar, tooltip, and contextual popup" above) calls it from exactly one of its cases, always passing one fixed shared global "current selection" descriptor rather than a per-call object. Critically, **the object this function renders is not a mix of planet/fleet/design/race records — it is, in every one of the three call sites, the same (category, subtype) descriptor `ship-design-and-components.md` §4 documents**, down to sharing that exact resolver: the renderer calls `FUN_1008_5194` on its own input near the top of the function to populate a cached far pointer to the resolved component/hull data record before drawing anything. This corrects the framing in the paragraph above (inherited from an earlier, partial sampling pass) that described the renderer's layouts as keyed to different *object types* ("planets," "ship/component," a generic "resource bar"); what that pass was actually seeing were different **component categories** sharing one dispatch function, not different kinds of game object.

Structurally, the function is a shared chrome wrapped around genuinely bespoke, hand-written per-category bodies, not one reusable template instantiated per type:

- **Shared chrome (applies to every category):** a two-tone raised/sunken bevel border is painted first (the same border primitive family as the "Segmented bar/gauge" custom controls documented under "Custom widgets" below); a null/empty selection short-circuits immediately after, drawing only a small placeholder box and a generic "nothing selected"-style message. For a live selection, the icon block itself branches in two ways: a record whose category is a hull-family category (`0x4000`, and very likely its 5-subtype sibling `0x0400` — both are the only two categories in `ship-design-and-components.md` §4's table with the same unusually large 143-byte record stride, consistent with one being the ship-hull category and the other the starbase-hull category) gets an actual bitmap icon blit of the miniature hull/design picture; every other, ordinary component category instead gets a flat palette-driven color swatch synthesized from packed bit-fields of the component's own data value. A centered title/caption line follows using a caller-supplied string buffer rather than a name the function looks up itself.
- **Per-category body (bespoke, confirmed distinct for at least five of the sixteen categories):**
  - **Category `0x0080`** — independently identified in `ship-design-and-components.md` §5 as the **Bomb family** (8 subtypes) — gets the lightest treatment here: no numeric stat block at all, just a single caption line chosen from one of two message-id groups by subtype, with subtype 7 (the Claim-Adjuster-exclusive Retro Bomb, per that same section) singled out into its own branch with a different message pair. This is a strong cross-confirmation between the two documents' independent findings.
  - **Category `0x0040`** (15-subtype family) draws a compact 3-line "label: value" numeric block, reading three word-sized fields directly out of the resolved data record (offsets +0x34/+0x36/+0x38 from the record base) through the client's shared generic numeric-format string.
  - **Category `0x0100`** (10-subtype family) gets the richest confirmed body: subtype buckets into one of three canned 4-number parameter tuples whose shape (a low/high pair plus two larger scaled values) matches a classic engine-style "ideal speed / max safe speed / fuel-use" stat set, followed by a separate mass/cost line and a closing free-text blurb rendered through the shared word-wrap text-layout engine (see "Word-wrap text layout engine" below). Note this is a *different* category value from the Engine family `ship-design-and-components.md` §5 already identified as category `0x0001`; whether `0x0100` is a related-but-distinct drive/engine-adjacent category or something else entirely was not resolved in this pass.
  - **Category `0x0800`** — flagged in `ship-design-and-components.md` §7 as "not fully mapped," there tied to a design-wide percentage-style defense/shielding accumulator and a separate compounding mass/cost multiplier — gets its own dedicated 17-way subtype switch (values 0 through 0x10) here, each producing one caption line, several built from a shared "N of `<label>`" template that substitutes the resolved record's own +0x34 field into the message. One of these caption paths picks between two candidate label strings depending on whether the subtype is above or below 7, and one of the two literal strings involved is confirmed to be **"Ironium"** — a mineral name, not a generic label — tying category `0x0800` concretely to a mineral/mining-flavored component family, most plausibly the Mining Robot components gated by the Advanced Remote Mining LRT already referenced in `ship-design-and-components.md` §6. This is offered as a strong candidate identification for §7's previously-unnamed category, not a certainty.
  - A further, not-firmly-identified category (reached only after ruling out `0x0100` and one other numeric value the decompiler renders as a string-relative constant rather than a clean literal) renders a simple two-line cost/count summary, reading the same record's +0x34 field twice at different scales.
  - Every branch, regardless of category, converges on one shared trailing element: an optional final status/caption line (skipped if the branch set no message id), drawn through the same word-wrap/`DRAWTEXT` primitive with its text color dimmed when the record is flagged unavailable to the current race. This trailing line — not a full generic stat block — is the only piece of the per-category body that is genuinely shared across all sixteen categories.

**Net finding, answering this document's open question directly:** the renderer displays exactly one kind of object (a component/hull category+subtype descriptor, the same 16-value bit-flag system `ship-design-and-components.md` §4 documents), not a mixture of planets, fleets, designs, and races. It does not reuse one fixed "icon + name + stat lines" layout for every type; only the icon/border/title chrome and the single trailing status caption are shared, while each category's actual stat content is separately hand-written, differing in field count, byte offsets into the data record, and message-string ranges. The full 16-category dispatch was not exhaustively mapped in this pass (several categories' exact numeric values are obscured by decompiler pointer-type artifacts rather than clean literals), but the dispatch shape itself — chrome, then a per-category bespoke body, then a shared trailing caption — is now confirmed rather than sampled, and this segment's previously-flagged "not exhaustively traced" gap is closed.

## Object inspectors and operational editors

### Planet inspector

The planet inspector is an object-bound information surface. It redraws from the selected planet's known state, maintains a current display mode, and enables only planet-appropriate actions. Changing the active planet refreshes the inspector rather than reusing the previous planet's data.

Confirmed by inspection of the exported client: the object-information panel's "current display mode" is one of exactly 6 mutually-exclusive values, selectable via the 1-6 number keys as well as by the panel's own controls — see `client-interface.md`'s "Object information and orders" section for the full shared view-option mechanism this participates in. A separate numeric control on this surface (or an adjacent one sharing its window procedure) accepts a "scanner display" percentage from 2 to 100, formatted as "N%": pressing Enter commits a typed value, Escape reverts to the previously stored value, and either action updates an associated slider position and unconditionally turns on the map's scan-range-circle overlay. While this control is being adjusted, a custom hover-tooltip window shows the live value, its visibility gated by how recently the value last changed (roughly a 400ms window). The exact game-facing effect of this percentage on displayed circle size was not conclusively confirmed — see `client-interface.md`'s "Map canvas" notes.

### Fleet orders and order details

The order editor manages an ordered list of fleet instructions. The detail surface shows the parameters of one selected instruction. A fleet with pending waypoints has its route displayed on the map while it is selected, as specified in the client-interface document.

Confirmed by inspection of the exported client: the detail surface's secondary control is context-sensitive to which instruction type is selected — observed variants include a combo box enumerating every other race in the game (for a "give this fleet to another race/player" instruction), a small combo offering several generated candidate fleet names plus a generic fallback (used when an instruction spins off a new fleet, e.g. a split or merge target), and further numeric-amount variants for cargo/mining-style instructions. This is a single context-sensitive control reused across instruction types, not several separate dialogs. A prior working hypothesis that this segment implemented a standalone "Fleet Composition" screen (with its own Split/Rename/Scrap/Give buttons) was not confirmed — no such standalone screen, nor a Rename-dialog invocation, was found; the confirmed behavior is the order-detail combo described here.

### Cargo transfer

The transfer editor is bound to two compatible inventories. It offers a quantity choice for each transferable category, updates the candidate result as values change, and commits only after validation. The editor cannot create a negative source amount or exceed a legal destination capacity.

### Fleet merge

The merge editor lists eligible fleets in the current context and requires an explicit choice before combining them. It excludes incompatible or unavailable entries. Accepting performs the merge request; cancelling preserves the pre-merge state.

Confirmed by inspection of the exported client: the merge editor pre-selects the fleet the merge was invoked from (and both fleets automatically, when exactly two are eligible). Per ship-design slot being merged, a design already at full fuel merges without penalty; a design below full fuel undergoes a probabilistic check that can leave some ships behind rather than merging them, with the result reported through one of five graduated messages. Designs with genuinely incompatible cargo or fuel capacity abort the merge outright rather than partially combining. After a successful merge, special-ability stats are recombined per field — some take the maximum value across the merged ships, others sum with a fixed cap. See `fleet-movement-scanning-cargo.md` for the full mechanic.

### Rename surfaces

The client has both ordinary rename and compressed-context rename surfaces. Each accepts a text value for the selected object, applies length and field validation, and commits only on accept. The compact variant has the same logical result and differs only in presentation.

Confirmed by inspection of the exported client: the two variants differ in *when* validation runs, not only in presentation. The ordinary rename surface filters and rewrites its text on every keystroke (live input filtering), in addition to validating again at accept time; the compact variant validates only once, at accept time, and shows different prompt wording depending on whether the target slot was previously empty.

Independently re-confirmed by a later pass reading both dialog window procedures directly: the ordinary variant's edit-control change notification is the only one of the two wired to an immediate live-filter call, while the compact variant's accept handler reads the field only once, at OK/Cancel time — corroborating the live-filter-vs-accept-time-only distinction above at the mechanism level rather than only behaviorally.

### Slot/equipment editor

The slot editor presents a finite collection of assignable positions and compatible choices. Selecting a position loads its current assignment; selecting a choice updates the working design or order. Incompatible choices are not offered as valid assignments.

Confirmed by inspection of the exported client: compatibility checking is graded, not a simple yes/no — the editor can distinguish a choice that is fully available from one that is exactly one technology level away from being available, from one that needs multiple fields raised, from one that is unavailable for other reasons. This finer distinction is not conveyed by the general phrasing above and should be reflected in a compatible implementation's feedback to the user.

See `ship-design-and-components.md` for the underlying component category/subtype resolver and the two race-trait gates (a per-subtype hard-coded PRT/boolean-flag check, and a generic 32-bit per-race "special ability" bitmask check) that back the "unavailable for other reasons" case. Both of those gates are binary; the tech-level-distance grading described above was not traced to a specific function in that pass and remains open there too.

**Candidate function individually confirmed by a later pass reading it directly (not just inferred from aggregate behavior).** `research-tech-tree.md` §4 documents a function in the Research dialog's own code segment (Ghidra `FUN_10d8_4a86`) that, given a target level for each of the 6 tech fields, temporarily simulates raising every currently-deficient field to that target — accumulating cost via the segment's own per-level cost primitive (`FUN_10d8_1580`) at each intermediate level — and totals the resources such a climb would cost, then restores the real tech levels unchanged before returning. Direct inspection confirms the mechanism exactly as previously inferred, including a `0xFFFF` sentinel return for a malformed/out-of-range target-level input. This produces exactly the kind of figure (and per-field level deltas) a graded "how far away, and what would it cost" indicator would need. What remains unconfirmed is only the final link from this function's output to a specific on-screen tooltip string in this editor — that connection is still an inference, not a traced call site, but the candidate function's own behavior is no longer in doubt.

### Ship and starbase designer

Confirmed by inspection of the exported client's real dialog resource (caption **"Ship & Starbase Designer"**): this is the single dialog behind the "lead not yet traced to a specific segment" noted in earlier passes. It presents one shared design list plus six mutually-exclusive category filter buttons — **Ships**, **Starbases**, **Existing Designs**, **Available Hull Types**, **Enemy Hulls**, **Components** — a name-entry field for a design under edit, a combo box, and three action buttons (**Copy Selected Design**, **Delete Selected Design**, **Edit Selected Design**) alongside the standard OK/Cancel/Help set. The slot/equipment editor described above is opened from this dialog's "Edit Selected Design" action.

See `ship-design-and-components.md` for the underlying design record layout (16 hull-design + 10 starbase-design slots per race, 147-byte records, up to 9 installed components per design), the component-to-slot write path, and a previously-undocumented mechanic confirmed there: deleting a filled component slot from an already-saved design checks every existing fleet using that design and prompts for confirmation if ships already built would be affected.

### Minefield and scanner views

The minefield view is an object-bound visual inspector. The scanner view displays scan-related coverage or results relative to the current selection or observer. Neither view grants information beyond the client's current known state. Both refresh when their input object, owner, or display parameters change.

**Minefield visibility popup, confirmed by inspection of the exported client.** The map's minefield overlay (see `client-interface.md`'s "Map canvas" section) draws minefields using one of 3 distinct fill patterns, one per minefield type, and its visibility is controlled by a dedicated popup checklist menu (opened from the same shared view-option slot that the keyboard's "8" shortcut and the panel's own control both address): the popup lists an "All"/"None" pair followed by one independently toggleable line per other player in the game, with checkmarks reflecting each player's current visibility bit. Selecting "All" or "None" sets every bit at once; selecting a specific player's line toggles only that bit. This is a compact-selector-style surface (see "Styled single-choice selector" under Custom widgets) rather than a full dialog.

## Session creation and configuration

### New-session flow

The client offers a simplified setup path and a multi-stage detailed setup path. Both operate on a session draft. The detailed flow separates general settings from later configuration stages; advancing carries the current draft forward, while cancellation leaves no finalized session.

See `new-game-setup.md` for the concrete parameter set (galaxy size/density options, player-slot assignment encoding) and the galaxy-generation algorithm this flow ultimately invokes, and `victory-conditions.md` for the detailed flow's final configuration stage.

### Randomization seed

The seed surface accepts a session-generation seed and validates its input before returning it to the setup draft. It distinguishes user-provided values from the request to generate a fresh random value.

**Confirmed by inspection of the exported client.** The dialog reads a typed decimal string one digit at a time (validated character-by-character against a shared digit-class lookup table) and accumulates it into a 32-bit value via repeated multiply-by-ten-and-add. An empty field is treated as "generate a fresh random value" (the dialog accepts without reseeding); a nonzero typed value is passed to the shared RNG engine's seed routine. This confirms, at the mechanism level, the underlying random-number generator: a combined multiplicative-congruential generator carrying two independent 32-bit state words, each advanced by its own large-modulus multiplier every draw and combined by subtraction (with modulus wraparound) to produce the returned value, reduced by the caller's requested upper bound. The seed dialog's own path derives its two lookup-table indices directly from the low 6 bits of the typed value (guaranteeing the two indices differ by construction). A small push/pop stack lets a caller temporarily substitute a different seed and later restore the exact prior state, so that borrowing the RNG for a one-off computation elsewhere in the client does not disturb ordinary gameplay random sequences.

**A second, independent seeding entry point, refined by a later pass.** A separate seed routine (deriving its two lookup-table indices from a bit-scrambled combination rather than a plain 6-bit split) reseeds this *same* shared generator from the system tick count — used, in the ordinary case, at application startup and at at least one other session-reset point, which is plain gameplay randomization rather than something "unrelated" to it as previously characterized here. That same routine is separately reused — with the RNG state saved and restored around the call via the push/pop stack above — by the Serial Number surface's accept-time check (see the Serial Number entry below), which seeds the shared generator from a value derived from the typed input rather than from the clock, draws several values from it, and compares the result against a second derived value. Consistent with this project's house rule on copy-protection mechanisms, no more of that check's internal derivation is documented here.

**A wholly separate, second instance of the same generator algorithm exists, confirmed by inspection of the exported client, carrying its own independent state pair rather than sharing the one described above.** It has its own matching push/pop save-restore pair (used to checkpoint and roll back the stream around a bounded retry loop — see the galaxy star-placement rejection-sampling loop in `new-game-setup.md`, which draws from this second stream) and its own explicit reseed-and-advance entry point: given a handful of small identity fields, it reseeds the stream via the same table-lookup scheme and then draws and discards a record-specific number of values from it before use, so that a given record's position in the stream is reproducible from its own identifying fields rather than depending on how much of the stream earlier records consumed. A companion routine XORs a byte buffer against successive draws from this stream. Together these back a lightweight, non-cryptographic **record-level scrambling scheme**: reading a certain flagged class of on-disk record involves reseeding this second stream from the record's own small header fields and XOR-unscrambling its payload bytes against the resulting keystream — distinct from, and layered independently on top of, the turn-file delta-record protocol documented in `save-turn-file-format.md`.

### Local access-secret entry and replacement

The access-secret entry surface requests an existing secret. The replacement surface collects a new value and confirmation. Mismatched replacement entries fail validation and remain uncommitted. Both surfaces conceal typed characters and do not display stored secret content.

## Planning and management

### Production and compact production editors

The production editor manages an ordered construction queue. The compact variant provides the same logical queue operation for a constrained context. Each supports selection of an active queue item and changes to that item's requested work. Queue changes remain local until accepted through the applicable editor or workflow.

**Correction, verified against the exported client:** the "compact variant" identified in the exported client is not the same logical queue operation in a smaller window — it is a distinct **saved production-template manager** exposing exactly 4 named template slots, each holding up to 12 auto-build entries plus one setting flag, that can be applied to any planet's queue in one action (see `production-queue.md` §9). The full per-planet queue itself is edited through the (uncompacted) production editor only. A compatible implementation should model these as two related but functionally distinct surfaces, not one editor in two sizes.

### Research preferences

The research editor has independently editable discipline focus and allocation settings. It displays the applicable current settings, records a modification only when a value changes, and commits the changed preference set upon acceptance.

### Battle plans and plan names

### Messages

The message view presents recorded messages and maintains a current position within the collection. It includes four category-selection controls, a current-message area, and a scrollable or otherwise selectable message list. Changing a category or row refreshes the current-message area. Reading or navigating messages does not alter their underlying content. The current message and navigation availability update when the collection changes.

Confirmed by inspection of the exported client: Next/Previous Message navigation supports an optional filter bit tested against each candidate message's stored classification, letting navigation skip to only messages matching (or not matching) that filter — consistent with an "unread only" or similar toggle, though the filter's exact real-world meaning was not confirmed.

**Message record store, confirmed by inspection of the exported client.** Each message is a variable-length record — a type code, a per-type field count (looked up from a small per-message-type table), and up to several data fields individually stored as either a single byte or a full word depending on a per-field size bit — appended to a growable in-memory buffer (bounded to roughly 64K); a companion 392-bit "read" bitmap tracks which message indices have already been seen. The Next/Previous navigation described above, and the filter bit, are backed directly by linear scans of this same read bitmap looking for the next/previous message whose read-state does or doesn't match the requested filter — confirming the filter is (at minimum) a read/unread distinction, not an arbitrary message-category filter. The same buffer is what gets serialized into a player's turn/save file as the "message-text blob" described in `save-turn-file-format.md` §6.

**Report-text formatting is a distinct mechanism layered on top of the message store — see "Escape-coded report-text formatting" under Custom widgets below** for the escape-sequence substitution engine that expands a stored message's raw format string and field values into final display text.

**Message record header, resolved bit-for-bit by inspection of the exported client's record-builder and record-scanner routines.** Every record has a fixed 5-byte header followed by a variable payload, matching the scanning routines' own stride computation (`recordLength = headerByte0 >> 4, plus 5`): byte 0's low nibble is the **target race/player index (0-15)** — confirming the 16-race population cap at this structural level, not just from race-design UI limits documented elsewhere — and its high nibble is the record's *extra* payload length in bytes (0-15) beyond the fixed header. The word at offset 1-2 packs the **message-type code in its low 9 bits (0-511)** plus, in its remaining high 7 bits, one flag bit per additional data field recorded (0 = stored as a single byte, 1 = stored as a full word) — bounding a message to **at most 7 additional fields**, on top of one fixed word value always stored at offset 3-4. A per-message-type **field-count table**, indexed directly by the masked 9-bit type code (i.e., up to a 512-entry byte array), gives the count of those additional fields for each type; the record-builder loops that many times, reading each extra field's value directly from the caller's stack (beyond its own declared parameters) and packing it as a byte or word per the flag bits above.

**Field-count table contents could not be enumerated from this material — an honest limitation, not an oversight.** The table itself is program *data*, and the exported decompile contains only the *code* that indexes into it (`*(byte *)(msgType + <fixed data offset>)`); no corresponding initialized-array literal survives in the exported `.c` file to read actual per-type values from. What could be confirmed instead is the *shape* of the table's use: every one of the **155 call sites** found for the three message-posting entry points in this segment passes exactly one explicit data value (the fixed offset-3 word), with zero call sites supplying additional stack arguments — meaning every message type actually exercised through these entry points in this codebase carries an effective field count of 0 or 1 (any further sub-values seen at call sites, e.g. two bytes packed via `CONCAT11`, are the *caller* manually packing multiple sub-values into that single fixed word, not the record store's own multi-field mechanism). Whether any message type elsewhere in the client actually uses field counts of 2-7 was not confirmed either way in this pass — the capability clearly exists in the format engine (the header's 7-bit flag field would be meaningless otherwise), but no exercised example of it was found.

### Word-wrap text layout engine

**Confirmed by inspection of the exported client.** A shared line-layout routine takes a run of text (either a length-delimited span or a NUL-terminated string), a left margin, a right edge, and a fixed line pitch, and lays it out one line at a time against the current font. Its wrapping strategy is a **greedy, whole-word breaker with no hyphenation**: for each line it first measures the *entire* remaining text against the available width; if that fits, the whole remainder becomes the line (and any fitting trailing spaces past the natural break are folded in, so a line can absorb trailing whitespace up to the next real content). If it does not fit, the routine repeatedly backs off from the tentative line end — first trimming trailing spaces, then skipping back over the entire overflowing word, then trimming any further spaces before that word — and re-measures, until the remaining span fits or nothing is left to remove. A break is never made in the middle of a word. Once a line's span is fixed, the routine can optionally paint it (a "measure only" mode exists, used to compute total wrapped height/width without drawing) before advancing the vertical cursor by one fixed line pitch, resetting the horizontal cursor to the left margin, and skipping any leading spaces at the start of the next line. This engine is called very widely — from message/report display, tooltip-style popups, and at least one report-grid cell renderer — making it the client's single shared multi-line text layout primitive, distinct from (and used by) the escape-coded report-text formatter described below, which expands the raw text before this engine lays it out.

**Companion text-drawing primitives, sampled from the same cluster.** The word-wrap engine's own line-break search is itself built from three small helpers — skip past any leading spaces at a line start, back up over trailing spaces before a candidate break, and back up further over an entire overflowing word — each a short, single-purpose span-adjustment routine. Alongside the wrap engine sit several simpler, single-line text-drawing primitives reused across dialogs: draw a string horizontally centered under a given anchor point; draw a string left-aligned while advancing a running vertical cursor by its measured height (used to stack several lines of text without a full wrap pass); draw a string centered in both axes within a rectangle, with an optional background fill first; and draw a string against a fixed-width field, either padding the unused space or clipping the string against the field's edge when it overflows (a candidate for fixed-width status-strip/label fields elsewhere in the client). A separate, unrelated helper truncates a string in place, one character at a time from the end, until it fits a given pixel width — a simple "shorten this label to fit" utility distinct from the shrink-to-fit *font-resizing* approach described below.

### Font-resource loader and autofit label sizing

**Confirmed by inspection of the exported client, extending the "embedded font-resource loader" finding.** Beyond the startup GDI-resource pass (see `client-interface.md`'s "Application shell" section, which builds a small fixed table of fonts once at launch), a separate on-demand routine creates a single additional font at a caller-specified point size in the same shared UI typeface: it builds a font-description record sized from the display's reported vertical DPI, copies in a shared face-name string, calls the standard font-creation API, and — if the caller wants it — selects the new font into the display context just long enough to read back its line metrics (ascent plus internal leading) before restoring the previous font, reporting that measured line pitch to the caller. This on-demand path is called with explicit point-size arguments (observed values 8 and 5) from outside the segment, i.e. it backs at least one further window's fonts beyond the startup table, rather than only being used during the startup pass.

A second, related routine implements **shrink-to-fit label sizing**: given a text string and a target rectangle, it builds a temporary font at an initial guessed size, measures the text, and — if it doesn't fit — iteratively rescales the guessed point size proportionally to how far off the fit is (via a scaled-ratio adjustment rather than a simple one-point step), rebuilding and re-measuring the temporary font each pass, until the text fits within both the rectangle's width and height (with an 8-pixel margin) or the loop bottoms out. Once a fitting size is found, it draws the text centered in the rectangle with that font and immediately deletes the temporary font handle — a "biggest font that still fits" label primitive, plausibly the mechanism behind the segmented bar/gauge's centered "value / value" label described below, though the exact call site backing that specific label was not traced.

### Escape-coded report-text formatting

**Confirmed by inspection of the exported client, extending the "custom escape-sequence string-format engine" hypothesis with concrete mechanism detail:** report/message text is not produced by the ordinary C-style format routine alone. A dedicated pre-pass scans a format string for a literal escape character followed by one of roughly a dozen one-letter codes and substitutes each with the correct kind of expanded text before final formatting: a ship/starbase component's display name; a race's display name (through the race-name/summary string builder described under "Title and status area" above); a plain string-table lookup; a race relationship-name lookup; a value formatted with automatic English singular/plural word-choice (checking whether the base word already ends "s" or "es" before appending a plural "s," rather than always appending one); a value formatted with an appended unit-name suffix chosen by magnitude; a conditional switch between two format strings depending on a threshold comparison; and a large-integer formatter that inserts thousands-separator punctuation (comma plus space) every three digits, with a special case for values that are an exact power of two. This is the mechanism underneath ordinary-looking report sentences such as "3 Large Freighters" versus "1 Large Freighter," or "1,234,500 resources," rather than those being pre-baked per-count string-table entries.

**Fuller escape-code enumeration, extending the above from direct inspection of the formatting engine's dispatch switch.** The engine recognizes a literal backslash followed by a single letter (case-sensitive; upper- and lower-case variants of the same letter sometimes share identical behavior, sometimes differ). Substantially more than "roughly a dozen" distinct *letters* are actually recognized — several simply alias to one of a smaller number of underlying *behaviors* — enumerated here to the extent this pass could resolve them:

- **E** — looks up a value by a single byte read from the field stream (a small fixed-table lookup; category not identified).
- **F** — looks up a value via a dedicated helper keyed by the raw field value (category not identified).
- **G** — a plain string-table lookup at one fixed table-index base.
- **I**, **j** — plain string-table lookups at two further, different fixed table-index bases (same underlying string-fetch helper as **G**, different base offsets).
- **L** / **l** — builds a race-name/summary string (via the same string-builder confirmed elsewhere for race-name and title-bar text) from a packed field value; the two cases parse that field's bits identically except for one derived flag, consistent with a singular/plural or short/long variant pair.
- **M**, **e**, **m** — three separate word-indexed lookup tables (three different fixed bases), each returning a short string keyed by a numeric field value — consistent with three distinct "unit name" or "category name" tables (e.g., mineral names vs. some other per-category label set), not yet individually identified.
- **O** — builds a race-name/summary string like **L**/**l** above, but derives the race index from a different (ship/component-slot-shaped) field layout rather than taking it directly.
- **P** — **confirmed:** the "conditional switch between two format strings depending on a threshold comparison" already documented above — compares a field value (divided by 100) against a fixed threshold constant and formats using one of two entirely different format strings depending on the result.
- **S** — a "self vs. other" substitution: compares a field value against the *currently active/viewing* race; if it matches, substitutes a different phrase (built and byte-reversed through a distinct pair of string-table entries) than when it doesn't, consistent with a "you" vs. "the `\`race`\`` grammatical substitution.
- **U** / **V** / **v** — **confirmed, extending the existing "unit-name suffix chosen by magnitude" note:** formats a 32-bit field value as a plain number, then (for **U**/**V** only, not **v**) appends a unit-name string looked up from a word-indexed table by a "current unit" index — **V** sets that index explicitly from a second field value; **U** reuses whatever unit index was last set (persisted across substitutions in the same message, defaulting to none); **v** always omits the unit suffix entirely.
- **X** — recognized by the dispatcher but performs no distinct substitution of its own (falls through to plain literal-character handling).
- **Z** — **confirmed, extending the existing "large-integer formatter" note into a second, separate mechanism:** given a bitmask field, if it is an exact power of two the single corresponding race's name is substituted (via the same builder as **L**/**O**); otherwise every set bit is expanded into a full, comma-and-"and"-joined list of race names (e.g., "Race A, Race B, and Race C") — i.e., a *race-bitmask-to-name-list* formatter, distinct from the single-value thousands-separator formatter already documented.
- **f** / **h** / **r** / **t** / **y** — a family of "current name" substitutions sharing one common name-buffer source (the same global text buffer used for the currently-edited object's name elsewhere in the client); they differ in what, if anything, is appended afterward — **y** and **h** each append a different fixed suffix (consistent with distinct grammatical/possessive endings), while **f**, **r**, and **t** instead fall through to plain-number formatting branches under certain conditions. The exact grammatical distinction between all five was not fully resolved.
- **g** — looks up a component/design display name (the same underlying helper used for ship/starbase component names elsewhere).
- **i** — aliases to the same plain-number-formatting branch as **r** above.
- **k** — **confirmed:** the "ship/starbase component's display name" already documented — resolves a component/design record and substitutes its stored name field directly.
- **n** — **confirmed:** the "automatic English singular/plural word-choice" formatter already documented — dispatches (through a shared category/count-formatting helper also used to look up plain planet, race, and component names by category code) to a paired singular/plural string-table entry pair chosen by whether the count is exactly one; two reserved field values redirect to the **g** and **o** substitutions instead of formatting a number at all.
- **o** / **p** — both substitute a planet's display name; **o** additionally checks one bit of the target's owner data and, when set, redirects to the **s** substitution (a race name) instead — consistent with "show the planet's name, unless a special ownership condition applies, in which case name the owning/related race instead."
- **s** — substitutes a race's display name, with a forced high-bit flag passed to the lookup (a distinct variant from plain race-name lookups elsewhere — possibly the "race relationship-name lookup" already noted above).
- **u** — plain numeric formatting with no unit suffix and (unlike the large-integer formatter) no thousands-separator punctuation.
- **w** — substitutes the current contents of a different global text buffer (the same one used elsewhere for the active window/dialog's title text).
- **z** — builds a per-design-slot component/race name similar to **O**, from a field value split into a race index and a design-slot index (0-31, split across two parallel design tables), with the same "is this the currently active race" special-casing seen under **S**.

**Underlying number-formatting primitives, sampled this pass.** The thousands-separator behavior described above (and under **Z**/the large-integer formatter) is implemented by a dedicated routine that re-copies an already-formatted digit string, inserting a comma after every third digit from the end — a distinct, separately-callable primitive rather than something built into the general-purpose sprintf-style formatter itself. A second, unrelated numeric primitive rounds a raw value and appends a compact "k" or "M" magnitude suffix (choosing the divisor and suffix by comparing the raw value against fixed 10,000 and 1,000,000 thresholds) — a "compact large quantity" formatter distinct from the plain thousands-separator behavior above; its call sites were not traced to a specific on-screen figure in this pass, but it is a plausible candidate for any compact resource/quantity readout that abbreviates rather than fully spelling out a large number.

**Total distinct letters recognized: 26** across the cases above (counting upper/lower-case pairs separately), collapsing to a substantially smaller number of underlying *behaviors* (roughly a dozen, matching the earlier estimate, once aliased letters are merged) — the previous "roughly a dozen" note undercounted the *letter* surface but was a reasonable estimate of the underlying *mechanism* count. Several helper-name/category mappings above (E, F, several of the M/e/m tables, the exact f/h/r/t/y suffix distinctions) could not be pinned to a specific real-world meaning — no string/label data survives to check them against.

## Known boundaries

The exported client identifies these UI surfaces and, for the dialogs whose real Windows resources were directly parsed (see the section above), now includes exact captions and static control label text as well. What remains unrecoverable from the exported material is: pixel layout/icon art for surfaces not covered by a parsed resource, keyboard mnemonic letters where a control's label is itself runtime-populated (the LRT and victory-condition wizard pages above), and host-side game-rule outcomes. A compatible clean-room implementation may choose different presentation while preserving the behaviors above.
