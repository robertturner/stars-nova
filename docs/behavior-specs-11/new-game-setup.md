# New Game Setup and Galaxy Generation

Behavior specification for the new-game creation flow and galaxy/universe generation in the 1995-2000 4X game *Stars!*. This document is derived directly from the exported client's decompiled logic; it is new material, since no prior document in this set covers game setup or galaxy generation. Facts are described in generic terms; no original identifiers or literal code are used.

## Overview

Creating a game follows one of two paths: a **Simplified** single-screen setup, or a **Detailed** three-page wizard (general settings, player-slot assignment, victory conditions). Both paths write into the same underlying game-setup draft, and both ultimately invoke the same galaxy generator once settings are finalized. A separate batch/scripted mode allows a game to be created from an external configuration source without going through the interactive wizard at all.

## Mechanics

### 1. Detailed setup wizard pages

The three detailed-setup pages are confirmed to be sequential pages of one wizard flow (each sets its window title from a shared string combined with its own page number):

1. **General settings** — Galaxy Size (5 mutually-exclusive options), Star Density (4 options), a third 4-option setting — **confirmed as Starting Distance by `client-ui-dialog-catalog.md`'s real dialog-resource extraction, with exact labels Close / Moderate / Farther / Distant**, which sets the spacing of the home worlds (§3, "Home-world placement and Starting Distance") — and at least 7 independent boolean game-option flags whose individual meanings could not be determined (no label text survives in the analyzed material). These option flags are consumed directly by the galaxy generator (§3) — for example, one flag affects whether certain player types receive an extra starting planet, another affects a mineral-concentration bonus, and another affects how randomization is seeded.

   **Confirmed by inspection of the exported client (galaxy-generation continuation routine, formerly rated Partial):** one of these boolean flags is confirmed at the mechanism level. When set, it forces every ordinary (non-home-world) planet's mineral concentration to a flat maximum value instead of the normal randomized range (see §3's new mineral-concentration bullet below) — this is almost certainly the "Beginner: Maximum Minerals" checkbox named in the exported dialog resource. The remaining flag bits gate smaller, harder-to-attribute effects: one extends the star-naming pool's duplicate-prevention ceiling from 999 to 1000 names and applies a small environment-value adjustment to two fixed planet indices in the per-planet initialization table (see the bit `0x08` paragraph below), and another scales newly-seeded surface mineral tonnage upward by a flat 25% and nudges a planet-age-like field upward when it rolls low. **Resolved by the table below and the step-6 pass:** the last of these is the "Accelerated BBS Play" checkbox (`0x20`), and the star-name/two-fixed-planet bit (`0x08`) is the tutorial-game marker; see the "Option-flag effects" table after the bit-to-label table.

   **Bit-to-label mapping now resolved for the six named checkboxes, by cross-referencing the batch/scripted format's own flag-array parser (§4).** The batch-config reader that populates this same options word reads its "7 boolean toggles" field in one fixed order and immediately re-packs each one into a specific bit of the options byte (a second, adjacent byte holds an 8th bit for the anti-clumping toggle described in §3): the read order is bit 0, bit 1, bit 5, bit 7, bit 4, bit 6 of the first byte, then bit 0 of the second byte. Two of these seven bits are independently confirmed by their *mechanism* elsewhere in this document (bit 0 of the first byte forces flat-maximum mineral concentration, matching "Beginner: Maximum Minerals"; bit 0 of the second byte gates the anti-clumping relaxation pass, matching "Galaxy Clumping") — both land exactly at the position their read-order rank predicts (first and last respectively), which is strong internal corroboration that this read order matches the on-screen checkbox order `client-ui-dialog-catalog.md` recovered from the plain dialog-resource extraction. Taking that order at face value maps the full set as:

   | Read order | Bit | Checkbox label |
   |---|---|---|
   | 1st | first byte, bit `0x01` | **Beginner: Maximum Minerals** (independently confirmed by mechanism, above) |
   | 2nd | first byte, bit `0x02` | **Slower Tech Advances** |
   | 3rd | first byte, bit `0x20` | **Accelerated BBS Play** |
   | 4th | first byte, bit `0x80` | **No Random Events** |
   | 5th | first byte, bit `0x10` | **Computer Players Form Alliances** |
   | 6th | first byte, bit `0x40` | **Public Player Scores** |
   | 7th | second byte, bit `0x01` | **Galaxy Clumping** (independently confirmed by mechanism, above) |

   This leaves exactly two bits of the first options byte (`0x04` and `0x08`) that the batch-format flag reader never touches — i.e. they are not any of the seven named checkboxes at all, but internally-derived flags set by other code. **Bit `0x08` is the tutorial-game marker** (the "deterministic galaxy" guess above was right and is now attributed): the game-commit routine skips the tick-count seed for the game id when it is set (`:51803`-`51808`), so the tutorial game has a fixed id; the star-name pool grows from 999 to 1000 names; planet index 5 gets its three environment values (current and original copies) lowered by 5 and planet index 11 gets +20 on its first environment value (`:50515`-`50529`; the earlier text of this section called these "mineral-concentration" tweaks, but the bytes written are at planet offsets `0xc`-`0x11`, the environment fields, while the concentrations are at `0x9`-`0xb`); and at turn time the bundled scripted orders for slot 0 are read in place of a file and the nonce test of the general file validator is skipped (`turn-generation-engine.md` §1a, `save-turn-file-format.md` §10.6). **Bit `0x04` is the single-human-player flag**, not a relationship-table bookkeeping bit (corrected by the step-6 pass): at the end of game commit the code walks the slots, treats a slot as human when its computer bit (`0x200` of the slot word at +2) is clear or its category field is 7, gives every computer slot a fixed value in its 4-byte per-race number field (`:51783`; the value is deliberately not recorded), and sets `0x04` only if the walk completes with exactly one human (`:51775`-`51791`; the walk stops at the second human it meets, so the computer slots after that point do not get the per-race number). **The rule, stated plainly:** a slot counts as a computer player for this test only when its computer flag is set **and** its AI category is not 7; category 7 is the driver of an inactive human and of the expansion player, the last entry of the human-race list (`ai-opponent-behavior.md` §1a), so those slots count as human. *Reimplementation note (recommendation, not original behavior): a port without the category-7 driver can use "has an active AI program" as the computer test, provided any substitute for an inactive or absent human (a housekeeping AI that only researches and builds) is counted as human here;* when it is set, every ordered pair of distinct slots gets relation value 2 (`:51792`-`51802`). Consumers found: client menu/dialog choices (`:8197`-`8225`, `:46146`, `:98242`, `:98591`) and the Mystery Trader design roll after year 100 (`:115565`).

**Option-flag effects (bit of `DAT_1128_0080`; "creation" = galaxy generation and game commit, "turn" = the master routine, whose step numbers are those of `turn-generation-engine.md` §1 and §1b).**

| Bit | Option | At creation | During turn generation |
|---|---|---|---|
| `0x01` | Beginner: Maximum Minerals | every planet's three concentrations are 100 instead of rolled, and both the high-radiation raise and the low-concentration roll of §3 are skipped (`:50533`-`50586`) | none |
| `0x02` | Slower Tech Advances | none | research costs double (buy loop, steps 12e/20/23g; salvage reward) |
| `0x10` | Computer Players Form Alliances | none | none in the master routine; read by the AI planning routines only |
| `0x20` | Accelerated BBS Play | every ordinary planet's mineral concentration below 40 gets +5 (`:50561`-`50565`); surface mineral tonnage +25% (`:50610`-`50617`); each home planet's starting population is multiplied by `(growth rate % + 5) x 2 / 10`, i.e. 4x at 15%, and its reported-population field rescaled to match (`:51007`-`51022`). The growth rate used is the race's growth setting, doubled for Hyper Expansion (`FUN_10e0_445a`). Full order of the starting-population steps: see "Starting population, exact order" below the table | none |
| `0x40` | Public Player Scores | none | every player's files carry every race's score record once the turn counter exceeds 19 (step 39) |
| `0x80` | No Random Events | no wormhole pairs (`:51702`-`51710`; without the bit the pair count is a per-galaxy-size random draw) and no planet artifacts (without the bit, 1 planet in 3 carries the artifact flag, `:50488`-`50495`) | no comet, environment-shift, mineral-deposit or Mystery Trader-creation rolls (step 20), no artifact research bounty (steps 12d/23f); the special-object passes and the salvage rolls still run |
| `0x100` | Galaxy Clumping | the relaxation pass of §3 | none |

"Public Player Scores" and "Slower Tech Advances" also have client-side effects (score window, cost displays) that are outside this table.

**Starting population, exact order (gap-report pass; per-player home-planet setup in `FUN_1078_*`, `stars.exe.export.c:50953`-`51022`, second planet `:51511`-`51533`).** Population is held in units of 100 colonists, and every division truncates. (1) Base: 250 units (25,000 colonists), or 175 units (17,500) if the race has Low Starting Population (lesser trait 11). (2) A computer player at the Expert skill tier (skill field 3) gets +10%, i.e. the population plus a tenth of itself, truncated (`:51000`-`51006`: the test is the computer-player bit together with a skill field above 2, and it sits in the same block that fixes every computer player's leftover points at 50). Human players and the Easy, Standard and Tough tiers get nothing, and the step does not depend on any game option. (3) If Accelerated BBS Play is on, the population is multiplied by (g + 5) × 2 and then divided by 10, where g is the race's growth-rate setting (doubled for Hyper Expansion). The multiplication comes first and the division last. (4) For the two primary traits that receive a second home planet (Packet Physics and Interstellar Traveler), the second planet is given 2/5 of the home planet's population as it stands after steps 1-3, and the home planet is then reduced to 4/5 of it (each truncated). So Low Starting Population changes the base and Accelerated BBS multiplies the result. Example: a Low Starting Population race with a 15% growth rate in an Accelerated BBS game gets 175 × 40 / 10 = 700 units, i.e. 70,000 colonists; the same race without the trait gets 100,000. A Hyper Expansion race with a 10% setting uses g = 20, a ×5 factor, so 875 units (87,500) with the trait. A Packet Physics race with the trait and 15% growth gets 700 units first, then 280 (28,000) on the second planet and 560 (56,000) on the home planet.
2. **Player-slot assignment** — a grid of per-slot rows, each encoding a small state (open / default-unassigned-or-computer-controlled / a specific race assigned / a relation-table-linked assignment) plus a sub-index identifying which race or preset. See `client-ui-dialog-catalog.md`'s "Slot/equipment editor" family for the shared UI patterns this reuses.
3. **Victory conditions** — see `victory-conditions.md`.

### 2. Simplified setup

A single-screen dialog (resource 209) with two radio groups, **difficulty** (Easy, Standard, Harder, Expert = 0-3; default Standard) and **galaxy size** (Tiny-Huge = 0-4; default Small), a drop-down of the seven predefined races plus the player's own race for slot 0, and buttons for Customize Race, Advanced Game, Begin Tutorial, OK, Cancel and Help. *(Rewritten from the code, `FUN_1078_4a82` `:53492`-`53582`, the dialog procedure at segment 16 `0x59e6` `:53971`-`54211`, and the player-count routine `FUN_1078_53c4` `:53602`-`53811`, raw segment 16 `0x53c4`-`0x55fa`; the earlier "about 2 / up to 4 / 12-15" summary was wrong.)*

**What OK (and Advanced Game) writes.** Before the dialog opens, the whole 64-byte game-setup block is cleared (the previous player count is kept); when it closes, the victory defaults of `victory-conditions.md` §1 are written. After OK or Advanced Game: slot 0 is the human with the chosen race; the player count and the computer slots come from the table below; **density is set to Normal**; **Starting Distance is Moderate for Easy and Standard and Farther for Harder and Expert**; the option flags Maximum Minerals, Slower Tech Advances, Accelerated BBS Play, No Random Events and Public Player Scores are cleared, **Computer Players Form Alliances is set only for Expert**, and Galaxy Clumping stays off (the block was cleared); the game name is dynamic string 459 + 5 × difficulty + size (twenty fixed two-to-five-word titles, one per difficulty and size); and the year gate is seeded as below. OK creates the game at once; Advanced Game opens the three-page wizard pre-filled with these values.

**Player count.** The count includes the human. Every "1 in n" below is a separate draw of the game's uniform random generator (0 to n − 1, a hit on 0), made in the order listed, and the first hit decides.

| Size | Easy, Standard | Harder | Expert |
|---|---|---|---|
| Tiny | 2 | 2 | 1 in 3: 3; otherwise 2 |
| Small | 3 | 1 in 4: 4; otherwise 3 | 1 in 4: 5; then 1 in 3: 4; otherwise 3 |
| Medium | 7 | 1 in 5: 8; then 1 in 5: 6; otherwise 7 | 1 in 10: 9; then 1 in 10: 5; then 1 in 4: 8; then 1 in 4: 6; otherwise 7 |
| Large | 12 | 1 in 5: 13; then 1 in 5: 11; otherwise 12 | 1 in 10: 14 or 15 (even chance); then 1 in 10: 9 or 10 (even chance); then 1 in 4: 13; then 1 in 4: 11; otherwise 12 |
| Huge | 16 | 1 in 7: 14; then 1 in 5: 15; otherwise 16 | 1 in 10: 11, 12 or 13 (equal chances); then 1 in 6: 14; then 1 in 4: 15; otherwise 16 |

Resulting probabilities: Tiny Expert 2 (2/3), 3 (1/3). Small Harder 3 (75%), 4 (25%); Small Expert 3 (50%), 4 (25%), 5 (25%). Medium Harder 6 (16%), 7 (64%), 8 (20%); Medium Expert 5 (9%), 6 (15.19%), 7 (45.56%), 8 (20.25%), 9 (10%). Large Harder 11 (16%), 12 (64%), 13 (20%); Large Expert 9 and 10 (4.5% each), 11 (15.19%), 12 (45.56%), 13 (20.25%), 14 and 15 (5% each). Huge Harder 14 (14.29%), 15 (17.14%), 16 (68.57%); Huge Expert 11, 12 and 13 (3.33% each), 14 (15%), 15 (18.75%), 16 (56.25%). So Easy and Standard games always get the same count for a size, and only Expert can go below the base count. The computer slots 1 to count − 1 are then filled by difficulty and shuffled (`:53706`-`53809`; the slot contents are in `ai-opponent-behavior.md` §1a).

**Year gate.** The same routine stores 2 × size as the raw year-gate value (victory field 9, `:53615`; raw `0x53dd`-`0x53e9`), which the (raw + 3) × 10 scaling turns into **30, 50, 70, 90 and 110 years** for Tiny to Huge (no clamp applies: the field's maximum raw value is 47). In the Advanced wizard the routine runs again when page 1 is left for the first time (player count, computer slots and year gate are recomputed from the page-1 galaxy size, using the difficulty chosen in this dialog), and the year gate alone is re-seeded each time page 1 or 2 is left until the victory page has been reached; after that the player's own year-gate value is kept (`:53019`-`53051`). Games opened through the other creation paths (game-definition file, tutorial) do not call it.

### 3. Galaxy generation

Once settings are finalized, a single galaxy-generation routine runs. *(Random races: while it sets up the players, `FUN_1078_1334` (`:50835`-`50841`) passes every race record with trait bit 30 set, which is the Race Designer's Random placeholder, through the random-race generator. The complete algorithm is in `race-designer-ui-and-availability.md`, "The Random button and the random-race generator".)* Its steps:

- **Galaxy diameter** is 400 light-years times (size setting + 1), where the size setting is 0-4 — producing the diameters 400/800/1200/1600/2000 light-years for the five galaxy-size options. Confirmed by inspection of the exported client's real dialog resource, the five size options' exact labels are **Tiny / Small / Medium / Large / Huge**, and the density setting's exact labels are **Sparse / Normal / Dense / Packed** — both drawn from the "New Game" wizard's general page, which also carries a separate starting-position-distance radio group (**Close / Moderate / Farther / Distant**, not otherwise documented above) and standalone checkboxes for "Beginner: Maximum Minerals," "Slower Tech Advances," "Accelerated BBS Play," "No Random Events," "Computer Players Form Alliances," "Public Player Scores," and "Galaxy Clumping" (the anti-clumping relaxation-pass toggle referenced below). **Independently re-confirmed by direct observation of the running client (2026-09-10):** every label and control on this page (the first of the three advanced-wizard steps, distinct from the Simplified path's own dialog) matched this static-resource extraction exactly, including a procedurally-generated default game name observed as two capitalized words (consistent with a "descriptive-word + descriptive-word" generator, though the underlying word list was not examined). Screenshot preserved at `docs/ui-reference/advanced-wizard-general-page.png`.
- **Star count** (target n). Start with n = D² ÷ 5000 for diameter D, then add (n ÷ 4) × (density − 1), where density is the **0-based** index (Sparse 0, Normal 1, Dense 2, Packed 3) and n ÷ 4 is truncated; for Packed, add a further quarter of the new value (truncated). Cap at **999**. *(Corrected from the raw code, segment 16 `0x1342`-`0x13a9`, `:50295`-`50306`: the adjustment applies to every density, so Sparse subtracts a quarter and Normal is the unadjusted base; the earlier "for any density above the sparsest" and "rounded" were wrong.)* Results, Sparse / Normal / Dense / Packed: Tiny 24 / 32 / 40 / 60; Small 96 / 128 / 160 / 240; Medium 216 / 288 / 360 / 540; Large 384 / 512 / 640 / 960; Huge 600 / 800 / 999 / 999. These are upper bounds: the separation rule below can leave fewer stars.
- **Star placement** (`:50307`-`50363`, raw `0x13ac`-`0x1535`). Candidates: n + n ÷ 7, capped at 999. Each candidate's x and y are drawn independently as 1,010 + a random 0 to D − 20, so stars lie between 1,010 and D + 990 on both axes (the map runs from 1,000 to 1,000 + D). The candidates are sorted by x. **Minimum separation is a fixed 12 light-years, not derived from the diameter**: it is a constant in the data segment (initial value 12, never written by any code). Sweeping in x order, every later candidate whose x is within 12 of a surviving earlier candidate, whose |dy| is at most 12 and whose squared distance is **at most 144** is removed (so surviving stars are always more than 12 ly apart, squared distance 145 or more, before clumping). If fewer candidates were removed than the surplus (candidates − n), random surviving candidates are removed one at a time until exactly n remain; if more were removed, the galaxy simply has fewer than n stars. Huge Dense and Packed have no surplus (n is already 999).
- **Galaxy Clumping** (option bit `0x100`; `:50364`-`50441`, raw `0x1538`-`0x1706`). One pass of exactly as many steps as there are stars. Each step picks a **random** star (with replacement, so some stars move several times and some never), finds its nearest other star by squared distance using the current positions (ties go to the lower index), and moves only the picked star, by truncating integer division, according to that squared distance d²: **d² ≤ 144: no move; 145-324: (4 × own + neighbour) ÷ 5; 325-625: (2 × own + neighbour) ÷ 3; 626-1,600: (own + neighbour) ÷ 2; 1,601 or more: (own + 2 × neighbour) ÷ 3, with no outer limit.** The bounds are exact (12², 18², 25² and 40² ly²). The stars are then re-sorted by x. *(Corrected: the earlier text inverted the weights, gave the bounds as approximate, ended the pull at about 40 ly and walked the stars in order.)* Clumping can bring stars closer than 12 ly.
- **Star naming** draws from the fixed pool of 999 names (identifiers 0-998, `extracted-game-data/default-names.txt`; mechanism in `dynamic-string-table.md` §7.5): a random start index, then a step forward to the first unused index. In the tutorial galaxy the wrap point is 1,000 instead of 999; index 999 would decode, through the decoder's modulo-999 wrap, as name 0, which the small tutorial galaxy never reaches in practice. With at most 999 stars every star gets a different name. *Reimplementation note (recommendation, not original behavior): a larger roster changes which names appear; use the 999-entry roster to match the original.*
- **Home-world placement and Starting Distance** (`:50620`-`50926`, raw `0x1b70`-`0x2054`). Starting Distance (Close 0, Moderate 1, Farther 2, Distant 3) is read only here and in one computer-player rule (`ai-opponent-behavior.md` §12, personality 0's colony ships). With D the diameter and P the player count, all divisions truncating and all distances squared (ly²): A = D² ÷ P − 6D, set to 0 if negative, otherwise A = 9A ÷ 10; S = (Starting Distance × A) ÷ 3 + 6D; lower bound L = 9S ÷ 10; upper bound U = 7S ÷ 6. The first home world is the first of up to 50 random stars that lies in the central box (both coordinates from 1,000 + D ÷ 4 to 1,000 + 3D ÷ 4), or else the tried star closest to that box. Each further home world must lie in a wider box (from 1,000 + 3D/20 to 1,000 + 17D/20 for 1-2 players, from 1,000 + D/10 to 1,000 + 9D/10 for 3-4, from 1,000 + D/20 to 1,000 + 19D/20 for 5 or more), must be at squared distance at least L (and not 0) from **every** earlier home world, and at most U from **at least one** of them. Up to 50 random stars are tried, then every star in turn starting after the last random pick. If none qualifies, L is lowered and U raised by S ÷ 35 and the whole placement restarts from the first home world. Finally the chosen stars are shuffled among the player slots. Typical bands in light-years (Close / Moderate / Farther / Distant): Tiny with 2 players 46-53 / 152-173 / 210-239 / 255-290; Small with 4 players 66-75 / 215-245 / 297-338 / 361-411; Large with 12 players 93-106 / 252-287 / 344-392 / 417-474; Huge with 16 players 104-118 / 274-312 / 373-425 / 451-514.
- **Home-world mineral concentrations** ~~are randomized to a value between 100 and 299 (inclusive) for each of the three minerals~~. *(Corrected, gap-report pass: "100-299" is wrong; no such roll exists, and the value is stored in an unsigned byte.)* Home worlds take their figures from the **first planet record** (planet index 0), which acts as a template. That planet's concentrations are rolled like any other planet's (below), and it alone is given starting surface minerals: for each mineral, a random 0 to 10 × concentration − 1, plus 10, topped up by 155 + random 0-149 if the result is under 200, then +25% under Accelerated BBS Play (`:50589`-`50619`). Each home world then copies the template's three surface stocks and sets each concentration to the template's value **floored at 30** (25 instead while the built-in tutorial is running, which in practice means only in the tutorial galaxy; see the resolved note below) (`FUN_1078_1334`, `:50967`-`50987`; raw segment 16 offsets `0x2322`-`0x23a1`). So every home world starts with the same minerals: concentrations 30-119 each (25-119 in the tutorial galaxy; exactly 100 under Beginner: Maximum Minerals). If no player's home is planet 0, its surface stock is cleared afterwards (`:51674`-`51681`). The only later change is the race's leftover-point bonus (`:51049`-`51093`, segment 16 offsets `0x259e`-`0x2640`), which applies when the race chose mineral concentrations, and also, on top of the surface-mineral choice, for computer players of skill tier 2 and above. With p leftover points (at most 50; computer players always count as 50), let e be p ÷ 2 rounded down (1 when p is 1 or 2). The lowest of the three concentrations (ties: the first in Ironium, Boranium, Germanium order) gains e, then all three gain (e + 1) ÷ 2 rounded down (all five leftover-point options are tabulated in the note below). The maximum home-world concentration is therefore 119 + 25 + 13 = **157**, well inside a byte. Values over 100 behave as on any planet (`population-growth.md` §5): mining yield uses the raw value, and the depletion step treats it as 100. On a home world the planet's own mines (and any mining of a planet owned by an Alternate Reality race) also yield as if the concentration were at least 30, even after the stored value has been mined below 30 (`FUN_1028_3a74`, `:13544`-`13546`).

  **The 25 floor belongs to the tutorial (resolved, code pass 2026-10-01).** The flag that lowers the floor is the client's "tutorial running" state: bit `0x08` of data-segment byte `0x078b`, which other specs write as bit `0x800` of the word at `0x078a` (`tutorial-system.md` §5). It is not a game option, race setting, AI skill level or game-definition field, and it is never saved to any file. Its initial value in the data segment is 0. A raw sweep of every code segment for operands at `0x0788`-`0x078b` found exactly two writers. The tutorial start routine sets it (`FUN_10f8_0522`, `:104274`, raw segment 32 `0x0588`). The tutorial exit routine clears it, and clears the game file's tutorial-game option bit `0x08` with it (`FUN_10f8_0914`, `:104503`, segment 32 `0x091f`). The tutorial starts from the tutorial menu command or from the new-game dialog's tutorial button (`:53593`). It restarts when the tutorial game file is reopened as player 0 (`:7003`-`7010`, `:10831`). When no game is open, the start routine builds the tutorial galaxy itself (`:104382`-`104383`, through the tutorial game builder `FUN_1078_4938`, which ends by calling the ordinary creation routine). That makes the tutorial galaxy the only galaxy ever created with the flag set. The ordinary New Game command first asks the player to leave a running tutorial (no question is asked from turn counter 30 on), and leaving clears the flag (`:7246`, `FUN_10f8_0b22`). In game terms, **home worlds in the built-in tutorial galaxy are floored at 25, and home worlds in every other game at 30.** The floor only matters when the template planet's low-concentration roll (next paragraph) has left one of its minerals under 30. The tutorial galaxy is generated from a fixed random seed (`:52894`), so its outcome is the same every time. That outcome was not computed. Maximum Minerals, Galaxy Clumping, Accelerated BBS Play and the AI skill tiers play no part.

  *Everything else the tutorial-running flag changes.* The raw sweep found 61 test sites in 21 code segments. Most of them only report a player action to the Tutor window or gate menu commands (`tutorial-system.md`). The sites that change game rules are these:
  - A factory costs 2 kT of each of the three minerals (1 kT each with the cheaper-Germanium checkbox), instead of 4 kT (3 kT) of Germanium alone (`FUN_10d0_208e`, `:87786`-`87802`). This is the "mask 8" form noted in `production-queue.md`.
  - Every turn generation reseeds the random number generator with the same fixed seed before it starts (`FUN_10b0_0000`, `:71707`-`71708`). Tutorial turns therefore replay identically.
  - The step-7 orders check exempts slot 0 (`:71829`, `turn-generation-engine.md` §1).
  - Computer players change in three ways. A computer player's factory purchase is also capped by its Ironium and Boranium (`FUN_10a8_1e8a`, `:70831`, `ai-opponent-behavior.md`). It handles its planets in table order, not shuffled (`FUN_1090_60de`, `:65968`). Its starbase advisor runs only before turn counter 31 (`FUN_1090_510a`, `:65090`). That last limit also applies to a category-1 computer player in any game that carries the tutorial's fixed game id.
  - When next-turn files are written, a patrolling fleet normally marks the fleet it has chosen as its target (eligibility follows its battle plan, not a fixed "enemies only" rule), and later patrols prefer unmarked targets. In the tutorial the mark is not set (`FUN_1070_374a`, `:47295`). The mark is the same bit (fleet byte 5 bit `0x80`) as the follow mark of turn-generation steps 9-11; it is cleared on every fleet at the start of each player's file pass in step 39, and only the follow logic and the patrol scan read it (resolved, code-only; the full Patrol rule and every writer and reader of the mark are in `fleet-movement-scanning-cargo.md` §5).

  **Leftover advantage points at game start (authoritative; resolved, code pass 2026-10-01).** The race setting at index 7 of the race record's 16-setting array (record byte `0x45`) is the **leftover-points choice** on the race wizard's first page. That page fills its drop-down list with dynamic strings 262-266 in order and selects the stored value. On OK it stores the selected position back (`:92170`-`92181`, `:92456`-`92459`; raw segment 29 `0x08cb` and `0x0903`). Value 0 is Surface minerals, 1 Mineral concentrations, 2 Mines, 3 Factories and 4 Defenses. Exactly one option applies: points are never split between options. ### 5. Player-slot record layout and per-category setup dispatch

**Confirmed by inspection of the exported client, upgrading this area from Partial to a confirmed mechanism:** each player slot is stored as a fixed **192-byte record** in a flat per-game array (one record per slot, up to the configured player-count maximum). A dedicated dispatcher routine drives slot initialization: given a slot index, it reads a 3-bit **category** field packed into the top bits of a 16-bit value at byte offset 2 of that slot's record, and switches on it to one of six distinct initializer routines (category values 0, 1, 2, 3, 4, and 5 are each handled by a separate routine; category 7 is handled by a seventh, simpler routine; category 6 is not handled — the dispatcher silently does nothing for it, consistent with an "empty slot" state). Two of the initializer routines (categories 4 and 5) additionally build a per-slot window title from a shared string template plus the slot's 1-based index, suggesting those two categories are the ones that can present the slot to the player as an interactive assignment rather than a fully automatic one.

This 3-bit "category" field is a **separate concept** from the "player type" code (values 0-9) described in §3 above that selects starting-fleet ship templates. That question is settled (see Open Questions): the "player type" is the race's PRT index, read through a separate per-slot accessor, while this category field is the AI personality selector that `ai-opponent-behavior.md` §1 dispatches on (values 0-5 and 7 each have a driver; 6 is inert). The bit widths differ accordingly (3 bits gives 0-7, PRT spans 0-9).

Each of the six category-specific initializer routines follows a common shape: optionally load a preset AI race/personality template from a fixed resource table, assign the slot a unique display name (see below), then construct that slot's starting fleet by repeatedly invoking a shared "add starting ship template" helper with template-id and quantity arguments, where the quantities are scaled to galaxy size using linear formulas of the same shape seen throughout this cluster: a baseline count (typically 3-6) plus `(currentGalaxyScale - lowThreshold) / stepDivisor`, clamped to a per-formula maximum (typical caps observed: 12, 50). The concrete coefficients differ per category and per count (at least two independent scaled counts — an apparent "scout/detector" count and a separate "defensive escort" count — were observed within a single category's initializer), so no single formula covers all categories; each category has its own pair (or more) of baseline/threshold/divisor/cap constants applied to the same shared galaxy-size scalar.

None of the six category-specific initializer routines, nor the dispatcher itself, create or manipulate any dialog, window, or control (confirmed by an exhaustive scan for window/dialog-management calls across their full source range) — this corrects the earlier characterization of this area as containing "wizard dialog-control creation." The actual wizard dialog procedures that call into this dispatcher live elsewhere (most likely the "New/open-game dialog wrapper" already noted in the coverage report), not in this cluster.

**Correction to this section's own "add starting ship template" claim, found by reading two of the six category routines in full this pass.** The two sampled bodies (the category-0 and category-2 initializers) do **not** read as one-time "build this slot's opening fleet" logic on close inspection — they are shaped exactly like an ongoing, once-per-invocation *production-planning* pass: scaled thresholds gated by the current galaxy-size scalar (matching this section's own baseline/threshold/divisor/cap formulas, confirmed exactly — the caps this section already cited, 12 and 50, are these same routines' own computed values), followed by per-owned-planet loops that check mineral stockpiles, existing defense counts, tech-level thresholds, and RNG rolls before conditionally queuing production items via a shared helper. This is the shape of a per-turn AI economic-behavior routine (plausibly the concrete implementation of the six *personality/difficulty* categories this section already distinguishes from the "player type" concept), not a per-PRT starting-fleet builder — the "category" field these six routines dispatch on is, as this section's own next paragraph already notes, a different concept from PRT entirely. **The real per-PRT "add starting ship template" mechanism was located elsewhere this pass — see the new §5a below** — so this section's original claim that *these* six routines are what builds a slot's starting fleet is superseded; the next paragraph confirms this for the remaining four bodies.

### 5a. The real per-PRT starting-fleet mechanism (found this pass, 2026-09-23)

The actual "add starting ship template" helper — the one that gives each PRT a distinctive opening fleet — lives in the same galaxy-generation continuation routine already documented in §3 and in `race-traits.md` §2a for the Packet Physics/Interstellar Traveler second-home-planet bonus (segment 16, `FUN_1078_1334`). ### 6. Unique-name assignment and home-star selection helpers

**Confirmed by inspection of the exported client:** a shared helper assigns each newly-initialized player slot a unique display name by repeatedly picking a random name from a fixed candidate range and checking it against the names already assigned to other slots (checked against either a small subset or the full roster depending on a per-slot flag). ### 7. New-game start commit — correction: this is the client's single master turn-generation routine, not a new-game-only function

**Previously described here (and in the coverage report) as a small "new-game start commit" step; re-examined this pass and substantially corrected.** The routine itself does begin exactly as previously documented: it switches to a busy (hourglass) cursor, then validates the entered game name/file-name against existing files; on failure it restores the cursor, shows an error status message, and aborts without side effects. On success it shows a "creating game" status message, then scans the player-slot array (192-byte records, as in §5) for any slot whose top status bits are non-zero. If **every** slot's status bits are still zero (i.e., no slot was ever configured — an edge case, not the normal path), it falls back to clearing/reinitializing those status bits uniformly across every slot in the array rather than leaving them undefined. It then sets up the game's core runtime buffers (an approximately 12,000-byte and an approximately 25,000-byte buffer, plus a per-star buffer sized at 2 bytes per star), guarded by what is structurally an error-recovery/unwind checkpoint (a saved-and-restored global context pointer plus a per-call stack buffer, consistent with a setjmp-style checkpoint rather than a simple "already initialized" flag) — so this setup step is best read as "run once per top-level attempt, with a clean abort path back to cursor-restore-and-return on internal failure," not as a one-time-only guard.

**This is not, however, a routine exclusive to game creation.** Tracing this routine's callers found it invoked from four separate sites elsewhere in the client, all of them turn-generation commands rather than new-game commands: the manual single "Generate Turn" command, and the batch **10/100/1000-turns-in-a-row** commands already documented in `turn-generation-engine.md` §8 (the batch loop's abort-on-held-key polling and remaining-turn counter are directly visible around these call sites). Past the buffer-setup step described above, the same routine's body goes on to drive the home-star/unique-name assignment already documented in §6, then calls this segment's five sibling routines (see `turn-generation-engine.md`'s new note on segment 23) to run per-planet ownership refresh, per-fleet fuel/docking and waypoint-task/Stargate-transit processing, and a large per-fleet task-dispatch pass, interleaved with calls into segment 24's own galaxy/production machinery — and finishes by writing every active player's next-turn file and freeing the turn's scratch buffers. In other words: **this single function is the concrete master "Generate Turn" routine** described in `turn-generation-engine.md` §1 (whose old 23-phase list has been replaced by the reconciled 40-step order), not a small setup-only helper — it is reused as-is to produce a new game's first turn and every subsequent turn alike. This corrects and significantly expands the coverage-report's one-line description ("verifies game name resource, initializes default player/race flags across player slots"); that description was not wrong about what happens during new-game creation specifically, but it covered only the first few hundred lines of a much larger routine.

### 8. Save-game filename dialog (correction to a prior mischaracterization)

**Correction, verified against the exported client:** the function previously described (in the coverage report) as "pipe-delimited race-string parsing for a race-selection list" is not that. It is a standard Windows **Save-As common file dialog** invocation (`GetSaveFileName`) for saving the in-progress game/host file.
