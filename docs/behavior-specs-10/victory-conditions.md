# Victory Conditions

Behavior specification for game-ending victory conditions in the 1995-2000 4X game *Stars!*. This document is derived directly from the exported client's decompiled logic — both the new-game setup screen that configures these conditions and the turn-generation routine that evaluates them once per turn. No prior document in this set covers victory conditions; this is new material. Facts are described in generic terms; no original identifiers or literal code are used.

## Overview

A game can be configured, at setup time, with a set of **10 configurable victory items**: 7 independently-toggleable boolean conditions (each pairing an enabled flag with a numeric threshold), one paired numeric value that rides alongside one of the 7 conditions without its own toggle, one derived "how many of the enabled conditions must be simultaneously true" meta-setting, and one "minimum game year before victory can be declared" meta-setting. Every turn, the turn-generation engine evaluates these against each race's current standing and declares victory once the configured bar is cleared.

## Mechanics

### 1. Configuration (new-game setup)

The setup screen backing this system exposes exactly **7 checkboxes**, each toggling one victory condition on or off, plus an adjustable numeric magnitude for each (steppable via a spinner control, one step at a time or five steps at once via Page Up/Down). Internally, each condition is stored as a single byte: the top bit is the enabled flag, the low 7 bits are a raw magnitude value clamped against a per-condition maximum.

The raw magnitude for each condition is transformed into its real-world threshold by a condition-specific scaling formula. Reconstructed from the code's control flow (not from any visible label text, so treat the *meaning* column as informed inference rather than a confirmed fact):

| Condition # | Scaling formula | Approximate range | Likely meaning |
|---|---|---|---|
| 1 | (raw + 4) × 5 | ~20 – 100 | Percentage of planets owned |
| 2 | raw + 8 | ~8 – 26 | Tech level required in a number of fields |
| 3 | raw + 2 | ~2 – 6 | Number of fields required at that tech level (paired with condition 2; not independently toggleable) |
| 4 | (raw + 1) × 1000 | 1000 – 20000 | Score exceeds this value |
| 5 | (raw + 2) × 10 | ~20 – 100 | Exceeds the second-place race's score by this percentage |
| 6 | (raw + 1) × 10 | ~10 – 100 | Production capacity of this many thousand (resources/turn) |
| 7 | (raw + 1) × 10 | ~10 – 100 | Owns this many capital ships |
| 8 | (raw + 3) × 10 | ~30 – 100+ | Has the highest score after this many years have passed |
| — (derived) | min(raw, count of currently-enabled conditions among 1-7 excluding condition 3) | 1 – 7 | Number of the enabled conditions that must be true simultaneously for anyone to win |
| — (year gate) | (raw + 3) × 10, seeded proportional to galaxy size | — | Minimum game year before a victory can be declared at all |

Condition 3 deliberately has no checkbox of its own — it is a secondary numeric value that only matters when condition 2 (tech level required) is enabled, representing "in how many fields" that tech level must be reached.

A "Simple New Game" setup path auto-seeds the year-gate meta-setting proportional to the chosen galaxy size (larger galaxies get a longer minimum-year floor before victory can trigger), rather than leaving it at a fixed default.

**Confirmed by direct observation of the running client (2026-09-10):** the setup screen's real default configuration was read directly off the actual dialog (all default raw values, decoded via the formulas above): condition 1 enabled at 60%; conditions 2/3 enabled at tech level 22 in 4 fields; condition 4 disabled, default threshold 11000; condition 5 enabled at 100% (exceeds second place); condition 6 disabled, default 100 (thousand production capacity); condition 7 disabled, default 100 (capital ships); condition 8 disabled, default 100 (years); the derived "must meet N of the above" meta-setting defaults to 1; the year-gate meta-setting defaults to 50. This independently confirms every condition's real-world meaning inferred above, including conditions 5-8 which previously had no confirmed label — all four match this document's own "likely meaning" guesses exactly. Screenshot preserved at `docs/ui-reference/advanced-wizard-victory-conditions.png`.

### 2. Runtime evaluation

Once per turn, the turn-generation engine evaluates every enabled condition against every race's current standing, using the same per-condition storage the setup screen writes to (confirming the setup screen and the runtime check share one underlying data structure, not two independently-maintained copies). For each race, it counts how many enabled conditions that race currently satisfies; a race meeting at least the required count (the derived meta-setting above) becomes eligible to win, provided the game year has also reached the year-gate meta-setting. When a sole eligible leader emerges (or a tie is detected), all races are notified.

**Confirmed by direct code tracing: located, and pinpointed within the phase order.** The evaluation lives in its own dedicated function (a single call site inside the master turn-generation routine), called once per turn shortly after the turn/year counter increment (step 33 of the reconciled order in `turn-generation-engine.md` §1, with only the output-path preparation of step 34 between them) and before the per-design pass of step 36 that the old list called a speculative "phase 22" — i.e., it is step 35 of the master routine, after all simulation and before the per-player turn files are written (step 39), so a victory declared this turn is already in that turn's files. Its internal structure was traced and matches every element of this document exactly: it reads all 10 configurable items via a shared per-game settings accessor (using item index numbers 0, 6, 3, 1, 2, 5, 7, 4, 9, 8 for the 10 items respectively, confirming there are exactly 10 as this document states); computes each race's owned-planet percentage, a 6-field tech-level bit-count, a score comparison, a production-capacity comparison, a "beats 2nd place by N%" comparison, and a "sole leader after N years" comparison, gates the whole evaluation on the year-gate meta-setting, and finally compares each race's satisfied-condition count against the derived "must meet N of the above" meta-setting; when a race clears the bar it sets a global victory flag and sends per-race notification messages through the client's message-record system. This closes both remaining Open Questions below about the function's existence/location and its exact phase position (to the precision the turn-generation phase list currently supports).

**The per-player score computation itself, and its relationship to the Score screen, traced this pass.** The function identified above (`FUN_10b8_3bbc`, `stars.exe.export.c:79008`-`79344`) does not compute condition 4/5/8's score values inline; it calls a dedicated scoring routine, `FUN_1038_384c` (`stars.exe.export.c:20027`-`20104`+), once per race (`stars.exe.export.c:79078`) — and `FUN_1038_384c` has exactly one call site in the entire executable, this one. That routine computes a race's score from: each owned planet's population in units of 100,000 colonists, rounded up and capped at 6 per planet, summed (units corrected below); 3 points per owned planet whose starbase hull has non-zero dock capacity (Orbital Forts do not count); the race's summed resource output (via `FUN_1048_4faa`) divided by 30; a nonlinear bonus from the same six-field per-race tech-level array documented in `turn-generation-engine.md`'s §5 paragraph on the 6-entry event table (higher tech levels contribute progressively more per level); and three ship-class terms. The exact formula and record layout are given in "Score record layout and formula" below. `FUN_10b8_3bbc` writes the resulting per-race scores into a shared, dynamically-allocated buffer (`_DAT_1128_1526`, allocated once with 24 bytes per race for the game's race count, via the allocator `FUN_1060_0248`) that it uses for its own condition 4/5/8 comparisons and rank computation. **This same buffer is independently read and written by a separate, unrelated routine elsewhere in the client** (`stars.exe.export.c:44707`-`44785`) that parses incoming historical per-turn records and indexes per-race entries by the master turn counter (`DAT_1128_0082` — see `tutorial-system.md`'s now-confirmed identification of that same global) — matching the shape of the "per-turn score-history snapshot, retained only for the most recent 100 turns" mechanism already documented in `save-turn-file-format.md` §3, and consistent with the Score screen's own documented "per-turn history" display. This is strong, direct evidence that the Score screen and victory condition 4 read the same underlying per-player score record via the same shared buffer and the same `FUN_1038_384c` formula — though the trace did not extend all the way into the Score dialog's own paint/`WM_PAINT` routine to confirm it reads from `_DAT_1128_1526` rather than recomputing independently, so this falls short of full certainty.

**Full certainty reached by a later pass — the Score dialog's own paint routine was traced.** Two of the Score display's paint functions, `FUN_1108_0fce` and `FUN_1108_15b4` (`stars.exe.export.c:108926`-`109002` and `109203`-`109340`; see `client-ui-dialog-catalog.md`'s "Score display" entry for the full detail), read player status bits and per-category numeric values directly out of `_DAT_1128_1526` at the same 24-byte (`0x18`) per-race stride this buffer's allocation already established. This closes the "falls short of full certainty" hedge directly: the Score screen does not recompute or maintain any separate score figure — it paints straight from the identical buffer `FUN_1038_384c`/`FUN_10b8_3bbc` write for victory conditions 4/5/8.

**Score record layout and formula (resolved; full detail and evidence in `client-ui-dialog-catalog.md`, "Score display").** Each race has a 24-byte record in the shared buffer. Bytes 0-3 are the header: the race number and status flags (bit 0 = eliminated) in the first word and the rank in the word at +2. The scoring routine's 20-byte block fills bytes 4-23:

| Bytes | Size | Contents |
|---|---|---|
| +4 | long | Score (the combined total below) |
| +8 | long | Resources: the summed resource output of every owned planet |
| +12 | word | Planets owned |
| +14 | word | Starbases: owned planets whose starbase hull has non-zero dock capacity |
| +16 | word, packed | Unarmed ships: ships whose design power rating is 0. For all three ship words, fleets carrying the "removed from play" mark (fleet byte 5 bit `0x4`: destroyed, scrapped, merged or spent colonizing this turn) are left out (`stars.exe.export.c:20171`), and starbases never count |
| +18 | word, packed | Escort ships: design power rating 1 to 1,999 |
| +20 | word, packed | Capital ships: design power rating 2,000 or more |
| +22 | word | Tech levels: the plain sum of the six tech levels |

The design power rating is the weapon-power figure of `ship-design-and-components.md` §9. The three ship counts are packed so large counts fit in 16 bits (see the catalog entry). With P planets and C capital ships, the Score is the sum of: each owned planet's population ÷ 100,000 colonists, rounded up, at most 6 per planet *(corrected, gap-report pass: the routine computes (stored population + 999) ÷ 1,000 with the stored value in units of 100 colonists, `stars.exe.export.c:20084`, so "in thousands" was wrong; 1-100,000 colonists score 1 and more than 500,000 score 6)*; Resources ÷ 30, rounded down; 3 × starbases; the tech curve (for each field at level L: L for 0-3, 2L − 3 for 4-6, 3(L − 3) for 7-9, 4L − 18 for 10 and up; skipped once the race is eliminated); half of the smaller of unarmed ships and P, rounded down; twice the smaller of escort ships and P; and, only when C > 0, 8PC ÷ (P + C), rounded down. The victory conditions read this block: condition 1 the Planets word, condition 6 Resources ÷ 1,000, condition 7 the (unpacked) Capital ships word, and conditions 4, 5 and 8 the Score long. Rank is 1 plus the number of races with a strictly higher score, so tied races share a rank.

**Elimination flag raised by the same pass (added by the step-6 pass).** While it computes each race's figures, `FUN_10b8_3bbc` also detects elimination: when four words of the 20-byte figure block that the scoring routine fills in for the race (`:79078`-`79089`) are all zero, namely Planets, Unarmed ships, Escort ships and Capital ships (no planets and no ships of any class; the Planets word is also the one condition 1 compares against its threshold, `:79111`-`79113`), and the race's status bit 0 is not yet set (`:79098`-`79101`), it sets that bit and sends message 187 (announcing that the named race has been wiped out of the galaxy) to every other race (`:79099`-`79109`); a later branch handles the "you alone are left" message 188. The bit persists in the host file and is read elsewhere as "this race is out of the game": the research buy loop leaves it out of the count of live races used for the Super Stealth passive research share (`:80062`-`80063`), and the output step gives every player that race's score record and data block (`turn-generation-engine.md` §1 step 39; `:47534`, `:47660`). Step 6 of the next turn still tries to load an eliminated race's order file (it has no skip test).
