# Client UI Dialog Catalog

This catalog extends the client-interface specification with every distinct interactive surface identified in the exported client. Names below are functional descriptions, not copied identifiers. An entry states only behavior supported by the client surface; it does not infer rules that belong to turn processing.

## Global dialog contract

Every modal surface has these common attributes:

- It is initialized from an explicit subject, selection, or session draft.
- It supports accept, cancel, and contextual help when help is available for that surface.
- Accept returns a meaningful result to its caller. Cancel returns a distinct no-change result.
- Editable surfaces use a local working state and commit only their own scoped fields.
- Read-only and authority-limited contexts disable mutation controls while retaining useful inspection controls.
- Keyboard and pointer activation of an accept, cancel, list, or button control follow the same state transition.

## Workspace surfaces

### Main workspace frame

The top-level frame creates and owns the map workspace, command menu, toolbar, status content, and subordinate information windows. It routes keyboard accelerators to the active child surface when that child is entitled to receive them. It supports normal, minimized, and restored display states.

The frame handles controlled shutdown. When unsaved state or an active session requires a decision, it opens a confirmation flow rather than terminating immediately. It may save or prepare pending session data before completing the close action.

### Title and status area

The title/status area presents the current context and supports lightweight updates without rebuilding the map. It refreshes when the active owner, open game, or current view changes.

**Race-name/summary string builder, confirmed by inspection of the exported client.** A shared routine builds a display form of a race's name from its stored singular and plural name fields, parameterized by: singular versus plural form; whether to prefix an article ("a"/"an," chosen by the name's leading sound); whether to apply a possessive/adjective suffix; and, when no explicit plural name was set, an automatic English pluralization fallback (append "s," unless the singular name already ends in "s" or in a sibilant-plus-"e" pattern, in which case a different suffix is used). This is the routine that renders the current race's name into the title/status area, and it is reused throughout the client wherever a race's name needs to appear in a sentence — reports, dialog captions, and the report-text escape-formatting engine described under Custom widgets below.

### Toolbar, tooltip, and contextual popup

The toolbar maintains an ordered group of icon actions. Each icon has an enabled state, a press/hover state, and explanatory tooltip content. Hovering does not change the selected object or persistent state.

The contextual popup is built from the current pointer target and selection. It contains only operations legal for that target. Closing it without activation has no effect.

### Search and record browser

The search surface accepts a query, evaluates it against the relevant object collection, and returns a selected result or no result. The browser surface presents a navigable collection with one current item and can update the workspace focus to that item.

**Find Planet or Fleet (View > Find, Ctrl+F, commands 4200/4201; template 4202; dialog procedure at raw `1058:677c`, `:41708`-`41766`, and matcher `FUN_1058_68c4`, `:41769`-`41870`), traced by the planet-view pass; code and the parsed template only, not exercised in play.**

- *Availability.* The command does nothing until a player is selected (`client-interface.md`, command table).
- *Controls.* A 162 by 55 dialog-unit box with a label, one single-line edit field (control 268, auto-scrolling, limited to 39 characters), OK (default), Cancel and Help. The field starts empty every time; the dialog reopens where it was last closed (centred the first time, kept on screen; position kept in DS `0x58e` for the session, `FUN_1040_2672`). Help opens help context 1085.
- *Comparison.* All comparisons ignore the case of the letters A-Z only (`FUN_1120_0538` for whole strings, `FUN_1120_057a` for a prefix); there is no trimming of the query and no substring search.
- *Order of the tests* on OK:
  1. Every planet of the universe, in planet-number order, is compared with the query as a whole name. The first exact match wins at once. While no exact match has been seen, the first planet whose name begins with the query is remembered.
  2. Fleet number. The query is read as a fleet number: an optional leading word for "fleet" (dynamic string 1256, compared over its own length, after which six characters are skipped), spaces, an optional number sign, spaces, then a decimal number starting with a digit 1-9. If the number ends before reaching 513 and the viewer owns a fleet with that number, that fleet wins. Only the viewer's own fleets can be found by number.
  3. Every fleet the viewer knows (own and foreign, in the client's fleet-list order) is compared as a whole with its displayed name (owner prefix, design or given name, number; `client-interface.md`, "Object identification text"). The first exact match wins. Fleets are never matched by prefix.
  4. The remembered prefix-matching planet, if any.
  5. Otherwise a stop-icon message box with dynamic string 526 (nothing found by that name); after it the dialog stays open with the whole text selected.
  An empty query therefore finds planet 1 (every name starts with the empty string). A planet always beats a fleet with the same exact name, a fleet number beats a fleet name, and an exact fleet name beats a planet prefix.
- *Result.* The found planet or fleet becomes the selected object exactly as a map click would make it (`FUN_1058_63a4`), the map is scrolled to centre it (`FUN_1058_5106`), the map is updated, and the dialog closes. Cancel closes without any change.

**Net finding, answering this document's open question directly:** the renderer displays exactly one kind of object (a component/hull category+subtype descriptor, the same 16-value bit-flag system `ship-design-and-components.md` §4 documents), not a mixture of planets, fleets, designs, and races. The full 16-category dispatch was not exhaustively mapped in this pass (several categories' exact numeric values are obscured by decompiler pointer-type artifacts rather than clean literals), but the dispatch shape itself — chrome, then a per-category bespoke body, then a shared trailing caption — is now confirmed rather than sampled, and this segment's previously-flagged "not exhaustively traced" gap is closed.

**Fully reconciled this pass: the Ironium caption belongs to category `0x0200`, not `0x0800` — and category `0x0800` turns out to have no bespoke body in this renderer at all.** The reused category local's value was tracked precisely across the whole ~250-line stretch rather than sampled:

So a fleet name is at most 31 characters and at most 160 pixels wide, whichever is shorter.
- *Fleet name, accept rules.* The prompt opens filled with the fleet's current display name. Cancel changes nothing. On OK the new text is compared with the current display name; when identical nothing happens. ### Randomization seed

The seed surface accepts a session-generation seed and validates its input before returning it to the setup draft. It distinguishes user-provided values from the request to generate a fresh random value.

**Confirmed by inspection of the exported client.** The dialog reads a typed decimal string one digit at a time (validated character-by-character against a shared digit-class lookup table) and accumulates it into a 32-bit value via repeated multiply-by-ten-and-add. An empty field is treated as "generate a fresh random value" (the dialog accepts without reseeding); a nonzero typed value is passed to the shared RNG engine's seed routine. This confirms, at the mechanism level, the underlying random-number generator: a combined multiplicative-congruential generator carrying two independent 32-bit state words, each advanced by its own large-modulus multiplier every draw and combined by subtraction (with modulus wraparound) to produce the returned value, reduced by the caller's requested upper bound. The seed dialog's own path derives its two lookup-table indices directly from the low 6 bits of the typed value (guaranteeing the two indices differ by construction). A small push/pop stack lets a caller temporarily substitute a different seed and later restore the exact prior state, so that borrowing the RNG for a one-off computation elsewhere in the client does not disturb ordinary gameplay random sequences.

**A second, independent seeding entry point, refined by a later pass.** A separate seed routine (deriving its two lookup-table indices from a bit-scrambled combination rather than a plain 6-bit split) reseeds this *same* shared generator from the system tick count — used, in the ordinary case, at application startup and at at least one other session-reset point, which is plain gameplay randomization rather than something "unrelated" to it as previously characterized here. That same routine is separately reused — with the RNG state saved and restored around the call via the push/pop stack above — by the Serial Number surface's accept-time check (see the Serial Number entry below), which seeds the shared generator from a value derived from the typed input rather than from the clock, draws several values from it, and compares the result against a second derived value. Consistent with this project's house rule on copy-protection mechanisms, no more of that check's internal derivation is documented here.

**A wholly separate, second instance of the same generator algorithm exists, confirmed by inspection of the exported client, carrying its own independent state pair rather than sharing the one described above.** It has its own matching push/pop save-restore pair (used to checkpoint and roll back the stream around a bounded retry loop — see the galaxy star-placement rejection-sampling loop in `new-game-setup.md`, which draws from this second stream) and its own explicit reseed-and-advance entry point: given a handful of small identity fields, it reseeds the stream via the same table-lookup scheme and then draws and discards a record-specific number of values from it before use, so that a given record's position in the stream is reproducible from its own identifying fields rather than depending on how much of the stream earlier records consumed. A companion routine XORs a byte buffer against successive draws from this stream. Together these back a lightweight, non-cryptographic **record-level scrambling scheme**: reading a certain flagged class of on-disk record involves reseeding this second stream from the record's own small header fields and XOR-unscrambling its payload bytes against the resulting keystream — distinct from, and layered independently on top of, the turn-file delta-record protocol documented in `save-turn-file-format.md`.

The access-secret entry surface requests an existing secret. The replacement surface collects a new value and confirmation. Mismatched replacement entries fail validation and remain uncommitted. Both surfaces conceal typed characters and do not display stored secret content.

### Reports

The report viewer presents a selected report and supports navigation among report entries. Its content is informational; accepting or closing the viewer does not modify the report data.

Confirmed by inspection of the exported client: one shared report-grid window class serves **four** distinct report types, switched via a mutually-exclusive main-menu selection; the grid's visible columns are individually configurable, and clicking a column header versus clicking a data row dispatch to different handlers, consistent with (though not fully confirmed as) column-sort and row-navigate behaviors respectively. The Fleets report additionally derives a per-row status indicator from each fleet's order/waypoint state: a distinguished "idle/no useful orders" state is highlighted, and a companion numeric column reads as a turns-to-arrival or fuel-sufficiency estimate, defaulting to a large sentinel value (effectively "never") when no valid estimate applies, with the figure shown in a warning color when a fuel or threshold check fails.

**Further confirmed by inspection of the exported client:** the report-grid's own layout logic decides whether a vertical scrollbar is needed by summing the pixel widths of every column whose visibility bit is currently set (against a per-column, per-report bit array) and comparing against the client width — the "individually configurable" columns above are toggled through this same bitfield, one bit per column per report type. ### Score display

The score surface displays comparative standings derived from the current session information. It is read-only and may provide selectable display categories without changing game state.

Confirmed by inspection of the exported client: the surface offers **three** cyclable display modes (an icon/medal grid, a per-category leader table, and a per-category history graph) over **nine** comparison categories *(corrected by the score-window pass: the "icon/medal grid" is the victory-conditions view; the three views, the Switch button and every label are given in "Score window views and the Switch button" below)*. Every value shown is read directly from a pre-computed per-player-per-turn record — no code in this surface computes a combined single "score" number from the nine categories, so a compatible implementation should not assume this dialog is where an aggregate score gets calculated, only where per-category standings get displayed. See `victory-conditions.md` for the separate victory-condition system, which is confirmed (below) to read the same underlying score record.

**Candidate source for (part of) that precomputed record, tentatively identified.** *(Settled two paragraphs below: this routine is the scoring function `FUN_1038_384c` itself, and it does feed the record.)* A large per-race scoring routine found in segment 8 (see `fleet-movement-scanning-cargo.md`'s "A large scoring computation" note) combines an owned-planet count and capped population total, a count of starbases with dock capacity (first misread as a Stargate count; see the table below), a stepped-curve tech-level score, and a ship-value-tier tally into a single summed figure — the right general shape for one input to this display's underlying record, though it was not traced forward to confirm it is actually the code that writes that record, nor which of the nine categories (if any single one) it corresponds to.

**Resolved this pass: the Score display's own paint routines read directly from the same buffer `victory-conditions.md` §2 traces victory conditions 4/5/8 to, settling the question that document's Open Questions left short of full certainty.** Two of the Score display's own paint functions — `FUN_1108_0fce` (`stars.exe.export.c:108926`-`109002`, the icon/medal-grid mode's player-name column) and `FUN_1108_15b4` (`stars.exe.export.c:109203`-`109340`, the per-category leader-table mode) — both read player status and per-category numeric values directly out of `_DAT_1128_1526`, the identical persistent per-race score buffer `FUN_1038_384c`/`FUN_10b8_3bbc` write for victory conditions 4/5/8 (`victory-conditions.md` §2). `FUN_1108_0fce` reads a per-player status bit at byte 1 of that race's record in the buffer (`stars.exe.export.c:108981`, stride `0x18` = 24 bytes per race — matching the buffer's own documented 24-byte/word-per-race allocation) to decide whether to gray out that player's name *(corrected, score-window pass: that bit, `0x40` of byte 1, is the winner mark and turns the name blue; the grey comes from the player's slot flags)*; `FUN_1108_15b4` does the identical status-bit read (`stars.exe.export.c:109259`) and then, in its leader-table cell loop, reads the nine comparison categories' actual numeric values straight out of the same buffer at fixed per-category byte offsets from each per-race record base (e.g. offsets `+0xc` and `+0xe` for the first two categories, `stars.exe.export.c:109316`-`109332`). This is a direct read of the buffer's contents, not merely a shared allocation site — it conclusively confirms the Score display and the victory-condition system read one shared score value rather than the display recomputing its own figure, closing the "does not contradict, but stops short of full certainty" hedge in `victory-conditions.md` §2/§4 and `open-items-report.md` item 14. (The segment-8 scoring routine cited above as a candidate source is resolved in the next paragraph: it is `FUN_1038_384c` itself.)

**Resolved this pass: the "segment-8 candidate" is not a separate contributor at all — it is `FUN_1038_384c` itself, and its "segment 8" attribution in `fleet-movement-scanning-cargo.md` was a mislocation, not a distinct routine.** Reading `FUN_1038_384c` (`stars.exe.export.c:20027`-`20239`) directly confirms every element `fleet-movement-scanning-cargo.md`'s "large scoring computation" note describes, line for line: a per-planet loop counting owned planets and summing each planet's population in units of 100,000 colonists (stored hundreds ÷ 1,000), rounded up and capped at 6 per planet, plus its resource output (`stars.exe.export.c:20080`-`20103`); a starbase count, gated on the starbase flag and a nonzero hull-record field resolved through the segment-8 accessor `FUN_1008_5118` (`stars.exe.export.c:20089`-`20096`; corrected below: the field is the hull's dock capacity, not a Stargate, so Orbital Forts are excluded); a 6-field tech-level array run through the identical stepped curve — for a level L: L itself below 4, 2L − 3 for 4-6, 3(L − 3) for 7-9, 4L − 18 for 10 and up (`stars.exe.export.c:20107`-`20127`); and a 16-slot loop over the race's hull designs bucketing each into one of three value tiers via a resolved per-design cached value (`stars.exe.export.c:20128`-`20157`), further reduced into three weighted output figures via `FUN_1038_3038` (`stars.exe.export.c:20220`-`20227`). This is not a resemblance — it is the same computation, previously sampled from a different angle (its heavy use of segment-8 helper accessors like `FUN_1008_5118` is almost certainly why an earlier pass filed it under "segment 8"); `FUN_1038_384c` itself resides in a different code segment (Ghidra address prefix `0x1038`), and `victory-conditions.md` §2 already independently established it has **exactly one call site in the entire executable** — from `FUN_10b8_3bbc`, the very function already confirmed above as one of `_DAT_1128_1526`'s two writers.

**Closed from raw bytes: there is no hidden FPU diagnostic. The only floating-point status code is the standard C runtime's.** Every code segment of `stars.exe` was swept byte by byte for x87 control-word and status-word stores and loads, environment saves, and coprocessor resets. The result was cross-checked by decoding the instruction at each of the executable's 810 OS-fixup relocation records, which mark the x87 instructions the loader may patch. Only the probe described below uses unmarked ones, and only after it has confirmed a coprocessor is present. All genuine hits outside the runtime segment (`1120`, NE segment 37) are the ordinary "compare, store status to AX, branch" idiom in the game's numeric code: 18 sites in segments `1030`, `1038`, `1058`, `10a8`, `10b0`, `10b8`, `10f0` and `1108`, each followed directly by a conditional jump. None saves the status anywhere. Inside segment `1120` the hits fall into five standard runtime pieces:
- the float-to-integer truncation helper (offset `0x0e52`);
- the maths-library routines that check the status after each operation (`0x13b5`-`0x174a`);
- the floating-point exception classifier (`FUN_1120_1c8e`, offsets `0x1cf5`-`0x1e09`), which feeds the runtime's floating-point error message boxes;
- precision-control save and restore (`0x20c3`-`0x2132`, `0x3014`-`0x303a`, `0x35a8`-`0x35f8`) and the printf-style float-to-text converter (`0x2949`-`0x29c2`);
- one routine Ghidra never decompiled, at `1120:2690` (it sits in the gap between `FUN_1120_2662` and `FUN_1120_2716`).

That last routine is the runtime's coprocessor-type probe. It asks the Windows maths-emulator interface whether a coprocessor is present. If one is, it saves the control word, resets the unit, compares positive and negative infinity, and inspects the saved environment, so it can tell an 8087-, 287- or 387-class unit apart. It records the answer as 1, 2 or 3 in one runtime variable, then restores the control word. It has no direct caller. It is reached only through a four-entry table of far pointers in DGROUP (offsets `0x1c32`-`0x1c3e`) that the runtime's startup code walks once (segment `1120` offsets `0x017f`-`0x0197`, walker at `0x026a`). Only the runtime's own maths routines read the result (`0x1472`-`0x1494`). The routine does not format text, open or append to any file, or test any `.ini` or player-file flag. The executable also has no debug or log format strings (no hex-dump formats, no coprocessor wording) apart from the runtime's own floating-point error texts. The code's x87 instructions carry OS-fixup relocations, so Windows can turn them into emulator calls on machines without a coprocessor; this is also standard runtime behaviour.

The "hidden diagnostic" described in the first of these paragraphs therefore does not exist as a game feature. That description most plausibly merged this startup probe (which does gather FPU status) with the separate audit-log append of the integrity sweep (`FUN_1038_5174`, which does write a log file). A compatible client needs neither: floating-point setup is a compiler/runtime matter, and the audit log is documented with the anti-cheat sweep.

### Word-wrap text layout engine

**Confirmed by inspection of the exported client.** A shared line-layout routine takes a run of text (either a length-delimited span or a NUL-terminated string), a left margin, a right edge, and a fixed line pitch, and lays it out one line at a time against the current font. Its wrapping strategy is a **greedy, whole-word breaker with no hyphenation**: for each line it first measures the *entire* remaining text against the available width; if that fits, the whole remainder becomes the line (and any fitting trailing spaces past the natural break are folded in, so a line can absorb trailing whitespace up to the next real content). If it does not fit, the routine repeatedly backs off from the tentative line end — first trimming trailing spaces, then skipping back over the entire overflowing word, then trimming any further spaces before that word — and re-measures, until the remaining span fits or nothing is left to remove. A break is never made in the middle of a word. Once a line's span is fixed, the routine can optionally paint it (a "measure only" mode exists, used to compute total wrapped height/width without drawing) before advancing the vertical cursor by one fixed line pitch, resetting the horizontal cursor to the left margin, and skipping any leading spaces at the start of the next line. This engine is called very widely — from message/report display, tooltip-style popups, and at least one report-grid cell renderer — making it the client's single shared multi-line text layout primitive, distinct from (and used by) the escape-coded report-text formatter described below, which expands the raw text before this engine lays it out.

**Companion text-drawing primitives, sampled from the same cluster.** The word-wrap engine's own line-break search is itself built from three small helpers — skip past any leading spaces at a line start, back up over trailing spaces before a candidate break, and back up further over an entire overflowing word — each a short, single-purpose span-adjustment routine. Alongside the wrap engine sit several simpler, single-line text-drawing primitives reused across dialogs: draw a string horizontally centered under a given anchor point; draw a string left-aligned while advancing a running vertical cursor by its measured height (used to stack several lines of text without a full wrap pass); draw a string centered in both axes within a rectangle, with an optional background fill first; and draw a string against a fixed-width field, either padding the unused space or clipping the string against the field's edge when it overflows (a candidate for fixed-width status-strip/label fields elsewhere in the client). A separate, unrelated helper truncates a string in place, one character at a time from the end, until it fits a given pixel width — a simple "shorten this label to fit" utility distinct from the shrink-to-fit *font-resizing* approach described below.

### Font-resource loader and autofit label sizing

**Confirmed by inspection of the exported client, extending the "embedded font-resource loader" finding.** Beyond the startup GDI-resource pass (see `client-interface.md`'s "Application shell" section, which builds a small fixed table of fonts once at launch), a separate on-demand routine creates a single additional font at a caller-specified point size in the same shared UI typeface: it builds a font-description record sized from the display's reported vertical DPI, copies in a shared face-name string, calls the standard font-creation API, and — if the caller wants it — selects the new font into the display context just long enough to read back its line metrics (ascent plus internal leading) before restoring the previous font, reporting that measured line pitch to the caller. This on-demand path is called with explicit point-size arguments (observed values 8 and 5) from outside the segment, i.e. it backs at least one further window's fonts beyond the startup table, rather than only being used during the startup pass.

A second, related routine implements **shrink-to-fit label sizing**: given a text string and a target rectangle, it builds a temporary font at an initial guessed size, measures the text, and — if it doesn't fit — iteratively rescales the guessed point size proportionally to how far off the fit is (via a scaled-ratio adjustment rather than a simple one-point step), rebuilding and re-measuring the temporary font each pass, until the text fits within both the rectangle's width and height (with an 8-pixel margin) or the loop bottoms out. Once a fitting size is found, it draws the text centered in the rectangle with that font and immediately deletes the temporary font handle — a "biggest font that still fits" label primitive, plausibly the mechanism behind the segmented bar/gauge's centered "value / value" label described below, though the exact call site backing that specific label was not traced.

### Escape-coded report-text formatting

**Confirmed by inspection of the exported client, extending the "custom escape-sequence string-format engine" hypothesis with concrete mechanism detail:** report/message text is not produced by the ordinary C-style format routine alone. A dedicated pre-pass scans a format string for a literal escape character followed by one of roughly a dozen one-letter codes and substitutes each with the correct kind of expanded text before final formatting: a ship/starbase component's display name; a race's display name (through the race-name/summary string builder described under "Title and status area" above); a plain string-table lookup; a race relationship-name lookup; a value formatted with automatic English singular/plural word-choice (checking whether the base word already ends "s" or "es" before appending a plural "s," rather than always appending one); a value formatted with an appended unit-name suffix chosen by magnitude; a conditional switch between two format strings depending on a threshold comparison; and a large-integer formatter that inserts thousands-separator punctuation (comma plus space) every three digits, with a special case for values that are an exact power of two. This is the mechanism underneath ordinary-looking report sentences such as "3 Large Freighters" versus "1 Large Freighter," or "1,234,500 resources," rather than those being pre-baked per-count string-table entries.

**Fuller escape-code enumeration, extending the above from direct inspection of the formatting engine's dispatch switch.** The engine recognizes a literal backslash followed by a single letter (case-sensitive; upper- and lower-case variants of the same letter sometimes share identical behavior, sometimes differ). Substantially more than "roughly a dozen" distinct *letters* are actually recognized — several simply alias to one of a smaller number of underlying *behaviors* — enumerated here to the extent this pass could resolve them:

- **E** — looks up a value by a single byte read from the field stream (a small fixed-table lookup; category not identified).
- **F** — looks up a value via a dedicated helper keyed by the raw field value (category not identified).
- **G** — a plain string-table lookup at one fixed table-index base.
- **I**, **j** — plain string-table lookups at two further, different fixed table-index bases (same underlying string-fetch helper as **G**, different base offsets).
- **L** / **l** — builds a race-name/summary string (via the same string-builder confirmed elsewhere for race-name and title-bar text) from a packed field value; the two cases parse that field's bits identically except for one derived flag, consistent with a singular/plural or short/long variant pair.
- **M**, **e**, **m** — three separate word-indexed lookup tables (three different fixed bases), each returning a short string keyed by a numeric field value — consistent with three distinct "unit name" or "category name" tables (e.g., mineral names vs. some other per-category label set), not yet individually identified.
- **O** — builds a race-name/summary string like **L**/**l** above, but derives the race index from a different (ship/component-slot-shaped) field layout rather than taking it directly.
- **P** — **confirmed:** the "conditional switch between two format strings depending on a threshold comparison" already documented above — compares a field value (divided by 100) against a fixed threshold constant and formats using one of two entirely different format strings depending on the result.
- **S** — a "self vs. other" substitution: compares a field value against the *currently active/viewing* race; if it matches, substitutes a different phrase (built and byte-reversed through a distinct pair of string-table entries) than when it doesn't, consistent with a "you" vs. "the `\`race`\`` grammatical substitution.
- **U** / **V** / **v** — **confirmed, extending the existing "unit-name suffix chosen by magnitude" note:** formats a 32-bit field value as a plain number, then (for **U**/**V** only, not **v**) appends a unit-name string looked up from a word-indexed table by a "current unit" index — **V** sets that index explicitly from a second field value; **U** reuses whatever unit index was last set (persisted across substitutions in the same message, defaulting to none); **v** always omits the unit suffix entirely.
- **X** — recognized by the dispatcher but performs no distinct substitution of its own (falls through to plain literal-character handling).
- **Z** — **confirmed, extending the existing "large-integer formatter" note into a second, separate mechanism:** given a bitmask field, if it is an exact power of two the single corresponding race's name is substituted (via the same builder as **L**/**O**); otherwise every set bit is expanded into a full, comma-and-"and"-joined list of race names (e.g., "Race A, Race B, and Race C") — i.e., a *race-bitmask-to-name-list* formatter, distinct from the single-value thousands-separator formatter already documented.
- **f** / **h** / **r** / **t** / **y** — a family of "current name" substitutions sharing one common name-buffer source (the same global text buffer used for the currently-edited object's name elsewhere in the client); they differ in what, if anything, is appended afterward — **y** and **h** each append a different fixed suffix (consistent with distinct grammatical/possessive endings), while **f**, **r**, and **t** instead fall through to plain-number formatting branches under certain conditions. The exact grammatical distinction between all five was not fully resolved.
- **g** — looks up a component/design display name (the same underlying helper used for ship/starbase component names elsewhere).
- **i** — aliases to the same plain-number-formatting branch as **r** above.
- **k** — **confirmed:** the "ship/starbase component's display name" already documented — resolves a component/design record and substitutes its stored name field directly.
- **n** — **confirmed:** the "automatic English singular/plural word-choice" formatter already documented — dispatches (through a shared category/count-formatting helper also used to look up plain planet, race, and component names by category code) to a paired singular/plural string-table entry pair chosen by whether the count is exactly one; two reserved field values redirect to the **g** and **o** substitutions instead of formatting a number at all.
- **o** / **p** — both substitute a planet's display name; **o** additionally checks one bit of the target's owner data and, when set, redirects to the **s** substitution (a race name) instead — consistent with "show the planet's name, unless a special ownership condition applies, in which case name the owning/related race instead."
- **s** — substitutes a race's display name, with a forced high-bit flag passed to the lookup (a distinct variant from plain race-name lookups elsewhere — possibly the "race relationship-name lookup" already noted above).
- **u** — plain numeric formatting with no unit suffix and (unlike the large-integer formatter) no thousands-separator punctuation.
- **w** — substitutes the current contents of a different global text buffer (the same one used elsewhere for the active window/dialog's title text).
- **z** — builds a per-design-slot component/race name similar to **O**, from a field value split into a race index and a design-slot index (0-31, split across two parallel design tables), with the same "is this the currently active race" special-casing seen under **S**.

**Underlying number-formatting primitives, sampled this pass.** The thousands-separator behavior described above (and under **Z**/the large-integer formatter) is implemented by a dedicated routine that re-copies an already-formatted digit string, inserting a comma after every third digit from the end — a distinct, separately-callable primitive rather than something built into the general-purpose sprintf-style formatter itself. A second, unrelated numeric primitive (`FUN_1040_1e0e`) rounds a raw value and appends a compact "k" or "M" magnitude suffix (choosing the divisor and suffix by comparing the raw value against fixed 10,000 and 1,000,000 thresholds) — a "compact large quantity" formatter distinct from the plain thousands-separator behavior above; its call sites are resolved in the next two paragraphs (the Score window's leader table and the Reports grid's numeric cells).

  **Call sites resolved this pass.** Both of this formatter's only two direct call sites sit in the Score display's own code segment (`FUN_1108_*`): one calls it directly while rendering a per-player numeric cell in the score surface's per-category leader-table mode, specifically inside `FUN_1108_15b4` (`stars.exe.export.c:109381`, the same leader-table paint function `_DAT_1128_1526` was just confirmed to feed above — the code path also chooses the cell's text color by comparing each player's value against the category's current leader, i.e. this is the "highlight the leader" rendering pass for the leader-table display mode over the surface's nine comparison categories); the other is inside a small shared helper, `FUN_1108_35a0` (`stars.exe.export.c:110791`-`110831`, itself calling the k/M formatter at `stars.exe.export.c:110827`), that sets a caller-supplied text color and then formats a caller-supplied value through this same k/M formatter — a generic "colored, magnitude-abbreviated number label" primitive.

  **Correction, resolved this pass: `FUN_1108_35a0`'s own four further call sites do *not* back the Score display at all — they were mis-attributed to it above.** All four (`stars.exe.export.c:110236`, `110354`, `110704`, `110720`) sit inside a single function, `FUN_1108_2508` (`stars.exe.export.c:109931`-`110790`), and that function is not part of the Score display — it is the Reports grid's own per-`(reportType, rowIndex, columnIndex)` cell-value dispatch function already documented under "Reports" above. This is confirmed by its one and only caller (`stars.exe.export.c:108530`-`108656`): a grid painter that iterates a column-visibility bitmask and a scrollable row range read from the report grid's shared state record, calling `FUN_1108_2508` once per visible cell with the cell rectangle, the report type, the row index and the column index — exactly the "report-grid's own layout logic... summing the pixel widths of every column whose visibility bit is currently set (against a per-column, per-report bit array)" mechanism the Reports section above already describes, with the state record's report-type field supplying the selector `FUN_1108_2508`'s own top-level switch (0-3, matching the four report types) dispatches on. `FUN_1108_2508` and `FUN_1108_5494` (see the Mode 1 corroboration above) both live in this same segment and both key off the same selection record, reinforcing that segment 0x1108 hosts the Reports grid, the Score display, *and* the object-information-panel logic as three sibling surfaces sharing one code segment, not one surface. **Net effect on `open-items-report.md` item 16:** the question "which of the Score display's modes" rests on a false premise for three of the four call sites — `FUN_1108_35a0` is used once, directly, by the Score display's leader-table mode (`FUN_1108_15b4`, above), and separately, four more times, by the unrelated Reports grid's numeric-column cell renderer; it is not reused across the Score display's own three modes. Which specific report type/column each of the four `FUN_1108_2508` call sites formats was not individually traced this pass — that would be a new, narrower question about the Reports grid rather than the Score display.

**Total distinct letters recognized: 26** across the cases above (counting upper/lower-case pairs separately), collapsing to a substantially smaller number of underlying *behaviors* (roughly a dozen, matching the earlier estimate, once aliased letters are merged) — the previous "roughly a dozen" note undercounted the *letter* surface but was a reasonable estimate of the underlying *mechanism* count. Several helper-name/category mappings above (E, F, several of the M/e/m tables, the exact f/h/r/t/y suffix distinctions) could not be pinned to a specific real-world meaning — no string/label data survives to check them against.

**Several of these resolved this pass by reading the raw file bytes at each table's base offset (same method already validated elsewhere in this document for the `0x1f6`/`0x2000` category literals), now that the recovered dynamic/message string tables confirmed the underlying convention.** All offsets below are relative to the shared `DAT_1128_*` data segment (Ghidra segment 38, `0x1128`, file offset `0xb0bc0`), read directly from `stars.exe`:

- **`m` (`stars.exe.export.c:15568`-`15571`, table base `0x48c`) is a resource/cargo-kind name table.** The field value directly indexes a word table whose first 6 entries resolve to the literal strings **"Ironium," "Boranium," "Germanium," "Colonists," "Fuel," "Resources"** — exactly the game's 4 cargo-hold kinds plus fuel and production resources, with garbage past index 5 confirming the table has exactly 6 live entries. This settles the earlier "mineral names vs. some other per-category label set" hedge in favor of mineral/cargo names specifically (also fully explaining why an "Ironium"-labeled string appears in this project's data segment independent of the category-`0x0800`/`0x0200` question resolved above — it is one shared literal reused by both mechanisms).
- **`e` (`stars.exe.export.c:15389`-`15391`, table base `0x43e`) is the environment-axis name table.** Its first 3 word-table entries resolve to **"Gravity," "Temperature," "Radiation"** — the exact three axes the hover-popup modes 8/12 and the planet inspector's axis breakdown already document, confirming `e`'s field value selects which of the three environment axes' name to substitute into report text (e.g. a line like "Gravity: too low").
- **`M` (`stars.exe.export.c:15175`-`15177`, table base `0x4b2`) is the minefield-type name table.** Its first 3 word-table entries resolve to **"Standard," "Heavy," "Speed Bump"** — the client's three named minefield types, matching the "3 distinct fill patterns, one per minefield type" already documented under "Minefield and scanner views" above (entries past index 2 are garbage, confirming exactly 3 live entries). `M` substitutes a minefield's type name into report text.
- **`h` / `y` (`stars.exe.export.c:15392`-`15521`) append literal save-file extensions, not a grammatical/possessive suffix as previously guessed.** Both share the same base text-copy step (the current-name global buffer, `DAT_1128_56c2`) already identified, then conditionally append a further literal string: `h`'s target string (`DAT_1128_0b1e`) reads **".hst"** (the game's turn/history-file extension) and `y`'s target string (`DAT_1128_0b28`) reads **".xy"** (the game's XY/position-file extension) — both confirmed genuine Stars! save-file extensions used elsewhere in this project's own file-format documentation. This means the shared "current name" buffer this letter family draws from is best understood as the **current game/save file's base name** (consistent with the "Stars! Host Mode" dialog's confirmed "current game name and file" readout under "Additional confirmed surfaces" below) rather than a generic "currently-edited object" name buffer as previously characterized — `h` and `y` build a full save-file name (base name plus extension) rather than applying an English grammatical ending. `f` and `r` (and `t`, when a separate "current race" check comes up unset) fall through to a plain-number-formatting branch with no suffix at all, as already documented; `t` otherwise reuses the same `.hst`-suffix path as `h`, gated on whether the global "currently active race" selector (`DAT_1128_014c`) equals its unset sentinel (`0xffff`) — i.e. `t` is a context-conditional alias between `h`'s file-name behavior and `r`'s plain-number behavior, not an independent fifth suffix.
- **`E` (`stars.exe.export.c:15152`-`15155`) is not a name/category lookup at all — it is a small numeric-formatting-style selector.** `FUN_1048_4010`, the helper `E` calls, is the environment-value display formatter (`:26997`-`27022`; formats read from raw segment 10 `4010`-`40b3` and the data segment): its first argument is the axis and the second the stored 0-100 value. Axis 1 (temperature) prints the value minus 50, times 4, followed by the degree sign and C; axis 2 (radiation) prints the value with the mR unit; any other axis (gravity) prints a g figure with two decimals: with d the distance of the value from 50, the figure is (d + 25) × 4 hundredths for d up to 25 and 24d − 400 hundredths above, inverted (10,000 divided by it) for values below 50, so 50 reads 1.00g and the ends read 0.12g and 8.00g. `E` therefore substitutes one environment value in the form the planet panel and the planet export (Grav, Temp and Rad columns) show, not a name from a table.
- **`F` (`stars.exe.export.c:15156`-`15158`) resolves a specific ship/starbase design's stored name, distinct from the `g`/`k` component-name substitutions elsewhere.** `FUN_1038_1c44` extracts a 4-bit (0-15) design-slot index packed into the field value's bits, indexes the current race's design array with the same 147-byte (`0x93`) stride documented in `ship-design-and-components.md`, and copies that design's own name field (offset `+8`) into the output — skipping deleted designs — then conditionally appends a literal `+` character when one flag bit of the field value is set (`stars.exe.export.c:18456`-`18457`), consistent with a "modified/upgraded design" marker convention. This resolves `F`'s "category not identified" hedge: it is a **design-name-by-slot** substitution, not a small fixed table.
