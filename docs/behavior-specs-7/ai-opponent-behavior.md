# Computer (AI) Opponent Behavior

Behavior specification for the built-in computer-controlled empires in the 1995-2000 4X game *Stars!*. Unlike the other specifications in this set, this document is derived directly from the exported client's own decompiled turn-processing logic rather than from public community research — no public source documents how the built-in AI actually decides what to do, so this is the first specification of its kind for this subsystem. Facts here describe the algorithm's observable shape (decision order, thresholds, formulas) in generic terms; they do not use any of the original identifiers, variable names, or literal code from the binary.

## Overview

Every non-eliminated computer-controlled empire is processed once per turn by a single "AI turn" driver, dispatched to one of several **personality drivers** based on a small numeric code stored on that player's record (the built-in AI "type"). Each personality driver runs the same broad decision sequence — refresh threat assessment, decide fleet cargo/colonization/mining actions, decide planet-level construction, then hand off to two subsystems shared by every personality (a starbase-management pass and a general per-planet production/resource-allocation pass). What differs between personalities is a set of tuning constants (probabilities, distance thresholds, aggressiveness multipliers) baked into each driver, not the overall shape of the decision tree.

At least **seven** built-in personality slots exist (numbered 0 through 7, with one slot unused/reserved and one essentially inert/passive), though the exact number of these that map to named, selectable difficulty or personality options in the game's setup screens was not established.

## Mechanics

### 1. Personality dispatch

A per-player field's top bits select which personality driver processes that player's turn. Each driver is a large (roughly 300-1100 "step") routine sharing this skeleton:

**The dispatch site itself, located this pass.** The per-player-slot initialization dispatcher documented in `new-game-setup.md` §5 (a 3-bit "category" field packed into the top bits of a 16-bit value at byte offset 2 of each slot's 192-byte record) is the *same* dispatcher this document's §1 has always described — confirming that section's own speculation that its six category-specific routines might really be "the concrete implementation of the six personality/difficulty categories." The dispatcher function itself is `FUN_1088_0000` (segment 18; takes the slot index as its first parameter), and its dispatch switch reads `*(uint *)(&DAT_1128_59c6 + slotIndex*0xc0 + 2) >> 0xd` — the same per-race/per-slot record base (`DAT_1128_59c6`, stride `0xc0` = 192 bytes) already confirmed as the relationship-table base in `diplomacy-relations.md` §1, here read at record offset 2 instead. The switch has cases for values 0-5 and 7 (case 6 has no code at all — the dispatcher silently does nothing for it, confirming this document's "entirely disabled" slot as category 6 specifically); each handled case calls one large per-personality driver function, all of which end by calling the shared production-allocation entry point `FUN_10a8_1e2a` (§6):

Category 7's driver (`FUN_1098_0000`) is confirmed by inspection to be the "near-total no-op" personality described below: its ~34-line body does one threat-refresh helper call and then immediately calls the shared production-allocation pass, with no fleet/planet decision logic of its own. This resolves the "first finding the concrete dispatch site" blocker this document's Open Questions previously flagged — the exact mapping from categories 0-5/7 to a named, player-visible AI-difficulty or personality label in the setup UI is still not established (see Open Questions).

1. Compute turn-scaled tuning constants — several thresholds scale continuously with the game's current turn/year number (not in discrete difficulty "eras"), generally becoming more aggressive/expansive as the game goes on.
2. Refresh an assessment of nearby threats (enemy fleet strength, economy) using shared helper routines.
3. Iterate every fleet the AI owns, deciding per fleet whether to: transport cargo/minerals to a shortfall location, redirect toward a colonization or invasion target, scrap, or hold.
4. Iterate every planet the AI owns, deciding whether to queue a starbase, adjust defensive posture, or trigger an "opportunistic build" scan (queuing a currently-affordable ship design or component upgrade with some random retry chance).
5. Call the shared starbase-management pass (§3) and the shared production-allocation pass, common to every personality.

One personality slot is a near-total no-op (it only runs the two shared passes, no independent fleet/planet decisions) — the most passive built-in AI available. Another slot is entirely disabled (its driver function does nothing at all).

### 2. Colonization and fleet-destination selection

Target selection is built from a small set of generic, reusable search primitives that walk the planet/fleet lists computing squared distance from a reference point and applying a caller-supplied acceptance test:

- **"Nearest match"** — returns the closest object for which the caller's predicate is non-zero.
- **"Best match"** — returns the object maximizing the predicate's numeric return value, ties broken by distance.

Concrete predicates observed include: ownership filters ("not mine"), an "economy strong enough to spare a colonizer" gate (a threshold on summed cargo/mineral fields, tuned per personality), and habitability-based scoring functions.

**Colonization-target scoring.** A candidate planet's score (roughly 0-100) combines a habitability estimate with a distance bonus using a fixed set of concentric range bands (squared-distance thresholds at roughly 50, 100, 150, and 200 light-years) — closer candidates score higher. Once scored, acceptance is **probabilistic**: a random roll out of 100 must fall under the candidate's score, so even a strong candidate is not always chosen immediately and a marginal one is occasionally still picked. A separate "too eager" flag on some candidates adds an additional flat 25% chance of random rejection specifically, to add jitter and avoid every AI fleet rushing the single best-looking planet simultaneously.

**Late-game colonization becomes distance-conservative.** After roughly turn 59, a candidate's distance to the AI's *nearest already-owned colony* is checked against three graduated thresholds and probabilistically rejected the farther out it is: certain rejection beyond ~350 light-years, a 50% rejection chance beyond ~300, and a 50% rejection chance beyond ~250. This does not apply in the early game.

**Random exploratory colonization** uses reservoir sampling over an expanding search radius when no strong candidate is found nearby, so early scouting fleets don't get stuck idle simply because nothing scores well yet.

### 3. Starbase management (shared across all personalities)

After a personality driver finishes its own fleet/planet logic, it always calls one shared "starbase AI" pass that iterates every AI-owned starbase:

- If any of a starbase's three mineral stockpiles falls critically low (below roughly 700 units) while a nearby friendly planet holds a healthy surplus (above roughly 700), a transfer order is queued to move the shortfall mineral there. If no single planet is critically low, any overall surplus is instead split three ways across the three mineral types, weighted by distance to the nearest source.
- Separately, each starbase decides whether to build a Stargate/orbital structure, redirect colonists toward a low-population candidate planet, or fall back to a scrap/consolidation action.
- A combat-readiness check gates whether a fleet uses an aggressive or a cautious attack-order profile: it requires the fleet be farther than roughly 14 units from its target, hold more than roughly 499 cargo/fuel, and — if every one of the fleet's three weapon-slot counts individually exceeds 15 — escalates to the more aggressive profile.

### 4. Threat assessment and defense/minefield decisions

- A base **threat rating** (roughly 4-6) is computed per nearby enemy presence, with random jitter and a possible +1 bump gated on a racial-trait check, cached per-target.
- The AI sweeps its own multi-ship fleets, builds a scratch list of nearby enemy or unclaimed strength indicators, and computes an aggregate threat code feeding the rating above.
- A dedicated defense-need evaluator (the most fully worked-out of the threat functions) is skipped entirely for passive personalities, or once a global aggressiveness flag is off past roughly turn 30. Otherwise it recommends building defensive minelaying/countermeasure capacity only if accumulated threat stays at or below `(raceTraitValue * 20) + 10`, and existing minefield unit count stays at or below `(ownedPlanetCount * 4) / 5`; below a threat level of 5 it instead flips a 50/50 coin on whether to build anyway.

### 5. Automated mineral/cargo transport

A dedicated freighter-routing routine sums a fleet's cargo hold, avoids double-assigning a delivery target another friendly fleet is already servicing that turn, and searches for the nearest reachable planet needing that cargo type, falling back to a random pick if nothing scores above a cutoff (roughly 180 light-years squared). A companion value-per-time-of-arrival scoring function normalizes its result by a constant of 25 — consistent with the game's warp-squared ("distance covered scales with the square of warp speed") movement rule, since 25 = 5², suggesting the routine is implicitly comparing routes as if traveled at warp 5.

**The routing routine itself pinned this pass: `FUN_1090_1438` (segment 20).** This is the fleet-scoped counterpart to the planet-scoped `FUN_1090_420c` already ruled in/out above — it takes a candidate freighter fleet as its first argument (`param_1`), a list of other owned fleets as its second (`param_2`, walked to detect a delivery target another fleet is already servicing that turn — matching this section's "avoids double-assigning" claim structurally, checking each other fleet's own order-target field against the candidate destination), and a list of candidate delivery targets as its third (`param_3`). It opens by summing 16 fields starting at the fleet record's offset `+6` (`stars.exe.export.c:61874`-`61881`) — this is the "sums a fleet's cargo hold" step. Its target-search loop computes squared distance to each candidate and compares it against the literal `0x7e90` (`stars.exe.export.c:61955`), which is exactly 32,400 — **180², an exact match** to this section's own "roughly 180 light-years squared" cutoff, confirming the figure precisely rather than approximately. When no candidate clears that cutoff, a fallback branch (`stars.exe.export.c:61962`-`62076`) picks essentially at random among all owned-planet or all-fleet candidates by nearest-squared-distance with no cutoff, matching "falling back to a random pick." The function commits its choice by calling `FUN_1090_2668`, which itself opens with `FUN_1048_2c12(2, *param_1)` (`stars.exe.export.c:62650`) — the project's confirmed fleet-scoped tag, independently corroborating that `FUN_1090_1438` operates in a fleet-scoped context rather than a planet-scoped one. `FUN_1090_1438` has exactly three real call sites (`stars.exe.export.c:58881`, `68516`, `69812`), each inside a personality-driver body's per-owned-fleet loop, consistent with Overview step 3 ("iterate every fleet... deciding... whether to transport cargo/minerals"). **What was not found:** a textually separate "value-per-time-of-arrival" helper function performing the `/25` (warp-5-squared) normalization described in this section's second sentence — no division by 25 appears anywhere inside `FUN_1090_1438` itself, and the earlier candidate for that normalization (`FUN_1090_420c`) was already ruled out as planet-scoped in a prior pass (see the Open Questions entry below). It remains possible the `/25` normalization the earlier pass observed belongs to a genuinely different, still-unlocated helper, or that the "companion scoring function" framing above should be revised to describe a step folded directly into `FUN_1090_1438` (whose own distance-cutoff comparison this pass did not find any `/25`-shaped term inside) rather than a separate function — this narrower point remains open.

**Resolved this pass: `FUN_1090_19c8` (segment 20) is the missing value-per-time-of-arrival scorer, and it is not a sub-helper of `FUN_1090_1438` at all.** A full read of `FUN_1090_1438`'s own body shows it calls only two of the three previously-flagged untried candidates — `FUN_1050_29b8` (line 62032) and `FUN_1090_452c` (line 62034) — never `FUN_1090_19c8`; the assumption that `FUN_1090_19c8` was "one call frame deeper" inside `FUN_1090_1438` does not hold. `FUN_1090_19c8` is instead called directly, once per candidate delivery target, from inside the fleet-iteration loops of four of the six personality-driver bodies (`stars.exe.export.c:58794` inside `FUN_1088_0462`, `60320` inside `FUN_1088_2350`, `66696` inside `FUN_1098_0184`, `67356` inside `FUN_1098_131a`) — each call site sits inside a loop walking the confirmed global owned-fleet array (`DAT_1128_00ba`/`DAT_1128_5376`) filtered to the current player's own fleets, exactly matching Overview step 3. Inside `FUN_1090_19c8` itself, the candidate-scoring loop contains the missing `/25` term, appearing three separate times (`stars.exe.export.c:62242`-`62248`, `62276`-`62283`, `62345`-`62351`): each computes a 32-bit dividend from a pair of helper-function results plus a flat `+0x18`(24) offset, divides it by the exact literal `25` (`0x19`, high word `0`), and floors the result to a minimum of `1`; a per-candidate value figure (`iVar6`, built as a flat `*100` or `*500` multiple of a stored byte) is then divided by that floored quantity to produce the candidate's score (`uVar5`), and the candidate with the highest score seen so far is kept (`stars.exe.export.c:62257`-`62261`). This is an exact structural match for this section's "value-per-time-of-arrival... normalizes its result by a constant of 25" claim — the `+24`/`/25`/floor-to-1 shape reads as a rounded-up turns-to-arrival estimate consistent with a warp-5 assumption, with the winning candidate committed as the fleet's cargo-delivery order afterward in the same function (`stars.exe.export.c:62360`-on, via the fleet-scoped `FUN_1048_2c12(2, ...)` tag). Confirmed ruled out this pass, by full reads: `FUN_1050_29b8` (only 30 lines, `stars.exe.export.c:32392`-`32421`, a flat per-design-slot resource-cost summer with no division anywhere in its body) and `FUN_1090_452c` (only 18 lines, `stars.exe.export.c:64444`-`64461`, a thin wrapper around a target-lookup and an order-commit call, again no division). This closes the open item: the `/25` normalization has a confirmed home function, `FUN_1090_19c8`, which is a genuinely separate scoring routine from `FUN_1090_1438` rather than one of its callees — the two are companions called from the same per-fleet decision point, not caller/callee.

### 6. Production-queue insertion by the AI

The AI's per-planet production advisor is a fixed decision chain tried in order each turn: a defense-percentage-target advisor, a mass-driver/mineral-packet advisor, two further advisors for other component categories, and a fallback advisor if none of the above queue anything; a young colony additionally triggers an auto-load-cargo check. This chain always concludes by calling a shared resource-allocation routine that auto-fills the currently active production item's cost from available resources, spilling any excess into a secondary item slot.

Concrete observed thresholds:
- **Defense-percentage advisor**: the chance of the AI acting to close a gap toward its target defense percentage decreases the longer the gap has persisted, and drops to a flat 5% chance once the planet is already at or above its target.
- **Mass-driver/mineral-packet advisor**: requires a qualifying starbase component, combined mineral stockpile of at least 3,000, a minimum population score of at least 10, and only fires on a 25% random roll; queued quantity is capped at 25, with a secondary gate at 20,000 minerals.
- Two further, less-decoded advisors for other component categories cap their queued quantity at 4.
- **Resource-output percentage-discount**: net resource output is reduced by `resources * traitByte / 100` for some races, where `traitByte` is a per-player signed value — gated so it only applies when a particular global game-option flag is off. This is a race-trait-driven mechanic distinct from, and in addition to, the population/factory resource formula documented in `production-queue.md`.
- **Auto-load colony cargo**: triggers once projected resource surplus exceeds 49, provided a matching stocked component exists.
- **Production-queue insertion cap**: a build-order is refused outright once its queued-item count exceeds 200 (a hard structural limit, independent of the per-item 1,023-unit quantity cap documented in `production-queue.md`).
- **Isolation check gating further expansion investment**: before committing to expansion-oriented production (e.g. scouts/colonizers) from an owned planet, the AI evaluates that planet's isolation from any remaining unclaimed star — a check that was previously misattributed to new-game home-star selection in `new-game-setup.md` §6, corrected there this pass. It finds the nearest still-unclaimed star and rejects further expansion investment outright beyond roughly 353 light-years, applies a roughly 50% chance of rejection in the 300-353 and 250-300 ly bands, and always proceeds below roughly 250 ly; gated to only run once the galaxy has more than 59 stars. This runs per owned planet, per turn, as part of the same per-player production-planning pass documented above, not once at game start.

### 7. Ship auto-design pipeline

Distinct from the human-facing race-design and ship-design UI (`race-designer-ui-and-availability.md`), the AI maintains its own automated design-refresh pipeline:

- A new design is assembled from a base hull template plus researched-component picks (choosing the best currently-available tech level for each slot), then committed to a free slot in either the empire's 16-slot regular-design table or a separate 10-slot table the AI uses for its own bookkeeping.
- **Refresh scheduling** uses turn-age thresholds: a design is flagged for replacement once it reaches roughly 35 turns old (moderate urgency) or 50 turns old (high urgency), with the AI's very first (starting) hull class getting a longer, roughly 26-turn grace period before it's eligible for replacement at all. Past turn 49, the single most-outdated design category across two five-category groups is chosen for replacement each turn, but only if its age has reached at least 40 turns.
- A design flagged as flatly obsolete (a stored flag bit) is replaced immediately regardless of the age thresholds above.

**Cross-segment confirmation.** A re-verification pass over segment 31 (`FUN_10F0_*`, previously characterized as "mostly battle engine and AI production planning" — see `combat-resolution.md` §8 for the full re-check) independently located the slot-filling half of this pipeline: a function there iterates a design's component slots and calls the shared race/item-availability resolver documented in `client-interface.md`'s "Trait-gated control validation" section (the same validator used by the human-facing Ship/Starbase Designer) to pick the best currently-available component for each slot — confirming "choosing the best currently-available tech level for each slot" above at the code level, and confirming the AI design pipeline reuses the human-facing availability rules rather than its own separate gating logic.

### 8. Fleet turn-processing order is randomized

The list of fleets an AI empire owns is reshuffled (Fisher-Yates style, using the same bounded random-number generator used throughout the game) before each turn's fleet-processing pass, unless a specific global flag suppresses it. This means the *order* in which an AI's fleets receive their per-turn decisions is not stable or predictable from one implementation's fleet-array ordering to another's — any clean-room implementation reproducing bit-for-bit AI behavior needs to reproduce this shuffle, not just the decision logic itself.

**Pinned to a specific function by a later segment-31 sampling pass.** The shuffle is a plain, textbook Fisher-Yates: for each position (from a total count down to 1), it draws a bounded random index over the not-yet-shuffled prefix and swaps that slot into place using a fixed-size temporary buffer, over a single global array of 29-byte records. This independently confirms the mechanism's shape (not just its existence) at the code level, though the specific array's game-visible identity (fleets specifically, versus some other 29-byte-record table this shuffle is also reused for) was not re-derived from structure alone in this pass.

**Correction, from an exhaustive fourth pass over segment 31 (see `combat-resolution.md` §8's segment-31 note): this specific function's array is the per-battle token table, not an AI empire's owned-fleet list.** The function takes no parameters — it always shuffles the same two globals, which a neighboring function in the same segment populates immediately beforehand as the just-built battle-token array (one 29-byte record per token, for the current battle only), and its record count is capped at exactly 256, matching `combat-resolution.md` §2's token cap. Because the function is hard-wired to this one array, it cannot be a general-purpose "shuffle any 29-byte-record list" routine reused elsewhere for AI fleet-processing order — so the claim above, that *this* code path is what randomizes an AI empire's per-turn fleet-processing order, should be treated as unconfirmed rather than pinned. It remains true that *some* mechanism reshuffles AI fleet-processing order each turn (see the surrounding paragraph), and it may still use an identically-shaped Fisher-Yates helper elsewhere in the codebase, but the concrete function traced into segment 31 is now known to serve battle-token tie-break ordering (most likely underpinning `combat-resolution.md` §5's "randomly decides a firing priority... kept fixed for the rest of the battle" rule) rather than fleet-turn-processing order specifically. This paragraph supersedes the shuffle-mechanism attribution in the paragraph above; the general "fleets are reshuffled before per-turn processing" claim itself is not retracted, only its evidentiary link to this particular function.

**A second, genuine Fisher-Yates shuffle was located this pass — but for the AI's owned-*planet* list, not fleets.** `FUN_1090_60de` (segment 20) is one of four setup calls the dispatcher `FUN_1088_0000` (§1) makes for the current player immediately before invoking that player's personality driver. It first rebuilds a scratch array (`DAT_1128_13b4`/`DAT_1128_4968`) of every record the current player owns from a fixed source table (stride 56 bytes, owner field checked against the current player at record offset 2), then — unless a specific flag bit is set (`DAT_1128_078b & 8`) — reshuffles that array with a textbook forward Fisher-Yates using the same bounded RNG helper (`FUN_1040_1652`) documented throughout this project: for each index from 0 up to count-2, it draws a bounded random offset into the remaining unshuffled suffix and swaps that element to the front. This array is exactly the one `FUN_10a8_1e2a` (§6) walks immediately afterward, calling the confirmed per-*planet* resource-allocation pass (`FUN_10a8_1e8a`) once per entry with a "current object type" tag of `1` (via `FUN_1048_2c12(1, ...)`) — the same tag convention used elsewhere to mean "planet," contrasted with tag `2` used for fleet-scoped calls (see §10 below). So this shuffle randomizes **per-turn planet-processing order**, a real and previously-undocumented mechanism, but it does not appear to be the fleet-processing-order shuffle this section describes — no analogous "build a fleet list, then Fisher-Yates it" function was located feeding into the fleet-iteration step (§ Overview, step 3) inside any of the six personality-driver bodies in the time available. Whether fleet-processing order is separately randomized by a not-yet-located function, or whether the "fleets are reshuffled" framing above should instead be revised to "planets are reshuffled," is left open — see Open Questions.

### 9. Colonizer commitment and design tech-upgrade budgeting, confirmed by inspection of the exported client

Distinct from the colonization-target scoring in §2 (which decides *which* candidate planet to pursue), a separate per-turn AI routine decides, for a candidate star already near an AI-owned fleet, whether and how to actually commit that fleet as a colonizer:

- A fleet's carried cargo is checked against a **5,000-unit threshold**: below it, the fleet is treated as too small to found a colony and receives a lesser fallback order instead; at or above it, the fleet is colonizer-capable.
- For colonizer-capable fleets, the assigned ship design's 6 tech-field levels (one byte per field, each capped at the game's known maximum of **26**) are summed and bucketed against the ladder **59 / 71 / 84 / 95 / 108** to decide how ambitious a design upgrade is worth pursuing, further modulated by how much of the 5,000+ cargo threshold is exceeded.
- A companion routine computes, non-destructively, **what it would cost in research resources to raise a specific design's tech-field levels up to a target** (saving and restoring the current levels around the calculation) — i.e. a "what would this upgrade cost" query used to judge affordability before committing, reusing the same per-level research-cost mechanism documented in `research-tech-tree.md`.
- The candidate star must also be within roughly **100 units (squared-distance 10,000)** of whatever resource/production source is funding the decision, and the resource budget available for the upgrade is capped at **5,000**, or **3,500** for one specific design category.
- Every commitment/rejection reason is recorded against a persistent per-decision bitmask (used to avoid re-deciding the same case identically every turn) and mapped to one of several internal log/message codes — the exact codes could not be tied to visible game messages, but the mechanism (a "why did the AI choose this" audit trail) is confirmed.

This is a genuinely separate subsystem from §2's colonization-target scoring — it operates *after* a target and fleet already exist, deciding commitment and design-upgrade budget rather than picking the target planet itself.

### 10. Stale-slot sweeps and pool redistribution (supporting utilities)

Two smaller, confirmed utility mechanisms support the AI's per-field bookkeeping (the same fixed-size per-field slot arrays referenced in §6-7): one sums a slot range's values (capped at 32,000) while flagging any slot whose "last touched" turn is older than a caller-supplied threshold, optionally purging a stale-and-empty slot outright; the other redistributes a 16-slot shared pool into a matching owned fleet whenever a particular per-race stat drops below **501**, repeating until the stat recovers. The concrete real-world meaning of the redistributed pool and the race stat being monitored could not be determined from structure alone.

**The redistribution function pinned this pass: `FUN_1090_5bda` (segment 20).** Given a caller-supplied 16-slot boolean "which slots matter" array, it first reads a per-race stat from the same per-race/per-slot record base used for the personality dispatch and the relationship table (`DAT_1128_59c6`, stride 192 bytes — see §1 and `diplomacy-relations.md` §1), specifically a 12-bit sub-field (`value & 0xfff`) at the record's very first word, and loops (`while (stat < 501)`) rebuilding a fresh candidate list each iteration by walking the same fleet-shaped source table referenced in §5/§9 (filtered to the current player's own fleets, excluding a specific flag bit), searching each candidate's own 16-slot field for the first slot the caller's array also flags. Once a match is found, it marks the operation as fleet-scoped (`FUN_1048_2c12(2, ...)` — the counterpart of the planet-scoped `1` tag used by `FUN_10a8_1e2a` in §6/§8 above), copies a shared 16-entry pool (`DAT_1128_4992`/a companion parallel array) into a scratch buffer, zeroes the source slots the flag array selects, writes the redistributed values into the candidate fleet's own matching slots, and commits the change before re-checking the stat and looping. This confirms the "matching owned fleet" wording in this section's own description at the code level (fleet-scoped, not planet-scoped) and pins the exact gating stat's storage location (a 12-bit field at per-race-record offset 0, compared against decimal 501), but the concrete real-world identity of both the monitored stat and the 16-slot pool's contents remains unresolved — the pool's backing global is heavily overloaded elsewhere in the decompile (the same address is used, in dozens of unrelated UI functions, as a scalar "currently selected object id," a much smaller type than the array access seen here, consistent with this project's previously-noted pattern of "globals... overlapping smaller symbols at the same address"), so no confident guess as to the pool's game meaning (mineral reserve, cargo allotment, waypoint/task slots, or something else) is offered here.

**Process-of-elimination pass on both the pool and the gating stat, this pass.** For the pool's backing global (`DAT_1128_4992`): a search of every other behavior-spec file in this project for that exact symbol found no hits outside this document — the "dozens of unrelated UI functions" reusing the address as a scalar object-id are not independently documented anywhere else in this project's own material, so there is no cross-document corroboration to triangulate against; this is a genuine negative result, not an oversight; the elimination approach the Open Questions item suggested cannot be carried out against other spec files because no other spec file has occasion to name this address. For the *gating stat* (the 12-bit field at per-race record offset 0, `DAT_1128_59c6 + race*0xc0 + 0`), a direct sweep of every other read/write of that same field across the executable (found via the equivalent `(undefined4 *)&DAT_1128_59c6 + race*0x30` pointer-arithmetic form, `stars.exe.export.c:18602`-`18605`, `18694`-`18697`, `30336`-`30369`, `44193`-`44194`, and others) turned up two functions that adjust it by exactly ±1 in lockstep with membership changes to the game's global owned-fleet array (`DAT_1128_00ba`/`DAT_1128_5376`, the same fleet table §5's routing search and §8's planet-shuffle discussion both reference): `FUN_1038_1f72` (`stars.exe.export.c:18648`-`18746`), which allocates a new slot in that array and immediately increments the current record's field by 1 (`18694`-`18697`), and `FUN_1038_1db4` (`stars.exe.export.c:18547`-`18644`), which removes a slot from that array and immediately decrements the same field by 1 (`18602`-`18605`). `FUN_1038_1db4` is independently corroborated elsewhere in this project: `save-turn-file-format.md`'s own note on opcode `0x18` (fleet-merge) names it as the post-merge cleanup step that "frees/clears a design slot if all of a hull's 16 component counts reach zero — consistent with one fleet's design being fully absorbed into the other's," i.e. a confirmed fleet-deletion/absorption routine, from a document that was not looking at the redistribution mechanism at all. Taken together, this is reasonably strong (though not certain) evidence that the gating stat is a **per-race live-fleet count** (or a quantity that tracks fleet-array membership one-for-one) rather than a mineral, cargo, or waypoint figure — every other candidate meaning considered above would need some other event to move it by exactly 1 per fleet created/destroyed, which is a specific and unusual coincidence for an unrelated stat to exhibit. This reading sits in tension with the `while (stat < 501)` gate, though: a race's live fleet count is expected to stay well under 501 for the overwhelming majority of a normal game, which would make `FUN_1090_5bda`'s redistribution loop fire on essentially every call rather than act as a meaningful low-resource trigger — an odd shape for a deliberate gate, and this tension is not resolved here. It is offered as the best-evidenced candidate so far, not a confirmed identification; the pool's own contents remain completely open.

**A fresh, exhaustive re-sweep of every write to this exact field this pass, specifically hunting for a non-fleet-event write site.** Every occurrence of the field's two addressing idioms (`DAT_1128_59c6 + race*0xc0 + 0` and the pointer-arithmetic `(undefined4 *)&DAT_1128_59c6 + race*0x30`) was re-checked across the whole export, filtering out the many unrelated reads/writes of the *other* sub-fields packed into the same 192-byte record (byte offsets +1/+2/+3 are a completely different set of flags, unrelated to the 12-bit field at offset 0). Two genuinely new things came out of this, beyond the already-documented ±1 pair (`FUN_1038_1f72`/`FUN_1038_1db4`):

- **A packed neighbor, not the field itself.** The 32-bit word at record offset 0 is shared: bits 0-11 (masked `& 0xfff`) are this section's gating stat, but bits 12 and up hold a *second*, independent counter, adjusted in fixed steps of `0x1000` by an entirely different mechanism — a design-table slot-free/allocate handler (`stars.exe.export.c:30297`-`30372`, `case 0x1b`/`0x1c`/`0x1d` of what reads as a save/turn-file opcode dispatch) that branches on whether a freed or allocated ship/starbase-design slot index falls in the empire's 16-slot regular design table (index `< 0x10`, adjusts an unrelated byte field instead) or its 10-slot AI-bookkeeping table (index `0x10`-`0x19`, adjusts *this* word's bits ≥12 by `±0x1000`, e.g. `stars.exe.export.c:44269`-`44270`, `83176`-`83177`). Because `±0x1000` never carries into or out of the low 12 bits, this is a real, previously-unnoticed second write path to the *word*, but not to the *field* this section is asking about — it explains why the field is read with an explicit `& 0xfff` mask (to isolate it from this packed neighbor), not a clue to the field's own meaning.
- **A genuine non-fleet-event write to the field itself, found this pass.** Inside what reads as the same save/turn-file record loader (a `while` loop keyed on a record-type byte, `DAT_1128_26b6._1_1_ & 0xfc`, matching the high-nibble opcode convention `save-turn-file-format.md` documents elsewhere), one specific opcode branch (value `0x18`, `stars.exe.export.c:44417`-`44431`) does, for each per-player-slot record it visits: `DAT_1128_5376 = DAT_1128_5376 + (field & 0xfff)`, immediately followed by `field &= 0xf000` (zeroing the low 12 bits outright — not a ±1 step). **`DAT_1128_5376` is this project's own already-confirmed running count of the global owned-fleet array** (the companion of the fleet array `DAT_1128_00ba`, the same pair §5's freighter-routing search and §8's planet-shuffle discussion both reference) — so this line folds a race's current tally in this exact field *directly and by value* into the live global fleet count, then clears the per-race field to zero. A second, near-identical zero-reset (without the `DAT_1128_5376 +=` step) recurs three more times in the same loading routine at different opcode branches (`stars.exe.export.c:44193`-`44194`, `44958`-`44959`, `45210`-`45211`), consistent with per-player-slot (re)initialization at file/turn-load time rather than a fleet-lifecycle event.

**Net effect on the open question.** This *is* a write that is not itself triggered by a single fleet's creation or deletion (it is a bulk file-loading/slot-reset operation), directly answering the task of finding a non-±1 write site — but its own content (`DAT_1128_5376 += field`) reads the field as a fleet-count subtotal being folded into the confirmed global fleet-count variable, which if anything strengthens rather than undermines the "per-race live fleet count" reading from the prior pass, via a completely independent code path from the ±1 pair. The `while (stat < 501)` tension noted previously is not resolved by this — a normal race's fleet count would still be expected to sit far below 501 almost always — but there is now direct, confirmed structural evidence (not just ±1-lockstep correlation) connecting this field's value to the game's actual fleet-count bookkeeping, for whatever the resolution of that remaining tension turns out to be.
