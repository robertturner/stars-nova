# Client Interface Specification

This specification defines the observable desktop interface exposed by the exported client. It uses generic terminology for screens and controls. It specifies user-facing state and transitions, not implementation technology, window messages, resource identifiers, artwork, or original text.

## Application shell

The application has a single top-level workspace with these persistent regions:

- A title area that identifies the current game or document context.
- A command menu for file/session operations, map navigation, object operations, reports, configuration, and help.
- A toolbar that exposes frequently used navigation and object commands as icon buttons.
- A primary map canvas.
- Transient status text, tooltips, progress feedback, and modal dialogs.

The workspace supports a draggable divider between its map and auxiliary regions. While the divider
is dragged, the client shows a live split preview and clamps the result to minimum usable sizes for
both regions. Releasing the pointer commits the new layout and redraws the affected views. This is
a layout preference only; it does not alter game data.

Commands may be available in more than one place. A toolbar button and its corresponding menu command must have the same availability, effect, and enablement state.

Confirmed by inspection of the exported client: the file-open command maintains a **9-slot Recent Files list**, which reuses the same load pathway as an ordinary Open command (loading is gated on whether a filename was pre-supplied by the recent-files list versus prompted via the standard file picker). Map printing (see below) computes its page layout from the printer device's reported resolution and prints a paginated grid of planet rows using the same small per-planet status icon set used elsewhere in the client.

The interface responds to resizing by recomputing the usable client area and redrawing the active view. Controls that depend on text width or current display scaling must be repositioned rather than clipped.

**Startup display detection, confirmed by inspection of the exported client.** At launch, the client reads the screen resolution and classifies it into one of four quality tiers, each tier enabling or disabling a distinct internal display-quality flag pair: below 800×600 is the lowest tier; 800×600 up to 1023×767 is the second tier; 1024×768 up to 1110×887 is the third tier; 1111×888 and above is the highest tier. Separately, the client computes a device color-capacity figure (color planes times bits-per-pixel) and, if that figure falls below a fixed threshold (equivalent to a very low color mode), shows a one-time startup warning unless the user has previously dismissed it (tracked by a dedicated persisted flag) or has already run the client several times. Startup also builds the full shared GDI resource set used throughout the client in one pass: solid-color brushes and pens derived from a fixed palette table, several pattern brushes loaded from bitmap resources, a set of cursors and icons, and a table of fonts constructed via CreateFontIndirect from a shared font-name table, with point sizes computed from the display's reported DPI and per-font row heights cached for reuse by later layout code.

**On-demand GDI resource helpers, extending the startup GDI-resource-pass finding above.** Beyond the fixed table of brushes/pens/fonts built once at launch, several further helpers create and manage GDI resources on demand:

- A small **reference-counted solid-brush cache** (capacity 32 entries, keyed by color value): requesting a brush for a given color returns an existing cached handle and bumps its use count if one already exists, or creates a new one via the standard brush-creation API and adds it to the cache otherwise; releasing a brush decrements its count and only actually deletes the underlying GDI object once the count reaches zero. This avoids repeatedly creating and destroying identical solid brushes for the same color across many draw calls.
- A small cluster of **device-independent-bitmap (DIB) helpers**: a header parser reads a DIB resource's declared color-table size across both the older and newer bitmap-header formats (handling the fixed 12-byte legacy header as a distinct case from the newer, larger header, and falling back to a bit-depth-implied count — 2/16/256 — when no explicit count is stored); a paired "pixel-data offset" helper uses the same header-format distinction to compute where the actual pixel data begins after the header and color table; a **palette builder from a DIB resource's own color table** locks the resource, copies its color entries into a temporary logical-palette buffer, byte-swaps each entry's red/blue components, and creates a GDI palette from the result; and a **DIB blit helper** either flat-fills a rectangle (when passed no bitmap handle) or locks a DIB resource and stretches it into the destination via the standard DIB-stretch API, using the pixel-offset helper above to locate the source pixels. A separate, simpler routine builds a **fixed default 256-entry palette** (not derived from any resource) for use before a resource-specific palette is available.
- A **chunked large-resource loader**: rather than using the ordinary resource-load API, this pair locates a named resource, allocates memory for it directly, opens the executable itself as a plain file to access the resource's raw bytes, and reads it in bounded chunks (capped per individual read call, looping until the full declared resource size has been transferred) directly into the allocated buffer — a technique for pulling in a single resource larger than the ordinary 16-bit resource/read-call size limits would otherwise allow.

**Persisted settings, confirmed by inspection of the exported client.** Beyond the toolbar layout and autosave interval already noted below, startup reads a large block of `.ini`-resident settings, including: up to four windows' saved placement (position, size, and a Maximized/Restored/Iconic state letter) via a shared decode routine; a registration/serial-style value stored as a hex string and parsed manually into a 32-bit number; default player-name and race-name strings; up to nine saved play-by-email player addresses and up to thirteen obscured per-player passwords, each read from a block of indexed keys into fixed-size tables; and a two-character default-game-type code (a mode letter plus a constrained secondary letter) decoded into flag bits, whose exact real-world labels could not be recovered from decompiled code alone. **Revisited now that the dynamic string table is decoded, without success:** the `.ini` reader itself decodes this key by direct character comparison (e.g. testing the stored byte against literal characters), not by looking up a label through the shared string-lookup routine, so this table gave no new leverage on it; the reader's own call site was inspected but the specific letters it compares against were not isolated from the surrounding startup-settings code in the time available. (Resolved by the next paragraph, by reading the comparison code directly.)

**Resolved this pass, with a correction: this is not a "game type" code at all.** The literal comparison code was finally isolated (`FUN_1000_0d9c`, the startup `.ini`-settings reader, at the point it reads a `0x14`-byte string keyed to internal id `0xa4`/table offset `0x6fa`): the first character is compared against the literal bytes `'S'`, `'E'`, and `'P'` (any other value, or a string under 3 characters, clears the field to "unset"); the second character is range-checked against `'B'`..`'Q'` (16 letters) and stored as that letter minus `'B'`, i.e. a 0-15 index. **Tracing the matching write-side routine (`FUN_1020_5924`, ~line 10058) that regenerates this same key on save proves what it actually encodes:** it is not a default new-game type at all, but the client's **persisted "last-tracked/selected object" state**, saved across sessions so the previously-viewed fleet or planet is re-selected on the next launch. The save routine writes the two letters plus a decimal object ID through one shared `sprintf`-style call using format-table string 798, which the now-fully-decoded dynamic string table confirms is a two-characters-then-decimal-number format — directly corroborating the two-letter-plus-number shape inferred from the reader. The mode letter is written from the same global that also selects between the object-information panel's Planet and Fleet layouts (`DAT_1128_497a`, see `client-ui-dialog-catalog.md`'s "Toolbar, tooltip, and contextual popup" section): value 0 writes `'N'` (no tracked object), 1 writes `'P'`, 2 writes `'S'`, and 4 writes `'E'`. Reading the letters back the other way (traced through `FUN_1020_1b9a`, the routine that restores a saved tracked-object reference once the right race's data is available) confirms `'P'` dispatches to the planet-record accessor (`FUN_1038_01e4`, the same binary-search/direct-index planet-by-ID lookup documented under "Working-copy record accessors" above) and `'S'` dispatches to the fleet-by-ID accessor (`FUN_1038_14ec`) — i.e. **`P` = Planet, `S` = Fleet** (most plausibly "Ship"), confirmed functionally rather than merely by initial letter. The third value, `'E'`, is not reached by either of those two dispatches in the code traced this pass; a third, rarer trackable-object kind (plausibly a bare map location or another non-fleet/non-planet object) remains unidentified.

**Second letter and `'E'`, settled from the reader, writer and restorer together.** The second letter is not a free code. It is the current player's slot number written as a letter (`'B'` for the first slot, up to `'Q'` for the sixteenth). The writer builds it by adding the slot to `'B'` (`FUN_1020_5924`, `stars.exe.export.c:10070`). The reader rejects anything outside `'B'`-`'Q'` (`FUN_1000_0d9c`, `stars.exe.export.c:2470`-`2475`). The restorer (`FUN_1020_1b9a`) compares it with the player now loaded: if they differ (or a second saved value, stored under a neighbouring key, does not match), the saved object is dropped and the player's default planet is selected instead. The full key is therefore "kind letter, player letter, object number". `'N'` (nothing selected) is written but never accepted back: the reader turns it, or any other unknown letter, into "unset". `'E'` (internal kind value 4) is a dormant kind. The writer would emit it and the reader accepts it, but no code ever puts the client into kind 4. Every call to the tracked-object setter (`FUN_1048_2c12`, 82 call sites) passes kind 1 (planet), kind 2 (fleet) or a value taken from a hit-test that yields only 1, 2 or 8. The setter itself only has a planet branch and a fleet branch. The object-name formatter (`FUN_1038_2612`) names kinds 1, 2 and 8 and, for anything else, falls back to the deep-space or coordinate caption. On restore, an `'E'` entry is not handled by the fleet or planet branch. It falls through to the final step, which treats the saved number as a planet number and selects it if this player owns that planet, or otherwise selects the default. A compatible client may treat `'E'` as an unused, reserved kind that degrades to a planet lookup.

**Third trackable-object kind, resolved this pass (with a correction to the framing).** The restore-dispatch bitfield (`_DAT_1128_22ba`'s bits `0x1e0`, read in `FUN_1020_1b9a`, `stars.exe.export.c:6275`) actually spans four sub-values, matching its producer one-for-one (the `.ini`-read letter decoder in `FUN_1000_0d9c`, `stars.exe.export.c:2454`-`2475`): `'S'`→`0x40` (Fleet), `'P'`→`0x20` (Planet), `'E'`→`0x80`, and an unused fourth slot at `0x100` that no letter ever produces. But the *live*, in-game "currently tracked/selected object" mechanism uses a different value domain entirely. The general-purpose object-selection setter, `FUN_1048_2c12` (`stars.exe.export.c:25889`), which writes `DAT_1128_497a` directly, is called with `1` (Planet) or `2` (Fleet) from essentially every site — but also, from the map's "click the same spot repeatedly to cycle through co-located objects" handler (`stars.exe.export.c:12779`-`12800`, inside the frame window procedure's mouse-click handling), with the literal value `8`, sourced from a separate table (`DAT_1128_15fe`, stride `0x12`/18 bytes, bounded by `DAT_1128_1602`) that `turn-generation-engine.md` §10 already identifies as the galaxy's special deep-space object table (wormholes, and, per the map-icon-sheet catalogue below, plausibly Mystery Trader ships, nebulae, and debris clusters too). The right-click disambiguation popup (`FUN_1050_7d44`, `stars.exe.export.c:36923`) independently computes this same `8` value for a matching table entry, but then explicitly discards any kind other than 1 or 2 (`stars.exe.export.c:37500`) before ever calling the selection setter — so the popup only ever *offers* fleets and planets, while the click-cycle path can select a special object directly.

This means the client's real trackable-object kinds are `{0=none, 1=Planet, 2=Fleet, 8=special deep-space object}`, not `{N,P,S,E}`. The `.ini` persistence code was never updated to match: `FUN_1020_5924`'s write side (`stars.exe.export.c:10058`-`10069`) has explicit cases only for `DAT_1128_497a` values `0`, `1`, `2`, and `4` — there is no case for `8` at all, so saving with a special object as the tracked selection leaves the output letter as whatever incidental byte was left in an unrelated local variable, not a designed encoding. And nothing in the traced code ever assigns `DAT_1128_497a` the value `4` that would round-trip back out as `'E'` on save and be read back in by `FUN_1020_1b9a`'s `0x80` case. The best-supported reading is that `'E'`/`4` is dead code — a vestigial fourth slot in an encoding that at some point was renumbered (bit-shifted values `1/2/4` becoming plain small integers `1/2/8`) without the `.ini` read/write pair being updated to match, and without the special-object kind ever being given its own persistence letter. A compatible implementation should treat a saved `'E'` key as unrecognized/no-selection and should not expect to ever produce one. The secondary letter (`'B'`-`'Q'` → 0-15) is the tracked object's owning race/player index, cross-checked directly against the currently-active race (`DAT_1128_014c`) before the restore is applied. This resolves the open question but changes its scope: there is no "default game type" `.ini` setting in this client at all — the earlier framing was a misreading of a session-selection-restore mechanism.

## Command availability

Every command is evaluated against the current session, selected owner, selected object, and editing permission. A command is disabled when its required context is absent or read-only. Disabled controls remain visible unless the surrounding mode explicitly hides them.

Opening a modal editor suspends conflicting workspace commands until the editor is accepted or cancelled. Opening an informational view does not itself modify game state.

**Trait-gated control validation, confirmed by inspection of the exported client.** A shared dialog-control validator decodes a packed control/item identifier into one of 16 categories plus a sub-index, resolves the sub-index to a caption/resource string through a per-category lookup table, and then — for most sub-indices — separately checks the currently selected race's Primary Racial Trait and up to 11 distinct trait/technology-availability flags, rejecting an item whose category conflicts with the current race's configuration. A companion routine walks a category's items from the highest sub-index downward, calling the validator until it finds one still valid for the current race (or exhausts the category), and is used to pick a new default selection when the previously active one becomes invalid after a trait change. A related helper performs a graded comparison between a candidate race's environment/trait value vector and the corresponding stored vector, distinguishing "identical," "differs by exactly one step in one field," "differs by more than one step in exactly one (linked) field" (returning the signed step count), and "differs in more than one field" — the same graded-compatibility shape documented below for the ship/component slot editor, here applied to race data.

**Correction, verified against the exported client.** This validator is not primarily a *dialog* gate at all — tracing every call site (over 60, across roughly 20 of the client's ~37 code segments) shows it is the client's single general-purpose "is this game item legal for the current race" resolver, called far more often from plain game-logic code than from any dialog procedure: ship/starbase design cost and mass aggregation, the map's per-planet Starbase/Stargate/Mass-Driver icon-dot checks (see "Starbase capability indicators" above), AI starting-fleet template hull selection during new-game setup (segments 19 and 21, which contain no dialog/window-control code at all — see `new-game-setup.md`), and the production-queue item validator's fallback to a new default sub-item when the previously selected one becomes illegal (segment 24; the "find next valid default" companion routine documented above). The race-design wizard's own trait-toggle stage (the slider/checkbox segment) was searched specifically and contains **no calls** to this validator, refuting the earlier "most plausibly the trait pages" guess as stated. Two genuine, concrete UI call sites were found instead: (1) the same segment that builds the wizard's trait-conflict explanatory text (`race-traits.md`'s and `race-designer-ui-and-availability.md`'s "Trait stage") also uses this validator, immediately after a trait changes, to walk every installed component slot of the affected ship/starbase design and silently clear (uninstall) any slot whose component fails re-validation under the new configuration — a previously-undocumented "trait change strips now-illegal components from existing designs" mechanic, distinct from the explanatory-message behavior already documented; and (2) the Ship and Starbase Designer's Slot/equipment editor (see `client-ui-dialog-catalog.md`) calls it while building the list of components offered for a slot, including a specific, size-class-filtered case for the shared "orbital special equipment" category that also drives the map's Stargate/Mass-Driver dots. The validator itself remains a strict binary (legal/illegal) gate in all of these call sites; it does not implement the graded tech-level-distance feedback described for the slot editor. That feedback comes from a separate function in the Research dialog's segment, whose result the shared detail-card renderer draws as one of four caption variants (`research-tech-tree.md` §4; `client-ui-dialog-catalog.md`'s "Slot/equipment editor").

All editable dialogs use a working copy. Accept commits validated changes; cancel discards uncommitted edits. If a dialog changes a record before the user moves to another record, the interface commits the previous record's working copy before loading the new record.

**Working-copy record accessors, confirmed by inspection of the exported client.** At least two concrete instances of the underlying load/commit mechanism were traced: one pair of routines looks up a planet record by its stored ID (a direct-index fast path when the live planet count has no gaps, falling back to a binary search over a sorted array otherwise) and either copies it out into a caller's working-copy buffer or, on commit, swaps the working copy back into the live array while carefully preserving one field that is itself an out-of-line pointer (a per-planet production-queue block) rather than overwriting it wholesale — so the "record" and its variable-length queue data are committed through two different paths in the same operation. A second, differently-sized record table has its own analogous get/set pair. Both commit paths conditionally trigger a full dependent-value recalculation afterward, gated on a "not currently viewing another race's data" check, consistent with the rule that accepting an edit should not silently recompute state for a race the user isn't looking at. **A third instance, sampled this pass:** a commit routine for a record carrying a variable-length trailing string swaps the fixed-size portion of the record wholesale, then separately grows or shrinks a backing allocation and copies the trailing string into it — the same "fixed fields swapped directly, variable-length trailing data handled through its own allocate/copy path" shape as the planet/production-queue case, applied to a different (unidentified) record type.

## Map canvas

The map is the primary navigable surface. It displays spatial objects and accepts selection, navigation, and contextual interaction.

- Selecting an object makes it the active subject for object-specific commands and information panes.
- Selecting a fleet displays its pending route on the map. The route is drawn as an ordered series of legs from the fleet's current position through its remaining waypoints, so its intended travel path is inspectable without opening the order editor.
- The active fleet's current position, route origin, intermediate waypoints, destination, and leg direction are visually distinguishable. The selected route overlay takes precedence over ordinary map clutter and is redrawn whenever the selected fleet, its orders, or the map viewport changes.
- Selecting a different fleet replaces the previous route overlay. Deselecting the active fleet, closing the game context, or entering a mode that hides fleet data removes the overlay.
- Object-specific actions are unavailable until a compatible object is selected.
- A search dialog can locate a named or otherwise filterable object and then focus the map on the result.
- Map printing opens a configuration dialog before output is produced.

**Correction, verified against the exported client.** The map's contextual popup is **not** an action/command menu — it never offers a per-object action (no rename, no scrap, no order-editing verb). It is purely an **object-disambiguation picker**: right-clicking a map position lists every fleet present there, then every planet present there (with a divider between the two groups when both exist), with the currently-selected object shown checked; choosing an entry simply makes that object the active selection and syncs the fleet/planet side panels — nothing else happens. Plain left-clicking selects an object directly, and clicking the same already-selected position repeatedly cycles through a stack of co-located objects one at a time as an alternative to opening the picker. Clicking the small status strip beneath the map viewport (as opposed to the map itself) opens a separate, unrelated read-only popup showing the selected object's cargo/mineral breakdown; that popup has no interactive controls either.

**Plotting a course, confirmed by inspection of the exported client.** Holding Shift while right-click-dragging, or dragging with the middle mouse button, draws a live rubber-banded line from the drag origin to the current cursor position and shows a tooltip naming whatever object (or "Deep Space") is currently under the cursor; releasing commits the course/waypoint. Separately, holding Ctrl while left-clicking during multi-fleet route editing inserts a new waypoint into the route being edited at the clicked position, provided it falls far enough from any existing waypoint.

*Correction (waypoint-placement pass; the map window procedure at raw `1058:0000`, `:37100`-`37633`; full rule in `fleet-movement-scanning-cargo.md` §5, "Waypoint placement and editing (client)").* Both statements above are wrong. Shift+right-drag and middle-drag only draw a temporary measuring line (`FUN_1058_6bca`); releasing the button erases it and nothing is committed. A waypoint is added by Shift+left-click while a fleet is selected (or with view-option bit `0x10` latched), which calls `FUN_1058_5388`. The new waypoint goes after the current waypoint and snaps to the nearest object within 20 screen pixels. Ctrl+left-click adds no waypoint: with a planet selected it sets that planet's route (rally) destination. Waypoints are moved by left-dragging their markers, and the bit-`0x10` reader cited below at `:37485` is this left-button branch of the map window procedure, not `FUN_1050_7d44`.

**Object-identification text builder, confirmed by inspection of the exported client.** A shared routine turns a found object handle (as returned by the nearest-object search described in `fleet-movement-scanning-cargo.md`'s "Object-proximity search utility") into the descriptive phrase used by this under-cursor tooltip: for an object owned by another race it substitutes that race's display name (via the race-name/summary string builder) into an "owned by ___" template; for an object in the map's "orbital special equipment" component category it selects among a small set of alternate templates depending on whether a qualifying component (matching the same Stargate-range check documented under "Starbase capability indicators" above) is actually present; other categories fall back to a plain category-name template. This is the most likely source of the course-plotting tooltip's object name and a plausible source for the status-strip text as well, though the exact call sites tying it to each specific surface were not individually traced. A separate, much simpler routine (design-name-by-index) was also sampled this pass: given a race and a hull/starbase design slot index, it checks the design's deleted-flag bit and, if clear, copies out the design's own stored name string — a plain accessor, most plausibly feeding a design picker/dropdown rather than the map tooltip itself.

**Default planet-name table, newly identified this pass.** A dedicated decompression routine takes a numeric index (wrapped into a fixed range of roughly a thousand entries) and unpacks one entry from a compact, variable-width-nibble-encoded name table into a plain capitalized string (capitalizing the first letter and the first letter after any internal space or hyphen). Its caller combines that decompressed name with a small numeric suffix — an index value plus one, formatted directly after the name — matching the game's known "`<default name> <number>`" convention for automatically-assigned planet names before a player renames them. This is the client's built-in default planet-name generator; the underlying name table itself is compressed program data with no surviving plain-text initializer in the exported source. ~~So the actual roster of names could not be recovered.~~ *(Superseded: the table was later decoded from the raw executable, 999 names sorted alphabetically, wrapped modulo 999; mechanism in `dynamic-string-table.md` §7, data in `extracted-game-data/default-names.txt`.)*

The map supports additional overlays and inspector windows for scanning and minefield-related information. These views are derived from the current game state and refresh when the relevant selection or viewpoint changes.

**Starbase capability indicators, confirmed by inspection of the exported client.** The map's planet-icon painter draws up to three small colored square overlays ("dots") on a planet's icon, one per independent boolean condition, each in its own fixed position relative to the icon and its own distinct color:

- **Starbase presence** — read directly from the planet's stored status: a specific status bit is "has a starbase." When present, the code separately inspects the starbase's own design record: if a specific leading field of that design equals a distinguished value, the dot is drawn in a second, different color instead of the ordinary one — i.e., the client distinguishes at least one specific starbase design/type from an ordinary starbase using a different color for this same dot.

  **Resolved this pass, by cross-reference with `extracted-game-data/component-stats.tsv`.** The compared field is the design's hull-type index (the same "hull-type index at a fixed offset" documented in `ship-design-and-components.md` §13, resolved through the shared 37-entry hull/starbase-chassis table spanning categories `0x4000` and `0x0400`). The distinguished value read in the map painter (`FUN_1058_0b46`, segment 12) is `0x20` (32 decimal) — and per that same unified numbering (ship hulls occupy unified indices 0–31; starbase chassis continue the same table at 32–36, one per `0x0400` subtype 0–4), unified index 32 is exactly subtype 0 of the starbase-chassis category, which `component-stats.tsv` names **Orbital Fort**. The second dot color therefore marks a starbase built on the Orbital Fort chassis specifically — the cheapest and only non-refueling/non-repair-capable starbase chassis of the five — as distinct from a "real" Starbase/Space Dock/Space Station/Ultra Station/Death Star, which is a sensible distinction for the map to surface (an Orbital Fort cannot service visiting fleets the way the other four chassis can).
- **Stargate capability** — a dedicated check walks the starbase's installed components looking for any component in a shared "orbital special equipment" category whose subtype falls in the lower half of that category's range, consistent with the game's roughly six Stargate tiers. Drawn as a second dot, in a second color, at a different fixed offset from the starbase dot.
- **Mass Driver capability** — the same shared component category is checked again, this time for a subtype in the upper part of its range, mapped to a driver level; the *highest* level found across all installed components is used. This range and mapping line up exactly with the game's known Mass Driver → Super Driver → Ultra Driver progression (levels 5 through 13). Drawn as a third dot, in a third color, at a third fixed offset.

**Resolved this pass: the dots render for every colonized planet simultaneously, not only the selected one.** Re-reading `FUN_1058_0b46`'s planet-iteration loop (segment 12, the same `for` loop bounded by the live planet count that computes the starbase/Stargate/Mass-Driver flags for each planet in turn) shows the flag computation itself runs unconditionally per planet, gated only by whether that planet's projected position falls inside the current redraw's clip rectangle — the same visibility test every other per-planet overlay in this routine uses. The dot-painting code that consumes those flags is duplicated in two sibling branches of the same loop body: one branch draws a larger base icon plus the dots when the planet matches the client's tracked/selected-object position, the other draws a smaller base icon plus the *same three dots* for every other visible planet. Both branches test the identical three per-planet flags, so a compatible implementation should show these indicators on every colonized planet's icon at once, sized only slightly differently for the currently-selected planet — the earlier hedge in this document was overly cautious.

**Planet display-mode ring/bar overlay, newly identified this pass, confirmed by inspection of the exported client (including exact pen/brush RGB constants).** Independent of the dots above, every colonized planet also gets an optional second overlay whose *shape* and *color* are driven by the same selector documented under "Shared view-option slots" below as choosing the object-information panel's content mode — i.e., the panel and this map overlay are the same "Planets:" view selection, changed together by the same six-way toggle (bound to the top-row digit keys). The four modes that paint something distinct on the map are:

- **Two modes draw a stacked 3-segment color bar** (blue / dark green / yellow, in that fixed order) above the planet icon, one segment per value read from three parallel per-planet fields. One of the two modes normalizes each value against a shared reference maximum and scales it into a 0-20-step bar; the other instead reads a plain 0-100 byte-percentage field per value and divides by 5 into the same 0-20 scale. This is consistent with one mode showing absolute mineral stockpile/amount and the other mineral *concentration*, though which of the two field sets maps to which real label could not be confirmed from decompiled code alone. (An earlier note linked this to the hover popup's "Mode 4" in `client-ui-dialog-catalog.md`; that link is withdrawn — Mode 4 turned out to be an object ID/X/Y readout, and the two features share no data source.)
- **One mode draws a two-tone "bullseye" ring pair** (an outer, larger circle and an inner, smaller one, both centered on the planet) whose color encodes the planet's **habitability value for the currently-viewed race**, computed via the same tolerance-distance routine documented in `population-growth.md` (a per-environment-axis distance-from-range calculation, returning a negative "hostility" count when outside the race's tolerance or a positive 0-100 value when inside it). The ring's radius is proportional to that value, clamped to at most 10 zoom-scaled steps. Fill and outline colors are chosen as a matched dark/bright pair of the same hue: **dark-red fill / bright-red outline** when the value is negative (outside tolerance), **dark-green / bright-green** when non-negative, and **dark-yellow (olive) / bright-yellow** for a third, narrower case — reached only when a helper that re-derives the value from the planet's *visible/estimated* environment readings (rather than the exact stored one) disagrees with the exact value's sign, gated by whether the current race's Primary Racial Trait is Claim Adjuster (PRT index 3): for a race whose exact value is negative, the olive styling is used unless the race is Claim Adjuster; for a race whose exact value is non-negative, the exact-vs-estimated recheck (and possible olive styling) is performed only because the race *is* Claim Adjuster. This is consistent with Claim Adjuster's known ability to found colonies outside normal habitability limits — the client appears to give that PRT a different (estimate-based) value read in exactly the cases where its bonus would matter. A small additional square marker is drawn in one of this same mode's sub-branches when the planet has no owner at all, independent of the ring.
- **One mode draws a single ring**, sized by bracketing the planet's population (own planets read a precise two-field population value; other planets read a smaller, coarser 12-bit estimate field, consistent with an imprecise scan-derived figure) against a fixed table of 19 ascending thresholds, giving a 0-18 step count (plus 2, then halved at the lowest zoom levels). Its color is a solid **green** fill/outline for the viewer's own planet, **yellow** for a planet belonging to a race the per-relationship detection table marks as already "seen"/friendly, and **red** otherwise (unknown or hostile owner).
- The remaining two selector values draw no additional per-planet overlay at all (the map falls back to the dots/icon already described above).

**None of these four modes is conditioned on whether a fleet is orbiting the planet** — they read only the planet's own stored/estimated environment, mineral, and population data for the currently-viewed race, and stay the same whether zero or several fleets share that map position.

**Fleet-in-orbit ring, confirmed both by direct observation of the running client and by isolating its exact drawing code.** A colonized planet with a fleet in orbit is additionally ringed with a small circular overlay, tightly sized to the planet icon itself (roughly a 9-11 zoom-scaled-pixel radius) — clearly distinct from, and drawn independently of, the much larger scan-range disc and the habitability/population ring/bar overlays described above. Live observation (pixel-sampled at 255,255,255) confirmed this ring renders solid **white** when the fleet in orbit belongs to the currently-viewed player; it was present regardless of the current "Planets:" view-mode selector. (This was verified only after discovering that an outdated build of the `otvdm` Win16 emulator used earlier in this project silently fails to render this one overlay while still rendering the scan-range/value/population circles correctly — a fixed development build, folder name `otvdm-master-2697`, was required to see it at all, so an earlier pass of this project that used the old build and concluded no such ring existed was working from a rendering bug, not a genuine absence.)

Unlike the scan-range and habitability/population overlays (all drawn with `ELLIPSE`), this ring is composited as a pre-rendered bitmap sprite via a same-position pair of `BITBLT` calls using the classic 1-bit-transparency "mask then paint" idiom (an AND-mask blit to clear the icon's silhouette, immediately followed by an OR/paint blit of the color tile into the cleared area — recovered by decoding the literal raster-op words each call passes, which match the standard `SRCAND`/`SRCPAINT` constants split across two 16-bit arguments). It is drawn by the map's fleet-list loop, not the planet-list loop (the planet loop never references the fleet list at all), at the exact same projected screen position the planet loop used for the planet's own icon — i.e. it is composited on top of, not instead of, the ordinary planet icon. The gating mechanism is a once-per-repaint, per-planet tally byte (cleared for every planet immediately before both loops run): drawing a ring increments the tally by 1 for a fleet belonging to the current race or by 2 for any other fleet, and a planet's tally is only allowed to advance twice total per frame — once via the "belongs to current race" path and once via the "belongs to someone else" path — so in effect each planet gets at most one "own fleet present" ring draw and at most one "foreign fleet present" ring draw per repaint, using a race-relationship index (current race vs. not) to select which color tile from the icon sheet is painted. **Confirmed by direct extraction and visual inspection of the icon-sheet bitmap resource itself** (a 48×101-pixel, 16-color resource loaded by name rather than numeric ID, distinct from — and much smaller than — the various ship-hull, ship-component, race-emblem, and planet-thumbnail sheets documented below): the sheet contains exactly two stacked groups of three ring tiles apiece, an 11×11 group and a 19×19 group, each group ordered **top-to-bottom as light-gray/silver, red, then magenta/purple**, immediately followed on the sheet by one shared black-and-white AND-mask silhouette per size. This lines up precisely with the tally-driven, three-outcome gate described above (own-race-only reaches the first row, foreign-only the second, both-present the third) and independently corroborates the user-reported color scheme in full: a race-relationship-colored ring, red for a hostile fleet, and a third, distinct (magenta/purple) tile specifically for the both-present case — not a visual side-effect of overlapping draws. The one open discrepancy: this pass's live pixel-sampling of an own-race ring measured pure white (255,255,255), while the raw asset's own-race tile is stored as the standard light-gray palette entry (192,192,192) rather than the white palette entry also present elsewhere on the same sheet; the most likely explanation is a runtime palette remap (swapping a template gray for the viewing player's actual assigned color) rather than an error in either measurement, but this was not independently confirmed.

The two families are **not** colored identically:
- The **small (11×11) ring's own-race row** (y=0-10) is drawn as a two-tone bevel using palette indices 7 and 8 — i.e. light gray (192,192,192) and a darker gray (128,128,128). The "discrepancy" therefore dissolves once the two sizes are treated separately: **the large ring's own-race tile genuinely is pure white in the raw asset**, exactly matching this pass's live 255,255,255 sample, while the light-gray (192,192,192) reading from the earlier pass is *also* correct — but for the small ring's own-race tile, a different, differently-colored variant that the earlier pass's asset inspection evidently sampled instead (the two tiles sit close together on the sheet and are easy to conflate without coordinate-level extraction). **Scan-range overlay.** A view-option toggle (bit 0x20 of the view-options word — see the "shared view-option slots" note below) draws a scan-range circle for every planet and fleet belonging to the current race, using the standard circle-drawing primitive in an XOR/overlay drawing mode so the circles never obscure underlying map content. Each circle's true-scale radius comes from a per-object range lookup and is then passed through the same zoom-scaling arithmetic used for all map coordinates (see below), plus an additional correction whenever a separate "scanner display" percentage setting (2-100%, default 100) is below 100. That percentage is edited through a dedicated numeric/slider control (documented in `client-ui-dialog-catalog.md`'s Planet inspector entry) that always force-enables the scan-circle overlay when changed.

**Resolved this pass: the exact arithmetic, confirmed by inspection of the exported client.** Everywhere the map-painter applies this correction (four separate sites within the scan-circle-overlay branch, covering both the current race's planets and its fleets, and both the primary and the half-radius secondary/penetrating-scan circle), the formula is the same: the true-scale radius is multiplied by 100 and divided by the scanner percentage (a single multiply-then-divide), applied only when the percentage is below its 100 default (at 100 the correction is skipped outright, a no-op). Because the divisor shrinks as the slider is lowered, this **enlarges** the drawn circle as the percentage drops below 100 (up to 50× the true radius at the minimum setting of 2%), the opposite of what the control's name might suggest at first read. This is consistent with the setting acting as a "minimum on-screen scan-circle size" floor rather than a literal display-percentage cutoff: it keeps small scan ranges visible on a zoomed-out map rather than shrinking them further. (One of the four sites renders the multiplication's first argument as a segment-number constant rather than the preceding computed radius — a recurring decompiler artifact seen throughout this file for far-call arguments the decompiler fails to resolve to a variable; a sibling occurrence of the identical call renders the same argument as a proper variable, confirming the reading above.) Objects whose range lookup also reports a positive secondary detection value get a *second* circle drawn at exactly half the primary radius — consistent with the game's separate penetrating-scan range being distinct from its normal scan range. A batching helper accumulates circles per redraw region and skips drawing any circle fully nested inside another already-queued circle in the same region, an overlap-culling optimization that does not otherwise change what is visible. When this same toggle is on, the client also separately re-draws a small solid square at the exact center of every owned fleet (in addition to its scan circle), most plausibly so the fleet's precise position isn't lost inside a large scan circle.

**Minefield visibility overlay, confirmed by inspection of the exported client.** A separate overlay toggle (bit 0x40 of the same view-options word) draws minefields using one of three distinct fill patterns (matching the game's three minefield types), gated by an independent 4-bit visibility mask covering the player's own fields, other owners' fields, and a further split for enemy fields depending on whether they have been detected (checked against a per-relationship detection table). **Route-overlap overlay, confirmed by inspection of the exported client.** A further overlay toggle (bit 0x80 of the same view-options word) affects the route/waypoint editor's map drawing: when the plotted route contains two legs sharing the same pair of endpoints (an overlap or reversal), the overlapping leg is drawn with a distinct dashed pen instead of the normal solid one, and an underlying straight base path connecting every waypoint in order can optionally be drawn beneath the actual route. **Cloak-adjusted circle rendering, re-examined this pass with a confirmed negative result.** The shared per-fleet range-lookup routine the scan-circle overlay calls (`FUN_1038_32be`, which combines a fleet's installed scanners into one effective range) can also compute and return the fleet's cloak percentage and a design-ability bitmask through two further output parameters — the same cloak-percentage lookup used by the turn-generation engine's actual detection formula (see `fleet-movement-scanning-cargo.md`'s "Scanning formula" note). But at both of the map painter's own call sites for this routine (`FUN_1058_0b46`, segment 12, inside the scan-circle-overlay branch, one call for each of the two fleet sub-loops it runs), the map explicitly passes null pointers for those two output parameters, discarding them before the radius is ever computed. The scan-circle overlay's radius is therefore never adjusted for the drawn object's own cloak state — not because of a missing branch in the paint code, but because the caller deliberately declines the value the shared routine would otherwise supply. This is consistent with the overlay's own semantics: it only ever draws circles for the current race's own planets and fleets (see above), and a fleet's cloak reduces how far *other* observers can detect it, not how far it can itself scan — so there is no in-game reason for the circle showing your own scan reach to shrink because you are also cloaked. A compatible implementation should not add cloak-based shrinking to this overlay.

## Planning and diplomacy

The client exposes independent editors for research preferences, battle plans, and inter-owner relations.

- Research preferences select a focus discipline and allocation behavior.
- Battle plans are ordered, named records with targeting, movement/behavior, and opponent-policy attributes. The first record cannot be removed; later records can be created, selected, edited, and removed subject to the applicable plan limit.
- Relations are edited through a dedicated dialog and are separate from battle-plan targeting preferences.

These editors must preserve the selected owner context, distinguish a changed working copy from a stored record, and synchronize accepted changes through the ordinary persistence pathway.

**Battle Plans and Relations dialogs, confirmed by inspection of the exported client.** Both real dialog window procedures were located and traced directly (previously misattributed as living elsewhere, or not attributed at all — see the segment 31 note in `combat-resolution.md` §8 for the full correction):

- The **applicable plan limit is exactly 15** additional plans per race (a per-race count byte is refused once it reaches 15), on top of the un-removable first plan, matching this document's "subject to the applicable plan limit" wording with a concrete number.
- The **"first record cannot be removed" rule** is enforced simply by disabling the Delete control whenever the currently-selected plan index is 0 — there is no separate special-case check inside the delete handler itself.
- **Deleting a plan that is still assigned to at least one fleet** triggers a confirmation prompt (a generic Yes/No message box) before proceeding; declining leaves the plan and every fleet assignment untouched. Accepting (or deleting an unused plan, which skips the prompt) removes the plan record, shifts every later plan down one slot, and walks every fleet in the game once to renumber any fleet whose assigned plan index needs to shift down to match, so existing fleets' plan assignments stay consistent with the new, shorter list rather than silently pointing at the wrong (shifted) plan.
- The dialog's working copy is a **36-byte record** loaded/committed as 9 packed fields at a time, independently corroborating the "fixed 36-byte structure" already documented in `combat-resolution.md`'s "Correction, verified against the exported client" note for the primary/secondary target type and movement-tactic byte layout.

## New-session and game-setup flow

The client supports both simplified and detailed new-session flows. The detailed flow is divided across multiple dialogs and presents one coherent setup draft. A random-seed dialog is available where reproducibility or explicit randomization configuration is required.

The setup flow includes a six-stage race designer. Its stages cover identity and archetype, environmental tolerance, optional traits, economy, research, and finalization. The full behavior of that wizard is specified in the race-designer specification.

The setup flow must retain user-entered values while moving between stages and must not create a usable session until required stages have accepted valid input.

## Reports, messages, and playback

The client has separate information surfaces for messages, reports, scores, tutorials, and battle or event playback.

- Message and report windows present recorded information without changing it merely by opening it.
- A score view presents comparative standings.
- A tutorial view can be opened independently of game-state editing.
- A replay controller presents recorded event progression using transport-like controls; playback changes only the displayed point in the recording, not the underlying game state.
- Long-running actions use a progress dialog with a gauge and may display a failure or recovery dialog when the action cannot complete normally.

## Authentication and sensitive settings

The client contains entry and replacement dialogs for a local access secret. These dialogs must keep entered characters concealed, require explicit acceptance to save a replacement, and discard incomplete or cancelled input. The secret entry surface must not reveal the stored value through tooltips, reports, or ordinary editing controls.

## Reusable control behavior

Several custom controls supplement standard text fields, lists, and buttons:

- A styled editable field behaves as a text input while preserving the application's visual treatment.
- A styled selection field behaves as a compact single-choice control.
- A list control supports selection changes and event-driven redraw.
- Tooltip controls describe adjacent actions without mutating state.

For all of these controls, keyboard activation and pointer activation must reach the same logical command. Focus changes must be visible and must not silently commit unrelated input.

**Correction, verified against the exported client.** A previously-noted "generic dialog window-proc subclass for keyboard navigation among controls" is **not** a Tab-order/arrow-key control-to-control navigator. Confirmed by inspection of the exported client, it is a fixed-key global hotkey relay installed on an auxiliary (non-main-frame) window, used so a handful of keyboard shortcuts keep working while focus sits in a modeless side panel rather than the main frame:

- Escape closes a tracked popup window when specific tracked-window conditions hold.
- Escape and Enter, when focus is within a specific tracked parent window, are forwarded as an accept/cancel signal into the object-information panel's own key handler (see "Object information and orders" below), rather than being handled generically.
- The digit keys 1-9 and 0 (plus Shift+0) are intercepted and dispatched to the shared view-option slot mechanism documented in "Navigation controls" above, rather than to whichever control currently has focus.
- Delete and Backspace remove the currently selected waypoint, but only while a specific route-editing mode is active.
- The `[` and `]` keys step to the previous/next message.
- `,` and `.` step a bounded (0-11) per-item field of the currently selected production/order-list row up or down, again only while the same route-editing mode is active.
- Any other handled navigation key (Up, Down, Home, End, and similar) that reaches a control outside a fixed exclusion list of specific controls is relayed unchanged to the main application window, so the main frame's own accelerators still fire; keys outside this fixed set are not intercepted at all and reach their control normally.

## Help and error feedback

Most modal editors provide contextual help. Invoking help leaves the editor's working copy unchanged. Invalid operations or unrecoverable conditions produce a generic message or recovery dialog rather than silently changing state.

The UI must preserve a distinction between an informational warning, a validation failure, and a cancelled operation. Only an accepted operation may alter persistent game or configuration state.
