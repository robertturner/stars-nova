# New Game Setup and Galaxy Generation

Behavior specification for the new-game creation flow and galaxy/universe generation in the 1995-2000 4X game *Stars!*. This document is derived directly from the exported client's decompiled logic; it is new material, since no prior document in this set covers game setup or galaxy generation. Facts are described in generic terms; no original identifiers or literal code are used.

## Overview

Creating a game follows one of two paths: a **Simplified** single-screen setup, or a **Detailed** three-page wizard (general settings, player-slot assignment, victory conditions). Both paths write into the same underlying game-setup draft, and both ultimately invoke the same galaxy generator once settings are finalized. A separate batch/scripted mode allows a game to be created from an external configuration source without going through the interactive wizard at all.

## Mechanics

### 1. Detailed setup wizard pages

The three detailed-setup pages are confirmed to be sequential pages of one wizard flow (each sets its window title from a shared string combined with its own page number):

1. **General settings** — Galaxy Size (5 mutually-exclusive options), Star Density (4 options), a third 4-option setting — **confirmed as Starting Distance by `client-ui-dialog-catalog.md`'s real dialog-resource extraction, with exact labels Close / Moderate / Farther / Distant** — and at least 7 independent boolean game-option flags whose individual meanings could not be determined (no label text survives in the analyzed material). These option flags are consumed directly by the galaxy generator (§3) — for example, one flag affects whether certain player types receive an extra starting planet, another affects a mineral-concentration bonus, and another affects how randomization is seeded.

   **Confirmed by inspection of the exported client (galaxy-generation continuation routine, formerly rated Partial):** one of these boolean flags is confirmed at the mechanism level. When set, it forces every ordinary (non-home-world) planet's mineral concentration to a flat maximum value instead of the normal randomized range (see §3's new mineral-concentration bullet below) — this is almost certainly the "Beginner: Maximum Minerals" checkbox named in the exported dialog resource. The remaining flag bits gate smaller, harder-to-attribute effects: one extends the star-naming pool's duplicate-prevention ceiling from 999 to 1000 names and applies a small mineral-concentration adjustment to two fixed slot indices in the per-planet initialization table (plausibly special/reserved systems), and another scales newly-seeded surface mineral tonnage upward by a flat 25% and nudges a planet-age-like field upward when it rolls low. **Resolved by the table below and the step-6 pass:** the last of these is the "Accelerated BBS Play" checkbox (`0x20`), and the star-name/two-fixed-planet bit (`0x08`) is the tutorial-game marker; see the "Option-flag effects" table after the bit-to-label table.

   **Bit-to-label mapping now resolved for the six named checkboxes, by cross-referencing the batch/scripted format's own flag-array parser (§4).** The batch-config reader that populates this same options word reads its "7 boolean toggles" field in one fixed order and immediately re-packs each one into a specific bit of the options byte (a second, adjacent byte holds an 8th bit for the anti-clumping toggle described in §3): the read order is bit 0, bit 1, bit 5, bit 7, bit 4, bit 6 of the first byte, then bit 0 of the second byte. Two of these seven bits are independently confirmed by their *mechanism* elsewhere in this document (bit 0 of the first byte forces flat-maximum mineral concentration, matching "Beginner: Maximum Minerals"; bit 0 of the second byte gates the anti-clumping relaxation pass, matching "Galaxy Clumping") — both land exactly at the position their read-order rank predicts (first and last respectively), which is strong internal corroboration that this read order matches the on-screen checkbox order `client-ui-dialog-catalog.md` recovered from the plain dialog-resource extraction. Taking that order at face value maps the full set as:

   | Read order | Bit | Checkbox label |
   |---|---|---|
   | 1st | first byte, bit `0x01` | **Beginner: Maximum Minerals** (independently confirmed by mechanism, above) |
   | 2nd | first byte, bit `0x02` | **Slower Tech Advances** |
   | 3rd | first byte, bit `0x20` | **Accelerated BBS Play** |
   | 4th | first byte, bit `0x80` | **No Random Events** |
   | 5th | first byte, bit `0x10` | **Computer Players Form Alliances** |
   | 6th | first byte, bit `0x40` | **Public Player Scores** |
   | 7th | second byte, bit `0x01` | **Galaxy Clumping** (independently confirmed by mechanism, above) |

   This leaves exactly two bits of the first options byte (`0x04` and `0x08`) that the batch-format flag reader never touches — i.e. they are not any of the seven named checkboxes at all, but internally-derived flags set by other code. **Bit `0x08` is the tutorial-game marker** (the "deterministic galaxy" guess above was right and is now attributed): the game-commit routine skips the tick-count seed for the game id when it is set (`:51803`-`51808`), so the tutorial game has a fixed id; the star-name pool grows from 999 to 1000 names; planet index 5 gets its three environment values (current and original copies) lowered by 5 and planet index 11 gets +20 on its first environment value (`:50515`-`50529`; the earlier text of this section called these "mineral-concentration" tweaks, but the bytes written are at planet offsets `0xc`-`0x11`, the environment fields, while the concentrations are at `0x9`-`0xb`); and at turn time the bundled scripted orders for slot 0 are read in place of a file and the nonce test of the general file validator is skipped (`turn-generation-engine.md` §1a, `save-turn-file-format.md` §10.6). **Bit `0x04` is the single-human-player flag**, not a relationship-table bookkeeping bit (corrected by the step-6 pass): at the end of game commit the code walks the slots, treats a slot as human when its computer bit (`0x200` of the slot word at +2) is clear or its category field is 7, gives every computer slot a fixed value in its 4-byte per-race number field (`:51783`; the value is deliberately not recorded), and sets `0x04` only if the walk completes with exactly one human (`:51775`-`51791`); when it is set, every ordered pair of distinct slots gets relation value 2 (`:51792`-`51802`). Consumers found: client menu/dialog choices (`:8197`-`8225`, `:46146`, `:98242`, `:98591`) and the Mystery Trader design roll after year 100 (`:115565`).

**Option-flag effects (bit of `DAT_1128_0080`; "creation" = galaxy generation and game commit, "turn" = the master routine, whose step numbers are those of `turn-generation-engine.md` §1 and §1b).**

| Bit | Option | At creation | During turn generation |
|---|---|---|---|
| `0x01` | Beginner: Maximum Minerals | every ordinary planet's three concentrations are 100 instead of 31-119, and the extra random boost roll is skipped (`:50533`-`50572`) | none |
| `0x02` | Slower Tech Advances | none | research costs double (buy loop, steps 12e/20/23g; salvage reward) |
| `0x10` | Computer Players Form Alliances | none | none in the master routine; read by the AI planning routines only |
| `0x20` | Accelerated BBS Play | every ordinary planet's mineral concentration below 40 gets +5 (`:50561`-`50565`); surface mineral tonnage +25% (`:50610`-`50617`); each home planet's starting population is multiplied by `(growth rate % + 5) x 2 / 10`, i.e. 4x at 15%, and its reported-population field rescaled to match (`:51007`-`51022`) | none |
| `0x40` | Public Player Scores | none | every player's files carry every race's score record once the turn counter exceeds 19 (step 39) |
| `0x80` | No Random Events | no wormhole pairs (`:51702`-`51710`; without the bit the pair count is a per-galaxy-size random draw) and no planet artifacts (without the bit, 1 planet in 3 carries the artifact flag, `:50488`-`50495`) | no comet, environment-shift, mineral-deposit or Mystery Trader-creation rolls (step 20), no artifact research bounty (steps 12d/23f); the special-object passes and the salvage rolls still run |
| `0x100` | Galaxy Clumping | the relaxation pass of §3 | none |

"Public Player Scores" and "Slower Tech Advances" also have client-side effects (score window, cost displays) that are outside this table.
2. **Player-slot assignment** — a grid of per-slot rows, each encoding a small state (open / default-unassigned-or-computer-controlled / a specific race assigned / a relation-table-linked assignment) plus a sub-index identifying which race or preset. See `client-ui-dialog-catalog.md`'s "Slot/equipment editor" family for the shared UI patterns this reuses.
3. **Victory conditions** — see `victory-conditions.md`.

### 2. Simplified setup

A single-screen path that auto-selects a reasonable player count scaled to the chosen galaxy size (roughly 2 players for the smallest galaxy size, up to 4 for a small galaxy, and 12-15 for a large one), using weighted random selection within that range rather than a single fixed default. It also seeds the victory-conditions year-gate meta-setting proportional to galaxy size (see `victory-conditions.md` §1).

### 3. Galaxy generation

Once settings are finalized, a single galaxy-generation routine runs:

- **Galaxy diameter** = `(gallaxySizeSetting + 1) * 400`, where the size setting is 0-4 — producing the diameters 400/800/1200/1600/2000 light-years for the five galaxy-size options. Confirmed by inspection of the exported client's real dialog resource, the five size options' exact labels are **Tiny / Small / Medium / Large / Huge**, and the density setting's exact labels are **Sparse / Normal / Dense / Packed** — both drawn from the "New Game" wizard's general page, which also carries a separate starting-position-distance radio group (**Close / Moderate / Farther / Distant**, not otherwise documented above) and standalone checkboxes for "Beginner: Maximum Minerals," "Slower Tech Advances," "Accelerated BBS Play," "No Random Events," "Computer Players Form Alliances," "Public Player Scores," and "Galaxy Clumping" (the anti-clumping relaxation-pass toggle referenced below). **Independently re-confirmed by direct observation of the running client (2026-09-10):** every label and control on this page (the "Advanced New Game Wizard - Step 1 of 3" screen, distinct from the Simplified path's own dialog) matched this static-resource extraction exactly, including a procedurally-generated default game name observed as two capitalized words (consistent with a "descriptive-word + descriptive-word" generator, though the underlying word list was not examined). Screenshot preserved at `docs/ui-reference/advanced-wizard-general-page.png`.
- **Star count** is derived from `diameter² / 5000`, then adjusted by the density setting with an additive quarter-scale term (confirmed formula: `count += round(count/4) * (density - 1)` for density settings above the sparsest, with an extra `+round(count/4)` again applied once more when density exceeds index 2, i.e. the two densest settings each add a further quarter-scale increment on top of the first), and hard-capped at **999** stars regardless of the formula's raw output.
- **Star placement** over-generates exactly `count/7 + count` candidate positions (capped at 999), applies rejection sampling against a minimum-separation distance derived from galaxy diameter, and — gated by one of the boolean option flags from §1 — runs an optional relaxation/anti-clumping pass afterward.

  **Confirmed by inspection of the exported client:** the relaxation pass is a per-star weighted-average repositioning, not a generic jitter. For each star (in placement order) it finds the closest other star, then blends the star's own coordinates toward that neighbor's coordinates with a distance-dependent weight: neighbors closer than ~144 (squared-distance units) pull with a 4:1 weight (new position ≈ 4 parts self + 1 part neighbor), neighbors between ~144 and ~626 pull with a roughly 1:1 weight (simple midpoint average), and neighbors between ~626 and ~1601 pull with a 2:1-toward-neighbor weight (new position ≈ 1 part self + 2 parts neighbor); no adjustment is made beyond that outer threshold. This runs as a single pass over all placed stars, not an iterative convergence loop.
- **Star naming** draws from a fixed pool of 999 unique names (extended to 1000 when one of the §1 option flags is set) with a duplicate-prevention bitmap.
- **Home-world mineral concentrations** are randomized to a value between 100 and 299 (inclusive) for each of the three minerals.

  **Confirmed by inspection of the exported client, not previously documented:** ordinary (non-home-world) planets use a different, lower-range formula for initial mineral concentration: the sum of two independent 0-44 random rolls plus a flat 31, giving a range of **31 to 119** per mineral — unless the "maximum minerals" option flag (§1) is set, in which case concentration is forced to a flat **100** for every mineral on every planet. Each planet's starting surface mineral tonnage is then separately randomized proportional to that planet's concentration (roughly `concentration × random(0-9) + 10`, with a further top-up roll if the result is under 200), and one of the other option-flag bits increases the resulting tonnage by a flat 25% when set.
- **Per-player starting fleet composition** is determined by a numeric "player type" code (values 0-9 observed, presumably corresponding to Human plus several built-in AI personality/difficulty presets — see `ai-opponent-behavior.md`), which selects which starting-ship templates get copied into that player's initial fleet.
- **Second home planet.** On non-smallest galaxies, a second home-world-tier planet is placed via a nearest-valid-position search (up to 100 attempts within galaxy bounds) — an asymmetric starting bonus tied to galaxy size rather than a universal rule. **Gating confirmed by inspection of the exported client (2026-09-23 pass), correcting the "player type" attribution above:** this bonus is not keyed to the numeric "player type" code from this section, but directly to the player's race PRT index (the same field/accessor used throughout `race-traits.md`) — specifically PRT 6 (Packet Physics) and PRT 7 (Interstellar Traveler) are the only two values that reach this code path, both gated on the identical galaxy-size condition, both jumping into one shared block of logic. See `race-traits.md` §2a for the full structural trace (distance-banded candidate search around the home star, reservoir-sampled selection, 100-attempt validity retry with a mineral-concentration fallback) and for the three-way PRT-index cross-check (Packet Physics=6, Interstellar Traveler=7) that resolves an earlier apparent contradiction between this bonus and a since-superseded dead-code finding.

This also confirms, rather than merely suggests, the closing hedge below: the wizard's non-numeric settings (Galaxy Size/Density/Starting Distance, player-slot race/relation assignment, game name/file) remain the only wizard-exposed settings with no batch-key equivalent found — the batch format's entire numeric surface is devoted to victory conditions and player setup, not a full proxy for every wizard page.

### 5. Player-slot record layout and per-category setup dispatch

**Confirmed by inspection of the exported client, upgrading this area from Partial to a confirmed mechanism:** each player slot is stored as a fixed **192-byte record** in a flat per-game array (one record per slot, up to the configured player-count maximum). A dedicated dispatcher routine drives slot initialization: given a slot index, it reads a 3-bit **category** field packed into the top bits of a 16-bit value at byte offset 2 of that slot's record, and switches on it to one of six distinct initializer routines (category values 0, 1, 2, 3, 4, and 5 are each handled by a separate routine; category 7 is handled by a seventh, simpler routine; category 6 is not handled — the dispatcher silently does nothing for it, consistent with an "empty slot" state). Two of the initializer routines (categories 4 and 5) additionally build a per-slot window title from a shared string template plus the slot's 1-based index, suggesting those two categories are the ones that can present the slot to the player as an interactive assignment rather than a fully automatic one.

This 3-bit "category" field is a **separate concept** from the "player type" code (values 0-9) described in §3 above that selects starting-fleet ship templates — the two were not confirmed to be the same field, and the bit widths don't obviously match (3 bits yields 0-7, not 0-9). Reconciling them is an open question.

Each of the six category-specific initializer routines follows a common shape: optionally load a preset AI race/personality template from a fixed resource table, assign the slot a unique display name (see below), then construct that slot's starting fleet by repeatedly invoking a shared "add starting ship template" helper with template-id and quantity arguments, where the quantities are scaled to galaxy size using linear formulas of the same shape seen throughout this cluster: a baseline count (typically 3-6) plus `(currentGalaxyScale - lowThreshold) / stepDivisor`, clamped to a per-formula maximum (typical caps observed: 12, 50). The concrete coefficients differ per category and per count (at least two independent scaled counts — an apparent "scout/detector" count and a separate "defensive escort" count — were observed within a single category's initializer), so no single formula covers all categories; each category has its own pair (or more) of baseline/threshold/divisor/cap constants applied to the same shared galaxy-size scalar.

None of the six category-specific initializer routines, nor the dispatcher itself, create or manipulate any dialog, window, or control (confirmed by an exhaustive scan for window/dialog-management calls across their full source range) — this corrects the earlier characterization of this area as containing "wizard dialog-control creation." The actual wizard dialog procedures that call into this dispatcher live elsewhere (most likely the "New/open-game dialog wrapper" already noted in the coverage report), not in this cluster.

**Correction to this section's own "add starting ship template" claim, found by reading two of the six category routines in full this pass.** The two sampled bodies (the category-0 and category-2 initializers) do **not** read as one-time "build this slot's opening fleet" logic on close inspection — they are shaped exactly like an ongoing, once-per-invocation *production-planning* pass: scaled thresholds gated by the current galaxy-size scalar (matching this section's own baseline/threshold/divisor/cap formulas, confirmed exactly — the caps this section already cited, 12 and 50, are these same routines' own computed values), followed by per-owned-planet loops that check mineral stockpiles, existing defense counts, tech-level thresholds, and RNG rolls before conditionally queuing production items via a shared helper. This is the shape of a per-turn AI economic-behavior routine (plausibly the concrete implementation of the six *personality/difficulty* categories this section already distinguishes from the "player type" concept), not a per-PRT starting-fleet builder — the "category" field these six routines dispatch on is, as this section's own next paragraph already notes, a different concept from PRT entirely. **The real per-PRT "add starting ship template" mechanism was located elsewhere this pass — see the new §5a below** — so this section's original claim that *these* six routines are what builds a slot's starting fleet should be treated as superseded, though it was not fully disproven (only 2 of the 6 bodies were read in full; the other 4 were not re-checked against this correction).

**Full confirmation this pass (2026-09-23): the remaining four category routines were read in full and match the same shape.** Category 1 (`FUN_1088_2350`, segment 18, dispatched at `FUN_1088_0000` line "`case 1:`"), category 3 (`FUN_1098_131a`, segment 20), category 4 (`FUN_10a8_0000`, segment 22), and category 5 (`FUN_10a0_0000`, segment 21) were each read start to finish. Category 1 opens with the identical galaxy-scale-gated baseline/threshold/divisor/cap formula shape already cited for categories 0/2 (the exact same scaled-count field layout, `DAT_1128_517c`/`517d`/`517e`/`517f`, is recomputed verbatim at the top of category 1's body, and again — with independent coefficients — at the top of category 5's body), then falls into a per-owned-planet loop (stride `0x1c`, iterating `DAT_1128_00b6`) testing mineral-stockpile subtraction (with an underflow/insufficiency check that aborts the item), tech-level thresholds indexed into the `DAT_1128_3fa3`/`DAT_1128_3f20` per-race-tech tables, and RNG-gated (`FUN_1040_1652`) branches before conditionally queuing production via the same shared `FUN_1090_2736` helper category 0/2 use — this is category 0's own shape almost line-for-line. Category 4 (`FUN_10a8_0000`) matches as well: the same baseline-plus-galaxy-scale formulas, the same per-planet mineral-stockpile-threshold loop (checking whether stored Ironium/Boranium are below fixed floors of 10 or 1000 depending on a per-planet type-nibble test), followed by a further per-fleet loop. Category 3 (`FUN_1098_131a`) differs in the *second half* of its body — after an initial planet loop and one or two galaxy-scale-gated `FUN_1090_2736` calls near-identical to category 0's opening, the bulk of the function is a per-*fleet* (not per-planet) task-dispatch pass: it walks the player's own fleet list and, for each fleet, evaluates and commits colonization (`FUN_1090_3c80`), reassigns/clears orders (`FUN_1090_19c8`), or scraps ships — still unambiguously an ongoing per-turn AI *behavior* pass (fleet-order AI rather than production AI), not a one-time starting-fleet seeder. **This closes out the open question from the paragraph above: none of the six category-dispatch routines build a slot's starting fleet; all six are per-turn AI personality/difficulty behavior passes (five production-planning, one fleet-order-planning), and §5a's mechanism remains the sole starting-fleet builder.**

### 5a. The real per-PRT starting-fleet mechanism (found this pass, 2026-09-23)

The actual "add starting ship template" helper — the one that gives each PRT a distinctive opening fleet — lives in the same galaxy-generation continuation routine already documented in §3 and in `race-traits.md` §2a for the Packet Physics/Interstellar Traveler second-home-planet bonus (segment 16, `FUN_1078_1334`). Immediately upstream of that routine's second-planet-placement code, for every player slot, it reads the slot's PRT index (the same field/accessor used throughout this project) and runs a chain of PRT-gated branches that call a single shared helper (`FUN_1078_39a8`) with a **template index** and a **flag byte**.

**The helper's real behavior, traced from its own body:** when the flag is nonzero, it treats the template index as an index into a **fixed, 22-entry table of named starting-ship designs** and copies that design record into the player's own per-race design array (appending at the race's next free hull-design slot — see `ship-design-and-components.md` §1 for the 147-byte design-record convention this reuses exactly), then returns the index the design landed at within the player's own array. When the flag is zero, the "template index" argument is instead one of those already-returned player-local indices, and the call just adds one more ship of that already-created design to the new fleet — this is the concrete mechanism behind Hyper Expansion's already-documented "3x colony ship": one call with the flag set creates the design, then two more calls with the flag clear and the same returned index each add another ship of it.

**The 22-entry template table itself was recovered directly from the executable.** It is static data in the same segment-2 data block `extracted-game-data/component-stats.tsv` already documents (base offset `0x8a6` relative to that segment, file offset `0x3ae6` in `stars.exe`, confirmed by direct inspection), one 147-byte record per entry, immediately followed — with no gap — by that TSV's own 32-entry "Ship hulls" table (category `0x4000`, at the already-documented base `0x1548`/file offset `0x4788`), which is what pins the entry count at exactly 22 (0-21). ### 6. Unique-name assignment and home-star selection helpers

**Confirmed by inspection of the exported client:** a shared helper assigns each newly-initialized player slot a unique display name by repeatedly picking a random name from a fixed candidate range and checking it against the names already assigned to other slots (checked against either a small subset or the full roster depending on a per-slot flag). It retries up to roughly 20 times; if no unique name is found in that many attempts, it falls back to appending a random two-digit numeric suffix to a chosen candidate name rather than continuing to retry indefinitely.

A separate shared helper selects a slot's home star. It first builds a per-star eligibility marker for every star in the galaxy: unclaimed stars are marked available (or diplomatically-blocked, if a scan of existing fleets finds a hostile presence there under certain relation settings), stars already owned by the slot being initialized are marked as such, stars owned by other slots are marked as such, and stars found to contain another empire's defended fleet are separately marked blocked. It then searches all "available" stars for the one with the minimum squared distance to a target anchor position and returns that star's index (or -1 if none qualify).

**Correction — the following is not part of home-star selection at all, despite an earlier pass's placement of it in this section.** A separate isolation-distance check exists with these exact thresholds: given a candidate star, it finds the closest other not-yet-claimed star and rejects the candidate outright if that distance exceeds roughly 353 light-years (a 350-ly threshold), rejects it with roughly 50% probability between roughly 300 and 353 light-years, again with roughly 50% probability between roughly 250 and 300 light-years, and always accepts distances below roughly 250 light-years, gated to only apply once the galaxy has more than 59 stars. A later pass traced this check's only two call sites in the entire executable and found both are deep inside the AI's **per-turn, per-owned-planet production/expansion-planning loop** (reached through the same PRT/personality dispatch documented in `ai-opponent-behavior.md`), not inside new-game setup — the candidate star being tested is one of the current AI player's *already-owned* planets, evaluated turn after turn to decide whether to queue further expansion-oriented production (e.g. scouts/colonizers) from it, not a prospective home star being chosen once at game start. The likely real intent: "is this planet too isolated from any remaining unclaimed star to be worth investing further expansion production in," not an anti-isolation rule for the starting empire's placement. See `ai-opponent-behavior.md` for the fuller AI production-planning context this check belongs to; this document's own home-star-selection helper above does not appear to use it.

### 7. New-game start commit — correction: this is the client's single master turn-generation routine, not a new-game-only function

**Previously described here (and in the coverage report) as a small "new-game start commit" step; re-examined this pass and substantially corrected.** The routine itself does begin exactly as previously documented: it switches to a busy (hourglass) cursor, then validates the entered game name/file-name against existing files; on failure it restores the cursor, shows an error status message, and aborts without side effects. On success it shows a "creating game" status message, then scans the player-slot array (192-byte records, as in §5) for any slot whose top status bits are non-zero. If **every** slot's status bits are still zero (i.e., no slot was ever configured — an edge case, not the normal path), it falls back to clearing/reinitializing those status bits uniformly across every slot in the array rather than leaving them undefined. It then sets up the game's core runtime buffers (an approximately 12,000-byte and an approximately 25,000-byte buffer, plus a per-star buffer sized at 2 bytes per star), guarded by what is structurally an error-recovery/unwind checkpoint (a saved-and-restored global context pointer plus a per-call stack buffer, consistent with a setjmp-style checkpoint rather than a simple "already initialized" flag) — so this setup step is best read as "run once per top-level attempt, with a clean abort path back to cursor-restore-and-return on internal failure," not as a one-time-only guard.

**This is not, however, a routine exclusive to game creation.** Tracing this routine's callers found it invoked from four separate sites elsewhere in the client, all of them turn-generation commands rather than new-game commands: the manual single "Generate Turn" command, and the batch **10/100/1000-turns-in-a-row** commands already documented in `turn-generation-engine.md` §8 (the batch loop's abort-on-held-key polling and remaining-turn counter are directly visible around these call sites). Past the buffer-setup step described above, the same routine's body goes on to drive the home-star/unique-name assignment already documented in §6, then calls this segment's five sibling routines (see `turn-generation-engine.md`'s new note on segment 23) to run per-planet ownership refresh, per-fleet fuel/docking and waypoint-task/Stargate-transit processing, and a large per-fleet task-dispatch pass, interleaved with calls into segment 24's own galaxy/production machinery — and finishes by writing every active player's next-turn file and freeing the turn's scratch buffers. In other words: **this single function is the concrete master "Generate Turn" routine** described in `turn-generation-engine.md` §1 (whose old 23-phase list has been replaced by the reconciled 40-step order), not a small setup-only helper — it is reused as-is to produce a new game's first turn and every subsequent turn alike. This corrects and significantly expands the coverage-report's one-line description ("verifies game name resource, initializes default player/race flags across player slots"); that description was not wrong about what happens during new-game creation specifically, but it covered only the first few hundred lines of a much larger routine.

### 8. Save-game filename dialog (correction to a prior mischaracterization)

**Correction, verified against the exported client:** the function previously described (in the coverage report) as "pipe-delimited race-string parsing for a race-selection list" is not that. It is a standard Windows **Save-As common file dialog** invocation (`GetSaveFileName`) for saving the in-progress game/host file. The `'|'`-delimited string it manipulates is the ordinary Win16/Win32 file-dialog filter string idiom: since a string-table resource cannot embed literal NUL bytes, the filter's description/pattern pairs are stored with `'|'` as a placeholder and the code walks the buffer replacing each `'|'` with `'\0'` immediately before passing it to the OS call. No race data is parsed here. The same segment also contains a set of small generic accessor helpers (get/set with a clamped value and an independent high-bit flag) operating on the same 192-byte-per-slot player table described in §5, plus the routine that resets all new-game settings to their documented defaults and immediately regenerates the galaxy (confirmed defaults on reset: galaxy size = smallest, density = sparsest, a starting-distance-like setting = index 2, and a fixed option-flag bit pattern applied unconditionally).
