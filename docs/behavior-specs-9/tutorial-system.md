# New-Player Tutorial / Advisor Sequencer

Behavior specification for the built-in new-player tutorial system in the 1995-2000 4X game *Stars!*. This document is derived directly from the exported client's decompiled logic; it is new material, since no prior document in this set covers the tutorial. Facts are described in generic terms; no original identifiers or literal code are used.

## Overview

A scripted, turn-gated hint sequencer drives a persistent "coach" overlay during a player's first several dozen turns, waiting for the player to perform an expected action before advancing to the next step. It is implemented as a state machine layered on top of the ordinary game UI, separate from the tutorial window's own message-routing code (`client-ui-dialog-catalog.md`'s "Tutorial surface" entry describes the outward-facing window; this document describes the underlying sequencer that drives it).

## Mechanics

### 1. Lesson/step structure

Progress is tracked as a **lesson index** (observed range 0 through roughly 29) and, within a lesson, a **step index** that always advances in multiples of 8 (observed up to roughly 568, i.e. about 15 sub-steps per lesson). **Confirmed by direct inspection of the exported client: the lesson index is not a separate stored field at all — it is the master turn/year counter itself, read directly, not merely correlated with it.** The master counter was identified by tracing the turn-generation engine's year-counter increment (step 33 of the reconciled order in `turn-generation-engine.md` §1; evidence `stars.exe.export.c:72186`), which happens after all simulation steps and before the victory-condition evaluation (step 35, described in `victory-conditions.md` §2) and the per-player turn-file generation (step 39). The per-(lesson, step) validation dispatcher documented in §2 below (`FUN_10f8_0b5c`, `stars.exe.export.c:104665`, with a counterpart at `stars.exe.export.c:107847`) branches directly on that turn counter's value, with the step index selecting sub-cases within each turn-numbered case. The "skip tutorial before turn 30" gate described in §3 reads the same counter: `FUN_10f8_0b22` (`stars.exe.export.c:104640`-`104657`) only lets the skip-confirmation prompt be bypassed once the counter has reached 30. No separate lesson-index storage location exists anywhere in the tutorial segment.

A debug/design-mode override flag exists that, when set, makes nearly every condition-check helper in the sequencer automatically report its expected condition as already satisfied — consistent with a development/testing shortcut rather than anything reachable through normal play.

### 2. Advancement conditions

A large family of "has the expected game/UI state been reached" condition-checker functions gates step advancement: whether a particular planet or fleet is currently selected, whether a specific dialog page is open, whether a production-queue slot contains an expected item, whether a specific research field is selected, and a general per-lesson "visited" bitset. One dedicated dispatcher maps specific (lesson, step) pairs to hard-coded expected production-queue item identifiers — i.e., certain tutorial steps require the player to have queued one specific kind of component or ship, not just "any" production action.

### 3. UI presentation

- The tutorial overlay's paint routine draws up to **8 tabs** (a breadcrumb-style progress bar across lessons), highlighting the currently active one.
- On first show, the dialog buckets the available screen width into 4 size classes (thresholds around 800/1024/1280 pixels) to choose its own layout.
- A debounced popup mechanism caps any single repeated hint message at **3** occurrences, to avoid nagging the player with the same message indefinitely if they don't perform the expected action.
- Skipping the tutorial before turn 30 is gated behind an explicit confirmation prompt.
- Turning the tutorial off temporarily saves and restores roughly 26 bytes of UI/mode state (a "demo mode" swap) and toggles one associated menu item's checked state.

### 3a. Tutor and panic-recovery dialogs, confirmed by inspection of the exported client's real dialog resources

The tutorial overlay's persistent window (captioned as the game's "Tutor") exposes exactly three controls: a **Hide** button (dismisses the overlay), a **Hint** button (surfaces contextual help for the current step), and a **Panic!** button. The Panic button opens a distinct, larger dialog whose caption conveys that something has gone badly wrong; it offers three recovery choices, each paired with a static line of explanatory text next to it (paraphrased here):

- **Redo Turn** — explains that it discards all of the player's changes and restarts the turn from scratch.
- **Complete Turn** — explains that it restarts the turn and performs every required tutorial task automatically, so a stuck player can still see the results.
- **Never Mind** (the dialog's default/cancel-equivalent choice) — explains that it closes the dialog with no changes.

A fourth static line documents the dialog's own **Help** button: it opens context-sensitive help for the task the player is stuck on, the same as the Tutor window's own help button. This confirms the panic dialog is a tutorial-only escape hatch (an automated "do the rest of this turn for me" recovery path) rather than a general error-recovery surface, and that its three choices are the complete set — no other recovery options exist.

### 3b. Recovered lesson content, from the decoded dynamic string table

Now that the client's dynamic string table is fully decoded (see `dynamic-string-table.md`), the per-(lesson, step) dispatcher described in §2 can be read against real recovered text rather than structure alone. The dispatcher's own validation switch (keyed on the lesson index and, within it, the step index) resolves failure paths to roughly two dozen distinct "you haven't done the expected thing yet" hint strings, each of which is a genuine, previously-unrecoverable window into what a given lesson actually expects the player to do. Representative, concrete examples (paraphrased, not quoted verbatim beyond short illustrative fragments per this project's clean-room rules):

- One step requires the player to have queued a ship design carrying a specific engine, three of a specific beam weapon, two of a specific armor, a fuel tank, and a battle computer.
- Another step requires a design built around a specific engine, a specific scanner, and two mining modules.
- Another requires a design with a specific engine and three of a specific mine-dispersal component.
- Another requires a design with a specific engine, eight of a specific bomb, and a fuel tank.
- Two separate steps require the player to rename a ship design to one specific exact name each (one step's expected name maps to a "mine-layer"-themed design, the other to a "gate"-themed design); a further step name-checks a "Zip Order" transport preset against one specific exact name.
- Other steps check for: selecting the correct hull in the hull/ship dropdown, selecting the correct fleets before a Merge Fleets command, having actually been prompted to merge fleets that year before allowing the merge, loading the correct cargo before departure, and giving a fleet the correct waypoint destination and waypoint task (including one step that explicitly expects the "no task" placeholder rather than a real task).
- A dedicated final-lesson message confirms completion and explicitly permits the player to keep playing the current game or start a new one from the file menu — i.e., the tutorial does not force an exit or a new game afterward.
- The tutorial's own persistent overlay window title is a formatted string combining the Tutor name with the current page number out of a fixed total of 80 pages — an exact, previously-unknown total step count (roughly consistent with, and more precise than, this document's earlier "~568 max step index / 8 ≈ up to ~71 sub-steps" estimate).
- A distinct, separate confirmation prompt (outside the per-step dispatcher) gates leaving the built-in tutorial game early, warning the player that doing so will discard the in-progress tutorial game.

This content confirms the dispatcher is checking concrete, specific ship designs, names, and orders (not generic "did the player do anything" checks), and gives a real per-step content sample even though the surrounding instructional/narrative prose the player reads before each step (the actual "lesson text") does not appear to be stored in this same string table — see the Open Questions update below.

### 4. Auto-advance

A dedicated routine can auto-advance through lessons automatically (without waiting for player input) until either player input becomes genuinely required or the lesson index exceeds its maximum bound. This same routine is called from at least one other UI surface (the Score dialog) as a generic "notify the tutorial system something happened" hook, suggesting the tutorial sequencer listens for state changes broadly across the client rather than only from its own window.

### 5. The tutorial game's marker bits and bundled scripted orders (added by the turn-generation step-6 pass)

Two flags identify the tutorial. `DAT_1128_078a` bit `0x800` is the client's "tutorial in progress" state (it gates tutorial menu and window code, e.g. `stars.exe.export.c:6831`, `:8033`, `:8080`). Bit `0x08` of the game-option word `DAT_1128_0080` marks the *game file* as the tutorial game: game creation then keeps a fixed game id instead of seeding it from the tick count (`:51803`-`51808`), so files can be prepared in advance for it, and hand-tunes two planets and the star-name pool (`new-game-setup.md` §1). The orders loader uses that fixed id: while the host generates a tutorial turn, for slot 0 only, `FUN_1048_7c66` first tries a bundled resource (type 10000, id `0x2711`, `:30709`-`30739`): if the turn counter is below the resource's leading count byte, the records of the counter-th group (groups start at type-8 header records, the same layout as an orders file, `save-turn-file-format.md` §10) are read instead of the player's `.x1` file. This is the only place the executable ships pre-made turn orders; which player slot the human occupies in the tutorial, and the scripted orders' content, were not traced (the resource is not part of the decompile). The "Complete Turn" and "Redo Turn" recovery buttons of §3a were not connected to this loader.

## Open Questions

- ~~Whether the lesson index is genuinely identical to the turn counter, or merely correlates with it, was not conclusively established.~~ **Resolved — see §1 above.** The lesson-validation dispatcher switches directly on the master turn counter's own storage location; there is no separate lesson-index field.
- **Partially resolved by the now-decoded dynamic string table (see §3b above).** The per-step *validation/correction* text — what a given step expects the player to have done, phrased as a "you got this wrong" hint — is now recovered in full for every step reachable through the per-(lesson, step) dispatcher (roughly two dozen distinct hint strings, several naming exact ship designs, exact components, and exact required names). What remains unrecovered is the *positive* instructional prose a player would read before attempting each step (the actual lesson text explaining what to do, as opposed to the correction shown after doing it wrong): an exhaustive search of the tutorial segment's own calls into the shared string-lookup routine found only 3 direct calls (one of them the page-*n*-of-80 title format), plus the validation dispatcher's own ~26 hint identifiers — no separate block of ~30 lesson-introduction paragraphs was found anywhere in the decoded table. The likeliest explanation is that this instructional text is not stored in this string table at all (e.g. it may be composed from a combination of the recovered hint strings themselves, from generic UI-help sources not specific to the tutorial, or from a resource this pass did not examine); this remains a genuine gap, now narrower and better-characterized than before rather than fully closed.

  **Follow-up pass — checked directly against the plain dialog-resource text (raw executable, not the decompile), with a further negative result.** This project has independently recovered several genuine plain-text (uncompressed) dialog resources elsewhere in this exact binary — the Tutor window and panic-dialog captions and explanatory lines documented in §3a above among them — confirming that at least some UI text in this client bypasses both compressed string tables entirely and sits as ordinary static control text inside a `DIALOG` resource. A direct byte-level scan of the shipped `stars.exe` for long runs of printable ASCII (independent of the decompiled `.c` export, which does not reliably preserve resource-segment text) was run at two thresholds (15 and 20+ consecutive printable characters). The method is validated by what it *does* find: the panic-dialog explanatory lines already paraphrased in §3a turn up cleanly in the raw scan, confirming plain dialog-resource text really is recoverable this way when it exists. Filtering the results for tutorial/lesson-shaped language (openings like "You", "Now", "First,", "Before you", "Select", "Choose", "Build", "Design", instructional verbs, etc.) surfaced **no candidate lesson-introduction paragraphs anywhere in the binary** — only already-known short UI strings (dialog captions, menu items, the two panic-dialog lines already documented). This is a genuine, if not fully exhaustive, negative result: the positive pre-step instructional text does not appear to exist as recoverable plain text in the shipped executable at all, in either compressed string table or as static dialog-resource text. Combined with the string-table search already recorded above, this strengthens (without finally proving) the conclusion that this content was cut, externalized to a file this project does not have, or never shipped as separate text from the hint strings in the first place — not merely stored somewhere this project hasn't looked yet.
