# Diplomacy and Inter-Race Relations

Behavior specification for the inter-player relationship system in the 1995-2000 4X game *Stars!*. This document is derived directly from the exported client's decompiled logic; it is new material, not a correction to any existing specification, since no prior document in this set covers diplomacy. Facts are described in generic terms; no original identifiers or literal code are used.

## Overview

Every ordered pair of races (race A's opinion of race B, distinct from race B's opinion of race A) has exactly one stored relationship value, editable by the player via the same order-submission path a built-in AI race could in principle use, but — per §3's findings, and now confirmed by a full inventory of the AI's own decision code (see Open Questions) — no built-in AI personality actually exercises that path in this build; the value is not otherwise adjusted automatically by gameplay events either. The relationship value gates whether two races' fleets can peacefully "meet" at a shared location, and is the basis for how a Battle Plan's "legitimate enemies" setting resolves into an actual list of hostile races during combat.

## Mechanics

### 1. Relationship states

Exactly **three** relationship states exist, editable via a small dialog offering three mutually-exclusive choices. The states are stored as one byte per ordered (race, other-race) pair. Based on how the stored value gates other systems' behavior, the three values correspond to **Neutral** (the default), **Friend**, and **Enemy**. **The exact on-screen labels are now confirmed:** `client-ui-dialog-catalog.md`'s plain dialog-resource extraction recovered the real dialog caption **"Player Relations"** and the exact three radio-button labels, in their on-screen order, **Friend / Neutral / Enemy** — this is static MENU/DIALOG resource text, not dynamic-string-table content, so it was recovered independently of (and before) this project's dynamic-string-table work.

- A newly created race's relationship row toward every other race initializes to the default (Neutral) value.
- The relationship table is referenced from roughly twenty distinct places across the game's logic — colonization/meeting eligibility and Battle Plan enemy resolution consult it, but the built-in AI's decision code does not: a raw scan of the AI driver segments finds no reference to the table, and the "Computer Players Form Alliances" option only biases AI target choice toward human-owned targets (`ai-opponent-behavior.md` §12) (an originally-suspected "turn-generation relations-decay pass" was searched for exhaustively and is now believed not to exist — see §3). **Now individually enumerated (confirmed by a later pass):** the byte-per-ordered-pair table is confirmed stored at offset 0x5A32 of the per-race record block, as one 192-byte row per race holding one byte per other race; its ~20 read-only consumers were traced to two segment-23 turn-generation functions (meeting/exchange eligibility and remote-mining/merge/Stargate interaction gating), a cluster of Battle-Plan/combat-adjacent gating call sites (including a live per-fleet "legitimate enemies" bitmask builder and a single-pair legitimate-enemy check used during combat setup), and the "Player Relations" dialog's own radio-button UI — matching every category already described in this section. Its only two confirmed *write* paths are: the turn-file relationship-write opcode described in `save-turn-file-format.md` §3 (fed by the dialog's own commit routine, confirmed to be exactly this table, not a similarly-shaped but distinct one), and the per-race row reset to Neutral performed when a race's record is (re)initialized. A dedicated search found no other writer anywhere in the client (§3).

### 2. Relationship changes are queued orders

Changing a relationship is submitted as a queued turn order (the same generic order-queuing mechanism used for fleet waypoints, production-queue edits, and other player actions) rather than mutating the relationship table immediately — the change takes effect at the next turn generation, alongside every other player's submitted orders.

### 3. No automatic relationship decay was found

**Revised finding, superseding the previous framing of this section.** An exhaustive search (detailed under Open Questions) found no evidence of an automatic per-turn decrement of the stored relationship byte anywhere in the client. The relationship value is best understood as **purely player-set-and-forget**: it only ever changes because a human player, via the "Player Relations" dialog, explicitly picks a new Friend/Neutral/Enemy state, or because a race's relationship row is (re)initialized to Neutral at creation — a later pass (see Open Questions) confirmed that no built-in AI personality ever submits this kind of order itself, so "AI race choosing to submit the same kind of order" should be read as a mechanism the order-queuing path would support in principle, not one any AI driver in this build actually uses. There is no evidence of it drifting on its own over time, and no evidence of a "war declared" notification tied to a decay crossing a threshold. This section previously described a decaying "aggression counter" on the strength of general community knowledge about the *Stars!* design rather than anything observed in this binary; that description is now believed to have been an incorrect inference for this specific game, not a confirmed mechanism (see Open Questions for the full evidentiary basis, including a caveat about what was *not* checked).

### 4. Relationship gates "meetings" between fleets

A fleet sitting in orbit of a foreign planet, or co-located with a foreign fleet, is only acted on by the end-of-battle orbital-bombardment pass (`turn-generation-engine.md` §4) when a dedicated relationship check between the fleet's owner and the planet's owner passes; the exact rule of that check was not re-derived here, and no cooperative colonist/mineral/fuel exchange mechanic has been found.

### 5. Battle Plan "legitimate enemies" resolution

A Battle Plan's enemy-selection field (see `combat-resolution.md`) is a single small numeric category, not a per-race checklist as might be assumed from a plain "list of races considered legitimate enemies" description. The observed categories are:

- **None** — no race is targeted regardless of relationship.
- **Every race with an Enemy relationship** to the plan's owner.
- **Every race with an Enemy or Neutral relationship** (i.e., "everyone except my Friends").
- **All races**, regardless of relationship.
- **Exactly one specific race**, chosen individually.

So for three of these five categories, which races actually count as "enemies" for that Battle Plan is derived live from the relationship table at the moment orders are evaluated, rather than being an independent list stored per plan. Changing a relationship can therefore change who a fleet on an unmodified Battle Plan will engage, without the plan itself being edited.

    - `FUN_10b8_4138` — a string/path-building routine that assembles a backup-file name using the turn counter; entirely unrelated to race relationships and contains no reference to the table.
    - `FUN_10f0_111a` — a per-fleet cargo/plunder decay routine (decrements a captured-cargo-like value toward zero by a percentage each turn) gated on a per-fleet flag array; operates on a single-fleet-indexed field, not a race-pair matrix, and contains no reference to the relationship table's offset.
  - None of the five exhibits the doubly-race-indexed (both loop bounds over race count) access pattern required, matching the same negative result as the eight candidates ruled out in the prior pass.
  - **A full-file search for every remaining reference to the literal table offset (`0x5A32` / `23602`) was then done, independent of the phase-6-19 orchestration window entirely**, covering all ~29 occurrences of that constant across the whole decompile. This surfaced a few additional read consumers not individually named before (a Battle-Plan-owner's live "legitimate enemies" bitmask builder that scans all races for each fleet's owner, and a single-pair "is this specific race a legitimate enemy" helper used during combat setup) — both are read-only and consistent with the already-documented consumer categories (§1), not new writers.
  - Critically, **only two sites in the entire decompile ever assign a new value to this byte** (as opposed to merely reading/comparing it): (1) the "Player Relations" dialog's radio-button command handler, which writes the clicked Friend/Neutral/Enemy choice directly into the current player's row and sets a "dirty" flag, later consumed by a dedicated commit routine that packages that same row into the turn-file relationship-write opcode (`save-turn-file-format.md` §3) when the dialog closes — i.e., exactly the "queued order" mechanism described in §2, now traced end to end from UI click to outgoing order; and (2) a blanket loop that sets every entry in one race's row to 0 (Neutral), found inside a large routine that also resets that race's production summary, mineral-concentration defaults, and similar per-race state in the same pass — i.e., the already-documented "a newly created race's row initializes to Neutral" behavior (§1), now with a concrete source location. **No third writer exists, and neither of these two writers performs a decrement or is gated on a battle/treaty-breaking event** — both are exactly the two mechanisms already described elsewhere in this document (player edit, and row initialization).
  - A further structural observation argues against the original premise itself: every one of the ~29 references to this byte compares or assigns it only the values 0, 1, or 2 — there is no evidence anywhere that the byte is ever treated as a wider-range counter capable of gradual decrement, which is what "decaying aggression counter, clamped at its bounds" would require. This is consistent with the byte being a pure 3-state enum, not a decayable scalar.
  - **Given this — two independent full sweeps (orchestration-window call tree, and every literal reference to the storage offset) both turning up zero decay writers and zero evidence the field is anything but a 3-state, player/AI-order-driven enum — this is now assessed as a likely-incorrect original inference, not an unresolved search.** The prior framing of §3 was apparently based on general community knowledge of *Stars!*'s design (which does describe relationship drift in some contexts) rather than anything observed in this specific binary. The residual uncertainty is narrow: an AI race could still choose, via its own aggression/diplomacy logic, to submit an ordinary relationship-change order (mechanically identical to a human player's dialog edit) in response to game events — that would not be a "decay" in the sense §3 previously described (a blind per-turn drift with clamps and a war threshold), and no such AI decision logic was specifically traced in this pass; only the storage/write side of the relationship table itself was exhaustively searched. If a future pass wants to fully close this out, the remaining work is to check the AI's own diplomacy/aggression decision code (as opposed to the table's storage and consumers, which are now believed fully enumerated) for any logic that automatically triggers this kind of order.
  - **This residual question is now closed, by a later pass cross-referencing `ai-opponent-behavior.md`'s own newly-completed inventory of AI decision code.** That document's §1 (this pass) pinned all seven built-in personality-driver functions by address (`FUN_1088_0462`, `FUN_1088_2350`, `FUN_1098_0184`, `FUN_1098_131a`, `FUN_10a8_0000`, `FUN_10a0_0000`, `FUN_1098_0000`) and the shared production/starbase passes they all funnel into. Separately, the turn-file relationship-write opcode named in §1 above (`0x26`) is emitted from exactly **one** call site in the entire decompile — a single call to the order-record writer `FUN_1048_66f0` inside `FUN_1048_5f10`, passing the current player's whole relationship row — and `FUN_1048_5f10` itself has exactly **one** caller: the Player Relations dialog's window procedure (segment 31), specifically its handler for one particular dialog notification, gated behind a "user actually changed something" dirty flag that only the dialog's own radio-button click handler sets. No personality-driver function, no shared AI pass (starbase management, threat assessment, production planning, colonizer-commitment budgeting, etc.), and no other code path anywhere in the binary calls either `FUN_1048_5f10` or emits opcode `0x26` directly. Combined with §1's already-exhaustive finding that only two sites ever write the relationship byte at all (both attributable to this same human-UI path or to race-row initialization), this rules out AI-driven relationship-change orders definitively rather than merely by absence-of-evidence: the single emission path for this order is entirely contained inside the human-facing "Player Relations" dialog's own commit logic, with no AI code anywhere upstream of it. **This document's diplomacy/relationship-change mechanism is therefore confirmed purely player-initiated — human or (mechanically) AI-editable in principle via the same order-queuing path, but in this build, AI personalities do not exercise that path.**
