# Turn Generation Engine

Behavior specification for the "Generate New Turn" pipeline in the 1995-2000 4X game *Stars!* — the batch process that runs once per turn, after every player's orders are collected, to advance the game state and produce the next turn's files. This document is derived directly from the exported client's decompiled turn-processing logic; no public source documents the exact phase ordering or the mechanics below, so this is presented as new material rather than a correction to an existing specification. Facts are described in generic terms; no original identifiers or literal code are used.

## Overview

Turn generation is a single, strictly ordered master routine. It does not resolve all of one player's actions and then move to the next player in a naive way — instead, it runs a fixed sequence of *phases*, each phase sweeping across every relevant object (fleet, planet, race) once, before the next phase begins. This phase ordering matters: a fleet that is destroyed in the battle phase, for example, can no longer be acted on by phases that run afterward.

## Mechanics

### 1. Phase order

The master per-turn routine executes, in this order:

1. **Open and validate submitted order files** for every player; abort with an error if the turn file cannot be read.
2. **Randomize AI/player processing order** for the turn (a full reshuffle of the player index list, not a fixed slot order).
3. **Load and validate each player's submitted turn file** in that randomized order, with progress reported to the player generating the turn.
4. **Detect and flag duplicate/conflicting player identity records** (e.g., name/password collisions between two player slots).
5. **Tech-field "reveal" pass** — for every player, any technology that has become newly visible (e.g., due to scanning an enemy design using it) is flagged as known.
6. **Fleet-flag reset and starbase-reveal pass.**
7. A general per-fleet recompute pass (capability/statistics refresh).
8. **Hull-upgrade cascade** — up to 8 repeated passes propagating any automatic "fleet composition promoted to a newer type" changes until the fleet list is stable.
9. **Combat-detection and resolution pass** — every location with a multi-race fleet stack not already flagged is checked for a hostile-race conflict (see `combat-resolution.md`); if found, the battle-resolution engine (§2 below) runs for that location. This phase is followed immediately by the fleet-meets-foreign-colony exchange pass (§4 below).
10. **Diplomacy/relations decay** — every ordered pair of races has its stored relationship-aggression counter decremented toward neutral, clamped at its bounds; crossing a threshold triggers a "war declared" notification to both parties. (See `diplomacy-relations.md`.)
11. **Economic/production turn pass** — remote-mining and waypoint-task execution across every fleet, described in `production-queue.md` and `fleet-movement-scanning-cargo.md`.
12. **Random map-feature/event pass** (first of two identical passes at steps 12 and 16) — see §5.
13. **Fleet movement execution** — the actual per-fleet movement resolution for the turn (warp travel, fuel consumption).
14. **Home-planet-related fleet-flag pass.**
15. **Further economic passes**: mass-packet/minefield processing (§3), colonization-tie-break resolution, research allocation (all described in their respective sections/specs below).
16. **Second random map-feature/event pass.**
17. **Starbase refuel pass** — fleets docked at a friendly starbase, or carrying ramscoop-type engines, have their fuel adjusted: ramscoop engines contribute a flat 200 fuel per engine while docked/in transit, offset against a mass/cargo-driven burn rate.
18. **Second fleet-flag-reset/scan pass**, also clearing each fleet's first waypoint slot once reached.
19. **Further economic passes and an autosave/checkpoint operation.**
20. **Turn/year counter increment** — the master turn counter advances here, roughly two-thirds of the way through the overall turn-generation sequence, not at the very start or end.
21. **Per-player turn-file generation** — builds each player's next-turn output file and notifies them it is ready.
22. **A per-race numeric computation**, executed twice per player against two different record tables, with the result squared. **Now resolved: this is not the score/ranking computation it was speculatively flagged as, and is not the victory-condition check either (see below) — it is a per-ship-design "capability rating" feeding production-queue auto-build eligibility.** The code (`stars.exe.export.c:72270`-`72333`, immediately after the victory-condition evaluation call described in `victory-conditions.md` §2) walks, once per race, both the 10-slot starbase-design table and the 16-slot regular-hull-design table (the same 147-byte-record, 16+10-slot layout documented in `save-turn-file-format.md` §3) — this is what "twice... against two different record tables" refers to, not two calls to one function. For each occupied design slot it computes a normalized ~0-100 "capability rating" (`FUN_1048_57b6`, `stars.exe.export.c:28428`, for starbase designs; `FUN_1038_337e`/`FUN_1038_4e50` for regular-hull designs) by summing a per-component value across the design's installed components plus race-trait-gated bonuses, stores `100 - rating` per design (`stars.exe.export.c:72284`), and then squares that stored value in place (`stars.exe.export.c:72288`-`72290`). This squared per-design field (design-record offset `0x87`) is later *read*, not by any score or victory-condition code, but by production-queue auto-build eligibility checks (`FUN_1090_2db6`, `FUN_1090_2e52`, `FUN_1090_2e94`, `stars.exe.export.c:63096`-`63189`), which treat "squared value > 0" as "the race owns a suitable, non-maximal-rated design of this category" when deciding whether certain auto-build production items are available. `victory-conditions.md`'s own victory-check function (`FUN_10b8_3bbc`) was independently read in full this pass and does not perform this per-design squaring anywhere in its body — the two are confirmed to be genuinely separate pieces of logic that merely happen to run back-to-back in the master routine.
23. **Cleanup** — frees turn-processing scratch memory, restores UI state.

### 2. Battle resolution engine

Combat is resolved by a dedicated routine invoked once per location with a detected hostile-race conflict. Its structure:

- Two growable, persistent "battle log" record pools are ensured to exist (allocated on first use).
- A scratch table tallying per-race, per-design-slot ship-stack quantities is built from the fleet ring at that location (a same-location "linked stack" of every fleet present), including the defending planet's starbase if it is a valid combat participant.
- The full combatant roster is built by flattening every ship stack present — one aggregate record per (race, design) pair with quantity > 0 — computing each aggregate's derived combat statistics (armor/shield/cloak/jamming totals, etc.) via shared per-design stat functions.
- **The battle runs for up to 16 rounds** — an explicit, hardcoded loop bound. This directly confirms the round cap already documented (from public sources) in `combat-resolution.md`.
- Within each round, a per-ship "rate"/initiative value is computed with rounding that depends on the round number's parity (odd/even), then combatant firing order is reordered by a shared "priority" computation. Targeting scans distances/ranges across up to 3 weapon-range brackets per shot.
- Damage is logged into the growable event log as it's applied (not computed all at once), and after the round's shots resolve, a resource-salvage step calls into the production-planning subsystem (`ai-opponent-behavior.md` §6-adjacent logic) to decide whether destroyed-ship minerals should be pulled toward nearby friendly production needs.
- After the battle concludes, a message/outcome-selection routine picks from roughly 20 distinct message codes describing the aftermath (destroyed participants, salvage available, etc.) per race present.

**This confirms the 16-round cap directly from the executable, independent of the public FAQ material `combat-resolution.md` was originally built from.** A later, dedicated pass over segment 31 (`FUN_10F0_*`) went further than this section's original scope and did fully decode several of the specific formulas flagged here as unconfirmed — see `combat-resolution.md` §§6 and 8 for the details, summarized here:
- **The accuracy formula is now confirmed and arithmetically cross-checked** against `combat-resolution.md`'s own worked numbers (`FUN_10f0_41ca`, segment 31) — it combines base accuracy, computer bonus, and jam via a subtractive-cancellation-then-branch formula, reproducing all three documented percentages exactly.
- **The armor-quantization scheme's apparent mismatch (7-bit field found vs. 1/512 claimed) is resolved**, not just re-confirmed: the field is a packed 16-bit word whose low 7 bits and high 9 bits serve two different purposes, and the high 9 bits (explicitly clamped to 0–499 in code) give a real granularity of 1/500 — close to, and likely the real source of, the documented 1/512 figure.
- **The energy-capacitor beam-damage bonus's mechanism (not its exact percentage) is now confirmed**, and the "one missile, one kill" salvo-accounting aside was checked against the actual missile damage-application path and found to have no distinct code-level counterpart — the whole-ship-kill division formula appears to govern missile kills the same way it governs beam kills.
- **The beam APN's RangeModifier term and the Battleship-specific firing-order quirk's generality were specifically searched for as part of this pass and not found at the time** (the relevant code was large enough that this was reported as "not found" rather than "confirmed absent"). **Both have since been resolved by a later pass — see `combat-resolution.md` §4/§5/§8:** the RangeModifier term is confirmed absent from the APN formula (a full re-read found the distance value used only as a binary in-range gate, discarded before the APN math), and every hull is confirmed to fire its weapon slots in plain stored array order, not a Battleship-specific special case.

Separately, the battle-replay ("VCR") viewer that players use to watch a completed battle is confirmed to be **pure play-back**: it reads the round-by-round event log built above (token position, a "beam fired" or "missile fired" flag, and a raw damage/delta value per event) and only ever *displays* pre-decided outcomes — it performs no targeting, accuracy, or damage computation of its own. The viewer's own grid-drawing and hit-testing code independently confirms the battle board is exactly a 10×10 grid, with each token's position packed as one 4-bit column and one 4-bit row value.

### 3. Minefields and mass packets

Processed once per turn as part of the economic passes:

- **Mass-packet decay in flight**: a percentage of a packet's mineral cargo is lost each turn, scaled by the packet's warp-speed tier (roughly 10%/25%/50% for increasing speed tiers), and halved for a specific racial trait. On arrival (or when flagged for detonation), a packet's remaining cargo is delivered to (or impacts) planets within its blast radius.
- **Minefield regrowth and collision**: each turn, minefields regenerate some mine-unit strength, then two collision passes check every free-flying fleet and every fleet stationed at/orbiting a planet against every enemy minefield in range: a squared-distance test against the field's radius, with damage/mine-loss scaled by field "type" (a heavier field type inflicts roughly a third the normal mine-loss-to-damage ratio of an ordinary field), decrementing the field's strength and possibly destroying it if depleted. Both affected races are notified.
- **Minefields are edited via the same order-queuing mechanism used everywhere else** — a minefield-window command issues a turn order that is applied during this pass, rather than mutating the minefield immediately.
- **Mine-laying rate, confirmed by inspection of the exported client.** A fixed lookup table gives a base per-component mine-laying rate keyed by component category and subtype, with observed values **20, 40, 50, 60, and 70** (units per component per turn, before fleet-wide weighting by ship count); one specific component category instead reads a rate directly from that component's own data rather than the fixed table. A fleet's total mine-laying output is a ship-count-weighted average of its installed mine-layers' rates, passed through a further piecewise scaling curve that flattens toward a cap around **98%** for large fleets — the exact real-world meaning of this final scaling step (a diminishing-returns efficiency factor, distinct from the raw per-component rate table) was not conclusively resolved.

  **Follow-up pass — the rate function itself was read in full and contains no such curve; the "98%" claim could not be relocated this pass.** `FUN_1080_1aea` (`stars.exe.export.c:57210`-`57311`), confirmed as this project's own citation for the per-component rate formula (cross-referenced from `fleet-movement-scanning-cargo.md`'s "Lay Mine Field" entry), was read line-by-line in its entirety: it walks each occupied design slot, accumulates `shipCount × perUnitRate` (with a flat ×2 for one mine-type category, `stars.exe.export.c:73296`-`73298` equivalent logic inline at `57296`-`57298`) into a running total, and returns that total ×10 at the end (`57305`-`57308`) — a plain weighted sum with a flat doubling case, no percentage curve, no asymptotic cap, and no reference to ship count except as the linear weight already described. Reading forward from both of its call sites inside `FUN_10b0_3f3a`'s Lay Mine Field handler (`stars.exe.export.c:75916`, `75937`) turned up one nearby scaling step that *is* real but does not match the "flattens toward 98% for large fleets" description: at `75941`-`75943`, the combined per-type rate is unconditionally **halved** (`lVar18 = CONCAT22(uVar34,uVar14) / 2`) unless a specific fleet-status flag (bit `0x20` of the fleet's status byte, set once per fleet the first time `FUN_10b0_1f8c` visits it that turn, `stars.exe.export.c:73370`) is already set — a flat, binary 50% cut tied to a per-fleet "already had its first pass this turn" flag, not a fleet-size-dependent curve. No other scaling step, percentage table, or asymptotic-cap arithmetic was found between the rate computation and the point the value is written into a minefield's strength field. **This pass could not locate the "flattens toward ~98%" mechanism this document previously described**, and offers this as a genuine, checked negative result rather than a further guess: either that finding belongs to a different code path this pass's search of `FUN_1080_1aea` and its two call sites did not cover, or it was a misreading of the flat ÷2 halving documented here (which is a binary flag gate, not a curve, and does not asymptote toward 98% or any other fleet-size-dependent bound). A future pass should treat the "98%" figure as unconfirmed pending a fresh source.

**Where laid mines are actually applied, confirmed by inspection of the exported client.** This rate formula only produces a per-turn mine-unit *quantity* for a fleet executing a Lay Mine Field order; the previously-missing other half — searching for (or creating) the target minefield and adding that quantity to it — is implemented inside segment 23's `FUN_10b0_3f3a`, documented in `fleet-movement-scanning-cargo.md`'s "Segment 23's largest function" note.

### 4. Colonization simultaneous-arrival and fleet/colony exchange

- **Simultaneous colonization tie-break.** When multiple fleets from different races arrive at the same uninhabited location in the same turn, the arrival with the largest accumulated population/quantity wins the colonization race; an exact tie between the largest two contenders results in **no one** colonizing that turn. All races present are notified of the win/lose/tie outcome.
- **Fleet-meets-foreign-colony exchange.** Once per turn, for every fleet sitting in orbit of a planet it does not own, where the diplomacy/relations system (`diplomacy-relations.md`) permits a "meeting" and the fleet is neither cloaked nor hostile, a probabilistic exchange of colonists/minerals/fuel occurs between the fleet and the planet. The resulting notification message differs depending on whether the colony belongs to the fleet's own race or a foreign one — the game maintains two parallel sets of outcome messages for this distinction.

### 5. Random turn events

Once per race per turn, gated behind a roughly 50%-plus base chance, the game rolls for **at most one** random empire-wide event from two independent tables:

- A **13-entry table** of percent-chance-weighted events, each with its own enable flag and per-race "already triggered" tracking so a given event fires for a given race only once.
- A **6-entry table** of counter-vs-threshold events that, on success, generate and accumulate a numeric reward.

Only one event total fires per race per turn (a flag prevents both tables from firing the same turn for the same race). Concrete, gameplay-recognizable events identified among these include:

- **A "comet strike"-style event** (roughly 1-in-20 base chance per eligible turn): randomly shifts an eligible planet's three environment axes (Gravity/Temperature/Radiation) by magnitudes in roughly the 50-350 range, and separately adjusts mineral concentration.
- **A simpler, related environmental-shift event** using the same 1-in-20 gate but a single randomized delta rather than three.
- **A "new mineral deposits discovered"-style event**: chance scales with the game's current year, bumps a mineral-concentration value up by roughly 5-20 (capped near the top of the concentration scale).
- **A "Mystery Trader"-style wandering-ship spawn**: gated to no earlier than roughly turn 39, with further modulo-100/128 "special turn" windows or an even-turn-only fallback; spawns a new fleet-like object at a random galaxy position with a partially tech-gated component loadout (higher-tier components suppressed in early appearances, becoming more likely to appear as the game year advances), and broadcasts its appearance to every race.

**Per-race "already triggered" tracking and notification, confirmed by inspection of the exported client.** A dedicated routine (`FUN_1118_1196`, segment 36) takes one event's bit-flag value, ORs it into that race's stored per-race event-history bitmask (confirming the "already triggered" mechanism operates as a persistent per-race bitmask, one bit per distinct event, rather than a counter or timestamp), and maps that same bit value to one specific notification-message code plus a packed icon/detail value — 11 distinct single-bit values were recovered with individually mapped message codes, consistent with (though not conclusively proving an exact count for) the 13-entry table described above. This confirms the per-event notification message a player receives is looked up from a fixed bit-to-message table rather than being freely composed per event.

**The table's exact size and the two remaining unmapped bits, resolved by tracing the dispatcher's own caller.** `FUN_1118_1196`'s only "roll and check" call site (`FUN_10f0_61a2`, segment 31) draws its per-turn event index with `FUN_1040_1652(0xd)` — a bounded random draw over exactly **13** values (0-12) — independently confirming the table's size as exactly 13, not merely "roughly." That same call site ORs `1 << index` into the per-race history bitmask before ever reaching the dispatcher, so the dispatcher's own bit-value switch is indexed identically. Reading `FUN_1118_1196` in full shows it explicitly special-cases bit values `0x0002` through `0x0800` (indices 1-11 inclusive, 11 values, each with its own message code) but has **no dedicated arm for index 0 (bit `0x0001`) or index 12 (bit `0x1000`)** — both of those fall through to the same generic default message code the function also uses for any out-of-table value. In other words, the two entries this document previously flagged as "the remaining ~2 unidentified bits" are now pinpointed precisely: they are the table's first and last entries, and structurally they are distinguishable from the other 11 only in that they share a single generic notification code rather than each getting an individually chosen one — they are not missing from the table, just less individually surfaced by it. Which of the concrete gameplay events named above (if any) these two indices correspond to was not established in this pass.

**Follow-up pass — the shared fallback traced forward to its actual displayed text, with a partial, honestly-caveated result.** `FUN_1118_1196`'s return value (this project's "message code," `0x10b` for the default/fallback case) is not itself the final message-store type code: its one caller, `FUN_10f0_61a2`, adds a fixed `0x2f` to it before logging (`FUN_1030_7444(param_1, CONCAT22(local_8, iVar3 + 0x2f))`, `stars.exe.export.c:103009`), so the fallback's real, stored type code is `0x10b + 0x2f = 0x13a` (314 decimal). `extracted-game-data/message-strings.txt` row 314 reads: *"Examination of wreckage from the battle at \n uncovered plans for a new part to place on your ships."* This is a genuine, gameplay-plausible flavor event (salvaging tech from an old battle site) not previously among this document's four named events, and is the concrete text a player would see for indices 0 and 12 if this reading is right. **The honest caveat, checked directly rather than glossed over:** this exact same type code (`0x10b`/314) is *also* what 9 of the *other* 11 individually-mapped bit values (every mapped case except bit `0x100`, which instead yields type code `0x10c`/315 — "...uncovered plans for a new ship hull" — and bit `0x400`, which yields `0x10f`/318 — a ship-dismantled/tech-discovered variant) resolve to as well; only the packed icon/detail parameter passed alongside it (`param_3`, e.g. `0xcb04`, `0xc608`, `0xcc04` for the default case) differs between these 9 slots and the fallback. So at the message-*type* level, indices 0 and 12 are not uniquely distinguished from most of the table's other entries — they share the same generic "battle-wreckage" template text, differing only in a numeric detail/icon parameter whose own meaning (which system, which specific part) was not decoded this pass. This is offered as a real, traced answer to "what text/context does the fallback path carry" (as asked), while being explicit that it does not uniquely fingerprint indices 0/12 against the rest of the table by severity or icon alone.

**Follow-up pass — a systematic review of message-strings.txt confirms no hidden distinct text exists for indices 0/12, but a separate, already-completed cross-document finding answers what they concretely *grant*, which is more informative than text-matching could be.** `FUN_1118_1196`'s own body (`stars.exe.export.c:115815`-onward) was already read in full by a prior pass (see `ship-design-and-components.md` §14a) and shown to be an exhaustive `if`/`else if` chain with individually-assigned messages for bit values `0x02`-`0x800` (indices 1-11) plus one bit-0-and-everything-else fallback — a hard, code-level proof, not an inference, that indices 0 and 12 mechanically cannot reach any text other than the row-314 fallback already traced above; no amount of further message-string review can turn up a "hidden" distinct text the dispatcher itself is not wired to produce. A scan of every other random-event-flavored string near row 314 in `message-strings.txt` (rows 300-320) turns up only the already-attributed rows 314/315/318 and unrelated combat/construction text, confirming this negative directly rather than by code inspection alone.

What the systematic pass *does* newly connect is more useful than a text match: `ship-design-and-components.md` §14a independently discovered (while investigating an unrelated question, the ship-design "ability" gate `FUN_10d8_4b8e`) that this exact per-race bitmask and dispatcher pair is **also** the record of a **one-time, per-race, per-component random component grant** — reused verbatim from a second call site, the wormhole heavy-cargo-transit routine `FUN_1118_0784` (this document's own §9, `stars.exe.export.c:115653`), which independently re-rolls `FUN_1040_1652(0xd)` (0-12) until it lands on a bit not already set in the same field, then calls the identical `FUN_1118_1196`. `FUN_10d8_4b8e` (`stars.exe.export.c:91837`-`91913`) reads the same 13-bit field and maps 12 of its 13 possible bits (`0x0001` through `0x0800`, i.e. **indices 0-11**) to 12 specific, named components (Multi Cargo Pod, Multi Function Pod, Langston Shell, Mega Poly Shell, Alien Miner, Hush-a-Boom, Anti Matter Torpedo, Multi Contained Munition, Mini Morph, Enigma Pulsar, Genesis Device, and Jump Gate, in bit order — see that document's §14a table), each becoming buildable for a race only once its corresponding bit is set. **This directly identifies index 0's real gameplay effect, despite it sharing the generic fallback notification text with 9 other indices: winning index 0 grants the race the Multi Cargo Pod component.** Index 12 (`0x1000`) falls *outside* this 12-bit component table entirely (which only spans bits 0-11), matching `ship-design-and-components.md` §14a's own conclusion that "the 13th slot most plausibly grants a bare tech-level bump with no attached component" — consistent with index 12 carrying no named-component payload and, like index 0, only ever surfacing the generic wreckage-flavor text. This resolves the practical version of the open question (what do indices 0 and 12 *do*, not just what text they print) more concretely than a string-matching pass could have: index 0 = Multi Cargo Pod grant; index 12 = a component-less reward, plausibly a raw tech bump. `ship-design-and-components.md` §14a should be treated as the canonical source for this mechanism's component side; this document's own framing of the 13-entry table as purely "empire-wide flavor events" undersells it — several of its slots are one-time part/hull unlocks, not narrative-only events.

**A fourth confirmed event, reconciled from `combat-resolution.md` §8's "genuinely new, uncategorized mechanic" flag: a racial-trait-gated fleet/planet attrition event, structurally distinct from the two tables above.** A prior pass sampling segment 31 found a per-turn routine that reduces fleet cargo-like fields and planet mineral-concentration-adjacent fields by a random percentage, and flagged it as unreconciled with this section rather than merging it speculatively. Tracing its one call site and internals resolves it as follows:

- **Not part of either the 13-entry or 6-entry table above.** It is invoked directly from the master turn routine as its own step, immediately preceding the phase-20 turn/year counter increment (§1) — i.e., it runs once per turn near the very end of the sequence, not during either of the two "random map-feature/event pass" phases (12 and 16) that the two tables above are gated behind. It also carries no "already-triggered" bit — unlike every event in the two tables above, it can fire repeatedly for the same race across many turns, not just once per game.
- **Gating.** The whole routine is skipped unless at least one race in the game has a specific stored per-race flag (bit 2 of a per-race status byte, structurally similar to — but a different field from — the per-race relationship/trait bytes documented in `combat-resolution.md`'s "legitimate enemies" note); which named racial trait this corresponds to was not established (no surviving string data). It is further gated on the turn/year counter exceeding a fixed value of 9 — i.e., it cannot fire before turn 10, an early-game grace period consistent in shape with the "roughly 50%-plus base chance...gated" framing used for the two tables above, though this event uses a hard turn floor rather than a percentage chance for its outer gate.
- **Fleet effect.** For every fleet belonging to a gated race that is not already flagged removed: a 1-in-12 roll flags the fleet as destroyed/removed outright and logs one message code; otherwise, three consecutive stored numeric fields on the fleet (a cargo-like triple, offset and stride consistent with a 3-mineral-type cargo hold) are each independently reduced by a random 10-20% (a single per-fleet roll of 10 + random(11), reused for all three fields), with a floor of at least 1 unit lost per field if the field is positive; if any field was reduced, a second, distinct message code is logged.
- **Planet effect.** For every planet whose owner race is gated: most of the time, a further 1-in-15 roll reduces one randomly-chosen field of a different stored triple (offset and stride consistent with mineral-concentration-adjacent storage, distinct from the fleet-side triple) by a random 5-45% (5 + random(41)), logged via its own message code; in the remaining, rarer case (roughly 1-in-8, reachable only when that planet's triple is not already zeroed), a packed sub-field embedded in two adjacent stored bytes is instead reduced by a random 5-35% (5 + random(31)), with a floor of 1, logged via yet another distinct message code.
- **Four distinct message-log notification codes in total** are used across the fleet-destroyed, fleet-field-reduced, and two planet-side branches, each appended through the same message-record-store append routine documented in `client-ui-dialog-catalog.md`'s "Messages" section — confirming this event surfaces to the player exactly like an ordinary logged event, not silently.

This is a real, fourth confirmed per-turn random-effect mechanism, additional to the two event tables already documented above — not a variant or extension of either. `combat-resolution.md` §8 has been updated to note the reconciliation and point here rather than carry an open item.

**Follow-up pass — the gating "racial trait" identified, and the premise revised: it is not a Primary or Lesser Racial Trait at all.** The routine itself is `FUN_10f0_111a` (`stars.exe.export.c:98704`-`98846`), confirmed by direct inspection to match every previously-documented behavior above line-for-line (the per-race gate, the turn-10 floor, the 1-in-12 fleet-destroy roll and its message, the shared-percentage three-field cargo reduction, and the two planet-side branches). Its gate reads, per race: `local_2c[i] = (byte)(DAT_1128_5a16[i*0xc0] >> 2) & 1`, i.e. **bit 2 (mask `0x4`) of the per-race status byte `DAT_1128_5a16`** (`stars.exe.export.c:98736`-`98738`) — confirming the bit position this document already cited. Cross-referencing this exact field against every other reader/writer of `DAT_1128_5a16` in the decompile (60+ sites) shows it is *not* the PRT-index field (that is a separate field, per-player record offset `0x3e`, read through the shared `FUN_10e0_222c`/`FUN_10e0_226e` accessors documented throughout this project — e.g. `race-traits.md` §1a, `ship-design-and-components.md` §8) and is not an LRT bitmask either (LRTs are read through the same `0x4e`-offset 32-bit field `research-tech-tree.md` and `race-traits.md` both cite for Generalized Research/Ultimate Recycling/Bleeding Edge Technology). `DAT_1128_5a16` is instead a general-purpose per-race status byte with several unrelated bits (bit 0 gated dozens of unrelated per-race checks throughout the client; bit 1 is §9's own gating bit, see the revision there; bit 3 is the "already fired a random event this turn" flag `FUN_10f0_61a2` itself sets, `stars.exe.export.c:103011`/`103045`; bit 4 appears once more, unexamined this pass) — a scratch/flags byte, not a trait table.

**What bit 2 concretely does elsewhere strongly suggests it is a copy-protection/integrity status flag, not a gameplay trait.** The identical bit, on the identical field, is independently tested at `stars.exe.export.c:73381` (inside `FUN_10b0_1f8c`, see §10's new note below) where — on a turn-staggered, per-race roll — it logs message type `0x102`, which `extracted-game-data/message-strings.txt` row 258 gives as *"`\s` has refused to move, doubting your authority to rule. Press the 'Goto' button to enter your UNIQUE Stars! serial number and assert your authority."* This is the same "doubting your authority" family as message rows 257 (productivity/growth penalty, also a serial-number prompt) and 259 (fleet-movement strike, also a serial-number prompt) — a cluster of penalty notifications this project has not previously traced to code, sitting alongside the two copy-protection notices (`dynamic-string-table.md`'s identifiers 279/386) this project has already, deliberately, chosen only to note the existence of rather than explain. Bit 2's write site was not traced (consistent with this project's standing house rule never to document how the Serial Number/tamper check itself is computed), but its *read* sites are unambiguous: this is a status/penalty flag family, not a Primary or Lesser Racial Trait, and the attrition mechanic's "racial trait" framing above should be read as superseded by this finding — it is gated by a copy-protection-adjacent per-race status bit, consistent in shape with the other documented penalties in the same message family (reduced productivity, halved growth, refused movement, fleet strikes — fleet/planet attrition is a plausible fifth penalty in the same cluster). Per this project's standing rule, no further detail on how or when the flag is set is pursued here.

**The 6-entry counter-vs-threshold table's contents, resolved by tracing its second roll in full.** `FUN_10f0_61a2`'s second roll (`stars.exe.export.c:103016`-`103049`, immediately following the 13-entry-table roll documented above) draws a field index 0-5 with `FUN_1040_1652(6)`, then compares a per-race, per-index byte counter (stored at `race*0xc0 + index + 0x59dc`) against a global per-index threshold byte (`DAT_1128_257c[index]`). This is **not** six independent gameplay events: the counter storage at `0x59dc` is the same per-race array the Technology Browser dialog (`BROWSERDLG`, confirmed by cross-reference against `client-ui-dialog-catalog.md`'s "Technology Browser" entry) reads and paints with the labels **"Ener:", "Weap:", "Prop:", "Const:", "Elect:", "Bio:"** (dynamic-string identifiers 91-96, i.e. the six research fields from `research-tech-tree.md` in their documented order) — so the table's six "slots" are simply the six tech fields, each independently eligible once its field-specific counter is below the threshold. On success, `FUN_10d8_1580(index, counter+1, race)` (`stars.exe.export.c:89438`) computes a reward equal to `(sum of the race's six tech-field counters) * 10 + costTable[counter+1]`, where `costTable` is a per-level dword lookup at `0x630` shaped like the tech level-cost constant referenced by `research-tech-tree.md` §3's `totalLevels` formula; the raw reward is then scaled by a per-race-trait modifier (`FUN_10e0_222c` checked against trait value `index+8`) and doubled outright if a global option bit (`DAT_1128_0080 & 2`) is set. The result is accumulated — not overwritten — into a persistent per-race, per-field 32-bit total (`DAT_1128_59e2`/`DAT_1128_59e4`, word stride `0x30` per race) and a message is logged (type code `0xfffe`) via the shared message-append routine documented in `client-ui-dialog-catalog.md`'s "Messages" section. **Important caveat:** the per-race, per-field counter this roll gates on and reads (`0x59dc`) is never incremented anywhere in this code path — only compared — so this event does not appear to actually grant a tech level; it produces and banks a resource-like reward value whose ultimate real-world consumption (e.g. feeding into phase 7's research allocation, versus being a pure flavor/bounty number) was not traced further this pass. The same `0x59dc` counters and `DAT_1128_59e2`/`DAT_1128_59e4` accumulator are also read (not written) by an unrelated debug/inspection routine (`FUN_10d8_4a86`/`FUN_10d8_49c6`, `stars.exe.export.c:89753`-`91750`) that is not reachable through normal turn generation.

**Resolved — the banked reward is genuinely spent, not merely logged.** `DAT_1128_59e2`/`DAT_1128_59e4` (the accumulator this event banks its reward into) is the same per-race, per-field memory `research-tech-tree.md`'s already-documented ordinary research buy-loop, `FUN_10b8_4ce4`, reads as its **starting spendable pool for that field, that turn**: at `stars.exe.export.c:80069`-`80072`, the buy loop takes `local_20 = (undefined4*)((int)(undefined2*)&DAT_1128_59e2 + iVar10)` and immediately reads `*local_20` as `local_e`, the pool value its "price the next level, subtract, loop" logic (already described in that document's "Exact overflow/carryover rule" note) spends down. This is confirmed to be the identical field, not merely a same-named coincidence, by cross-checking the *other* known writer into it: the Super Stealth passive-bonus code inside the same function (`stars.exe.export.c:80017`-`80035`) adds its bonus into `puVar13 + 0x10` (words) off a per-race base of `&DAT_1128_59c2`, and `&DAT_1128_59c2 + 0x10 words (0x20 bytes) == &DAT_1128_59e2` exactly — i.e. the Super Stealth bonus (already documented as feeding directly into the ordinary research pool) and this event's banked reward (written at `stars.exe.export.c:103029`-`103033`) both deposit into the same array the buy-loop reads from. **This settles the open question: the banked reward is not a pure flavor/bounty number — it is added to the race's genuine per-field research resource pool and is spent by the same buy-loop, on the same carryover terms, as ordinary turn-to-turn research income**, including the possibility of buying more than one tech level in a turn if the combined pool is large enough (per that document's own confirmed carryover behavior).

### 6. Mineral Alchemy auto-conversion (Alternate Reality)

Distinct from the manually-queued "Mineral Alchemy" production item documented in `production-queue.md`, races with the Alternate Reality primary trait receive an **automatic, non-queued** per-turn conversion: any leftover planetary resources beyond a threshold are converted directly into minerals at a race-specific ratio (`resources * ratio / 100`, where `ratio` is a per-race stored byte), with any local shortfall optionally transferred in from a linked planet.

### 7. Research allocation

Once per turn, per race, accumulated research resources are applied to whichever field(s) the player has selected (see `research-tech-tree.md`), advancing tech levels and firing a level-up notification. Any resource surplus left over after an initial allocation pass is redistributed in a second pass, so a turn's research spending is not strictly capped by the exact cost of the next level in the primary field — genuine overflow carries within the same turn into the next field or the next level.

### 8. Turn-generation UI entry points, confirmed by inspection of the exported client

The main menu's command dispatcher confirms several turn-generation-adjacent features not previously documented anywhere:

The loop polls the keyboard each iteration and lets the player abort the batch early by holding down a key — there is no separate "cancel batch" dialog, just a held key.

### 9. Fleet-linked habitat-tolerance drift (one specific primary trait)

A per-turn pass, gated to run only when at least one race in the game has a specific primary racial trait, drifts that race's stored per-gas habitat-tolerance value by exactly **±1 per turn** (clamped to the 1-99 range) for fleets meeting certain field thresholds, under three combined random gates (roughly 1-in-3, 1-in-10, and 1-in-1000 chance checks together with threshold comparisons), notifying the race when a shift occurs. A related calculation can also adjust per-gas values directly. This reads as a "race's tolerance genome gradually shifts based on fleet exposure" mechanic tied to one specific PRT, not previously documented anywhere; which named trait this is was not confirmed (no string data survives to check against `race-traits.md`'s PRT table).

**Trigger identified, cross-confirmed against `fleet-movement-scanning-cargo.md`'s "Heavy-fleet transit arithmetic" note.** This is the *same* drift routine invoked from the fleet-vs-wormhole heavy-cargo check documented there: a fleet carrying 5000+ kT of minerals through/at a wormhole computes a tier (6-10, one step per further 1200 kT, adjusted down by the transiting race's own gas-tolerance-sum), and that tier becomes this pass's per-iteration count for the drift loop described above — heavier mineral cargo means more drift iterations for that race this turn. The "gated to run only when at least one race has a specific primary racial trait" condition in that same code path corresponds to a race whose *entire* 6-value gas-tolerance array already exceeds a threshold (a broadly gas-tolerant race), which is instead diverted to a separate 20%-chance fleet-relocation branch rather than the drift loop — so the drift mechanic itself runs for *ordinary* (non-exempt) races, triggered specifically by heavy mineral-cargo wormhole transits, not by a flat per-turn roll independent of fleet activity as the "per-turn pass" framing above might suggest.

**Resolved by a later pass, and the "specific primary racial trait" premise overturned — cross-referenced here from `fleet-movement-scanning-cargo.md`, which had already settled this independently.** Reading `FUN_1118_0784` (`stars.exe.export.c:115255`-`115814`) directly at the threshold-selection point (`stars.exe.export.c:115354`) shows the "26 or 10" gas-tolerance-sum threshold used by the "broadly gas-tolerant race" exemption above is not a PRT-index comparison at all: `local_1a = (-(uint)((DAT_1128_5a16[race*0xc0] & 2) == 0) & 0x10) + 10` — the threshold is chosen by **bit 1 (mask `0x2`) of the same per-race status byte, `DAT_1128_5a16`**, this document's §5 "fourth event" gating bit now identifies as a copy-protection/status field rather than a trait table (see §5's new finding there). No call to the confirmed PRT-index accessor (`FUN_10e0_222c`/`FUN_10e0_226e`, reading player-record offset `0x3e`) appears anywhere in this threshold-selection code path, and any race of any PRT can enter the "all six clear" exemption branch if its own rolled tolerance values happen to be wide enough. **This means the drift mechanic documented in this section is not gated by a Primary Racial Trait at all** — the premise this section originally set out to resolve does not hold up under direct inspection. `DAT_1128_5a16` bit 1's own write site was not traced (per this project's standing rule around the copy-protection-adjacent status bits on this same field), but by analogy with bit 2's confirmed role (§5) and this field's other observed uses — gating a reduced research-level cap at `stars.exe.export.c:80138`-`80145`, and a percentage adjustment inside population-growth-adjacent code at `20983`/`76404` — bit 1 is plausibly a second, related status/penalty flag on the same byte rather than an independent gameplay trait; this reading is offered as well-evidenced, not certain. This section's title and framing ("gated to run only when at least one race has a specific primary racial trait") should be read as superseded: the mechanic is a per-race tolerance-data comparison, modulated by this status-byte bit, not keyed to a named PRT.

### 10. The master routine's concrete identity, confirmed by inspection of the exported client

The 23-phase pipeline above is not spread across an unidentified set of routines: it is implemented, concretely, by a single function plus five sibling routines all living in one segment, previously catalogued in `code-coverage-report.md` and `new-game-setup.md` §7 under the mischaracterization "new-game start commit." That routine is confirmed (by its four call sites — the manual "Generate Turn" command and the batch 10/100/1000-turn commands of §8 above) to be the client's actual master turn-generation entry point, reused verbatim to produce a new game's first turn and every later turn. Of its five sibling routines in the same segment:

- One drives a per-planet ownership-flag refresh and calls into a separate large (~560-line) fleet-vs-wormhole mineral-cargo-transit routine (documented in `fleet-movement-scanning-cargo.md`'s wormhole-transit note) — i.e. phase-adjacent bookkeeping wrapped around an already-documented mechanic living in a different segment, not a new mechanic itself.
- One implements a per-fleet docking/fuel pass matching phase 17's **starbase refuel pass** closely enough to treat as confirmed: fleets not validly docked at an allied starbase are checked for ramscoop-type engine components contributing fuel.
- One hosts the already-documented **waypoint-task execution / Stargate cargo-transit-restriction** mechanic (`fleet-movement-scanning-cargo.md`'s "Waypoint-task feasibility" and Stargate sections — phase 11), confirmed to be reached through this same master routine rather than a separately-running turn-loop function. It also contains a further large per-fleet block (mining/fuel-capacity-style bookkeeping with a per-slot RNG-gated stochastic pass) whose exact real-world mechanic was **not** conclusively identified this pass; it superficially resembles §9's habitat-drift shape (per-gas-type loop, comparable RNG odds) but is a separate, unconfirmed piece of logic — §9's own drift mechanic's traced call chain runs through segment 36 (`FUN_1118_0784`, see `fleet-movement-scanning-cargo.md`), not through this function, so no correction to §9 is being made here.

  **The stochastic sub-block itself, structurally identified this pass.** This routine is `FUN_10b0_1f8c` (`stars.exe.export.c:73289`-`74079`); its per-slot RNG-gated block sits at `stars.exe.export.c:73472`-`73560`. It is gated to fleets whose hull/design record carries a specific "class" byte (the high nibble of a byte at offset 6 within the hull record reachable from the fleet, read as `*(byte*)(hull+6) & 0xf0`) equal to `0xa0` — a value distinct from the `0xb0` class checked immediately nearby in the same function for starbase-like hulls, but whose real-world hull category was not otherwise identified. For such a fleet, the block walks up to 16 component slots, skipping component-type codes `7`, `8`, `9`, `0xe`, and `0xf` (categories excluded from this effect), and for every remaining installed unit in a slot rolls `FUN_1040_1652(10)` — a flat 1-in-10 chance of that individual unit being lost this turn. Per-slot losses are tallied; if every slot's quantity is reduced to zero across the whole design, the fleet is flagged destroyed/removed (bit `4` of its status byte) and a distinct message (type code `0xe1`) is logged through the shared message-append routine; if only some components are lost, the fleet's derived combat/capability statistics are recomputed (`FUN_1050_6e52`) rather than the fleet being removed. This reads as a genuine, previously-undocumented **per-component attrition/breakdown mechanic** — structurally distinct from all four random events already catalogued in §5 and from §9's habitat-drift mechanic — gated to one specific, unidentified hull class. Which hull class carries byte value `0xa0`, and therefore which ships this attrition actually applies to, remains unresolved.

  **Follow-up pass — the exact byte address was pinned down precisely, but the cross-reference against `extracted-game-data/component-stats.tsv` this raised did not resolve the hull name.** The "`hull+6`" phrasing above is a `long*`-stride artifact of how the decompiler typed the pointer, not a literal byte offset of 6: tracing the pointer chain from the fleet record shows `local_50` (the variable actually indexed) is computed as `designBase + 4` (`stars.exe.export.c:73375`-`73377`, `designBase` itself read as a cached far pointer stored directly in the fleet record at byte offset `0x64`), and `*(byte*)((long*)local_50 + 6)` therefore reads the byte at `designBase + 0x1c` (28 decimal) — the same byte independently confirmed at line `73380` (`*(byte*)(iVar8 + 0x1c) & 0xf0`, `iVar8` being `designBase` itself). So the real target is **record-relative offset `0x1c`** of whatever `designBase` points to, not offset 6.

  Whether `designBase` is the per-owned-design (147-byte, `ship-design-and-components.md` §1) record or the static per-hull-*type* definition table (`extracted-game-data/component-stats.tsv`'s "Ship hulls"/"Starbase chassis" combined 37-entry, 143-byte-stride table, per `ship-design-and-components.md`'s own §"hull-type index" note) was not conclusively determined this pass — the fleet record's cached far pointer could plausibly be either, and both are 143-147 bytes. Checking the raw offset against the static table's own documented layout does not yield a clean answer either way: the table's universal per-category header only defines offsets `0`-`7` (an ordinal plus six tech-prerequisite bytes) before the 32-byte name field begins at offset `8`, so offset `0x1c` (28) falls **inside that name-text region** for every one of the TSV's 32 extracted hull records (whose six prerequisite bytes are all `0`, confirming the name field truly starts at `8` for this category) — not a plausible location for a single classifying "hull class" byte. This suggests either (a) `designBase` is not this static table at all, or (b) the 143-byte hull/starbase-chassis table's internal layout diverges from the generic per-category header past the shared 8-byte prefix (consistent with the TSV's own header note that "hull records additionally carry a slot array" and other extra structure beyond the generic layout). Cross-referencing `component-stats.tsv` as instructed therefore did not identify a named hull this pass — it narrowed the question (the real offset is `0x1c`, not `6`) without answering it, and is recorded here as a well-evidenced negative result rather than a resolution.

  **Resolved by tracing the pointer's origin at its call sites precisely, as instructed — and the premise of the original either/or question turns out to be false.** `designBase` (the fleet record's cached far pointer at byte offset `0x64`) is **neither** the static hull-definition table **nor** the per-owned-design 147-byte record directly — it is a small, **per-fleet, heap-allocated, growable array of design-stack entries**, private to that one fleet record, unrelated to either fixed table by storage location. This was established by tracing every site that allocates, resizes, or copies this exact field (all identifiable by the identical `+0x32`-word/`+0x64`-byte offset into the same global owned-fleet array `DAT_1128_00ba` that `ai-opponent-behavior.md`'s "Process-of-elimination pass" independently confirms this project's fleet table to be):
  - **Fleet creation** (`FUN_1038_1f72`, `stars.exe.export.c:18648`-`18743`) allocates this field fresh for every new fleet via a generic array allocator, `FUN_1060_057e(0x12, 3, 0)` (`stars.exe.export.c:18717`-`18720`) — 3 slots of 18 (`0x12`) bytes each, plus a 4-byte header recording the per-slot size and a slot count/capacity — and immediately populates the first slot (at `designBase+4`) with the new fleet's map position and its raw **design *index*** (`puVar5[3]`, the small integer 0-25 slot number passed in as the design to build, not a pointer) at `designBase+8` (`stars.exe.export.c:18722`-`18727`). A design index, not a pointer, is exactly what one would expect this array to cache if it exists to let a fleet track *which* of a race's design slots each of its (possibly several, once merged) ship stacks belongs to — not to directly address either candidate table.
  - **Fleet splitting** (`FUN_1038_2180`, `stars.exe.export.c:18747`-`18801`) and **fleet merging** (`FUN_1038_1582`, `stars.exe.export.c:17908`-`18000`) both treat this field as fleet-owned memory needing a deep copy, not a shared reference: they read a per-unit-size byte embedded in the block's own header (`*param & 0xff`, set to `0x12` at creation) to compute a new byte count, call a realloc-style allocator (`FUN_1060_053e`, `stars.exe.export.c:42459`-`42472`) to grow the *destination* fleet's own copy of the array, and then `memcpy` the *source* fleet's entries into it slot-for-slot (`stars.exe.export.c:17961`-`17979`, `18779`-`18797`). `FUN_1038_1582` (Merge Fleets) additionally compares the two fleets' `designBase` pointers for simple equality to decide "same design vs. different design" (`stars.exe.export.c:17953`) — this by itself rules out the static hull table as the referent, since two different owned designs sharing one hull *type* would incorrectly compare equal under that scheme, while it is consistent with either the per-owned-design table (which this per-fleet array does *not* turn out to be) or, as traced here, a fleet-private cache addressed by design identity. If `designBase` pointed into either shared, fixed-position table, none of this resize/deep-copy machinery would be needed at all — a bare pointer copy would do, exactly as the surrounding ~100 bytes of each fleet record *are* copied verbatim in the same functions (`stars.exe.export.c:17983`-`17989`).

  Net result: the attrition mechanic's hull-class byte at `designBase+0x1c` is read from inside this private per-fleet array (specifically, from 24 bytes past the start of its first 18-byte entry — which, given the entries' own 18-byte stride, actually falls at the start of the *second* entry, byte offset 6 within it), not from a byte that this project's two extracted tables (`component-stats.tsv`'s static hull table, or the per-owned-design record) can be indexed into directly. This also newly explains the immediately-preceding gate this same block applies, `puVar17[0x31] < 2` (`stars.exe.export.c:73379`): fleet-level word `0x31` mirrors this same array's own entry count, so the gate is plausibly "this fleet must be carrying at least two distinct merged-in ship designs" before the second entry it inspects is even populated — i.e. the attrition mechanic, on this reading, specifically inspects a fleet's *second* merged-in design stack rather than its primary one. This narrower point (which entry index, and why specifically the second one) was not independently confirmed beyond the offset arithmetic above and is offered as a plausible but unverified corollary, not a certainty; the main question this pass was asked to settle — static table vs. per-owned-design record — is resolved: it is neither.

  **Follow-up pass — the exact line pair re-read directly, corollary upgraded from "plausible" to directly confirmed.** `stars.exe.export.c:73378`-`73380` reads as a single compound skip-condition: `if ((*(byte*)(iVar8+10) & 0xf) == 1 || ((*(byte*)(iVar8+10) & 0xf) == 6 || puVar17[0x31] < 2 || (*(byte*)(iVar8+0x1c) & 0xf0) == 0)) goto LAB_10b0_1fd7;` — i.e. `iVar8` (`designBase`) is read fresh at the top of this exact statement (`iVar8 = *(undefined4*)(puVar17+0x32)`, `stars.exe.export.c:73375`, the fleet's cached far pointer at byte offset `0x64` already traced above), and the `puVar17[0x31] < 2` entry-count gate and the `*(byte*)(iVar8+0x1c) & 0xf0` class-byte read sit in the *same* OR-chain, evaluated together rather than in separate, independently-reached statements. This directly confirms — by reading the two conditions side by side rather than by separately reconstructing their offsets — that the class byte at `designBase+0x1c` (the second design-stack entry's own byte 6) is only meaningfully consulted once the entry-count gate has already established that a second entry exists; the corollary in the paragraph above is correct as stated, not merely plausible.

  A structurally related, previously-uncatalogued branch sits immediately after this same gate (`stars.exe.export.c:73381`-`73394`) and is worth flagging here even though it is not part of the attrition mechanic itself: it re-reads `designBase` and, before falling through to the hull-class (`0xa0`) attrition check this section documents, tests bit 2 of `DAT_1128_5a16` for the fleet's owning race (`(((undefined1*)&DAT_1128_5a16)[puVar17[1]*0xc0] & 4) != 0`) — the identical per-race status byte and bit this document's §5 "fourth event" gating condition uses (see the new finding there). When that bit is set, and a turn-counter/race-index staggering condition additionally holds, the fleet has a 1-in-4 chance per relevant turn of being logged with message type `0x102` (`extracted-game-data/message-strings.txt` row 258, "`\s` has refused to move, doubting your authority to rule...") and is unconditionally skipped for the rest of this block (`goto LAB_10b0_1fd7`) regardless of whether that roll succeeds. This is a second, independent call site using the same status bit as §5's fourth event, discovered while re-reading this line pair; it is not part of the design-stack/hull-class question this note was asked to settle and is not analyzed further here.
- One is a per-star pass with an RNG-gated conditional branch, taking a mode parameter that selects between two mutually-exclusive object categories at its two call sites. **Fully identified as `FUN_10b0_0f9a` (`stars.exe.export.c:72509`), called with mode 1 at line 72171 and mode 0 at line 72142 — both calls sit inside the same master routine, immediately after `FUN_10b0_1f8c` (§10's next bullet) and before the combat-detection phase.** The category active when the mode parameter is non-zero walks the special-object (wormhole-type) table and calls directly into segment 36's stability-tier extractor (`FUN_1118_0742`) ahead of a 1-in-100 roll, then — on success — repeatedly re-rolls a candidate position (up to 100 attempts) and re-scores it through segment 36's placement rejection-sampler (`FUN_1118_0456`) before committing the best candidate found; this is consistent with, and plausibly the concrete driver of, the annual wormhole drift/relocation behavior already attributed to those two segment-36 routines in `fleet-movement-scanning-cargo.md`'s "Segment coverage" note. **The complementary, mode-zero branch (`stars.exe.export.c:72623`-`72673`) is now traced and matches the "roughly 1-in-25, 1-in-3, and 1-in-2 gates" description exactly**: it walks the *same* special-object table (`DAT_1128_15fe`, stride 9) as the mode-1 branch, but selects entries whose category byte (`*(byte*)(entry+1) & 0xe0`) reads `0x60` rather than the wormhole branch's `0x40`. For an eligible entry, a `FUN_1040_1652(0x19)` roll (1-in-25) gates entry into the block at all; on success, a `FUN_1040_1652(3)` roll (1-in-3) selects between two sub-paths, and on the "both fail" sub-path a further `FUN_1040_1652(2)` roll (1-in-2) picks between two candidate value pairs — one built from `DAT_1128_0074` (the same per-game scaling constant used elsewhere for galaxy-size-scaled ranges) plus fixed offsets `0x564`/`0x169`, the other a fixed `0x3fc` — writing the chosen pair into the entry's two "stat" fields (`entry[3]`/`entry[4]`). Control then falls through into the *same* shared tail the mode-1 branch also reaches (`LAB_10b0_11c6` onward): a squared nibble-field computation, a position delta via `FUN_1038_2924`, a distance check against two stored double-precision thresholds (`DAT_1128_1d52`/`DAT_1128_1d5a`), and a candidate-scoring call into `FUN_10b8_4200`. Because both category branches feed the identical position/distance/placement tail and operate on the identical table, the mode-zero branch is most plausibly the *creation* half of the wormhole mechanic (materializing a new wormhole-table entry with freshly rolled stat/mass values before the placement tail positions it), complementing the mode-one branch's *relocation* of already-existing entries — but which stored category byte value is "freshly created" versus "already active" was not independently confirmed against a labeled constant, so this reading, while well-evidenced, stops short of certainty.

  **Follow-up pass — additional, corroborating (not conclusive) evidence found elsewhere in the client.** A map-rendering routine (`FUN_1058_3bc6`, code-coverage segment 12, `stars.exe.export.c:39599`-onward) that computes a distance/delta line from a reference point to a selected special-object-table entry branches on this exact same category-byte mask (`stars.exe.export.c:39667`-`39680`): entries whose category reads `0x60` have their position read **directly** from the entry's own two stored coordinate fields (`iVar3+6`/`iVar3+8`), while entries whose category reads `0x20` instead resolve their position **indirectly**, through an index into the separate star-position table (`DAT_1128_2f60`) stored in the entry. In other words, `0x60`-category entries carry their own free-floating galaxy position rather than being anchored to a star — consistent with wormholes, which are placed at arbitrary rejection-sampled galaxy coordinates rather than at a star (per `fleet-movement-scanning-cargo.md`'s "Wormhole placement and stability" note), and inconsistent with a star-attached mechanic. This does not independently prove `0x60` is specifically the wormhole-creation state rather than some other free-floating special-object type (e.g. the Mystery Trader spawn documented in §5), but it is one further piece of evidence pointing the same direction as the existing hypothesis, found via a completely different code path (map rendering) than the one the hypothesis itself was built from (the per-star pass). The category byte's exact real-world label is still not confirmed against any string/constant data; this remains a well-evidenced, not certain, reading.

  **Resolved, and the "wormhole creation" hypothesis overturned — a real associated message string was found this pass.** The instruction to search for *other* code reading/writing category byte `0x60` (beyond the placement/relocation branches above) turned up a waypoint-task validity check, `FUN_1070_374a` (`stars.exe.export.c:47132`-`47765`), whose body (`stars.exe.export.c:47410`-`47450`) resolves a fleet's waypoint target through the same special-object table (`FUN_1038_01a0`, an ID-based lookup into `DAT_1128_15fe`) and branches on the identical `*(byte*)(entry+1) & 0xe0` mask to decide which of three distinct "target has vanished, orders changed to last known location" messages to log: category `0x40` logs type code `0xf8`, category `0x60` logs type code `0x110`, and category `0` logs type code `0x111` (`stars.exe.export.c:47431`-`47447`). `extracted-game-data/message-strings.txt` gives these three identifiers' actual text verbatim: `248` ("The Wormhole \s was heading for has vanished..."), `272` ("The Mystery Trader \s was heading for has vanished..."), and `273` ("The Mine Field \s was heading for has vanished...").
