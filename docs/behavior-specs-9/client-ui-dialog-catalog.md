# Client UI Dialog Catalog

This catalog extends the client-interface specification with every distinct interactive surface identified in the exported client. Names below are functional descriptions, not copied identifiers. An entry states only behavior supported by the client surface; it does not infer rules that belong to turn processing.

## Global dialog contract

Every modal surface has these common attributes:

- It is initialized from an explicit subject, selection, or session draft.
- It supports accept, cancel, and contextual help when help is available for that surface.
- Accept returns a meaningful result to its caller. Cancel returns a distinct no-change result.
- Editable surfaces use a local working state and commit only their own scoped fields.
- Read-only and authority-limited contexts disable mutation controls while retaining useful inspection controls.
- Keyboard and pointer activation of an accept, cancel, list, or button control follow the same state transition.

## Workspace surfaces

### Main workspace frame

The top-level frame creates and owns the map workspace, command menu, toolbar, status content, and subordinate information windows. It routes keyboard accelerators to the active child surface when that child is entitled to receive them. It supports normal, minimized, and restored display states.

The frame handles controlled shutdown. When unsaved state or an active session requires a decision, it opens a confirmation flow rather than terminating immediately. It may save or prepare pending session data before completing the close action.

### Title and status area

The title/status area presents the current context and supports lightweight updates without rebuilding the map. It refreshes when the active owner, open game, or current view changes.

**Race-name/summary string builder, confirmed by inspection of the exported client.** A shared routine builds a display form of a race's name from its stored singular and plural name fields, parameterized by: singular versus plural form; whether to prefix an article ("a"/"an," chosen by the name's leading sound); whether to apply a possessive/adjective suffix; and, when no explicit plural name was set, an automatic English pluralization fallback (append "s," unless the singular name already ends in "s" or in a sibilant-plus-"e" pattern, in which case a different suffix is used). This is the routine that renders the current race's name into the title/status area, and it is reused throughout the client wherever a race's name needs to appear in a sentence — reports, dialog captions, and the report-text escape-formatting engine described under Custom widgets below.

### Toolbar, tooltip, and contextual popup

The toolbar maintains an ordered group of icon actions. Each icon has an enabled state, a press/hover state, and explanatory tooltip content. Hovering does not change the selected object or persistent state.

The contextual popup is built from the current pointer target and selection. It contains only operations legal for that target. Closing it without activation has no effect.

### Search and record browser

The search surface accepts a query, evaluates it against the relevant object collection, and returns a selected result or no result. The browser surface presents a navigable collection with one current item and can update the workspace focus to that item.

**Located and confirmed by a later pass, previously unattributed to any segment.** A distinct dialog procedure (in the same code segment as the Research dialog below, but otherwise unrelated to it) populates a roughly 17-entry listbox from a string-table run at initialization and, on selection change, renders a detail card for the highlighted entry through the same large, shared "object/context detail" content renderer that also backs the mode-switched hover/info popup's richer modes above — an object-type/subtype dispatch that draws whichever of several layouts (a color-coded environment/habitability-style value breakdown, a proportional resource/mineral bar summary, or a ship/component-style info block, among others) matches the selected entry's kind, rather than one fixed layout for every row. This matches the "browser-style selection window for moving through a collection of records" bullet in `client-interface.md`'s "Navigation controls" list at the mechanism level, and is a strictly richer per-item detail display than that entry currently describes.

**The 17-entry listbox content is now pinned down with high confidence, resolving the prior open question.** The listbox-selection handler and the dialog's Prev/Next step buttons all index the same fixed lookup table through a listbox/step index that is confirmed (by the step buttons' own wraparound logic) to range only over **1 through 16, never 0** — the table itself spans 17 word-sized slots, but slot 0 is dead/unused, which is why an earlier pass's raw byte-count read as "roughly 17 entries." Each of the 16 live slots holds one value that is fed directly, unchanged, as the "category" tag into the shared component category/subtype availability resolver (`FUN_1008_5194`, this project's segment 2, documented in full in `ship-design-and-components.md` §4) — and the values found are exactly that resolver's 16 valid category bit-flags (`0x0001` through `0x8000`, one bit each). Stepping to the next/previous entry then walks that category's subtypes (via the same resolver call, skipping any subtype the resolver reports as nonexistent or unavailable to the current race) rather than walking a separate flat list of records. **This makes the browser dialog a component/hull-slot category browser, not a browser over some other collection:** its outer listbox lists the 16 fixed component categories from `ship-design-and-components.md` §4 (the same categories the Ship/Starbase Designer's slot editor validates against), its Prev/Next buttons cycle through the eligible subtypes (individual components) within the selected category, and each selected component is rendered through the shared detail-card renderer described above. This confirms the "component category list" candidate over the "hull/design-type list" alternative previously floated here, and ties this dialog directly to the same resolver `ship-design-and-components.md` documents from the design-slot-editor side.

**The shared detail-card renderer (`FUN_10d8_1e40`, segment 28, 1847 lines) has now been traced systematically rather than sampled, closing this segment's last substantial gap.** All three call sites were confirmed by direct inspection: the browser dialog's paint handler calls it with the dialog's own selected-item descriptor; the Research dialog calls it similarly; and segment 25's mode-switched popup (see "Toolbar, tooltip, and contextual popup" above) calls it from exactly one of its cases, always passing one fixed shared global "current selection" descriptor rather than a per-call object. Critically, **the object this function renders is not a mix of planet/fleet/design/race records — it is, in every one of the three call sites, the same (category, subtype) descriptor `ship-design-and-components.md` §4 documents**, down to sharing that exact resolver: the renderer calls `FUN_1008_5194` on its own input near the top of the function to populate a cached far pointer to the resolved component/hull data record before drawing anything. This corrects the framing in the paragraph above (inherited from an earlier, partial sampling pass) that described the renderer's layouts as keyed to different *object types* ("planets," "ship/component," a generic "resource bar"); what that pass was actually seeing were different **component categories** sharing one dispatch function, not different kinds of game object.

**Net finding, answering this document's open question directly:** the renderer displays exactly one kind of object (a component/hull category+subtype descriptor, the same 16-value bit-flag system `ship-design-and-components.md` §4 documents), not a mixture of planets, fleets, designs, and races. It does not reuse one fixed "icon + name + stat lines" layout for every type; only the icon/border/title chrome and the single trailing status caption are shared, while each category's actual stat content is separately hand-written, differing in field count, byte offsets into the data record, and message-string ranges. The full 16-category dispatch was not exhaustively mapped in this pass (several categories' exact numeric values are obscured by decompiler pointer-type artifacts rather than clean literals), but the dispatch shape itself — chrome, then a per-category bespoke body, then a shared trailing caption — is now confirmed rather than sampled, and this segment's previously-flagged "not exhaustively traced" gap is closed.

### Randomization seed

The seed surface accepts a session-generation seed and validates its input before returning it to the setup draft. It distinguishes user-provided values from the request to generate a fresh random value.

**Confirmed by inspection of the exported client.** The dialog reads a typed decimal string one digit at a time (validated character-by-character against a shared digit-class lookup table) and accumulates it into a 32-bit value via repeated multiply-by-ten-and-add. An empty field is treated as "generate a fresh random value" (the dialog accepts without reseeding); a nonzero typed value is passed to the shared RNG engine's seed routine. This confirms, at the mechanism level, the underlying random-number generator: a combined multiplicative-congruential generator carrying two independent 32-bit state words, each advanced by its own large-modulus multiplier every draw and combined by subtraction (with modulus wraparound) to produce the returned value, reduced by the caller's requested upper bound. The seed dialog's own path derives its two lookup-table indices directly from the low 6 bits of the typed value (guaranteeing the two indices differ by construction). A small push/pop stack lets a caller temporarily substitute a different seed and later restore the exact prior state, so that borrowing the RNG for a one-off computation elsewhere in the client does not disturb ordinary gameplay random sequences.

**A second, independent seeding entry point, refined by a later pass.** A separate seed routine (deriving its two lookup-table indices from a bit-scrambled combination rather than a plain 6-bit split) reseeds this *same* shared generator from the system tick count — used, in the ordinary case, at application startup and at at least one other session-reset point, which is plain gameplay randomization rather than something "unrelated" to it as previously characterized here. That same routine is separately reused — with the RNG state saved and restored around the call via the push/pop stack above — by the Serial Number surface's accept-time check (see the Serial Number entry below), which seeds the shared generator from a value derived from the typed input rather than from the clock, draws several values from it, and compares the result against a second derived value. Consistent with this project's house rule on copy-protection mechanisms, no more of that check's internal derivation is documented here.

**A wholly separate, second instance of the same generator algorithm exists, confirmed by inspection of the exported client, carrying its own independent state pair rather than sharing the one described above.** It has its own matching push/pop save-restore pair (used to checkpoint and roll back the stream around a bounded retry loop — see the galaxy star-placement rejection-sampling loop in `new-game-setup.md`, which draws from this second stream) and its own explicit reseed-and-advance entry point: given a handful of small identity fields, it reseeds the stream via the same table-lookup scheme and then draws and discards a record-specific number of values from it before use, so that a given record's position in the stream is reproducible from its own identifying fields rather than depending on how much of the stream earlier records consumed. A companion routine XORs a byte buffer against successive draws from this stream. Together these back a lightweight, non-cryptographic **record-level scrambling scheme**: reading a certain flagged class of on-disk record involves reseeding this second stream from the record's own small header fields and XOR-unscrambling its payload bytes against the resulting keystream — distinct from, and layered independently on top of, the turn-file delta-record protocol documented in `save-turn-file-format.md`.

## Information, reports, and output

### Messages

The message view presents recorded messages and maintains a current position within the collection. It includes four category-selection controls, a current-message area, and a scrollable or otherwise selectable message list. Changing a category or row refreshes the current-message area. Reading or navigating messages does not alter their underlying content. The current message and navigation availability update when the collection changes.

Confirmed by inspection of the exported client: Next/Previous Message navigation supports an optional filter bit tested against each candidate message's stored classification, letting navigation skip to only messages matching (or not matching) that filter — consistent with an "unread only" or similar toggle, though the filter's exact real-world meaning was not confirmed.

**Message record store, confirmed by inspection of the exported client.** Each message is a variable-length record — a type code, a per-type field count (looked up from a small per-message-type table), and up to several data fields individually stored as either a single byte or a full word depending on a per-field size bit — appended to a growable in-memory buffer (bounded to roughly 64K); a companion 392-bit "read" bitmap tracks which message indices have already been seen. The Next/Previous navigation described above, and the filter bit, are backed directly by linear scans of this same read bitmap looking for the next/previous message whose read-state does or doesn't match the requested filter — confirming the filter is (at minimum) a read/unread distinction, not an arbitrary message-category filter. The same buffer is what gets serialized into a player's turn/save file as the "message-text blob" described in `save-turn-file-format.md` §6.

**Correction: the 392-bit bitmap is a per-message-type filter, not a per-message read flag.** Each bit is indexed by message *type* (the record's 9-bit type code), not by message position. The navigation scans look up each candidate message's type and test that type's bit (`FUN_1030_7010`/`FUN_1030_7082` via `FUN_1030_7762`, `stars.exe.export.c:14620`-`14672`, `15009`-`15077`). A second bitmap of the same size records which types occur among this turn's messages; it is filled as messages are appended (`stars.exe.export.c:16126`-`16128`). The filter bitmap is written into the player's file with the other client state (`stars.exe.export.c:31298`). As a player sees it:
- A tick or cross in the pane header shows whether the current message's type is shown (blue tick) or filtered out (red cross). Clicking it, or pressing the plus key, flips the filter for that type (`FUN_1030_8a80`).
- Some related types change together. Certain pairs, and several runs of consecutive type codes, always take the same filter setting, so filtering one hides its siblings too (`stars.exe.export.c:16413`-`16502`).
- A magnifier appears beside the tick only when some type present this turn is filtered. Clicking it, or pressing the minus key, switches between "hide filtered messages" (the default) and "show filtered messages" (`stars.exe.export.c:14155`-`14172`, `14195`-`14207`).
- In the default mode, Next and Previous skip messages whose type is filtered. In the show mode they step through every message.
- On a switch, the current message stays selected if its type is already filtered (when switching to show mode) or unfiltered (when switching back). Otherwise the selection moves to the next such message, or to the previous one if none follows.

The earlier "read/unread" reading was a misinterpretation. No per-message seen flag drives this navigation.

**Report-text formatting is a distinct mechanism layered on top of the message store — see "Escape-coded report-text formatting" under Custom widgets below** for the escape-sequence substitution engine that expands a stored message's raw format string and field values into final display text.

**Message record header, resolved bit-for-bit by inspection of the exported client's record-builder and record-scanner routines.** Every record has a fixed 5-byte header followed by a variable payload, matching the scanning routines' own stride computation (record length = the high nibble of byte 0, plus 5): byte 0's low nibble is the **target race/player index (0-15)** — confirming the 16-race population cap at this structural level, not just from race-design UI limits documented elsewhere — and its high nibble is the record's *extra* payload length in bytes (0-15) beyond the fixed header. The word at offset 1-2 packs the **message-type code in its low 9 bits (0-511)** plus, in its remaining high 7 bits, one flag bit per additional data field recorded (0 = stored as a single byte, 1 = stored as a full word) — bounding a message to **at most 7 additional fields**, on top of one fixed word value always stored at offset 3-4. A per-message-type **field-count table**, indexed directly by the masked 9-bit type code (i.e., up to a 512-entry byte array), gives the count of those additional fields for each type; the record-builder loops that many times, reading each extra field's value directly from the caller's stack (beyond its own declared parameters) and packing it as a byte or word per the flag bits above.

**The message-type code's own text is now recovered, resolving a separate open question raised elsewhere in this project.** The 9-bit type code above turned out not to be an identifier into the client's general-purpose dynamic string table (`dynamic-string-table.md` §1-§5); it indexes a **second, independent compressed string table**, built from the identical paging/nibble-decode mechanism but with its own base offsets, its own 72-character alphabet, and its own code-segment location inside this same message-record-store segment — see `dynamic-string-table.md` §6 for the full mechanism and cross-references, and `extracted-game-data/message-strings.txt` for the complete recovered set (387 strings, identifiers 0-386, no gaps). Recovered examples, paraphrased, showing the kind of message bodies this store renders: identifier 10 announces that the player's colonists now control a named planet; identifier 78 reports that a named fleet has finished its orders; identifier 247 is the Merge with Fleet task's completion notice (one named fleet merged into another); identifier 340 reports how many battle recordings the player received this year; identifier 386 (the table's last populated slot) reports that a tampered ("hacked") race file was detected and that race's statistics were forced back to legal values. Every recovered string is a template using the backslash-letter escape convention documented immediately below in "Escape-coded report-text formatting," not finished, substituted text.

**Field-count table contents could not be enumerated from this material — an honest limitation, not an oversight.** The table itself is program *data*, and the exported decompile contains only the *code* that indexes into it (a byte read at a fixed data offset plus the type code); no corresponding initialized-array literal survives in the exported `.c` file to read actual per-type values from. **Multi-field messages are exercised (reconciled with the Known boundaries note and `production-queue.md` §10i).** An earlier pass counted 155 call sites for the three message-posting entry points and, trusting the decompiler's short prototypes, concluded that every call passes only the fixed offset-3 word (field count 0 or 1, with callers packing sub-values such as two bytes into that one word). That conclusion was wrong, as the raw-byte review below shows: several message types carry two to seven extra fields. Some callers do also pack two small values into the fixed word, which is a separate, caller-side convention. **Production-message review (raw bytes of segment 7, selector `0x1030`, offsets `0x7444`-`0x7590`):** the decompiler's two- and three-parameter prototypes for the posting entry points hide their extra words. `FUN_1030_7460` and `FUN_1030_74ba` forward ten stack words to the record builder `FUN_1030_752c` - the pair (recipient race, type), the fixed word, and **up to seven further words** - and `FUN_1030_7444` forwards five (recipient, type, fixed word and two extras). Real call sites do push extras: the terraforming-step notice 123 pushes four (planet, increase flag, axis, packed axis and value), the alchemy notice 140 two, the starbase-built notices 205-207 three, the lost-ships notice 186 three (see `production-queue.md` 10i for the exact words). So message types with field counts of 2-7 are exercised. **Resolved: the slot-by-slot layout of the per-race score record and the exact score formula.** The 20-byte figure block is not five like-typed longs. It is two longs followed by six words, and the writer copies it to bytes 4-23 of the race's 24-byte record (the copy pointer is advanced before the first store, `stars.exe.export.c:79083`-`79089`). Bytes 0-3 hold the record header: the race number and status flags in the first word, and the rank in the second. The leader-table painter reads nine rows in a fixed order, and each row's caption comes from consecutive dynamic-string entries 435-443 (`FUN_1108_15b4`, `stars.exe.export.c:109282`-`109357`). The rows map as follows:

| Row | Category | Record bytes | Contents (writer: `FUN_1038_384c`, `stars.exe.export.c:20027`-`20239`) |
|---|---|---|---|
| 1 | Planets | +12 (word) | Number of planets the race owns |
| 2 | Starbases | +14 (word) | Owned planets with a starbase whose hull has a nonzero dock capacity (hull field also used for dock capacity in `production-queue.md` and `turn-generation-engine.md`). An Orbital Fort, with no dock, does not count. |
| 3 | Unarmed Ships | +16 (word, packed) | Ships in the race's fleets (fleets carrying one particular status flag are skipped) whose design has a zero combat rating. The rating comes from `FUN_1038_079e`, the design's weapon-power figure built from its beams, torpedoes, bombs and capacitors. |
| 4 | Escort Ships | +18 (word, packed) | Ships whose design rating is from 1 to 1,999 |
| 5 | Capital Ships | +20 (word, packed) | Ships whose design rating is 2,000 or more (threshold confirmed in raw bytes, segment `1038` offset `0x39f6`) |
| 6 | Tech Levels | +22 (word) | Plain sum of the six tech levels (not the weighted curve) |
| 7 | Resources | +8 (long) | Sum of every owned planet's resource output |
| 8 | Score | +4 (long) | The combined score (also the routine's own return value) |
| 9 | Rank | +2 (word) | 1 plus the number of races with a strictly higher score, so tied races share a rank |

The three ship-count words are packed so that very large counts fit in 16 bits. A count below 8,192 is stored as is. Larger counts are divided by 4 as often as needed and the number of divisions is kept in the top three bits (`FUN_1038_3038`). The painter and victory condition 7 both unpack it the same way. Rank is computed after all races are scored (`FUN_10b8_3bbc`, `stars.exe.export.c:79201`-`79245`) and is forced to 1 when only one race exists (`:79342`). In each row the painter highlights the leading value, and in the Rank row it highlights 1. A race whose record is not yet valid shows a blank.

The **Score** is the sum of:
- for each owned planet, its population in thousands rounded up, at most 6 per planet;
- the Resources figure divided by 30 (whole points);
- 3 per qualifying starbase;
- for each of the six tech fields at level L: L for 0-3, 2L − 3 for 4-6, 3(L − 3) for 7-9, 4L − 18 for 10 and up (skipped once the race is eliminated);
- half of the smaller of (unarmed ships, planets), rounded down;
- twice the smaller of (escort ships, planets);
- if the race has capital ships: 8 × planets × capital ÷ (planets + capital), rounded down.

The same block feeds victory conditions. Condition 1 reads the Planets word. Condition 6 reads Resources divided by 1,000. Condition 7 reads the packed Capital Ships word. Conditions 4, 5 and 8 read the Score long (`stars.exe.export.c:79111`-`79185`). The elimination test (`:79098`) fires when the Planets, Unarmed, Escort and Capital words are all zero: no planets and no ships of any class. This agrees with, and completes, `victory-conditions.md` §2, which left the other three of those four words unidentified.

This is a real, distinct logging mechanism in its own right (worth a future pass to document as part of the anti-cheat detection flow), but it is not the routine this entry describes. The actual FPU-status diagnostic routine and its persisted trigger-flag writer were not relocated in the time available this pass.

**A second candidate searched for and also ruled out this pass, broadening the search beyond the previous attempt.** Grepping the entire exported source for the FPU-status/control-word read idiom (Ghidra's `in_FPUStatusWord`/`in_FPUControlWord` pseudo-registers, which only appear where the decompiler recognized an actual 8087 status/control-word read) turns up exactly one cluster of hits, all inside Ghidra segment `0x1120` (`stars.exe.export.c:118166`-`123000`, approximately): `FUN_1120_1c8e` (`stars.exe.export.c:118305`, reading the status word to classify a hardware floating-point exception into one of the standard x87 exception classes 0-6), and `FUN_1120_20c2`/`FUN_1120_2104`/`FUN_1120_290f` (`122287`-`122861`, saving/restoring the control word around software floating-point math). Tracing these confirms they are the **compiled C runtime library's own floating-point exception trap handler and math-library precision-control plumbing** — not a hidden diagnostic. `FUN_1120_1c8e` is the handler that produces the game's visible "M6100"-"M6109" `MATH - floating point error` `MESSAGEBOX` dialogs already cross-referenced elsewhere in this file (e.g. `stars.exe.export.c:82490`, `104334`, `104648`), a standard, always-reachable runtime crash dialog rather than a gated developer log; `FUN_1120_290f` and its neighbors are runtime log/exp-style math routines that save and restore the control word purely for numeric precision during their own computation. No other occurrence of either pseudo-register, and no other recognizable FPU status/control-word read idiom, exists anywhere else in the ~124,000-line exported source. This is a genuine, honestly-reported negative result: the search was broadened from a single candidate to an idiom-wide sweep of the entire file, and it confirms the hidden diagnostic (if its FPU-status read survives in the exported material at all) is not implemented through any of the compiler-recognizable idioms Ghidra can name — it may instead sit behind inline assembly opaque enough that Ghidra never labeled it as an FPU register read, which would make it effectively unsearchable by this method. The routine and its persisted trigger-flag writer remain unlocated.

**Closed from raw bytes: there is no hidden FPU diagnostic. The only floating-point status code is the standard C runtime's.** Every code segment of `stars.exe` was swept byte by byte for x87 control-word and status-word stores and loads, environment saves, and coprocessor resets. The result was cross-checked by decoding the instruction at each of the executable's 810 OS-fixup relocation records, which mark the x87 instructions the loader may patch. Only the probe described below uses unmarked ones, and only after it has confirmed a coprocessor is present. All genuine hits outside the runtime segment (`1120`, NE segment 37) are the ordinary "compare, store status to AX, branch" idiom in the game's numeric code: 18 sites in segments `1030`, `1038`, `1058`, `10a8`, `10b0`, `10b8`, `10f0` and `1108`, each followed directly by a conditional jump. None saves the status anywhere. Inside segment `1120` the hits fall into five standard runtime pieces:
- the float-to-integer truncation helper (offset `0x0e52`);
- the maths-library routines that check the status after each operation (`0x13b5`-`0x174a`);
- the floating-point exception classifier (`FUN_1120_1c8e`, offsets `0x1cf5`-`0x1e09`), which feeds the runtime's floating-point error message boxes;
- precision-control save and restore (`0x20c3`-`0x2132`, `0x3014`-`0x303a`, `0x35a8`-`0x35f8`) and the printf-style float-to-text converter (`0x2949`-`0x29c2`);
- one routine Ghidra never decompiled, at `1120:2690` (it sits in the gap between `FUN_1120_2662` and `FUN_1120_2716`).

That last routine is the runtime's coprocessor-type probe. It asks the Windows maths-emulator interface whether a coprocessor is present. If one is, it saves the control word, resets the unit, compares positive and negative infinity, and inspects the saved environment, so it can tell an 8087-, 287- or 387-class unit apart. It records the answer as 1, 2 or 3 in one runtime variable, then restores the control word. It has no direct caller. It is reached only through a four-entry table of far pointers in DGROUP (offsets `0x1c32`-`0x1c3e`) that the runtime's startup code walks once (segment `1120` offsets `0x017f`-`0x0197`, walker at `0x026a`). Only the runtime's own maths routines read the result (`0x1472`-`0x1494`). The routine does not format text, open or append to any file, or test any `.ini` or player-file flag. The executable also has no debug or log format strings (no hex-dump formats, no coprocessor wording) apart from the runtime's own floating-point error texts. The code's x87 instructions carry OS-fixup relocations, so Windows can turn them into emulator calls on machines without a coprocessor; this is also standard runtime behaviour.

The "hidden diagnostic" described in the first of these paragraphs therefore does not exist as a game feature. That description most plausibly merged this startup probe (which does gather FPU status) with the separate audit-log append of the integrity sweep (`FUN_1038_5174`, which does write a log file). A compatible client needs neither: floating-point setup is a compiler/runtime matter, and the audit log is documented with the anti-cheat sweep.

## Custom widgets

### Styled text entry

Styled text entry exposes ordinary editable text semantics: focus, text selection, insertion, replacement, validation, and commit. Its custom appearance must not change these semantics.

### Styled single-choice selector

The compact selector exposes one active choice from a finite option set. Changing the selection notifies the owning editor, which decides whether to mark the draft dirty.

### Styled list

The list widget maintains zero or one active row according to its owner's policy. It supports selection changes, redraw after content changes, and a callback into the owner for the new row. It does not autonomously persist an edit.

### Segmented bar/gauge and repeating-button controls

**Confirmed by inspection of the exported client, correcting an earlier "custom control paint routines... looks like a slider/gauge/bar control" hypothesis:** the client implements a genuine custom multi-segment horizontal bar/gauge primitive — given a frame rectangle, a list of (value, fill-color) pairs, and a total, it draws a border, insets it, then fills successive proportional slices left-to-right in each segment's own color (rescaling by 1000 first if the total would overflow a 32-bit accumulator). This is the drawing primitive behind at least one ship-design capacity/threshold bar (a "used of maximum" bar that switches among three fill colors depending on how close the value sits to the limit, with a centered "value / value" text label overlaid via the string-format engine below) and, separately, a fuel/cargo-style "amount of capacity" gauge reused for other numeric-limit displays. A related primitive draws a raised/sunken 3D bevel border (two-pixel light/dark edge pairs, selectable raised-versus-sunken by sign) used to frame these and other custom-painted panels. A third, independent primitive implements a **generic auto-repeating pressable control**: it takes mouse capture on press, redraws itself in a pressed/unpressed state as the pointer enters or leaves its rectangle, and — while the pointer stays down inside the rectangle — re-fires on an internal timer (an initial longer delay, then a fixed short repeat interval) rather than only once per click, the standard "click-and-hold to repeat" behavior for a spinner or scroll arrow. This same repeating-button primitive is reused by the race-design economic/tolerance sliders (see `race-traits.md` §1a) and by at least one custom-painted panel on the tactical battle-replay surface (see "Event replay" above).

### Word-wrap text layout engine

**Confirmed by inspection of the exported client.** A shared line-layout routine takes a run of text (either a length-delimited span or a NUL-terminated string), a left margin, a right edge, and a fixed line pitch, and lays it out one line at a time against the current font. Its wrapping strategy is a **greedy, whole-word breaker with no hyphenation**: for each line it first measures the *entire* remaining text against the available width; if that fits, the whole remainder becomes the line (and any fitting trailing spaces past the natural break are folded in, so a line can absorb trailing whitespace up to the next real content). If it does not fit, the routine repeatedly backs off from the tentative line end — first trimming trailing spaces, then skipping back over the entire overflowing word, then trimming any further spaces before that word — and re-measures, until the remaining span fits or nothing is left to remove. A break is never made in the middle of a word. Once a line's span is fixed, the routine can optionally paint it (a "measure only" mode exists, used to compute total wrapped height/width without drawing) before advancing the vertical cursor by one fixed line pitch, resetting the horizontal cursor to the left margin, and skipping any leading spaces at the start of the next line. This engine is called very widely — from message/report display, tooltip-style popups, and at least one report-grid cell renderer — making it the client's single shared multi-line text layout primitive, distinct from (and used by) the escape-coded report-text formatter described below, which expands the raw text before this engine lays it out.

**Companion text-drawing primitives, sampled from the same cluster.** The word-wrap engine's own line-break search is itself built from three small helpers — skip past any leading spaces at a line start, back up over trailing spaces before a candidate break, and back up further over an entire overflowing word — each a short, single-purpose span-adjustment routine. Alongside the wrap engine sit several simpler, single-line text-drawing primitives reused across dialogs: draw a string horizontally centered under a given anchor point; draw a string left-aligned while advancing a running vertical cursor by its measured height (used to stack several lines of text without a full wrap pass); draw a string centered in both axes within a rectangle, with an optional background fill first; and draw a string against a fixed-width field, either padding the unused space or clipping the string against the field's edge when it overflows (a candidate for fixed-width status-strip/label fields elsewhere in the client). A separate, unrelated helper truncates a string in place, one character at a time from the end, until it fits a given pixel width — a simple "shorten this label to fit" utility distinct from the shrink-to-fit *font-resizing* approach described below.

### Font-resource loader and autofit label sizing

**Confirmed by inspection of the exported client, extending the "embedded font-resource loader" finding.** Beyond the startup GDI-resource pass (see `client-interface.md`'s "Application shell" section, which builds a small fixed table of fonts once at launch), a separate on-demand routine creates a single additional font at a caller-specified point size in the same shared UI typeface: it builds a font-description record sized from the display's reported vertical DPI, copies in a shared face-name string, calls the standard font-creation API, and — if the caller wants it — selects the new font into the display context just long enough to read back its line metrics (ascent plus internal leading) before restoring the previous font, reporting that measured line pitch to the caller. This on-demand path is called with explicit point-size arguments (observed values 8 and 5) from outside the segment, i.e. it backs at least one further window's fonts beyond the startup table, rather than only being used during the startup pass.

A second, related routine implements **shrink-to-fit label sizing**: given a text string and a target rectangle, it builds a temporary font at an initial guessed size, measures the text, and — if it doesn't fit — iteratively rescales the guessed point size proportionally to how far off the fit is (via a scaled-ratio adjustment rather than a simple one-point step), rebuilding and re-measuring the temporary font each pass, until the text fits within both the rectangle's width and height (with an 8-pixel margin) or the loop bottoms out. Once a fitting size is found, it draws the text centered in the rectangle with that font and immediately deletes the temporary font handle — a "biggest font that still fits" label primitive, plausibly the mechanism behind the segmented bar/gauge's centered "value / value" label described below, though the exact call site backing that specific label was not traced.

### Escape-coded report-text formatting

**Confirmed by inspection of the exported client, extending the "custom escape-sequence string-format engine" hypothesis with concrete mechanism detail:** report/message text is not produced by the ordinary C-style format routine alone. A dedicated pre-pass scans a format string for a literal escape character followed by one of roughly a dozen one-letter codes and substitutes each with the correct kind of expanded text before final formatting: a ship/starbase component's display name; a race's display name (through the race-name/summary string builder described under "Title and status area" above); a plain string-table lookup; a race relationship-name lookup; a value formatted with automatic English singular/plural word-choice (checking whether the base word already ends "s" or "es" before appending a plural "s," rather than always appending one); a value formatted with an appended unit-name suffix chosen by magnitude; a conditional switch between two format strings depending on a threshold comparison; and a large-integer formatter that inserts thousands-separator punctuation (comma plus space) every three digits, with a special case for values that are an exact power of two. This is the mechanism underneath ordinary-looking report sentences such as "3 Large Freighters" versus "1 Large Freighter," or "1,234,500 resources," rather than those being pre-baked per-count string-table entries.

**Fuller escape-code enumeration, extending the above from direct inspection of the formatting engine's dispatch switch.** The engine recognizes a literal backslash followed by a single letter (case-sensitive; upper- and lower-case variants of the same letter sometimes share identical behavior, sometimes differ). Substantially more than "roughly a dozen" distinct *letters* are actually recognized — several simply alias to one of a smaller number of underlying *behaviors* — enumerated here to the extent this pass could resolve them:

- **E** — looks up a value by a single byte read from the field stream (a small fixed-table lookup; category not identified).
- **F** — looks up a value via a dedicated helper keyed by the raw field value (category not identified).
- **G** — a plain string-table lookup at one fixed table-index base.
- **I**, **j** — plain string-table lookups at two further, different fixed table-index bases (same underlying string-fetch helper as **G**, different base offsets).
- **L** / **l** — builds a race-name/summary string (via the same string-builder confirmed elsewhere for race-name and title-bar text) from a packed field value; the two cases parse that field's bits identically except for one derived flag, consistent with a singular/plural or short/long variant pair.
- **M**, **e**, **m** — three separate word-indexed lookup tables (three different fixed bases), each returning a short string keyed by a numeric field value — consistent with three distinct "unit name" or "category name" tables (e.g., mineral names vs. some other per-category label set), not yet individually identified.
- **O** — builds a race-name/summary string like **L**/**l** above, but derives the race index from a different (ship/component-slot-shaped) field layout rather than taking it directly.
- **P** — **confirmed:** the "conditional switch between two format strings depending on a threshold comparison" already documented above — compares a field value (divided by 100) against a fixed threshold constant and formats using one of two entirely different format strings depending on the result.
- **S** — a "self vs. other" substitution: compares a field value against the *currently active/viewing* race; if it matches, substitutes a different phrase (built and byte-reversed through a distinct pair of string-table entries) than when it doesn't, consistent with a "you" vs. "the `\`race`\`` grammatical substitution.
- **U** / **V** / **v** — **confirmed, extending the existing "unit-name suffix chosen by magnitude" note:** formats a 32-bit field value as a plain number, then (for **U**/**V** only, not **v**) appends a unit-name string looked up from a word-indexed table by a "current unit" index — **V** sets that index explicitly from a second field value; **U** reuses whatever unit index was last set (persisted across substitutions in the same message, defaulting to none); **v** always omits the unit suffix entirely.
- **X** — recognized by the dispatcher but performs no distinct substitution of its own (falls through to plain literal-character handling).
- **Z** — **confirmed, extending the existing "large-integer formatter" note into a second, separate mechanism:** given a bitmask field, if it is an exact power of two the single corresponding race's name is substituted (via the same builder as **L**/**O**); otherwise every set bit is expanded into a full, comma-and-"and"-joined list of race names (e.g., "Race A, Race B, and Race C") — i.e., a *race-bitmask-to-name-list* formatter, distinct from the single-value thousands-separator formatter already documented.
- **f** / **h** / **r** / **t** / **y** — a family of "current name" substitutions sharing one common name-buffer source (the same global text buffer used for the currently-edited object's name elsewhere in the client); they differ in what, if anything, is appended afterward — **y** and **h** each append a different fixed suffix (consistent with distinct grammatical/possessive endings), while **f**, **r**, and **t** instead fall through to plain-number formatting branches under certain conditions. The exact grammatical distinction between all five was not fully resolved.
- **g** — looks up a component/design display name (the same underlying helper used for ship/starbase component names elsewhere).
- **i** — aliases to the same plain-number-formatting branch as **r** above.
- **k** — **confirmed:** the "ship/starbase component's display name" already documented — resolves a component/design record and substitutes its stored name field directly.
- **n** — **confirmed:** the "automatic English singular/plural word-choice" formatter already documented — dispatches (through a shared category/count-formatting helper also used to look up plain planet, race, and component names by category code) to a paired singular/plural string-table entry pair chosen by whether the count is exactly one; two reserved field values redirect to the **g** and **o** substitutions instead of formatting a number at all.
- **o** / **p** — both substitute a planet's display name; **o** additionally checks one bit of the target's owner data and, when set, redirects to the **s** substitution (a race name) instead — consistent with "show the planet's name, unless a special ownership condition applies, in which case name the owning/related race instead."
- **s** — substitutes a race's display name, with a forced high-bit flag passed to the lookup (a distinct variant from plain race-name lookups elsewhere — possibly the "race relationship-name lookup" already noted above).
- **u** — plain numeric formatting with no unit suffix and (unlike the large-integer formatter) no thousands-separator punctuation.
- **w** — substitutes the current contents of a different global text buffer (the same one used elsewhere for the active window/dialog's title text).
- **z** — builds a per-design-slot component/race name similar to **O**, from a field value split into a race index and a design-slot index (0-31, split across two parallel design tables), with the same "is this the currently active race" special-casing seen under **S**.

**Underlying number-formatting primitives, sampled this pass.** The thousands-separator behavior described above (and under **Z**/the large-integer formatter) is implemented by a dedicated routine that re-copies an already-formatted digit string, inserting a comma after every third digit from the end — a distinct, separately-callable primitive rather than something built into the general-purpose sprintf-style formatter itself. A second, unrelated numeric primitive (`FUN_1040_1e0e`) rounds a raw value and appends a compact "k" or "M" magnitude suffix (choosing the divisor and suffix by comparing the raw value against fixed 10,000 and 1,000,000 thresholds) — a "compact large quantity" formatter distinct from the plain thousands-separator behavior above; its call sites were not traced to a specific on-screen figure in this pass, but it is a plausible candidate for any compact resource/quantity readout that abbreviates rather than fully spelling out a large number.

  **Call sites resolved this pass.** Both of this formatter's only two direct call sites sit in the Score display's own code segment (`FUN_1108_*`): one calls it directly while rendering a per-player numeric cell in the score surface's per-category leader-table mode, specifically inside `FUN_1108_15b4` (`stars.exe.export.c:109381`, the same leader-table paint function `_DAT_1128_1526` was just confirmed to feed above — the code path also chooses the cell's text color by comparing each player's value against the category's current leader, i.e. this is the "highlight the leader" rendering pass for the leader-table display mode over the surface's nine comparison categories); the other is inside a small shared helper, `FUN_1108_35a0` (`stars.exe.export.c:110791`-`110831`, itself calling the k/M formatter at `stars.exe.export.c:110827`), that sets a caller-supplied text color and then formats a caller-supplied value through this same k/M formatter — a generic "colored, magnitude-abbreviated number label" primitive.

  **Correction, resolved this pass: `FUN_1108_35a0`'s own four further call sites do *not* back the Score display at all — they were mis-attributed to it above.** All four (`stars.exe.export.c:110236`, `110354`, `110704`, `110720`) sit inside a single function, `FUN_1108_2508` (`stars.exe.export.c:109931`-`110790`), and that function is not part of the Score display — it is the Reports grid's own per-`(reportType, rowIndex, columnIndex)` cell-value dispatch function already documented under "Reports" above. Which specific report type/column each of the four `FUN_1108_2508` call sites formats was not individually traced this pass — that would be a new, narrower question about the Reports grid rather than the Score display.

**Total distinct letters recognized: 26** across the cases above (counting upper/lower-case pairs separately), collapsing to a substantially smaller number of underlying *behaviors* (roughly a dozen, matching the earlier estimate, once aliased letters are merged) — the previous "roughly a dozen" note undercounted the *letter* surface but was a reasonable estimate of the underlying *mechanism* count. Several helper-name/category mappings above (E, F, several of the M/e/m tables, the exact f/h/r/t/y suffix distinctions) could not be pinned to a specific real-world meaning — no string/label data survives to check them against.

- **`E` (`stars.exe.export.c:15152`-`15155`) is not a name/category lookup at all — it is a small numeric-formatting-style selector.** `FUN_1048_4010`, the helper `E` calls, branches only on the value being exactly 1, exactly 2, or anything else (falling to a third, generic formatter, `FUN_1048_405c`); all three branches format a number via `_WSPRINTF` with the actual format string supplied through registers the decompiler could not recover, so the literal punctuation/precision each style applies could not be read back from this material — but the *category* of the earlier "small fixed-table lookup; category not identified" description is corrected: `E` picks one of (at least) three numeric display styles for a value, not a name from a table.

This resolves `F`'s "category not identified" hedge: it is a **design-name-by-slot** substitution, not a small fixed table.

## Known boundaries

The exported client identifies these UI surfaces and, for the dialogs whose real Windows resources were directly parsed (see the section above), now includes exact captions and static control label text as well.
