# Computer (AI) Opponent Behavior

Behavior specification for the built-in computer-controlled empires in the 1995-2000 4X game *Stars!*. Unlike the other specifications in this set, this document is derived directly from the exported client's own decompiled turn-processing logic rather than from public community research — no public source documents how the built-in AI actually decides what to do, so this is the first specification of its kind for this subsystem. Facts here describe the algorithm's observable shape (decision order, thresholds, formulas) in generic terms; they do not use any of the original identifiers, variable names, or literal code from the binary.

## Overview

Every non-eliminated computer-controlled empire is processed once per turn by a single "AI turn" driver, dispatched to one of several **personality drivers** based on a small numeric code stored on that player's record (the built-in AI "type"). Each personality driver runs the same broad decision sequence — refresh threat assessment, decide fleet cargo/colonization/mining actions, decide planet-level construction, then hand off to two subsystems shared by every personality (the end-of-pass routine, which includes the starbase-building and per-planet advisors, and a general per-planet production/resource-allocation pass). What differs between personalities is a set of tuning constants (probabilities, distance thresholds, aggressiveness multipliers) baked into each driver, not the overall shape of the decision tree.

Eight category values exist (0 through 7). Category 6 is unused, and category 7 is an inert, economy-only driver. The setup screen's AI menu offers 6 named archetypes plus a "random" choice, each with 4 skill tiers plus "random". The archetype becomes the category (0-5) and the tier becomes a separate 3-bit skill field (0-3) when the game is created (§1a). Category 7 is assigned only to an "Expansion player" slot and to a human player that the host marks as inactive.

## Mechanics

### 1. Personality dispatch

A per-player field's top bits select which personality driver processes that player's turn. Each driver is a large (roughly 300-1100 "step") routine sharing this skeleton:

**The dispatch site itself, located this pass.** The per-player-slot initialization dispatcher documented in `new-game-setup.md` §5 (a 3-bit "category" field packed into the top bits of a 16-bit value at byte offset 2 of each slot's 192-byte record) is the *same* dispatcher this document's §1 has always described — confirming that section's own speculation that its six category-specific routines might really be "the concrete implementation of the six personality/difficulty categories." The dispatcher function itself is `FUN_1088_0000` (segment 18; takes the slot index as its first parameter; its only caller is `FUN_1020_3fe6`, `stars.exe.export.c:8266`-`8344`, which runs once per game load on the host (after a game is opened or a turn has been generated; the guard bit `0x400` of `DAT_1128_078a` is cleared by every game discard), once for every slot whose computer bit (`0x200` of the same record word) is set and whose order file does not already validate, so an AI's decisions are recorded as ordinary change records, the dispatcher ends by saving them as that slot's `.x<N>` orders file and its history file (`:58023`-`58024`), and they reach turn generation as a normal file: `turn-generation-engine.md` §1a), and its dispatch switch reads the top 3 bits of the 16-bit word at offset 2 of the slot's record — the same per-race/per-slot record array (192-byte stride) already confirmed as the relationship-table base in `diplomacy-relations.md` §1, here read at record offset 2 instead. The switch has cases for values 0-5 and 7 (case 6 has no code at all — the dispatcher silently does nothing for it, confirming this document's "entirely disabled" slot as category 6 specifically); each handled case calls one large per-personality driver function, all of which end by calling the shared production-allocation entry point `FUN_10a8_1e2a` (§6):

1. Compute turn-scaled tuning constants — several thresholds scale continuously with the game's current turn/year number (not in discrete difficulty "eras"), generally becoming more aggressive/expansive as the game goes on.
2. Refresh an assessment of nearby threats (enemy fleet strength, economy) using shared helper routines.
3. Iterate every fleet the AI owns, deciding per fleet whether to: transport cargo/minerals to a shortfall location, redirect toward a colonization or invasion target, scrap, or hold.
4. Iterate every planet the AI owns, deciding whether to queue a starbase, adjust defensive posture, or trigger an "opportunistic build" scan (queuing a currently-affordable ship design or component upgrade with some random retry chance).
5. Call the shared end-of-pass routine `FUN_1090_59e6` (speed setter, starbase-building advisor and per-planet advisors, §3/§6/§12) and the shared production-allocation pass, common to every personality. *(Corrected: there is no separate shared "starbase-management pass"; see §3.)*

One personality slot is a near-total no-op (it only runs the research choice, the end-of-pass routine and the shared production pass, with no independent fleet/planet decisions) — the most passive built-in AI available. Another slot is entirely disabled (its driver function does nothing at all).

### 1a. How a computer player's category and skill are set (traced)

The word the dispatcher reads, at byte offset 2 of the 192-byte player record, keeps its control fields in its top byte:
- bit 9 is the computer-player flag;
- bits 10-12 are the 3-bit **skill** field;
- bits 13-15 are the 3-bit **category**.

**New game from the setup wizard** (`FUN_1078_4a82`, `stars.exe.export.c:53119`-`53199`). Each row of the player grid holds one working byte. For an AI pick, bits 2-4 of that byte hold the archetype (0-6) and bits 5-7 hold the tier (0-4); Open Questions has the menu trace. When the game is created:
1. A tier of 4 ("Random") is replaced by a uniform draw of 0-3. An archetype of 6 ("Random") is replaced by a uniform draw of 0-5.
2. The whole player record is overwritten with one of **24 built-in AI race templates**, chosen by archetype and tier (6 × 4). `FUN_1078_7aca` returns the address of template (archetype × 4 + tier): 192-byte records in a table at offset `0x10d` of code segment 16. The templates hold the race settings (habitability, growth, economy and similar), so each archetype and tier plays a different pre-built race; all 24 are tabulated in §14. The name field is empty.
3. The computer flag is set, the skill field becomes the tier and the category becomes the archetype.

The resulting categories are:

| Category | Archetype label |
|---|---|
| 0 | Robotoids |
| 1 | Turindrones |
| 2 | Automitrons |
| 3 | Rototills |
| 4 | Cybertrons |
| 5 | Macinti |

The skill values are 0 Easy, 1 Standard, 2 Tough and 3 Expert. The menu's seventh archetype and fifth tier ("Random") never reach the record. *(Gap-report pass: these names are the menu's own five-entry tier list in the data segment, Easy, Standard, Tough, Expert, Random in that order (file offsets `0xb160c`-`0xb162d`), and the wizard stores the menu position unchanged, so the mapping is direct, not inferred.)* The quick **New Game** dialog has its own four radio buttons, labelled Easy, Standard, **Harder** and Expert. Its choice (0-3) picks the computer players' slot bytes through `FUN_1078_53c4` (`:53602`-): Easy games use tier 0, Standard tier 1, Harder tier 2 (the Tough tier) and Expert tier 3. So "Harder" and "Tough" are two labels for the same stored skill value 2.

**Quick-dialog slot assignment, exact (`FUN_1078_53c4` `:53727`-`53810`, checked against the raw bytes, segment 16 `0x55fa`-`0x587e`).** Slot 0 is the human player: a predefined race (index 0-6, which includes the Random placeholder) or the player's own race file (`:53550`-`53558`). With N players in total (N chosen earlier in the same routine from size and difficulty, `new-game-setup.md` §2), computer slots 1 to N − 1 are filled in order from fixed groups. Slot *i* takes the first group whose limit is greater than *i*. All divisions are integer divisions rounded down.

Abbreviations: Rob Robotoids, Tur Turindrones, Aut Automitrons, Rot Rototills, Cyb Cybertrons, Mac Macinti. Every entry has the difficulty's own tier except: **R** = random archetype at the difficulty's tier, **RR** = random archetype and random tier. So a random archetype appears in Easy from N = 12, in Harder from N = 5 and in Expert from N = 7. A random tier appears only in Standard and Harder, from N = 8.

After filling, the computer slots are reordered: for each slot *i* from 1 to N − 2, it is swapped with a uniformly chosen *later* slot (*i* + 1 to N − 1), never with itself. This always yields a single cycle, so every computer slot moves. With N = 3 the two computer players are always exchanged. The mix of archetypes is fixed by N and only the player numbers are shuffled. The random archetypes and tiers are drawn later, when the game is created (archetype 0-5, tier 0-3, as in step 1 above). The setup wizard also calls the same routine after its first page (`:53024`). The routine fills slots only when its first argument is 0; with 1 it sets only the victory-year default, and with more than 1 it does nothing.

**Other paths that write the word.**
- *Game-definition file* (`FUN_1078_3a80`, `:52257`-`52298`). A player entry that starts with a marker character carries two numbers: archetype 0-6 and tier 0-4. Zero means random (archetype 0-5, tier 0-3); any other value n selects archetype or tier n − 1. The record is filled and packed as above. The first player entry is always read as a race-file name.
- *Tutorial* (`FUN_1078_4938`, `:52882`-`52893`). The computer opponent gets template archetype 1, tier 0, and category 1, skill 0.
- *Expansion player* (`:53137`-`53153`). The last entry of the human-race list copies one of the seven predefined races at random and sets the computer flag with **category 7, skill 0**. The draw is uniform over all seven records, so one time in seven it is the Random placeholder, which universe generation then randomises (`race-designer-ui-and-availability.md`).
- *Host player-status menu* (`:9325`-`9395`). The three choices are human, computer and inactive human. "Inactive" sets the computer flag and category 7 and leaves the skill bits alone. "Human" clears the computer flag. "Computer" is greyed out unless the player is already a computer player. An inactive human's empire therefore keeps researching and producing under the category-7 driver, but its fleets get no orders.
- No path ever produces category 6.

**Persistence.** The word is part of the player record in the host's data. Before each AI run, the host copies every slot's word (`FUN_1020_3fe6`, `:8293`-`8304`) and passes it to the dispatcher. The dispatcher writes it back over the freshly loaded player file (`FUN_1088_0000`, `:57996`-`57998`) before it switches on the category. Turn generation never changes it.

**The 24 lore-named presets** (dynamic strings 1390-1413) are only a pool of race names; nothing ties a name to an archetype or tier. There are exactly 24 of them, ids 1390 to 1413, and nothing ties a name to an archetype or tier. Names are set at game creation in this order (`FUN_1078_4a82`; the game-definition-file path `FUN_1078_3a80` repeats the same steps at `:52505`-`52610`):
1. A predefined-race player gets the preset's name (dynamic string 1383 + preset index) and that name plus "s" as its plural (`:53155`-`53157`). A race-file player keeps the names stored in its file. A computer player's template has empty name fields.
2. In the same loop, a human player whose race scores below 0 advantage points is first replaced by the whole Humanoid preset record and flagged as corrected (record byte `0x54` bit 4, `:53205`-`53222`). That copy empties both name fields. Every player whose singular name is then empty gets a uniformly random pool name, with no uniqueness check at this point. If its plural is empty too, the plural becomes that name plus "s" (`:53226`-`53233`).
3. Duplicate pass (`:53239`-`53345`). Players 1, 2, … are checked in order. A player is renamed only if its singular name equals the singular name of a player before it; the earlier player keeps the name. The new name is found by drawing a random pool index and then walking forward through the pool, wrapping from the last name to the first, until it reaches a name that no player in the game currently has. The renamed player's plural is set to that name plus "s". With at most 16 players and 24 names the walk always ends.
4. Later, during universe generation, a Random race named Random gets a uniformly random pool name from the random-race generator, with no uniqueness check (`race-designer-ui-and-availability.md`, "The Random button and the random-race generator"). That step runs after the duplicate pass, so it can repeat a name already in use.

The tutorial sets its two players' names directly: the human gets the Humanoid preset name and the computer opponent gets the first pool name (`:52879`, `:52893`). That there are 24 templates and 24 names is a coincidence of count; the code never pairs them.

How the drivers use the skill field is listed in §12 ("What the skill field changes").

### 2. Colonization and fleet-destination selection

Target selection is built from a small set of generic, reusable search primitives that walk the planet/fleet lists computing squared distance from a reference point and applying a caller-supplied acceptance test:

- **"Nearest match"** — returns the closest object for which the caller's predicate is non-zero.
- **"Best match"** — returns the object maximizing the predicate's numeric return value, ties broken by distance.

Concrete predicates observed include: ownership filters ("not mine"), an "economy strong enough to spare a colonizer" gate (a threshold on summed cargo/mineral fields, tuned per personality), and habitability-based scoring functions.

**Colonization-target choice (corrected).** The colony-ship target is not scored. `FUN_1090_098e` (`stars.exe.export.c:61187`-`61369`) first marks every planet as own, foreign, unowned, unowned but uninhabitable (for categories other than 0 and 5, using the terraformed habitability test `FUN_1048_47ec`) or already targeted by another own colony fleet, and then returns the nearest planet still marked unowned, by squared distance, with no distance bands and no random acceptance roll. Before year 120 the caller may divert to a wormhole instead (§12, "Colony ships"). `FUN_1090_0868` (`:61121`) then writes the Colonize order to the chosen planet. *(Detail, traced `:61220`-`61297`.)* For categories 0 and 5 the classification is rebuilt on every call, and a planet counts as claimed only when another own fleet's next waypoint is that planet with the Colonize task. For the other categories it is built once, on the first call after the driver resets the cache before its colony-ship pass (`:60142`, `:66530`, `:69421`). There any own fleet whose next waypoint is the planet claims it, whatever the task, and the drivers mark the planets they order colonized later in the same pass themselves. An earlier version of this paragraph described a habitability-plus-distance score with bands at about 50, 100, 150 and 200 ly, a roll-under-score acceptance and a "too eager" 25% rejection. That description does not match the colonization code; it appears to conflate this search with the attack-target search of §12, whose bonus bands are 50/100/150/200/300/500 ly and which rejects an already-targeted planet three times in four.

**Late-game colony-ship production becomes distance-conservative (corrected).** Once the turn counter exceeds 59, the isolation check `FUN_1090_6012` (`:65887`-`65933`) gates whether an owned planet may queue a colony ship. It does not look at a colonization candidate or at the AI's own colonies: it measures from the producing planet to the nearest planet whose per-turn "own planet" scratch flag is clear, that is, the nearest planet the AI does **not** own (unowned or another race's). Beyond 350 ly (squared distance above 122,500) the ship is refused; beyond 300 ly and beyond 250 ly it faces a separate 50% refusal roll each; under 250 ly it always proceeds. The flags are set only by personality 5's driver (`:67791`-`67801`, after the whole scratch array is zeroed at the start of each AI player's run, `:57987`-`57991`). Personality 4 also calls the check (`:69985`) but never sets the flags, so for it the nearest unflagged planet is the producing planet itself, at distance 0, and the check always passes. See §6.

**Random exploratory colonization** uses reservoir sampling over an expanding search radius when no strong candidate is found nearby, so early scouting fleets don't get stuck idle simply because nothing scores well yet.

### 3. Starbase building advisor (part of the shared end-of-pass routine)

The end-of-pass routine `FUN_1090_59e6` (`:65510`-`65605`, run by every driver) first calls the starbase-building advisor `FUN_1090_510a` (`:65069`-`65144`). This section is the governing description of that advisor. It queues a *first* starbase on a planet that has none. Replacing an existing starbase is the job of the starbase-upgrade advisor (`FUN_1090_52da`, §6), the first advisor of the per-planet chain that follows, and which designs the starbase slots hold is decided by the AI starbase designers (§15a).
- *When it runs.* Never for category 5 (Macinti) and never for category 7, whose driver passes no default slot. In a tutorial session (client state bit `0x800` of `DAT_1128_078a`), and for a category-1 AI in a game carrying the tutorial's fixed game identifier (set by `FUN_1078_4938`, `:52866`), only up to year 30 (`:65087`-`65091`). Otherwise every turn. It walks every planet in planet-table order, not in the shuffled order of §8.
- *Category 4 (Cybertrons).* The planet test is `FUN_10a8_2bf8` (`:71168`-`71190`): an own planet with no starbase, a habitability value (`FUN_1048_490e`) above 14 and a stored population (planet `+0x28`) above 499 units (more than 49,900 colonists). When all three mineral concentrations (planet bytes `+9` to `+0xb`) exceed 15, the design is the default slot D (slot 5 when it holds a design not marked deleted and created later than slot 0's, else slot 0; `FUN_1090_50e4`). Otherwise it is the hub slot H (slot 6 under the same test against slot 1, else slot 1; `FUN_1090_50bc`).
- *Categories 0-3.* An own planet qualifies when it is one of the AI's freighter hubs (§5), has no starbase (or a starbase slot number above 9), has a stored population above 79 units (at least 8,000 colonists) and does not carry the urgent-supply flag of §5. The design is the default slot D.
- *Queue test and order.* Nothing is queued when the planet's queue already holds a starbase design (a queue item of the design kind whose type is 16 or more). Otherwise one unit of the chosen starbase design goes to the bottom of the queue (`FUN_1090_2736`, position 1). Minerals and resources are not checked.
- *History.* Earlier versions of this section described a shared "starbase AI" pass that moved minerals between starbases (a 700-unit transfer), chose Stargate or orbital builds, and switched fleets between aggressive and cautious attack profiles through a "14 / 499 / three counts above 15" readiness check. No such pass exists, and that text has been removed. The 700 kT figure belongs to personality 4's packet routine `FUN_10a8_123e` (§12, personality 4, *Packets*). The figures 14, 499 and 15 are the habitability, population and concentration thresholds of the category-4 planet test above.

### 4. Threat assessment and defense/minefield decisions

**Status (re-checked against the driver code): the legacy bullets below are misreadings of two routines documented elsewhere; do not implement them.** No AI driver path computes a threat rating or decides minefield building this way.
- *The "threat rating of 4-6 with jitter and a +1 trait bump"* and the *"scratch list of nearby enemy indicators"* are the end-of-pass speed setter `FUN_1090_12be` (`:61751`-`61836`): its list is the foreign minefields (leaving out Speed Bump fields), and the 4-6 value is the warp chosen for a leg that crosses one (6 for Heavy, 5 or 4 for Standard), plus 1 for a Super Stealth race. §12 ("Speeds are set at the end of the pass") is the governing description.
- *The "defense-need evaluator"* is the colony-ship gate `FUN_1090_2baa` (`:62955`-`63092`), used by personalities 0 and 5 (§12). It is evaluated once per AI run, before the planet pass (`:58229`, `:67730`), and its yes/no applies to every planet that turn. *(Resolved; re-read in full against the decompile. The steps run in this order, and the first that decides wins.)*
  1. *Easy AI, odd years.* At skill 0 (bits 10-12 of the control word, §1a) it refuses whenever the year counter (0 in the first year) is odd, in every year including the first 30. An earlier text applied this rule only from year 30.
  2. *Early game.* Before year 30 it allows.
  3. *Colony designs.* It marks every one of the AI's 16 ship-design slots whose design is not flagged deleted (bit 1 of design byte `0x7c`) and is built on hull 14 or 15, the Mini-Colony Ship and the Colony Ship. With no such design it refuses.
  4. *Fleet count F.* F is the number of the AI's own fleets that hold at least one ship in a marked slot, each fleet counted once however many such ships it carries (fleet stack counts at fleet `+0x0c`). F is also handed back to the caller. If F exceeds 20 × the galaxy-size index + 10, it refuses: 10 colony fleets in a Tiny galaxy, 90 in a Huge one.
  5. *Planet tally P.* P is the sum of the planet-count word at offset 2 of each 192-byte player record (the record base used by the trait accessors, §14) over every player record whose bit 8 of the control word (record offset 6) is set. The count is not stored in the file. The loader zeroes it and adds 1 for every planet record it reads whose owner is that player (`:44192`, `:44509`), so it counts the planets that the AI's own file shows as owned by that player. Bit 8 is set on the records the AI's file carries in full: the loader allocates design tables only for such players (`:44587`, `:44646`), and turn processing sets the bit when another empire becomes known (`:47826`-`47831`). So P is, presumably, the planets known to be owned by the AI itself and by the empires it knows. If F + P exceeds four fifths of the galaxy's planet count (planets × 4 ÷ 5, rounded down), it refuses.
  6. *Build-counter test.* B is the sum, over the marked designs, of each design's built counter. This is the 32-bit count at design offset `0x7f`, beside the "number in existence" count at `0x83`. The counter rises by the number of ships each time ships of the design are completed (`:77514`) and is set to 0 whenever a new design is written into the slot (designer `:82908`, `:83291`; the AI builder overwrites the whole record, `FUN_1090_0634`). Starting designs get their counters at game creation (`:51211`, `:51922`). Losing ships never lowers it. If B − (F + P) lies between 0 and 25 inclusive, it allows. The test is a 32-bit unsigned comparison, so a negative difference fails.
  7. *Small-fleet coin.* Otherwise, if F is below 5 and a 1-in-2 roll succeeds, it allows.
  8. Otherwise it refuses.

  *What this means in play.* Step 6 compares colony ships ever built from the current colony designs with colony fleets plus known owned planets, home worlds included. Since every known empire's planets count in P, B − (F + P) is usually negative, so after year 30 the gate mostly comes down to steps 4, 5 and 7: new colony ships only while fewer than five colony fleets exist, each turn's permission granted with probability ½, and none once fleets plus known owned planets reach 80% of the galaxy. The gate has nothing to do with minefields or defences; the bomber-defence advisor is in §6.

### 5. Automated mineral/cargo transport

The AI's freighter router is `FUN_1090_19c8` (segment 19, `stars.exe.export.c:62101`-`62514`). Personalities 0-3 call it once for each idle hauler fleet (`:58794`, `:60320`, `:66696`, `:67356`), passing the freighter and its hub planet (see "Hubs" below). Personalities 4, 5 and 7 never call it. The router scores every planet, and through `FUN_1090_23de` nearby floating mineral objects, as *value divided by travel time*, and sends the freighter to the best one. Travel time is the straight-line distance converted into a rounded-up count of 25-light-year legs. 25 ly is one year's travel at warp 5 (distance per year is warp squared, `fleet-movement-scanning-cargo.md`), but nothing else in the routine assumes warp 5: the order it writes asks for warp 4, and the end-of-pass speed setter then replaces that speed anyway (§12). An earlier version of this section said the router sums the cargo hold, skips targets other fleets already serve and uses a 180-light-year (32,400 squared) cutoff with a random fallback. That described `FUN_1090_1438`, which is not a freighter routine: it is the warship enemy-fleet hunter (§12).

**Corrections to earlier passes (settled by reading the callers and the raw bytes).** These replace the two long paragraphs that stood here, which identified `FUN_1090_1438` as the freighter router.
1. `FUN_1090_1438` (`:61840`-`62097`) takes a warship fleet, the list of the AI's own combat fleets and the list of every foreign fleet. Its 16-word sum at fleet offset `+0x0c` is the fleet's ship count, not a cargo sum. Its 180-ly (32,400 squared) radius is the range at which the warship engages an enemy fleet. Its three call sites (`:58881`, `:68516`, `:69812`) sit in the combat-fleet branches of personalities 0, 5 and 4. Its behaviour is given in §12.
2. `FUN_1050_29b8` sums a fleet capacity, not a resource cost. Mode 2 is total cargo capacity: per design slot, the design's cargo figure (`FUN_1050_2a2e`) times the slot's ship count. Mode 1 is total fuel capacity. `FUN_1050_3c82` subtracts the four carried cargo amounts (fleet `+0x4c`-`+0x5b`) from mode 2 to give free cargo space. `FUN_1050_3cc8` subtracts carried fuel (`+0x5c`) from mode 1.
3. `FUN_1090_452c` (`:64444`) sends a fleet to the nearest owned planet that has a starbase (`FUN_1090_4434`). The warship hunters use it to send a fleet home when its fuel is below half its capacity.
4. `FUN_1090_420c` has nothing to do with cargo (§6, corrected).

The segment holding all `FUN_1090_*` routines is NE segment 19 (selector `0x1090`), not 20 as some earlier notes said.

**How the router scores and orders.** Each step below was checked against the raw bytes of segment 19, offsets `0x19c8`-`0x2667`. The decompile drops the floating-point operands, and these were read from the raw code.

1. *Setup* (`:62149`-`62223`). The router clears a per-planet "already served" mark. It then marks every planet that another of the AI's own fleets already has a Transport order to, when that other fleet has two or more waypoints and holds ships in the same design slot as this freighter's first occupied slot. The freighter's hub is never marked. A freighter with no cargo capacity gets no order. Fullness is 100 minus the truncated value of 100 × free space ÷ capacity, so fullness rounds up.
2. *Hub scarcity* (`:62166`-`62189`). The scarcest of the hub's three surface minerals is the first strictly smallest, taken in Ironium, Boranium, Germanium order. It is compared with the smallest of the minerals listed before it; when Ironium is the scarcest, the comparison value is effectively infinite. The scarcity level is 1 if the scarcest mineral is below half of the comparison value and 2 if it is below a quarter, else 0. Both the halving and the quartering round down.
3. *Travel time T* (`:62242`-`62251`, raw `0x1c0f`-`0x1c98`). Take the square root of the squared distance from the freighter to the candidate and truncate it to whole light-years; the runtime's float-to-integer conversion runs in truncation mode. Then T = (d + 24) integer-divided by 25, i.e. d/25 rounded up, raised to at least 1. Each score is a value divided by T, using 32-bit integer division that truncates.
4. *Candidates* (`:62233`-`62363`). The router makes one pass over the planet table, skipping the freighter's current planet and every marked planet.
   - An unowned planet that carries the remote-mining mark (bit 7 of its mining-value byte, set by personality 1's miners): value = 500 × the 7-bit mining value.
   - Any other planet not owned by the AI, including an unmarked unowned one. For personality 0 only, the value is 6,500 when the freighter is at its hub and either (a) the hub's population is over 1,100 stored units (more than 110,000 colonists) and the planet's reported population figure (§12) is at most 61 (about 24,400 colonists), or (b) the hub's population is over 300 stored units (30,000 colonists) and the figure is at most 14 (about 5,600 colonists). An unowned planet's figure is 0. (Units: §13.) Otherwise such a planet counts only if the personality has flagged it as habitable for itself (personalities 1-3 set this flag) and the freighter is at its hub; it is then scored like an owned planet.
   - An owned planet other than the hub, skipped if it has a starbase or if the first item in its production queue is a starbase design (a design item with index 16 or more). If the planet carries the urgent-supply flag (an owned planet with negative habitability; personalities 1-3 set it) and the freighter is at its hub, the score is a flat 25,000. Otherwise let M be the planet's surface stock of the hub's scarcest mineral (level 2); or all three minerals with the other two halved, rounded down (level 1); or all three minerals (level 0). If M is at least 10, value = 100 × the smaller of (truncated 100 × M ÷ capacity) and (100 − fullness).
   - The hub itself, when the freighter is elsewhere and more than 34% full: score 25,000 if the freighter is exactly 100% full, else 20 × fullness ÷ T. A T of zero skips the hub.

   The highest score wins. A later candidate must score strictly higher, so a tie keeps the earlier planet in table order.
5. *Floating minerals* (`FUN_1090_23de`, `:62521`-`62638`, raw `0x23de`-`0x2667`). The router next walks the map-object table for objects of class `0x20` whose byte-7 bits 2-5 are zero. *(Identified.)* Class `0x20` is the mineral-packet object kind. The special-object pass (`:72728`-`72745`) reads a packet's destination planet from the low 10 bits of word 3 and its speed from those same byte-7 bits (warp − 4). An object of this kind whose speed field is zero is a stationary **salvage** pile, made by `FUN_10f0_1850` (`:99101`). That routine adds to an existing pile at the same spot, never creates one on a planet, and is called for ships destroyed in battle (`:99071`, `:102250`), for ships destroyed by mines (`:74521`) and for a fleet scrapped in deep space (`:75699`). So the router collects salvage, never packets in flight.
   - An object at exactly the freighter's position is loaded on the spot by immediate transfers: the scarce mineral first when the level is not 0, then each mineral unless the level is 2. If that leaves the hold full, the destination becomes the hub.
   - Otherwise the object is a candidate if the freighter's x minus the object's x and its y minus the object's y are both at most 200. These are signed differences, so only objects lying more than 200 ly in the negative x or y direction are excluded. The object's M follows the same scarcity rule. Its score is 100 × min(truncated 100 × M ÷ capacity, 100 − fullness) ÷ T, with T from the true distance. It must beat the best planet score.
   - *What the AI knows about salvage* (traced: per-observer visibility pass `FUN_1070_5aa0` `:49218`-`49255`, fleet sweep `FUN_1070_5f00` `:49384`-`49425`, planet sweep `FUN_1070_64fc` `:49656`-`49690`; file writer `FUN_1070_374a` `:47670`-`47709`). The table the router walks is the map-object list of the AI player's own file, as the host wrote it at the end of the last turn generation; the AI never reads the host's data. A class-`0x20` object (packet or salvage) is written into a player's file only when that player saw it that year: it lay within the normal (non-penetrating) scanner range of one of the player's fleets or planets during the visibility pass, which runs after movement and battles. Cloaking plays no part, and a fleet without a scanner sees only objects at its own position. A Packet Physics player is given every class-`0x20` object in the galaxy (`:49227`), but personality 4, the Packet Physics archetype, never runs this router. The 18-byte record is copied whole, so the AI knows each visible pile's exact position and exact mineral contents, with none of the noise of planet reports. It knows nothing of piles outside its scanner coverage, and a pile seen in an earlier year but not this year is simply absent from its file. Salvage made this year by battles, mines or deep-space scrapping is included when it lies inside the coverage.
   - *Reimplementation note (recommendation, not original behavior).* Build the candidate list from the AI player's own scan results for the year: every salvage object inside the normal scanner range of its fleets and planets, with its true contents. A reimplementation that keeps no salvage reports can omit the floating-mineral candidates; this changes only the cases where a pile would have beaten every planet score.
6. *Order* (`:62378`-`62513`). With no candidate, the freighter gets no order. Otherwise the destination becomes its only next waypoint, written at warp 4 (the speed pass in §12 replaces this).
   - For a planet: task Transport, with each mineral set to Unload All at the hub and Load All anywhere else. For a floating object: no task.
   - When the destination is not the hub, the level is not 0 and the destination is a planet, the actions are narrowed. If the level is 2, or free space is no more than the destination's stock of the scarce mineral, only the scarce mineral keeps its action. Otherwise, if the destination is owned, every mineral switches to "fill up to a percentage": 66% for the scarce mineral and 33% for each of the others.
   - Colonists are loaded at the hub, immediately, only by personality 0 (category 0) and personality 1 (category 1).
     - All figures in these three bullets are stored population units (1 unit = 100 colonists = 1 kT of colonist cargo; §13). A load is an immediate transfer capped by the hub's population and the free hold.
     - Category 1: if the hub's population exceeds 1,200 units (120,000 colonists) and the destination is a planet owned by any player with a smaller population, the freighter loads 1,000 units (100,000 colonists).
     - Category 0, destination owned by the AI: no load if the destination's population is over 999 units (99,900 colonists), if the hub's population is at most 1.5 × the destination's, or if the hub's population is under 501 units (50,100 colonists). Otherwise it loads the hub's population × p ÷ 100 units, where p is 10 (hub over 2,000 units, 200,000 colonists), 8 (over 1,500 units), 5 (over 1,000 units) or (hub − 400) ÷ 100 (501-1,000 units).
     - Category 0, destination owned by another player: it loads 100 units (10,000 colonists), or 300 units (30,000 colonists) if the hub's population is over 900 units (90,000 colonists).
     - In both categories, a colonist-carrying run to a planet other than the hub also gets Unload All for colonists at the destination.

**Hubs** (`FUN_1090_2f16`, `:63196`-`63491`, run from the research-choice preamble `FUN_1090_2900`; skipped for categories 4 and 5). Each AI keeps a persistent table, loaded and saved with its file, of up to 64 hub planets, each with up to 8 assigned freighter fleets. From turn 20 on, every turn:
- hubs the AI no longer owns are dropped;
- every owned planet with a starbase becomes a hub;
- so does any owned planet without a starbase that meets all of these:
  - population over 79 stored units (at least 8,000 colonists);
  - at least 20 mines and 20 factories;
  - surface minerals plus 4 × the square of each mineral's concentration totalling at least 7,000;
  - for category 0 only, no existing hub within 50 ly;
- each unassigned hauler fleet joins the nearest hub that has fewer than 8 freighters;
- a hub with fewer than 4 freighters takes one from the first hub that has at least two more.

A freighter with no hub uses the AI's first owned planet with a starbase. Personality 0 routes no freighters at all if it owns no starbase. Where the table is stored, what happens when it is missing, and whether a stateless rebuild gives the same result are in §15.

### 6. Production-queue insertion by the AI

The AI's per-planet production advisors form a fixed chain run inside the end-of-pass routine `FUN_1090_59e6` (`:65510`-`65603`, raw segment 19 `0x59e6`-`0x5bd9`), right after the starbase-building advisor of §3. In order they are a starbase-upgrade advisor, the mass-driver/mineral-packet advisor, a planetary-scanner advisor that can never fire, a Defenses advisor and a Terraform advisor; the first one that queues something ends the chain for that planet (bullets below). *(Resolved, item "defence-percentage advisor": the earlier list here, "a defense-percentage-target advisor, a mass-driver/mineral-packet advisor, two further advisors for other component categories, and a fallback advisor", misread the chain. There is no defence-percentage advisor; its "age-dependent chance with a flat 5% branch" is the starbase-upgrade advisor `FUN_1090_52da`, whose flat branch is in fact 6%. Each advisor below was re-read in the decompile and checked against raw segment 19, `0x52da`-`0x59e5`.)* After this chain has run for every planet, a separate pass queues defences on planets threatened by enemy bombers (bullet below; earlier passes called it an auto-load-cargo check). Every driver then ends with the shared **end-of-pass top-up** (`FUN_10a8_1e2a` → `FUN_10a8_1e8a`, last bullet below). *(Corrected: earlier text said this routine fills the cost of the active production item and spills the excess into a secondary slot. It does neither. It queues Factories, Mines, Mineral Alchemy and, for one personality, Terraforming out of each planet's uncommitted surplus.)*

Concrete observed thresholds:
- **Which planets run the chain, and which advisors each personality gets** (`FUN_1090_59e6`, `:65533`-`65592`). The routine walks the AI's owned planets in the shuffled order of §8. All population figures here are stored units (1 unit = 100 colonists, §13).
  - *Population gate.* Category 0 takes a planet with a population of 40 units or more (4,000 colonists). The other categories take a planet with 60 units or more (6,000 colonists), or any planet carrying the urgent-supply flag of §5 (an owned planet with negative habitability; only categories 1-3 set it, so for the others the 60-unit rule is the whole test).
  - *Queue-affordability gate.* Except for category 5, a planet is skipped when, for any of the three minerals, the full cost of what its queue already holds exceeds the projected stock (surface stock plus this year's mining; `FUN_1090_355c` against `FUN_1090_3604`). Resources are not compared.
  - *Chain per category.* Categories 0-5 and 7 run the starbase-upgrade, packet, scanner and Defenses advisors in that order, stopping at the first that queues something. Then, for every category except 0, the Terraform advisor runs if nothing was queued. A planet carrying the urgent-supply flag (categories 1-3 only) skips the first four advisors and gets only the Terraform advisor. The advisors' own gates then narrow this further: the packet advisor returns at once for category 4 and needs skill 2 or more, the Terraform advisor returns at once for category 4, and the starbase-upgrade advisor does nothing for category 7 (its driver passes no starbase slot) and has a separate branch for category 5. In effect: category 0 gets starbase upgrades, packets and Defenses; categories 1-3 and 5 get all four working advisors; category 4 gets starbase upgrades and Defenses; category 7 gets packets, Defenses and Terraform.
  - Apart from the packet advisor, which can queue up to four packet items in one call (see its entry below), each advisor that acts puts exactly one item into the queue, at the bottom (`FUN_1090_2736`, position 1). The 200-entry cap below still applies.
- **Starbase-upgrade advisor** (`FUN_1090_52da`, `:65146`-`65289`; raw `0x52da`-`0x55af`). It replaces a planet's existing starbase with a newer design of the same role. It queues one starbase design and nothing else; it never queues Defenses.
  - *The default slot.* Categories 0-4 pass a default starbase slot D, chosen each turn by `FUN_1090_50e4` (called from the research-choice preamble `FUN_1090_2900`, and directly by category 4). D is 5 when starbase slot 5 holds a design that is not marked deleted and was created later than slot 0's design, else 0. Category 5 passes 0; category 7 passes "none", and the advisor then does nothing.
  - *How the ten starbase slots are read.* Slots 0-4 are the older generation and 5-9 the newer one. Inside each generation the even rungs (0, 2, 4 and 5, 7, 9) form the ordinary ladder and the odd rungs (1, 3 and 6, 8) the packet-hub ladder; slots 1, 3, 6 and 8 are exactly the starbase slots §12 calls packet hubs. For a hub slot the generation base is H instead of D: H is 6 when slot 6 holds a design that is not deleted and is newer than slot 1's, else 1 (`FUN_1090_50bc`).
  - *Common gates (categories 0-4).* Nothing is queued if the planet's queue already holds a starbase design, if the planet has no starbase, or, for category 4, before year 40.
  - *Starbase already in the current generation.* Let s be the planet's starbase slot. "In the current generation" means D ≤ s ≤ D + 4 (H ≤ s ≤ H + 2 for a hub slot). If s is the top rung (4 or 9; 3 or 8 for a hub), nothing happens. Otherwise the advisor queues slot s + 2, the next rung up, when all of these hold: slot s + 2 is not marked deleted; a roll of 0-99 is below 6 (a flat 6% per turn); and the planet holds at least 200 kT of each mineral on its surface.
  - *Starbase in the other generation.* Let a be the age in years of the current generation's base design (slot D, or H for a hub), minus 10. If a is negative it counts as 0; below 50 it is halved, rounded down; from 50 on it is used as is. The advisor acts when a roll of 0-99 is below a + 5, so the chance is 5% while the base design is under 10 years old, rises by one point every two years up to 29% at 59 years, and jumps to 55% at 60 years. It then queues the same rung in the current generation: slot (s mod 5) + D, or (s mod 5) + H − 1 for a hub slot. This branch checks neither minerals nor whether the target slot holds a design. For categories 0-4 the target is in practice never empty: the starbase designer builds a generation's rungs together, and its Space Station and Orbital Fort designs can always be built (§15a). If the target were empty or deleted, the order would still be queued. The cost calculator prices a deleted design at zero (`FUN_10d0_221a`, `:87592`-`87598`), so the item completes as soon as the production walk reaches it; the completion routine then refuses it with no message (`FUN_10b8_0e68`, `:77010`-`77011`) and the order is removed (`production-queue.md` §10e). Nothing is spent and nothing is built. It is also how a planet falls back to the old generation when slot 5 or 6 stops being newer than slot 0 or 1.
  - *Category 5* has its own branch (`:65246`-`65288`), driven by a ten-entry urgency mark per starbase slot that its starbase-design maintenance `FUN_1090_492e` (`:64636`-`64787`) computes each turn. For slots 1-3 the mark comes from the design's age: 2 at 35-49 years, 3 at 50 years or more, 0 when younger, 1 when the slot is empty and no design could be made. Only the most urgent of slots 1-3 keeps a mark above 1 (`:64697`-`64714`): the highest mark wins; between equal marks the design created earlier (smaller creation year, design `+0x7d`) wins; between equal years the lower slot wins. The other marks above 1 among slots 1-3 are reset to 0. This filter runs before the slot 2 and 3 override below, so after the override two of slots 1-3 can again carry mark 2. *(Slots 0 and 4-9 traced: `:64652`-`64781`, design builder `FUN_1090_4bea`, `:64791`-`64858`.)*
    - *Who writes the designs.* The same routine is category 5's starbase designer. A slot among 1-3 whose design is deleted or has no starbase of it in existence is rebuilt every turn, on chassis 1, 2 and 3 (Space Dock, Space Station, Ultra Station); a successful build gives mark 0, a failed one mark 1. One exception among the in-use designs: from year 26, slot 1 is marked 3 even when young unless its design has exactly 8 component slots (a Space Dock). The Macinti templates are Alternate Reality (§14), whose home world starts with the Space Station "Starbase" design in slot 1, so this pushes the home world out of slot 1. The chassis, templates and armament variants are tabulated in §15a.

    - *The rules.* Let s be the planet's starbase slot (the low nibble of planet word `0x2c`).

    - Otherwise, when s is 4, 5, 7 or 8, an 8% roll (a 0-99 roll below 8) queues slot s + 1.
    - Otherwise, when s is 0-3, it upgrades only if the planet's population is at least 16% of its capacity, with a chance of (percentage − 15) × 6%, certain from 32% up. The percentage is `FUN_1048_476c`: population × 100 ÷ capacity, rounded to the nearest whole number and capped at 999.

    - This branch does not require an existing starbase. The queue test at the top of the advisor (no starbase design already queued) runs for every category, category 5 included, but only when the planet has a starbase (`:65168`-`65181`, raw segment 19 `0x52e8`-`0x533d`); on a planet without one there is no queue test, and the branch works from whatever slot number the planet record holds, so it can queue a starbase there. *(Corrected: an earlier text said the branch never checks the queue.)* Taken literally this lets a starbase-less planet collect one more starbase order on every AI turn until one completes, whenever one of the rules above fires for the slot number the planet record still holds (a mark of 2 or 3, or the 8% rule; the population rule cannot fire, because an Alternate Reality planet without a starbase has a capacity of 0 and `FUN_1048_476c` then returns 0). The planet must still pass the advisor chain's 60-unit population gate, and category 5 has no queue-affordability gate. - **Mass-driver/mineral-packet advisor** (`FUN_1090_4d10`, `:64864`-`65028`; re-read in full, replacing an earlier summary that said "a minimum population score of at least 10"). This is the governing description of the shared per-planet packet advisor. (1) The category is not 4. (2) The queue holds no packet item (types 14-17). (3) The AI's skill is 2 or more (Tough or Expert). (4) Projected Ironium + Boranium + Germanium exceed 3,000 kT. (5) The planet has a starbase. (6) The starbase's best mass-driver warp is 10 or more. This is the plain best warp returned by `FUN_1048_5138`, without the +1 for a doubled driver.   - *Range.* The squared range comes from a two-entry table of 32-bit constants in segment 19 at offset `0x1db` (raw bytes, read past the end of the preceding routine).     | Best driver warp in | Squared range | About | Tripled | About |
    |---|---|---|---|---|
    | one slot | 7,056 | 84 ly | 21,168 | 145 ly |
    | two slots | 50,625 | 225 ly | 151,875 | 389 ly |

  - *Target.* Every planet in the galaxy table is tested, in table order. A candidate must meet all of these: it is owned by another player; its report on file is at most two years old (report year + 2 ≥ current year); its reported coarse defence value is below 14 *or* its reported population figure is below 750 (the 4-bit and 12-bit report fields of §12's invasion check); its owner is not Alternate Reality; it is not a Packet Physics planet with a starbase; and it is within range. With no candidate, nothing is queued, the destination is untouched, and the chain moves on to the next advisor.

The launch then follows the production rule of `production-queue.md` §10b: warp 13 is legal from any driver of warp 10 or more, and the overspeed class is 13 minus the launch rating (so 3 for a single warp-10 driver, 0 for a warp-13 driver). The mineral rules below never change the destination or the speed; they only choose what is queued. The destination is set even when those rules queue nothing.

- **End-of-pass top-up** (`FUN_10a8_1e8a`, `:70668`-`70898`; raw segment 22 `0x1e8a`-`0x23cf`, verified bit for bit). It runs once for each owned planet, in the shuffled planet order of §8. The planet's queue is opened for editing (`FUN_10d0_010c`) before the routine and committed after it.
  - *Surplus.* S is the planet's projected availability minus the full cost of everything already in its queue (`FUN_1090_3604`), taken separately for each mineral and for resources as 32-bit values. Projected availability is surface stock plus this year's mining for each mineral, and this year's resources after the research share (`FUN_1090_355c`, above). If the resource surplus S_R is negative, nothing is queued.
  - *Room and unit costs.*
    - Mine room is the operable-mine cap, minus the smaller of mines built and that cap, minus the manual Mine items (type 8) already queued, floored at 0.
    - Factory room is computed the same way with factories (type 7).
    - The one-unit costs of a Mine, a Factory and a Mineral Alchemy unit (type 11) come from the cost calculator in single-unit mode (`FUN_10d0_221a`, mode 1).
    - T is the quantity of Terraform Environment (type 12) the planet's build list still allows.
  - *Step 1, category 5 only.* If T > 0, n = min(T, ⌈S_R ÷ 70⌉), computed as (S_R + 69) ÷ 70. If n ≥ 1, n Terraform units go to the top of the queue and the routine stops.
  - *Step 2a, some mineral surplus is 0 or less.* If the queue's first item is Mineral Alchemy (auto or manual), nothing is queued. Otherwise no factories are queued. Mines m = min(mine room, S_R ÷ mine resource cost), and S_R loses m × that cost.
  - *Step 2b, all three mineral surpluses are positive.*
    1. Let f₀ be the factory room. If f₀ ≥ 1, it is capped by S_G ÷ factory germanium cost; only germanium is checked. In a tutorial session (client state bit `0x800` of `DAT_1128_078a`) it is also capped by the ironium and boranium quotients.
    2. If f₀ ≥ 1, factories f = min(f₀, S_R ÷ factory resource cost); otherwise f = 0. S_R loses f × that cost.
    3. Mines m = min(mine room, S_R ÷ mine resource cost). Mines are never checked against minerals. S_R loses m × that cost.
  - *Step 3, Mineral Alchemy.* It needs all six of the AI's tech levels at 26, a year counter above 100 and an alchemy unit cost above 0. The count is a = S_R ÷ alchemy resource cost + 1, one unit more than the leftover pays for.
  - *Where items go.* Factories go to the bottom of the queue and mines to the top. Alchemy goes to the bottom after step 2b and to the top after step 2a. A zero quantity is never queued, and the 200-item insertion cap below still applies.
  - *Rounding.* Every quotient is a signed 32-bit truncating division of non-negative operands, so it rounds down. The only exceptions are the Terraform ceiling (the +69) and the alchemy +1, which is added after truncating. Each quotient is compared with its room as a 16-bit signed value. The clamps are the floor of 0 on each room, the minimum with each room, and the minimum with T. Factories are settled before mines and mines before alchemy, and each step subtracts its spending from S_R before the next one starts.
  - *Worked example.* Take a surplus of 200 Ironium, 150 Boranium, 30 Germanium and 500 resources, with example costs of 10 resources plus 4 Germanium per factory and 5 resources per mine. Factory room is 40, mine room 25, there is no tutorial, the category is not 5 and the techs are not all 26.
    - f₀ = min(40, 30 ÷ 4 = 7) = 7, and f = min(7, 500 ÷ 10 = 50) = 7. That leaves 430 resources.
    - m = min(25, 430 ÷ 5 = 86) = 25. That leaves 305 resources.
    - Result: 7 Factories at the bottom of the queue and 25 Mines at the top.

    A category-5 AI with T = 10 and S_R = 141 would instead queue (141 + 69) ÷ 70 = 3 Terraform at the top and nothing else that turn. If all techs were 26 after year 100 and alchemy cost 100, the first case would also add 305 ÷ 100 + 1 = 4 Mineral Alchemy at the bottom.
- **Production-queue insertion cap**: a build-order is refused outright once its queued-item count exceeds 200 (a hard structural limit, independent of the per-item 1,023-unit quantity cap documented in `production-queue.md`).
- **Isolation check gating further expansion investment**: before committing to expansion-oriented production (e.g. scouts/colonizers) from an owned planet, the AI evaluates that planet's isolation from the nearest planet it does not own — a check that was previously misattributed to new-game home-star selection in `new-game-setup.md` §6, corrected there this pass. ### 8. Fleet turn-processing order is randomized

**Status: this section's original claim is now treated as an unconfirmed legacy claim (see the last Open Questions entry). What is confirmed is a shuffle of the AI's owned-planet order and of the per-year player order; no fleet-list shuffle was found.** The original claim read: the list of fleets an AI empire owns is reshuffled (Fisher-Yates style, using the same bounded random-number generator used throughout the game) before each turn's fleet-processing pass, unless a specific global flag suppresses it. Had that been true, fleet decision order would not be stable across implementations; as it stands, a clean-room implementation should walk fleets in plain array order and reproduce the confirmed planet-order and player-order shuffles instead.

**Pinned to a specific function by a later segment-31 sampling pass.** The shuffle is a plain, textbook Fisher-Yates: for each position (from a total count down to 1), it draws a bounded random index over the not-yet-shuffled prefix and swaps that slot into place using a fixed-size temporary buffer, over a single global array of 29-byte records. This independently confirms the mechanism's shape (not just its existence) at the code level, though the specific array's game-visible identity (fleets specifically, versus some other 29-byte-record table this shuffle is also reused for) was not re-derived from structure alone in this pass.

**Correction, from an exhaustive fourth pass over segment 31 (see `combat-resolution.md` §8's segment-31 note): this specific function's array is the per-battle token table, not an AI empire's owned-fleet list.** The function takes no parameters — it always shuffles the same two globals, which a neighboring function in the same segment populates immediately beforehand as the just-built battle-token array (one 29-byte record per token, for the current battle only), and its record count is capped at exactly 256, matching `combat-resolution.md` §2's token cap. Because the function is hard-wired to this one array, it cannot be a general-purpose "shuffle any 29-byte-record list" routine reused elsewhere for AI fleet-processing order — so the claim above, that *this* code path is what randomizes an AI empire's per-turn fleet-processing order, should be treated as unconfirmed rather than pinned. It remains true that *some* mechanism reshuffles AI fleet-processing order each turn (see the surrounding paragraph), and it may still use an identically-shaped Fisher-Yates helper elsewhere in the codebase, but the concrete function traced into segment 31 is now known to serve battle-token tie-break ordering (most likely underpinning `combat-resolution.md` §5's "randomly decides a firing priority... kept fixed for the rest of the battle" rule) rather than fleet-turn-processing order specifically. This paragraph supersedes the shuffle-mechanism attribution in the paragraph above; the general "fleets are reshuffled before per-turn processing" claim itself is not retracted, only its evidentiary link to this particular function.

**A second, genuine Fisher-Yates shuffle was located this pass — but for the AI's owned-*planet* list, not fleets.** `FUN_1090_60de` (segment 19) is one of four setup calls the dispatcher `FUN_1088_0000` (§1) makes for the current player immediately before invoking that player's personality driver. It first rebuilds a scratch array of every record the current player owns from a fixed source table (stride 56 bytes, owner field checked against the current player at record offset 2), then — unless a specific global flag bit is set — reshuffles that array with a textbook forward Fisher-Yates using the same bounded RNG helper (`FUN_1040_1652`) documented throughout this project: for each index from 0 up to count-2, it draws a bounded random offset into the remaining unshuffled suffix and swaps that element to the front. This array is exactly the one `FUN_10a8_1e2a` (§6) walks immediately afterward, calling the confirmed per-*planet* resource-allocation pass (`FUN_10a8_1e8a`) once per entry with a "current object type" tag of `1` (set via `FUN_1048_2c12`) — the same tag convention used elsewhere to mean "planet," contrasted with tag `2` used for fleet-scoped calls (see §10 below). So this shuffle randomizes **per-turn planet-processing order**, a real and previously-undocumented mechanism, but it does not appear to be the fleet-processing-order shuffle this section describes — no analogous "build a fleet list, then Fisher-Yates it" function was located feeding into the fleet-iteration step (§ Overview, step 3) inside any of the six personality-driver bodies in the time available. Whether fleet-processing order is separately randomized by a not-yet-located function, or whether the "fleets are reshuffled" framing above should instead be revised to "planets are reshuffled," was settled by later sweeps in favour of the latter — see the last Open Questions entry.

### 10. Stale-slot sweeps and pool redistribution (supporting utilities)

Two smaller, confirmed utility mechanisms support the AI's per-field bookkeeping (the same fixed-size per-field slot arrays referenced in §6-7): one sums a slot range's values (capped at 32,000) while flagging any slot whose "last touched" turn is older than a caller-supplied threshold, optionally purging a stale-and-empty slot outright; the other redistributes a 16-slot shared pool into a matching owned fleet whenever a particular per-race stat drops below **501**, repeating until the stat recovers. The concrete real-world meaning of the redistributed pool and the race stat being monitored could not be determined from structure alone. **Resolved (§16, item 3):** the "pool" is the 16 stack counts of the fleet being edited (the fleet scratch record), the 16-slot array is this turn's stale-design flags, and the routine splits the stale stacks of a mixed fleet off into a new fleet while the player owns fewer than 501 fleets; the monitored stat is the player's fleet count. The paragraphs below are kept as history.

**The redistribution function pinned this pass: `FUN_1090_5bda` (segment 19).** Given a caller-supplied 16-slot boolean "which slots matter" array, it first reads a per-race stat from the same per-race/per-slot record base used for the personality dispatch and the relationship table (stride 192 bytes — see §1 and `diplomacy-relations.md` §1), specifically the low 12 bits of the record's very first word, and loops while that stat is below 501, rebuilding a fresh candidate list each iteration by walking the same fleet-shaped source table referenced in §5/§9 (filtered to the current player's own fleets, excluding a specific flag bit), searching each candidate's own 16-slot field for the first slot the caller's array also flags. Once a match is found, it marks the operation as fleet-scoped (tag 2 via `FUN_1048_2c12` — the counterpart of the planet-scoped tag 1 used by `FUN_10a8_1e2a` in §6/§8 above), copies a shared 16-entry pool (a global array plus a companion parallel array) into a scratch buffer, zeroes the source slots the flag array selects, writes the redistributed values into the candidate fleet's own matching slots, and commits the change before re-checking the stat and looping. This confirms the "matching owned fleet" wording in this section's own description at the code level (fleet-scoped, not planet-scoped) and pins the exact gating stat's storage location (a 12-bit field at per-race-record offset 0, compared against decimal 501), but the concrete real-world identity of both the monitored stat and the 16-slot pool's contents remains unresolved — the pool's backing global is heavily overloaded elsewhere in the decompile (the same address is used, in dozens of unrelated UI functions, as a scalar "currently selected object id," a much smaller type than the array access seen here, consistent with this project's previously-noted pattern of "globals... overlapping smaller symbols at the same address"), so no confident guess as to the pool's game meaning (mineral reserve, cargo allotment, waypoint/task slots, or something else) is offered here.

**Process-of-elimination pass on both the pool and the gating stat, this pass.** For the pool's backing global: a search of every other behavior-spec file in this project for that exact symbol found no hits outside this document — the "dozens of unrelated UI functions" reusing the address as a scalar object-id are not independently documented anywhere else in this project's own material, so there is no cross-document corroboration to triangulate against; this is a genuine negative result, not an oversight; the elimination approach the Open Questions item suggested cannot be carried out against other spec files because no other spec file has occasion to name this address. For the *gating stat* (the 12-bit field at per-race record offset 0), a direct sweep of every other read/write of that same field across the executable (including those written in a 4-byte-unit pointer form, `stars.exe.export.c:18602`-`18605`, `18694`-`18697`, `30336`-`30369`, `44193`-`44194`, and others) turned up two functions that adjust it by exactly ±1 in lockstep with membership changes to the game's global owned-fleet array (the same fleet table §5's routing search and §8's planet-shuffle discussion both reference): `FUN_1038_1f72` (`stars.exe.export.c:18648`-`18746`), which allocates a new slot in that array and immediately increments the current record's field by 1 (`18694`-`18697`), and `FUN_1038_1db4` (`stars.exe.export.c:18547`-`18644`), which removes a slot from that array and immediately decrements the same field by 1 (`18602`-`18605`). `FUN_1038_1db4` is independently corroborated elsewhere in this project: `save-turn-file-format.md`'s own note on opcode `0x18` (fleet-merge) names it as the post-merge cleanup step that "frees/clears a design slot if all of a hull's 16 component counts reach zero — consistent with one fleet's design being fully absorbed into the other's," i.e. a confirmed fleet-deletion/absorption routine, from a document that was not looking at the redistribution mechanism at all. Taken together, this is reasonably strong (though not certain) evidence that the gating stat is a **per-race live-fleet count** (or a quantity that tracks fleet-array membership one-for-one) rather than a mineral, cargo, or waypoint figure — every other candidate meaning considered above would need some other event to move it by exactly 1 per fleet created/destroyed, which is a specific and unusual coincidence for an unrelated stat to exhibit. This reading sits in tension with the below-501 loop gate, though: a race's live fleet count is expected to stay well under 501 for the overwhelming majority of a normal game, which would make `FUN_1090_5bda`'s redistribution loop fire on essentially every call rather than act as a meaningful low-resource trigger — an odd shape for a deliberate gate, and this tension is not resolved here. It is offered as the best-evidenced candidate so far, not a confirmed identification; the pool's own contents remain completely open.

**A fresh, exhaustive re-sweep of every write to this exact field this pass, specifically hunting for a non-fleet-event write site.** Every occurrence of the field's two addressing forms (byte-offset and 4-byte-unit pointer forms of the same record address) was re-checked across the whole export, filtering out the many unrelated reads/writes of the *other* sub-fields packed into the same 192-byte record (byte offsets +1/+2/+3 are a completely different set of flags, unrelated to the 12-bit field at offset 0). Two genuinely new things came out of this, beyond the already-documented ±1 pair (`FUN_1038_1f72`/`FUN_1038_1db4`):

- **A packed neighbor, not the field itself.** The 32-bit word at record offset 0 is shared: bits 0-11 are this section's gating stat, but bits 12 and up hold a *second*, independent counter, adjusted one unit (of bit 12) at a time by an entirely different mechanism — a design-table slot-free/allocate handler (`stars.exe.export.c:30297`-`30372`, opcodes `0x1b`-`0x1d` of what reads as a save/turn-file opcode dispatch) that branches on whether a freed or allocated ship/starbase-design slot index falls in the empire's 16-slot regular design table (indices 0-15, adjusts an unrelated byte field instead) or its 10-slot AI-bookkeeping table (indices 16-25, adjusts *this* word's upper counter up or down by one, e.g. `stars.exe.export.c:44269`-`44270`, `83176`-`83177`). Because those steps never carry into or out of the low 12 bits, this is a real, previously-unnoticed second write path to the *word*, but not to the *field* this section is asking about — it explains why the field is always masked to its low 12 bits when read (to isolate it from this packed neighbor), not a clue to the field's own meaning.
- **A genuine non-fleet-event write to the field itself, found this pass.** Inside what reads as the same save/turn-file record loader (a loop keyed on a record-type byte, matching the record-type convention `save-turn-file-format.md` documents elsewhere), one specific record-type branch (value `0x18`, `stars.exe.export.c:44417`-`44431`) does, for each per-player-slot record it visits: add the field's low-12-bit value to the global fleet count, then zero the low 12 bits outright (not a ±1 step). **That global is this project's own already-confirmed running count of the global owned-fleet array** (the same fleet table §5's freighter-routing search and §8's planet-shuffle discussion both reference) — so this step folds a race's current tally in this exact field *directly and by value* into the live global fleet count, then clears the per-race field to zero. A second, near-identical zero-reset (without the add step) recurs three more times in the same loading routine at different opcode branches (`stars.exe.export.c:44193`-`44194`, `44958`-`44959`, `45210`-`45211`), consistent with per-player-slot (re)initialization at file/turn-load time rather than a fleet-lifecycle event.

**Net effect on the open question.** This *is* a write that is not itself triggered by a single fleet's creation or deletion (it is a bulk file-loading/slot-reset operation), directly answering the task of finding a non-±1 write site — but its own content (adding the field into the global fleet count) reads the field as a fleet-count subtotal being folded into the confirmed global fleet-count variable, which if anything strengthens rather than undermines the "per-race live fleet count" reading from the prior pass, via a completely independent code path from the ±1 pair. The below-501 gate tension noted previously is not resolved by this — a normal race's fleet count would still be expected to sit far below 501 almost always — but there is now direct, confirmed structural evidence (not just ±1-lockstep correlation) connecting this field's value to the game's actual fleet-count bookkeeping, for whatever the resolution of that remaining tension turns out to be.

### 11. Fleet-role predicates and the design weapon-value cache (settled by the step-36 reconciliation)

An earlier account named `FUN_1090_2db6`, `FUN_1090_2e52` and `FUN_1090_2e94` (`stars.exe.export.c:63096`-`63190`) as the AI's **production / auto-build eligibility checks**, said to test a "squared capability rating greater than zero" written by turn-generation step 36. **All of that was wrong.** They are three small **fleet-role classifiers** used inside the AI's per-fleet loops; none touches a production queue, none reads the starbase field step 36 squares (a cloak factor, see `turn-generation-engine.md` §1 step 36), and the field they do read is the ship design's *weapon value*, written by the AI's own preamble. The rules, per fleet (the fleet's per-design stack counts sit at fleet offset `+0x0c`, 16 words; a stack "counts" when its count is above zero):

| Predicate | Plain name | True when some occupied stack has ... |
|---|---|---|
| `FUN_1090_2db6` (`:63096`-`63136`) | combat fleet | hull id 6-10 (Destroyer, Cruiser, Battle Cruiser, Battleship, Dreadnought), **with no armament test**; or hull 5 (Frigate) whose weapon value is at least 1; or hull 29 (Nubian) or 31 (Meta Morph) whose weapon value is at least 1 **and** whose cargo capacity is under 500 kT |
| `FUN_1090_2e52` (`:63140`-`63156`) | scout-or-warship-line fleet | hull id 4-10 (Scout, Frigate, Destroyer, Cruiser, Battle Cruiser, Battleship, Dreadnought); no armament test, no `+0x87` read |
| `FUN_1090_2e94` (`:63160`-`63190`) | hauler fleet | hull id 0-3 (the four freighters) or 11-13 (Privateer, Rogue, Galleon); or hull 31 (Meta Morph) whose weapon value is at least 1 **and** whose cargo capacity is 500 kT or more |

Details. The hull id is design offset `+0` read from the data-segment-resident design table (16 records of `0x93` bytes), and the weapon value is offset `+0x87` read from the design table that the current player's entry in the per-player design-table pointer array refers to (`:63115`, `:63124`, `:63179`). These are the same table: the client's file loader stores the resident table's address into the loaded player's slot of that pointer array (`:44553`-`44554`), and the AI runs against the player file loaded for that run (`:8316`-`8324`, `FUN_1088_0000` at `:57969`). "Cargo capacity" is `FUN_1050_2a2e` mode 2 (`:32425`-`32497`): the hull's cargo figure plus 50, 100 or 250 kT per Cargo Pod, Super Cargo Pod or Multi Cargo Pod (category `0x1000`, subtypes 2, 3, 4) times quantity. Consequences: an unarmed Frigate, Nubian or Meta Morph is neither a combat fleet nor (for the Nubian, ever) a hauler; a Meta Morph with 500 kT or more of hold counts as a hauler only if it also carries a weapon; every warship hull from Destroyer up is a combat fleet even when it carries nothing but armor.

**The weapon value.** Offset `+0x87` of a ship design is `FUN_1038_079e`'s weapon value (`ship-design-and-components.md` §9), positive in practice exactly when the design mounts a beam-, torpedo- or bomb-category component. `FUN_1038_09ae` (`:17054`-`17088`) refreshes it for every non-deleted ship design of every loaded race, once per AI player per turn, as the first of the four setup calls in the dispatch preamble `FUN_1088_0000` (`:57992`), before the personality driver runs. It is never squared. (The earlier Open Questions note that `FUN_1038_09ae` "refreshes a per-race design-cost cache" is corrected accordingly: it refreshes this one field and nothing about cost.)

**Where the predicates are called (all inside AI fleet handling, none in production code).** `FUN_1088_0462`, the personality-0 driver: `:58518` (combat fleet, apparently selecting the military branch over the cargo/other branch), `:58522` and `:58745` (hauler), `:58854` (combat fleet). `FUN_1088_2350`, personality 1: `:60020` (scout-or-warship-line fleets chained onto a scratch list) and `:60248` (combat fleet, applied to a list of foreign fleets at the same position). `FUN_1098_0184`, personality 2: `:66424` and `:66621` (combat fleet), `:66431` and `:66546` (hauler). `FUN_1098_131a`, personality 3: `:67074` (scout-or-warship-line), `:67082` and `:67210` (hauler), `:67281` (combat fleet). `FUN_10a0_0000`, personality 5: `:68198` and `:68489` (combat fleet), `:68202` and `:68423` (hauler). Personality drivers 4 (`FUN_10a8_0000`) and 7 (`FUN_1098_0000`) call none of them. Two shared helpers use the hauler test: `FUN_1090_2aa8` (`:62936`, for its own fleets with two or more waypoints: role code `0x1e` for a hauler and `0xffff` for anything else, or a flat `0x10` early in the game for some personalities; its only consumer, the speed setter `FUN_1090_12be`, never reads that argument, raw segment 19 `0x12be`-`0x1437`, so the code has no effect) and `FUN_1090_2f16` (`:63382`, assigns hauler fleets to freighter hubs, §5).

**Plain-terms rule.** The AI sorts each of its own fleets by hull: fleets with a Destroyer-or-larger warship hull, or an armed light warship hull, go down the military path; fleets built on freighter or armed-freighter hulls go down the cargo path; everything else (unarmed frigates, scouts alone, colony ships, miners, bombers, layers) belongs to neither list. That is the whole hull gate; there is no "maximally rated design" notion. The drivers also route fleets by which of the AI's own design slots their ships occupy, since each personality reserves slot ranges for roles (§12).

**What the drivers do after classification** is traced in §12 for every personality. One quirk belongs here. At `:60248` (personality 1) and `:66621` (personality 2) the combat-fleet test is applied to *foreign* fleets. The case is a bomber group idle at another player's planet. If any foreign fleet at exactly the same position passes the test, the group runs the target search and moves on; otherwise it stays and keeps bombing. The predicate indexes the current player's own design table by stack slot, and a foreign fleet's stacks index its owner's designs, so the verdict says nothing about the foreign ships. It is true whenever the AI's own design in the same slot number counts as a combat design. *(Resolved as a defect of the original, not an open question.)* A reimplementation should test the foreign fleet's real designs, unless bit-exact replay is required.

### 12. What the drivers do with each fleet (every personality traced; summary table at the end)

**Two gates decide a fleet's role.** The first is the hull classifiers of §11. The second, which matters more, is the AI's own design slots. Each personality's design-refresh routine fills fixed ranges of the 16-slot design table with particular hulls, and its fleet branches test which of those ranges a fleet's ships occupy. The slot maps differ between personalities. The drivers issue orders in four ways:
- a single destination, which replaces every later waypoint (`FUN_1090_2668`; it overwrites the current waypoint instead when that already lies at the destination);
- a task on the current waypoint (Scrap Fleet, Lay Mines, Transport with per-cargo actions, or clearing the task);
- immediate cargo transfers between the fleet and the planet or floating object it is at (`FUN_1090_0754`, `FUN_1090_07f2`);
- cancelling a route, by cutting the waypoint list back to the current position.

Task numbers follow the client's Waypoint Task list (`fleet-movement-scanning-cargo.md`); cargo actions follow the Transport list (1 Load All, 2 Unload All, 5 fill up to a percentage). The year counter below is the game's turn counter, 0 in the first year.

**Speeds are set at the end of the pass, for every AI fleet** (`FUN_1090_59e6` → `FUN_1090_2aa8` → `FUN_1090_12be`, raw segment 19 `0x12be`-`0x1437`). Orders are written at warp 4, at warp 6 for rendezvous and remote mining, or at a computed speed for colonizing. The end-of-pass setter then revisits every own fleet that has a next waypoint, including personality 7's.
- It lists every foreign minefield, leaving out those whose type byte (`+0xc`) is 2. Read against the client's minefield-type name table (`client-ui-dialog-catalog.md`), 0 is Standard, 1 Heavy and 2 Speed Bump.
- If the fleet is inside a listed field, the warp becomes 6 for type 1, and 5 or 4 for type 0 (warp 5 with probability 6 in 10). The type-2 branch (5, or 6 three times in ten) is unreachable because those fields are not listed. A race whose primary trait index is 1 (Super Stealth) adds 1.
  - *What "inside" means (traced: `FUN_1090_1240`, `:61720`-`61745`; radius refresh `FUN_1090_5e3a`, `:65780`-`65805`, raw segment 19 `0x5e3a`-`0x5eab`).* Despite its earlier description this is not a leg-crossing test. The waypoint plays no part. The test is whether the fleet's current position is strictly inside a circle around the field's centre: squared distance (exact integer dx² + dy²) less than R². R is computed once per AI run, before the personality driver, for every minefield: the square root of the field's mine count, plus 10.5, truncated to a whole number. So R is the field's normal radius (√mines) rounded to the nearest light-year, plus 10 ly. The refresh overwrites the field's mine count with R² in the AI's working copy of the turn data; that copy is discarded after the AI's orders are written, so nothing persists. Only fields owned by another player whose status bits 5-7 (byte `+1`) are clear are listed. The first listed field that contains the fleet decides the warp.
  - *Reimplementation note (recommendation, not original behavior).* Use "fleet's current position within √mines + 10 ly of a foreign non-Speed-Bump field". Do not substitute a path-intersection test: the original reacts only to fleets already in or next to a field, even when the next leg crosses another field.
- Otherwise the warp comes from the shared automatic-speed routine `FUN_1058_56e2` (`:40868`-`41073`; the fuel comparisons were checked in raw segment 12 `0x58e3`-`0x5963`). For the leg ending at the waypoint:
  1. *Efficient warp e.* This comes from `FUN_1050_69c2`: the highest warp, at most 10, at which every engine in the fleet uses no more than 120% fuel, then, when the routine's second argument is 0, lowered by 1 to 3 warps to a warp the engine runs for free if there is one, and finally 10 cut to 9 except for five engines (full rule: `fleet-movement-scanning-cargo.md`, Patrol note, item 6). The speed routine computes the variant with that free-speed preference (argument 0, `:40905`) and the one without it (argument 1) only when the flag at DS `0x13aa` is set (`:40906`-`40907`). Waypoint 0 simply gets e; waypoint 1 runs the full rule below (the end-of-pass speed setter, raw `1058:575c`). *(Traced in full: `FUN_1050_69c2`, `:35873`-`35964`.)*
     - The candidate starts at 10. For each of the fleet's 16 design stacks that holds ships, in slot order, the routine finds the design's first engine entry; a design with no engine makes the whole result 0. Using that engine's fuel table (warp 0-10, `component-stats.tsv` columns fuelW0-fuelW10), it steps the candidate down from its current value until the table entry is 120 or less. The candidate is never raised again, so the result is the minimum over all designs.
     - *Free-speed preference.* When the caller asks for it (second argument 0: the automatic-speed routine's main figure and the client's own default-speed uses) and the engine is not the Trans-Galactic Mizer Scoop or Galaxy Scoop (engine indexes 14 and 15), and the chosen warp w costs fuel: if w is at least 5 and warp w − 1 is free, w drops by 1; otherwise if w is at least 6 and w − 2 is free, it drops by 2; otherwise if w is at least 7 and w − 3 is free, it drops by 3. For example a Fuel Mizer (free to warp 4, 35% at 5, 120% at 6) gives 4, not 6. The AI's colonizer and fleet-hunter orders pass a nonzero second argument and skip this step; the automatic-speed routine's step 7 uses that variant as its second figure.
     - *Warp-10 cap.* A result of exactly 10 becomes 9 unless the engine is Interspace-10, Enigma Pulsar, Trans-Star 10, Trans-Galactic Mizer Scoop or Galaxy Scoop (engine indexes 7, 8, 9, 14, 15).
     - Each design's adjustments apply while that design is being examined, so a later design can only lower the figure further.
  2. *One-way flag.* A leg is one-way when its task is Colonize or Scrap Fleet, or when any ship in the fleet carries a Colonization Module or an Orbital Construction Module.
  3. *If e is 9 or more,* the routine goes straight to step 5.
  4. *Otherwise it looks at the planet at the waypoint.*
     - *Round trip to a foreign planet or to empty space.* Start from e, or from the previous leg's warp when that is higher (at most 10). If this leg needs less fuel than a tenth of the fleet's fuel capacity, and the fleet holds at least 70% of that capacity, go one warp faster.
     - *Any other leg (one-way, or ending at an own or unowned planet).* Start at warp 9.
     - In both cases the warp then drops one step at a time, never below e, until the leg's fuel need fits within the fuel aboard and one of these holds: the destination is an own planet whose starbase can refuel ships, the leg is one-way, or the need is at most half the fuel aboard.
  5. *Same arrival year.* Unless the target is a fleet, the warp is then lowered as long as the leg still takes the same whole number of years (distance ÷ warp², rounded up), but not below 2.
  6. *Stargate and cap.* A leg the fleet can make through a stargate (`FUN_1038_4ae4`) gets warp 11, and any other result above 11 becomes 9.
  7. In one client mode (the global at `DAT_1128_13aa`), the result is also capped by a second efficient-warp figure.

**Personality 0, planet pass** (`:58252`-`58480`; traced in full, raw segment 18 checked for the 5,000 kT test at `0x0a66`-`0x0a98`). It runs after the attack values and before fleet pass 1.
- *Set-up, once per run* (`:58146`-`58229`).
  - The stale-slot sweep `FUN_1090_5d68` runs over slots 14-15, 11-13, 9-10, 2-5 and 6-7. Its age threshold is 50 years before year 120, 70 before year 200 and 100 after; slots 6-7 use 1.5 times that.
  - For each range the sweep returns the **newest** live design: the latest creation year, a tie keeping the lower slot. For slots 11-13 it also returns the number of ships in existence of all live designs in the range (design `+0x83`, capped at 32,000).
  - A Nubian design in slots 14-15 is never flagged stale.
  - The design refresh `FUN_1088_1730` runs after the sweeps.
  - The colony-ship gate `FUN_1090_2baa` (§4) is evaluated once. It gives a yes/no G and the colony-fleet count F.
- *Which planets.* The AI's own planets, in the shuffled order of §8. Each must have a starbase and a stored population of 200 units or more (20,000 colonists). A planet whose queue already holds a ship-design item (design slots 0-15; a queued starbase does not count) is skipped entirely, so a planet gets a new batch only once its earlier ship orders are built.
- *Conventions for the steps below.*
  - Every item goes to the bottom of the queue (`FUN_1090_2736`, position 1). Each call adds a separate queue entry. Quantities are not cut to the build list, because the queue is already open.
  - "Galaxy planets" is the galaxy's total planet count, not the AI's.
  - Ship counts are numbers in existence, read at the start of the run. Ships queued this turn never count.
  - *Surplus* is the projected availability of §6 (`FUN_1090_355c`) minus the cost of the queue as it stood when the planet was opened (`FUN_1090_3604`), separately for Ironium, Boranium, Germanium and resources. `FUN_1090_3604` prices the planet's committed queue, and items added during the pass join it only when the queue is committed at the end (`FUN_10d0_0842`), so a later step never sees what an earlier step queued.
- *The steps, in order.*
  1. *Freighters.* Let N be the larger of (own planet count ÷ 8) and 4 × the hub count (§5). If a slot-11-13 design exists, one ship of the newest is queued in either case below. The count does not change during the run, so every qualifying planet can queue one per turn.
     - The freighter ships in existence (slots 11-13) are fewer than N × 8 ÷ 10, truncated.
     - Or they are fewer than N and a 1-in-3 roll succeeds.
  2. *Colony ships.* The condition is: (G allows, or F is below 26 and a 1-in-(8 × hub count) roll succeeds) and the year counter is 5 or more.
     - With no hubs the roll always succeeds. The roll is drawn whenever G refuses and F < 26, even before year 5.
     - When the condition holds: two slot-1 ships before year 21, one from year 21.
     - Then let P = stored population × the growth rate (`FUN_10e0_445a`, doubled for Hyper Expansion) and R = the planet's annual resources (`FUN_1048_4faa`). One more ship is queued when P exceeds 2,300, R exceeds 35 and the skill is 1 or more. A further one is queued when, in addition, P exceeds 3,600, R exceeds 50 and the skill is 2 or more. That makes up to four ships a turn before year 21 and three after.
     - Personality 0 has **no isolation check**: `FUN_1090_6012` is called only by personalities 4 and 5.
     - G and F are not updated as ships are queued, so on a turn when G allows, every qualifying planet queues colony ships.
  3. *Minelayers.* This step needs the slot-0 design to be on the Frigate hull (the minelayer design, built only at skill 2 or more, slot map above) and a 1-in-4 roll to succeed.
     - Let n be the slot-0 ship count of the first own fleet, in fleet-table order, that is at this planet and holds slot-0 ships, or 0 if there is none.
     - Four slot-0 ships are queued when (n is below 10, or n is 10-16 and a 1-in-10 roll succeeds) and then a 1-in-(2n + 1) roll succeeds. Each roll is drawn only if the tests before it passed.
  4. *Big-batch test.* B5 holds when the planet's surface Ironium and Boranium are both 5,000 kT or more and its Germanium is under 5,000 kT. The code counts the leading minerals at 5,000 kT or more and requires exactly 2, so a planet with all three above 5,000 kT does not qualify.
  5. *Bombers.* This step needs a slot-9/10 design.
     - The own fleets at this planet are walked in fleet-table order to the first that passes the strength test (S = slots 2-5 plus twice slots 6-7, at least K; `FUN_1088_20f6`).
     - If that fleet holds fewer than Q bombers (slots 9 and 10), 4 ships of the newest slot-9/10 design are queued (6 when B5), and the **planet's pass ends here**.
     - Otherwise, including when no fleet passes, nothing is queued and the pass goes on. Bombers therefore only top up a strike group that already sits at the planet.
  6. *Strike warships.* This step needs a slot-2-5 design.
     - *Soft cap.* It goes ahead when the newest slot-2-5 design has fewer than galaxy planets ÷ 7 + 6 ships in existence, or otherwise on a 1-in-2 roll.
     - *Design.* The newest slot-2-5 design, replaced on a 1-in-2 roll by the newest slot-6/7 design when one exists. The cap counts the slot-2-5 design even then.
     - *Affordability.* If any surplus component is negative, the **planet's pass ends**. Otherwise three fifths of one ship's cost (each component × 3 ÷ 5, truncated) is taken off. If any component then goes negative, no strike ship is queued and the pass goes on to step 7.
     - *Batch.* Otherwise it queues 1 ship, or 5 when B5. Only 60% of a single ship has been checked.
  7. *Line warships.* This step needs a slot-14/15 design whose newest design has fewer than galaxy planets ÷ 12 + 8 ships in existence.
     - The surplus is computed afresh, and it still excludes anything queued in this pass. If any component is negative, the pass ends.
     - Otherwise up to 5 ships of the newest design are queued, each as its own one-ship entry. Each ship's full cost is taken off the surplus, and the first ship that would leave any component negative is not queued and ends the pass.

- *Packets.* It is the packet personality, and this bullet is the governing description of its packets: the shared per-planet packet advisor of §6 (`FUN_1090_4d10`) returns at once for personality 4, so `FUN_10a8_123e` is its only packet code. `FUN_10a8_123e` (`:70110`-`70433`; raw segment 22 `0x123e`-`0x1aeb`, including every floating-point operand, which the decompile drops) runs after the end-of-pass routine and before the top-up. It visits each owned planet that has a starbase, with or without a mass driver (see the last bullets), in the shuffled order of §8, and tries three branches in order. Each planet has a packet word in the bookkeeping block (§16).
  - *Common terms.* All packets are queued at the top of the queue. The launch speed and destination are written into the planet's packet settings (planet word `0x2e`: destination planet number + 1 in the low 10 bits, speed field = warp − 4 in bits 10-13; `production-queue.md` §10b). R is the planet's projected resources this year after the research share (`FUN_1090_355c`, §6). A planet's surplus of a mineral is its projected stock minus what its queue already costs. A planet's *launch rating* is its best mass-driver warp, plus 1 when that warp appears in two starbase slots (`FUN_1048_5138`). Distances are in light-years; a packet at warp w covers w² ly per year.
  - *1. Hub supply* (only while bit 7 of the packet word is clear). The planet must be a packet hub (starbase slot 1, 3, 6 or 8) holding more than 700 kT of at least one mineral. Let n = R ÷ 2 ÷ 5, rounded down at each step; 5 resources is the Packet Physics price of a single-mineral packet. With n below 7, or no target, the planet moves on to branch 2.
    - *Target* (`FUN_1090_393e` with the predicate at segment 22 offset `0x2882`, raw only). The nearest planet that the AI owns, has a starbase, has no cool-down, is flagged short of a mineral of which the source holds more than 700 kT, and lies within 3.5 × s² ly, where s is the smaller of the two planets' launch ratings. That is at most 3.5 years of flight. The shortage flags are rebuilt every turn by the driver (`:69594`-`69627`): a packet hub is short of a mineral below 10 kT, any other starbase planet below 1,000 kT.
    - *Loading.* For Ironium, Boranium and Germanium in that order: if the target currently holds less than 10 kT (1,000 kT if the target is not a hub) and the source more than 700 kT, it queues the smaller of n and 7 packets of that mineral, takes them off n and clears the target's shortage flag for that mineral, so no other hub serves the same need this turn.
    - If nothing was loaded, the planet is finished for the turn. Otherwise the speed is s, the smaller launch rating, so the packet flies at no overspeed and does not decay. The destination is the target, and the target gets no cool-down.
  - *2. Packet attack* (only while bit 7 is clear, and only at skill 2 or more, or at skill 1 when a 1-in-3 roll succeeds). This branch fires packets at other empires' planets; it is not a surplus transfer between the AI's own worlds, as an earlier text said. Let S be the three mineral surpluses summed, minus 210 kT. The *budget* is the smaller of S and 70 × ((R ÷ 2 − 5) ÷ 5, rounded down), and is kept for the target test. If S is 150 or less, the planet goes to branch 3.
    - *Speed and decay.* Let s be the source's best mass-driver warp plus 3, the fastest legal launch; it is 3 above the launch rating, or 2 when the driver is doubled. Let q be the fraction of a packet that survives one year at that overspeed: 0.75, or 0.875 when the driver is doubled (DGROUP constants at `0x1e7e` and `0x1e76`). These are exactly the Packet Physics decay rates for overspeed classes 3 and 2 (25% and 12.5% a year, half the normal rates, `production-queue.md` §10b), and the Cybertron templates are all Packet Physics (§14).
    - *Mass needed.* For a candidate target, let d be its distance, r its launch rating as the AI can see it (0 with no starbase or no visible driver), c its 4-bit coarse defence value and f its 12-bit reported population figure (§12). The mass needed is K = min(4 × (f + 25), 1,000) ÷ ((s² − r²) × (95 − c) ÷ 16,000), truncated. The 16,000 is the DGROUP constant 6.25 × 10⁻⁵ at `0x1e3e`. So K grows with the target's reported population, capped, and shrinks with packet speed and as the target's defence value rises. The product (s² − r²) × (95 − c) is formed in 16-bit unsigned arithmetic, so when r exceeds s it wraps and K becomes meaningless.
    - *Target* (`FUN_1090_393e` with the predicate at offset `0x29da`, raw only). The nearest planet that meets all of these: owned by another player (not unowned) whose race is not Alternate Reality; no cool-down; r different from s; d at most 2.5 × s² (2.5 years of flight); f not zero; and K no more than the budget × q^(d ÷ s²), truncated, which is the budget left after the flight's decay. With no target, the planet goes to branch 3.
    - *Amount sent.* M = min(S, K) × (1 ÷ q)^(d ÷ s²), truncated, with 1 ÷ q = 4/3 or 8/7 (DGROUP `0x1e4e`, `0x1e46`). This is enough that K arrives after decay. The runtime power routine `FUN_1120_0dde` is identified as pow by its library descriptor. M is split into 70-kT single-mineral packets, 70 kT being the Packet Physics packet. Each packet takes the mineral with the largest remaining surplus, ties going to the earlier of Ironium, Boranium, Germanium, and lowers that surplus by 70. This repeats while any of M is left, so it queues M ÷ 70 packets rounded up.
    - *Settings.* The speed is s, the destination the target. The target's cool-down is set to 3, bit 4 of the source's word is cleared, and **bit 7 is set when d exceeds s²**, that is, when the packets need more than one year to arrive (the comparison at raw `0x184b`-`0x185c`: distance from `FUN_1038_2924` against the double s²).
  - *3. Fallback and follow-up* (reached when branch 2 did not fire, and always while bit 7 is set).
    - If bit 4 is set and bit 7 is clear, bit 4 is cleared and nothing else happens. This is the rest turn after a fallback shot.
    - If bit 7 is clear, a new direction index is drawn: a 0-6 roll, plus 1 if it equals the stored index, so the index (bits 0-2) is 0-7 and never repeats. `FUN_10a8_1aec` then picks a target (traced case by case: `:70437`-`70595`, raw segment 22 `0x1aec`-`0x1d75`, jitter constants 0.3 and 0.15 read from DGROUP `0x1e56` and `0x1e5e`).
      - *Frame.* Work in map coordinates minus 1,000, so the galaxy is the square from 0 to L on each axis, L = (galaxy-size index + 1) × 400: 400 for Tiny up to 2,000 for Huge. Let (x, y) be the source planet. Inside this chooser s is the launch rating + 3, which equals branch 2's s except when the driver is doubled, when it is one more.
      - *Border point.* The index chooses a ray from the planet in one of eight compass steps of 45°, and the point is where that ray meets the square's edge. Index 0: +x, giving (L, y). Index 1: +x and −y together, giving (x + y, 0) when x + y < L, else (L, x + y − L). Index 2: −y, giving (x, 0). Index 3: −x and −y, giving (x − y, 0) when x > y, else (0, y − x). Index 4: −x, giving (0, y). Index 5: −x and +y, giving (0, x + y) when x + y < L, else (x + y − L, L). Index 6: +y, giving (x, L). Index 7: +x and +y, giving (L, y + L − x) when x > y, else (x + L − y, L). So even indexes are the four axis directions and odd indexes the diagonals, turning from +x towards −y.
      - *Slide along the edge.* Let j be a random whole number from −⌊0.15 L⌋ up to ⌊0.3 L⌋ − ⌊0.15 L⌋ − 1. On a vertical edge (x = 0 or L) the point moves j along y, on a horizontal edge j along x. Any overshoot past a corner is clamped to the corner, and the excess is carried round onto the adjacent edge, measured inward from the corner.
      - *Step inward.* A second random whole number from 0 to s² − 1 moves the point that far straight in from its edge: from y = 0 or y = L if it lies on one, otherwise from x = 0 or x = L. A corner point moves along y.
      - *Target.* The point is shifted back by +1,000 on each axis, and the target is the nearest object to it (`FUN_1038_2988`, class mask `0x21`). It is accepted only if the AI does not own it and it lies at least s² ly from the source, a year or more of flight; the chooser then returns its planet number + 1. *Quirk:* the distance test compares the squared distance with s⁴ formed in 16-bit arithmetic and sign-extended (raw `0x1d53`-`0x1d65`). From s = 14 (a launch rating of 11 or more), s⁴ no longer fits a signed 16-bit value, and every non-owned nearest object passes, however close.
      - With no target, the planet is finished.
    - *The cool-down word.* The cool-down test and mark here do not use the target's own packet word. The routine indexes the block with the chooser's return value, the target's planet number + 1, as if it were a planet number, so it reads and marks the word of the planet numbered one higher than the target (raw segment 22 `0x18f5`-`0x192c`). When the target is the last planet of the galaxy table, the word hit is the first entry of the rebuilt per-planet array (§16), which is not saved.
    - If that word shows no cool-down and `FUN_10a8_1d76` queues one packet of the mineral with the largest surplus (it needs a surplus above 169 kT), that word's cool-down is set to 3 and bit 4 is set, or cleared when this is a follow-up. Otherwise bit 4 is cleared. So the real fallback target gets no cool-down and can be picked again on the next fallback turn, while the planet numbered after it cannot be chosen by any branch for the next two years.
    - The speed becomes s (best driver warp + 3). The destination becomes the new target, or, on a follow-up (bit 7 set), stays as last turn's attack target and bit 7 is cleared.
    - So **bit 7 means "send a follow-up wave"**: on the turn after a long-range attack, the planet skips branches 1 and 2, does not choose a new target, and, surplus permitting, adds one more packet to the same target at the same overspeed.
    - *Which value a follow-up turn uses.* A follow-up turn makes no chooser call, so the cool-down test and mark use whatever the chooser-result variable still holds. That variable is not initialised when the routine starts; the chooser call is its only store (raw `0x18de`), and it is not reset per planet. The cases are:
      - an earlier planet of the same run called the chooser and got a target: the value is that target's number + 1, so the test and mark land on the planet after that earlier target;
      - that earlier call found no target: the value is −1, which indexes the block's first word, its length in bytes. The test reads bits 5-6 of the length's low byte. For a length of (N + 1) × 2 bytes (N planets) these are clear exactly when (N + 1) mod 64 is below 16. In that case the mark sets them, so the saved length grows by up to 96 bytes (harmless: the extra bytes are the rebuilt array, which every run overwrites) and every later −1 test finds a cool-down;
      - no chooser call has happened yet in this run: the value is whatever the stack held, which the game rules do not determine.

      In every case the destination is unaffected: on a follow-up it stays last turn's attack target.
    - *Reimplementation note (recommendation, not original behavior).* Unless bit-exact replay is required, apply the fallback cool-down to the fallback target itself and, on a follow-up turn, to last turn's attack target, which is evidently the intent.
    - *Planets whose starbase has no mass driver* (launch rating 0). The routine visits them too and runs all three branches.
      - Hub supply never finds a target: its range is 3.5 × s² with s the smaller launch rating, here 0.
      - The packet attack uses s = 3, so its range is 22.5 ly (2.5 × 9) and it fires only at a foreign planet that close.
      - The fallback also uses s = 3, and its chooser normally finds a target. So on every turn without the rest flag such a planet queues one 70 kT packet when its largest surplus exceeds 169 kT.
      - Every random number of these branches is drawn as usual (the skill-1 attack roll, the direction roll and the chooser's two draws). Cool-downs, bits 4 and 7 and the planet's packet settings are written as usual.
      - At turn generation the production step deletes these packets before buying anything, because the starbase has no usable driver (message 297, which a computer player never receives; `production-queue.md` §10i), so nothing is spent. During the AI run, though, they count in the queue cost that the end-of-pass top-up sees next, so that turn's Factories, Mines and Alchemy at the planet are smaller.
    - *Reimplementation note (recommendation, not original behavior).* Skipping planets without a driver changes only the random-number sequence, a few cool-downs (each of which bars a planet as a target for two years) and the top-up's surplus at those planets. Keep the visit if bit-exact replay is required.

When the option is set, every AI personality prefers targets owned by human players. Planets and fleets owned by any computer player (the computer bit, `0x200` of word `+2` of the owner's player record) are skipped. They are attacked only when no human-owned candidate exists at all. That fallback is a search with no exclusion, so an AI falls back to attacking other AIs, not just to idling. When the option is clear, AIs treat every other empire alike.

Beyond that preference the option does nothing:
- No AI code reads or writes the relations table (a raw-byte scan of the AI code segments `0x1088`-`0x10a8` finds no reference to the table at record offset `0x5a32`, while the same scan does find the known readers in segments `0x1048` and `0x10b0`). AIs neither propose nor accept relationship changes, consistent with `diplomacy-relations.md` §3.
- No visibility is shared.
- The battle engine is untouched: whether two AIs actually fight when they meet is still decided by their relations and battle plans (`diplomacy-relations.md` §5).

In short, the option is a target-selection bias. It is not an alliance mechanism.

The exact rule, in two places and nowhere else:
- *Fleet hunters* (`FUN_1090_1438` and `FUN_1090_3c80`). With the option set, the candidate list leaves out every fleet whose owner carries the computer-player bit. If that leaves no candidate at all, the search is repeated over all foreign fleets.
- *Planet target search* (the six tests listed above). With the option set, the search first uses the predicate that accepts only planets whose owner lacks the computer-player bit (`FUN_1088_2254`). If that finds nothing, it uses the ordinary predicate (`FUN_1088_216e`).

With the option clear, both go straight to the unrestricted search. A game that does not offer the option therefore reproduces the original exactly by always taking the option-clear path; apart from the settings display, nothing else reads the bit.

### 13. Population and colonist units used by the AI (gap-report answer)

**The two population quantities.** The AI reads exactly two population quantities, and never raw colonists:
- *Stored population* (planet record byte `0x28`, a 32-bit count in units of 100 colonists; `population-growth.md` §3). Colonist cargo uses the same unit: the transfer helper (`FUN_1090_0754` → `FUN_1050_3cee`, `:61064`, `:33394`) moves cargo kind 3 between a fleet's colonist field and this planet field one-for-one, so 1 unit = 100 colonists = 1 kT of hold. The message texts show the same convention: colonist counts are printed with two literal zeros appended (`client-ui-dialog-catalog.md`, Messages, "Message fields").
- *Reported population figure* (low 12 bits of planet word `0x12`, written by `FUN_10b8_321e`, `:78449`): about stored population ÷ 4 with ±12.5% noise, clamped to 1-4,090, 0 for an empty or Alternate Reality planet. One step is about 4 units, about 400 colonists; the maximum, 4,090, is about 1.6 million colonists.

**The coarse defence value and the owner's race: what they are and where the AI gets them** (traced: report refresh `FUN_10b8_321e` `:78449`-`78547`, raw segment 24 `0x32ca`-`0x3340`; visibility pass `FUN_1070_5aa0`, `FUN_1070_5f00`, `FUN_1070_64fc`, `FUN_1070_537e` `:48594`-`48643`; planet-record decoder `FUN_1070_1fee` `:45454`-`45645`; player-record writer `FUN_1070_343a` `:46863`-`46900` with its caller `:47532`-`47541`, and reader `FUN_1070_036a` `:43841`-`43873`).
- *Coarse defence value n* (top 4 bits of planet word `0x12`, above the reported figure). Turn generation computes it for every planet each year from the true state. It is 0 when the planet has no defences. Otherwise let F be the planet's normal bomb pass-through (`FUN_1038_0262`: (1 − c ÷ 1,000) to the power K, from the owner's best planetary-defence technology and working defences, `turn-generation-engine.md` §4), and v = F × 100 rounded to the nearest whole number (DGROUP constants 100.0 and 0.5 at `0x1d92` and `0x1d9a`). Then n = (104 − v) ÷ 6, truncated and clamped to 1-15. So n measures the defence coverage 100 − v in steps of 6%: 1 for coverage up to 7%, 9 at 50%, 15 from 86%. The invasion estimate's (n + 1) × 18 ÷ 4 (§12) turns it back into an approximate percentage.
- *Where the AI's planet values come from.* The AI decides from its own player file, never from the host's data. A foreign planet's record carries the figure and n only when the planet was reported at detail level 3 or more and has an owner (`FUN_1070_1fee` reads word `0x12` only then, `:45523`, `:45571`-`45575`).
  - Level 3 or more: a fleet of the AI with a scanner orbiting the planet, or the planet inside the penetrating range of one of the AI's fleets or planets (for a Packet Physics race, also of its packets).
  - Level 2, which carries neither value: a penetrating report whose range is shortened by a cloaked starbase (`turn-generation-engine.md`, step 36 note).
  - Level 1: an AI fleet in orbit without a scanner.

  The values are those of the latest such report; the planet's report year (`+0x32`, §12) gives their age, and the rules that use them test that age where §6 and §12 say so.
- *"Owner is Alternate Reality."* This is the primary trait (race setting slot 14) in the owner's player record as held in the AI's own file, read through the trait accessor (`FUN_10e0_222c`, selector 14). Scanning never supplies it. The host writes another player's record in full, race settings included, only when the observing player is a Claim Adjuster (primary trait 3: every known player's record, `:47536`-`47540`) or the other player has been flagged eliminated (record `+0x54` bit 0, set when it has nothing left, `:79098`-`79101`). The observer's own record is always full. Every other known player gets only an 8-byte header (which includes the control word with the computer-player bit) and its name; the reader zeroes the rest of the record (`:43858`-`43873`), so that player's primary trait reads as 0, Hyper Expansion. "Known" means seen this year in any way, such as a scanned fleet, planet, packet or minefield of that player (`:49074`-`49078`, `:48616`-`48623`).
- *Consequence.* None of the AI templates except the Rototills (category 3) is a Claim Adjuster (§14). So for categories 0-2, 4 and 5 every "owner is not Alternate Reality" test passes for every living foreign owner, AR included: those of the shared packet advisor (§6), of the colony-ship and freighter invasions and of the packet attack (§12). Only category 3 sees the real primary traits. Two protections still hold for every AI because they come from report values. An AR planet's reported figure is always 0, so the packet attack (which needs f above 0) never targets it, and its attack value is 2 (1 from the figure, plus 1 for its starbase). An AR planet always has a starbase in normal play, so personality 1's and personality 4's colonist landings, which need a planet without one, never reach it.
- *Reimplementation note (recommendation, not original behavior).* To match the original, compute n and the figure from the target planet's true state, but only for planets the AI currently sees at report level 3 or more, and keep the last values otherwise. Treat a foreign owner as not Alternate Reality unless the AI's own race is a Claim Adjuster or that owner is eliminated. A simplification that lets the Alternate Reality test always pass is the original behaviour for every archetype but the Rototills. A fixed value of n = 0 is exact only for undefended planets and makes the AI more willing to invade and to fire packets at defended ones.

The overruns come from the stronger settings the higher tiers get: colonists per resource of 800 (a 420-point charge), higher growth rates on wide or immune habitability, expensive research turned cheap, factory output and operation above 10 (charged again through the growth-rate penalty term), and, for Macinti, Cheap Energy on an Alternate Reality race (−33).
- *The Easy tier* is far above the budget (289 to 963 points); the surplus is simply lost, as below. *The Standard tier* sits at about zero (−169 to 96; Rototills 1, Turindrones 13, Cybertrons −2), which suggests it was balanced as the "fair" tier.
- *The game never checks computer players.* Three places score races, and all three skip any record carrying the computer flag. At game creation (`:53206`-`53224`) and on loading a game-definition file (`:52489`-`52504`), a human race scoring below 0 is replaced by the first predefined race and flagged. The per-turn check in turn generation (`:72090`-`72135`) penalises and degrades a human race that scores below 0, or whose record the scoring routine first had to clamp into range (it signals this by setting bit 4 of record byte `0x54`). On top of that, the home-world bonus counts every computer player as having exactly 50 leftover points whatever its template scores (`:50991`-`51001`; `new-game-setup.md`, home-world minerals). So the leftover-point convention is never applied to these templates: an Easy AI gets no more than 50 points of bonus, and a negative Expert AI gets the full 50 anyway (plus 10% extra starting population at skill 3, `:51001`-`51005`).

**Starting ships and designs of AI players.** The templates hold no designs. An AI player gets the ordinary per-PRT starting fleet of `new-game-setup.md` §5a, created in the same three passes, so its design slots are filled in creation order. Consequences: slot 0 is always a scout and slot 1 always a colonizer, which is why every driver treats slot 0 as scouts/minelayers and slot 1 as colony ships.
- Robotoids (HE): slot 0 Smaugarian Peeping Tom; slot 1 Spore Cloud (three ships of it).
- Turindrones (SS): slot 0 Peeping Tom or Shadow Sleuth (by starting Energy, as for any SS race); the Shadow Transport is skipped because the race-flag test at `:51359` is the computer-player bit; slot 1 Santa Maria; slot 2 Potato Bug (two ships: ARM without OBRM).
- Automitrons (IS): slot 0 Peeping Tom; slot 1 Santa Maria.
- Rototills (CA): slot 0 Peeping Tom; slot 1 Santa Maria; slot 2 Change of Heart.
- Cybertrons (PP): slot 0 Long Range Scout; slot 1 Santa Maria (plus the second-home-planet scout).
- Macinti (AR): slot 0 Peeping Tom; slot 1 Pinta; Tough and Expert (ARM without OBRM) also slot 2 Potato Bug.
All of these then receive the starting tech-upgrade pass of `new-game-setup.md` §5b.

### 15. The AI design templates (read from the executable)

**How a design is built** (`FUN_1090_0000`, `:60609`-`60763`; part resolver `FUN_1090_036a`, `:60767`-`60811`; both checked against raw segment 19). A refresh routine calls the builder with a target slot, a hull and a template. A template is one byte per hull slot, in the hull's slot order, each byte naming a *part group*. For each hull slot the resolver walks the group's entries in order; each entry names a component category, a top subtype and a number of steps, and is tried from the top subtype downward through that category's table. The first part the race can build (the shared availability check, `ship-design-and-components.md` §4-§5) is installed, filling the hull slot to its full capacity. If any slot finds nothing, the whole design fails and the slot is left alone; the callers then try another template or another hull. A built design is given a random name from the dynamic-string range for its hull family (re-drawn up to 20 times to avoid a duplicate of an existing design name, then a random number is appended), stamped with the current year (design `+0x7d`) and written over the target slot, replacing whatever was there (`FUN_1090_0634`). The group counts are data-segment bytes at `0x13b8` (45 groups) and the 139 entries are code-segment constants at segment 19 offset `0x23e` (Ghidra renders both as ordinary data references).

**How the refresh routines pick templates, and what they replace** (traced: personality 0 `FUN_1088_1730` `:58898`-`59081`, personality 2 `FUN_1098_1074` `:66769`-`66867`, personality 4 `FUN_10a8_2c74` `:71194`-`71384`, personality 5 `FUN_10a0_1d9e` `:68534`-`68751`).
- *Random choice, personalities 0, 2 and 5.* Up to five tries, each a uniform pick among all of the slot's alternatives, with repetition. The first design that can be built is kept; if all five fail, the slot is left as it was. Personality 0's slot 14 tries the Nubian template again before each of its five Destroyer picks. Personality 2's slot 14 has a single Destroyer template, tried up to four times. Personality 2's slot 9 makes the five tries among its four Battleship templates.
- *Random choice, personality 4.* With n alternatives, the k-th try (k = 1 to n) is a uniform pick among the first n − k + 1 of them, so the last alternatives become unreachable as the range shrinks. Slots 4 and 5 try their fixed first template once before year 76 and fall back to these tries only if it fails; from year 76 they go straight to the tries over all five.
- *Personality 2, slots 0 and 1.* When the slot's design is marked deleted or no ship of it exists, an unused design is first marked deleted and the Scout (slot 0) or the Medium Freighter colonizer (slot 1) is built in the same pass. So an unused slot 0 or 1 is redesigned every turn.
- *Personalities 0 and 5, slot 0.* When the slot-0 design is not on the Frigate hull, no ship of it exists, the skill is 2 or more and the tech gate holds (Biotechnology above 3, Electronics above 4, Construction, Propulsion and Energy above 5), the design is marked deleted and the Frigate built in the same step. There is no year gate.
- *Personality 4, slot 0.* When the slot-0 design is not on the Frigate hull, no ship of it exists, the skill is 2 or more and the year counter is above 5, the design is marked deleted. Separately, whenever slot 0 is empty (by this rule or any other), the Frigate minelayer is built, at any skill and with no tech gate. If its parts are not yet available the slot stays empty. The planet pass still queues slot-0 minelayers then; such an order costs nothing and is refused at completion (message 79, which a computer player never receives; `production-queue.md` §10e and §10i).
- *Personality 5, slot 2.* Before year 20, a slot-2 design that is not deleted and of which no ship exists is marked deleted. The Cruiser ladder that runs next has no age condition for slot 2, so it rebuilds slot 2 at once. The effect is that before year 20 an unused slot-2 Cruiser is redesigned every turn. For slots 3 and 4 the ladder tests only the age of the slot below, without checking that it still holds a design.
- *Personality 4, battle groups.* A group occupies slots g to g + 3, with g = 6 or 10. It is designed when slot g is empty and either g is 6 and the year counter is above 40, or g is 10 and slot 6 holds a design created more than 30 years ago. Only slot g's emptiness is tested; all four slots are then overwritten in this order:
  1. slot g + 2: a Nubian (three templates);
  2. the next slot down (g + 1 if the Nubian was built, else still g + 2): a Battleship from the four-template set;
  3. the next slot down after that: a Battleship from the three-template set. Each of these three steps moves down one slot only when its design was built;
  4. every remaining slot down to g: a Cruiser. The first Cruiser slot draws from the upper three Cruiser templates when it is g + 2, from the middle and upper six when it is g + 1, and from all nine when it is g. Each further slot below takes the middle three (at g + 1) and then the lowest three (at g). The step moves down even when a Cruiser build fails;
  5. slot g + 3: the Nubian top template, else the Battleship top template, else the two B-52 templates, one try each.

  So with the Nubian hull available a group is Battleship, Battleship, Nubian, Nubian from slot g up (the top slot falls back to a Battleship or B-52 when the Nubian top template's parts are missing). With Battleships but no Nubian it is Cruiser, Battleship, Battleship and a top Battleship or B-52. With neither, it is the lowest, middle and upper Cruiser and a B-52 top. Cruisers fill only the slots the larger hulls could not.
- *Personality 4, planetary guards (slots 14 and 15).* A Battleship from all seven Battleship templates, else a Cruiser from all nine, else a Destroyer from the ten slot-4/5 templates, each with the shrinking-range tries.
- *Personality 3* has no refresh: `FUN_1098_1eb4` is a bare return (raw segment 20 `0x1eb4`), so it plays only with its starting designs.
- *What the builder does not check.* The part resolver `FUN_1090_036a` tests only whether the race can build a part (`FUN_1008_5194`). It does not test a part against the hull slot's allowed categories, against a part's own hull restriction, or against a rule that a part may be fitted only to unarmed ships. None of these is needed: every template's groups match the hull's slots, and no group can reach the two restricted parts. Settler's Delight, usable only on the Mini-Colony Ship, appears only as group 44's zero-step entry, and Transport Cloaking (index 0 of the electrical table) lies below every "down to Stealth Cloak" range. A reimplementation that applies those checks gets the same designs.

A generation is rebuilt only when none of its rungs is in use, and so slot 0, the home world's starting design, is overwritten only once no starbase of it remains. Space Station and Orbital Fort need no technology, and every part group used by templates A and B has a part available from the start (Laser, Alpha Torpedo, Tritanium, Mole-skin Shield, Battle Computer), so these builds never fail.

**Category 5** (`FUN_1090_492e`), each turn:
1. Slots 1, 2 and 3: a slot whose design is empty or has no starbase in existence is rebuilt: slot 1 template C light, slot 2 template D light, slot 3 template E medium. The Space Dock needs Construction 4 and the Ultra Station Construction 12; a failed build leaves the slot as it was and gives it mark 1 (§6).
2. Slots 4-6 and 7-9: when no design of a group has a starbase in existence (empty slots count as unused), each of its three slots is rebuilt, the first light, the second medium and the third full, each trying template G (Death Star, Construction 17), then F, then B.

An unused slot or group is therefore rebuilt every turn and always carries the current year and the race's best parts. The urgency marks of §6 are computed in the same routine from these slots.

### 16. Cross-turn AI state: what persists, where, and whether a stateless AI decides the same

**Context.** Each AI run starts from the player's file as freshly loaded (`FUN_1088_0000`, `:57969`). Everything the drivers compute in scratch arrays (the per-planet 16-byte scratch table, the "already targeted" marks, the attack values, the owned-planet list and its shuffle, the fleet lists, the design weapon values) is rebuilt at the start of every run and freed at the end (`:57972`-`57995`, `:58025`-`58034`). Only the items below carry over between turns.

**1. The AI memory block (one per computer player).**
- *Storage.* An up-to-8 KB block (allocated at 8,192 bytes by the dispatcher, `:57977`-`57981`). Its first word is its used length in bytes. It is written into that player's **history file** (`.h<N>`, `save-turn-file-format.md` §10.3) as file-layer record type 41 (`0x29`), split into chunks of at most 1,023 bytes, and only when the length exceeds 2 (`FUN_1048_84c8`, `:31405`-`31421`). The loader reads type-41 records back only for a player whose computer flag is set (`:45015`-`45038`). A human player's history file never carries one.
- *Missing block.* With no block on file the dispatcher allocates a fresh one whose length word is 2 (empty). For categories 0-3 the hub routine then treats the table as empty and rebuilds it from turn 20 on; category 4 zeroes the whole block and re-initialises it on its first run (`:69411`-`69420`); categories 5 and 7 never touch it (their research preamble call passes no hub request, `:67554`, `:66012`).
- *Content, categories 0-3: the hub table* (`FUN_1090_2f16`). Word 1 is the hub count (0-64). Then one 20-byte entry per hub: the hub planet's id, the number of assigned freighters (0-8), and up to 8 freighter fleet ids. Hubs are appended in the order they first qualify; a hub is removed only when the AI no longer owns the planet (entries behind it close up). Freighter ids are never validated: a destroyed or merged fleet's id stays in its hub's list, still counting toward that hub's 8, until the hub itself is dropped, and a later fleet that reuses the id inherits the slot. Assignment and rebalancing are as in §5.
- *Content, category 4: packet bookkeeping.* The block holds one 16-bit *packet word* per planet of the galaxy (length = (planets + 1) × 2), indexed by planet number. Every bit was traced in `FUN_10a8_123e` and the category-4 driver (raw segment 22). How the bits are used is in §12, personality 4, *Packets*.
  - Bits 0-2 hold the fallback direction index, 0-7. Each fallback draw replaces it with a 0-6 roll, plus 1 when the roll equals the old value, so it never repeats on consecutive draws. An earlier text gave the range as 0-6.
  - Bit 3 is set on a turn when the planet pass queues a colony ship at this planet and cleared on a turn when the planet reaches the colony-ship test but none is queued; a planet that does not reach the test (no starbase, a hub starbase, or an over-committed queue) keeps its bit. It enforces the every-other-turn rule (§12, personality 4, planet pass). It is the only state the rule needs: one bit per planet, meaning "a colony ship was queued here the last time this planet reached the test", all clear when the block is first created.
  - Bit 4 is the fallback rest flag. It is set after a fallback packet is queued, except on a follow-up turn. While it is set, the next fallback attempt is skipped and the bit cleared. A packet attack or a failed fallback also clears it.
  - Bits 5-6 hold the target cool-down. It is set to 3 on the target of a packet attack and, because of an indexing slip, on the planet numbered one after the target of a fallback packet (§12, personality 4, *Packets*); hub supply does not set it. At the start of each category-4 run every nonzero cool-down drops by 1 (`:69590`-`69591`). A planet chosen in year t is refused in years t + 1 and t + 2 and can be chosen again in year t + 3. Planets owned by other empires carry cool-downs too.
  - Bit 7 is the follow-up flag. It is set after a packet attack whose target lies more than s² ly away, s being the launch warp (the source's best driver warp + 3), that is, when the packets need more than one year to arrive. The test is a floating-point comparison of the straight-line distance against s², read from raw `0x184b`-`0x185c`. While the bit is set, the next turn skips hub supply and the attack, chooses no new target, and queues at most one more packet to the same target through the fallback rule; the bit is cleared then.
  - Bits 8-15 are unused.
  - *Beyond the saved length.* A second per-planet word array follows and is rebuilt every turn: inbound-colony counters in bits 3-4, other planet-pass flags in the low byte, and the mineral-shortage flags for Ironium, Boranium and Germanium in bits 8-10. After it comes one 32-bit slot holding the current planet's attack budget for the target test. Neither is saved. The low-byte flags are bit 0 "no colony target here", bits 1-2 the hauler router's "nothing to deliver" counter, bit 5 "guard weak" and bit 6 "guarded". Those written by the fleet passes land N − 1 entries too far, because of the indexing defect described in §12 (personality 4, *Fleets*), so only the shortage flags, written by the planet loop itself, work as intended.
- *Content, categories 5 and 7:* none (an empty block of length 2, which is not written).

**2. State held in ordinary player data** (saved for every player, human or computer, so a reimplementation already has it): the design table with each design's creation year (`+0x7d`) and number in existence (`+0x83`), which drive every ladder, every "replace when unused" rule and the stale-slot sweep; the fleets' orders, cargo, battle-plan index and waypoints; the planets' production queues and packet destinations; the research field and spending percent; and the per-planet report year (`+0x32`) used by the attack handler.

**3. Stale-design flags are not persistent.** They are recomputed every turn by the sweep `FUN_1090_5d68` (`:65720`-`65776`) from the current year and each design's creation year and count: within a slot range, a design older than the threshold (50 years before year 120, 70 before 200, 100 before 400, 300 after, for personality 4; each driver passes its own) is deleted outright if no ship of it exists, otherwise flagged for this turn only. The flags then drive fleet pass 3's scrapping and the splitter (called by personalities 0, 1, 2 and 4; for personality 4 only from year 81) `FUN_1090_5bda` (`:65607`-`65716`), which repeatedly moves the flagged stacks of any fleet that mixes flagged and unflagged designs into a new fleet of their own, as long as the player has fewer than 501 fleets (the 12-bit field §10 discusses is indeed the player's fleet count). A stateless reimplementation computes exactly the same flags.

**Does a stateless AI decide the same?**
- *Stale flags, targets, attack values, speeds, production:* yes; these are recomputed from saved game data every turn in the original too.
- *Hub table:* not exactly. A per-turn recomputation of "current starbase planets plus planets that meet the hub thresholds now" differs from the original in four ways: (a) a planet that once qualified stays a hub after it stops qualifying (population lost, mines bombed); (b) hub order is first-qualification order, which decides ties in "nearest hub", the 50-ly exclusion for category 0 and which hubs survive the 64 cap; (c) freighter assignments are sticky, so a freighter keeps its hub after it would be nearer another, and rebalancing moves one freighter per under-filled hub per turn; (d) dead fleet ids keep occupying hub places. Item (d) is a defect-level quirk; (a)-(c) change which hub a freighter serves and therefore its routing (§5), and the hub count used by personality 2's freighter quota (§12).
- *Category 4 packet bookkeeping:* not exactly; without the cool-down a stateless AI can pick the same packet target on consecutive turns, and without the rotating index its fallback target choice differs. Colony-ship alternation (bit 3) cannot be derived from the saved game either: whether a colony ship was queued at a planet last time is not visible once the order has been built or the queue changed. A stateless AI therefore matches the original's frequency (one colony ship every second qualifying turn per planet) but not its phase. Each planet's phase starts on the first turn it reaches the test, so a global "odd years" rule gives the right rate but the wrong turns.

**Reimplementation note (recommendation, not original behavior).** Persist a small per-AI record in the reimplementation's own save: the ordered hub list with up to 8 assigned fleet ids each, and for the packet personality one cool-down counter (0-3), one direction index (0-7) and the three one-bit flags (colony alternation, fallback rest, follow-up due) per planet. That reproduces the original exactly at negligible cost. If state cannot be kept, rebuild hubs each turn as: every owned starbase planet, then every owned planet meeting the §5 thresholds, in ascending planet id; assign each hauler fleet to its nearest hub with fewer than 8 freighters; and treat any planet that received packets within the last three turns as ineligible (derivable from packets in flight). Expect small routing differences, not different strategies. Drop item (d) either way unless bit-exact replay of original games is required.
